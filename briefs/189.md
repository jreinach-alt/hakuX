## What's already measured

PR #191's canary-guarded write sweep (tools/nv2a_probe,
docs/testing/nv2a-probe-pmc-findings.md) found 0x004's low bit is the MMIO
endian switch on silicon: a write sweep set it and every later access was
byte-swapped until a power cycle. Two prior "findings" derived from that
flip have been WITHDRAWN as the endian artefact they were. 0x004 is
undeclared in nv2a_regs.h and unhandled in pmc.c today.

## Goal -- this issue's scope is deliberately unclaimed, resolve that first

The tracker note is explicit: do the grep before writing code. Search the
corpus and guest code this campaign already builds against (nxdk_pgraph_tests
sources under docs/testing, any XBE/disc tooling in the tree) for any access
to offset 0x004 / NV_PMC_BOOT_1. Modelling an MMIU-wide endian switch means
every subsequent MMIO access would need to check it -- that cost is only
worth paying if something in this campaign's corpus actually touches the
register.

## Falsifier

Not a code falsifier -- a search result. Report, with the exact grep/search
commands and their output: does any guest code or test disc this campaign
runs access 0x004? If none exists, this issue's dispatch_state should move
