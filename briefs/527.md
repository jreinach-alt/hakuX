# #527 -- ZPASS_PIXEL_CNT reads a constant (40,960) on both handhelds

Base: 4fcbe0262edd7e876db50cdd22678b8e31befddf (origin/master).
No device claim needed for this pass: the two separating runs are already
queued by lane.flip474 (see nv2a_issues.toml #527 status_note) -- read their
results rather than queueing new ones. If they have not landed yet, do the
source-side half first (below) and come back to them.

CONTEXT: 35 of 36 ZPass captures on the Nova/Thor read a constant 40,960
regardless of what the test draws; one run read 65,536, but that run differed
from the rest in TWO ways at once (TU_DEBUG=sysmem set, and a kept shader
cache), so it does not by itself show which factor moved the count, or
whether either did. lane.flip474 queued two runs that each flip one factor
alone; find them (dispatch/board-requests or the PR #530/#516 history) and
read the counts out.

GOAL:

1. Read the two separating runs' ZPass counts. If both still read 40,960,
   the outlier run's 65,536 was something else (a third variable, a fluke) --
   say what changed between the outlier run and everything else. If one run
   moves off 40,960, name which factor (sysmem vs shader cache) and by how
   much.
2. Independent of the runs, read the ZPASS_PIXEL_CNT report path in the pgraph
   code (occlusion query report writeback) for anything that would produce a
   fixed value irrespective of draw content -- a hardcoded report size, an
   early-return before the real count is written, a report struct field
   filled from the wrong source. Say what you found even if it is nothing.

FALSIFIER: a real occlusion-query bug means the reported count tracks actual
covered pixels when you vary geometry (more triangles drawn -> higher count)
in a case NOT stuck at 40,960. If every case you can find is stuck at
40,960 including ones with visibly different draw content, that argues for
the report path itself (goal 2), not a per-run artifact.

DONE WHEN: the two queued runs are read and reported, the report path is read
and its behavior on a constant-count is explained, and #527's status_note is
updated with what changed. No hw/ edit is required to close this pass --
only open a PR if you have a proposed fix; otherwise report findings as an
