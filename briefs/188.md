# lane.cloud-188 -- model NV_PMC_ENABLE's read/write storage

Issue: #188
Base: master @ 1e184b134f2e81f24a2457eeefac7b2473b8f8a5
Files: hw/xbox/nv2a/pmc.c, hw/xbox/nv2a/nv2a_int.h

## What's already measured

PR #191's read-only PMC sweep (tools/nv2a_probe), two independent runs with
a reboot between them, 1,024/1,024 identical: NV_PMC_ENABLE (0x200) reads
0x01110000 on silicon. pmc.c today has no storage for it -- pmc_read and
pmc_write both fall to default, so reads return 0 and writes are dropped.

## Hazard -- read before writing any code

Writing 0 to this register on real hardware halted the console outright (no
ICMP afterwards, power cycle required). Do NOT register a falsifier that
writes to this register, on real silicon or in any form that could be
mistaken for it. This lane is read-side and storage only.

## Goal

Give pmc.c a stored register for NV_PMC_ENABLE, initialised to the measured
0x01110000, returned verbatim by pmc_read and updated verbatim by pmc_write
with NO bit interpretation -- nv2a_int.h's `pmc` struct already carries
pending_interrupts/enabled_interrupts as a pattern to follow. Do not assert
what the header's bit positions (NV_PMC_ENABLE_PFIFO bit 8, PGRAPH bit 12)
mean against the measured set bits (16, 20, 24); that mismatch is flagged in
the issue and needs an envytools cross-reference this lane is not scoped to
do.

## Falsifier

A read-only desktop-build test: after reset, pmc_read(0x200) returns
0x01110000; after pmc_write(0x200, X) for an arbitrary X that is NOT
literally 0 (respect the hazard above -- this is a QEMU-model write, not a
real-device write, so the console-halt risk does not apply here, but keep
the test's intent legible), pmc_read(0x200) returns X verbatim.

## Done when

pmc.c stores and round-trips NV_PMC_ENABLE, the desktop build passes, and a
short note is posted to #188 and #190 (which explicitly asks not to be
folded into this register) confirming the two stayed separate.
