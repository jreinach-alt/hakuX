# Audit pass 1: PR #289, lane/texvol283 (#283)

Auditor: job.cloud, 2026-09-25. Head audited: `6b449f0fd9`.
Diff read: `git diff origin/master...origin/lane/texvol283`, 5 files.
The code is `psh.c` (+47) and `psh.h` (+3). The rest is NOTES, the
prediction, and an index that only moves line numbers.

**Verdict: no HIGH, no MEDIUM, three LOW.** Next state is `needs-audit-2`.

## What was checked

- **Byte order of the split against the view swizzle.** The VK and GL tables
  agree. R16B16 is `R16G16_UNORM` with swizzle `{G,R,R,G}`, so `t.r` is
  `b2|b3<<8` and `t.g` is `b0|b1<<8`. Y16 is `R16_UNORM` with `{ONE,R,R,ONE}`,
  so `t.g` is `b0|b1<<8`. The emitted GLSL yields (b2, b1, b0, b3) and
  (1, b1, b0, 1), which is what the comment and the PR body claim. The uint
  arguments to the `vec4` constructor are legal in GLSL 4.50 and ES 3.00.
- **Cache key.** `tex_bytes16` is in `PshState`. `pgraph_glsl_hash_shader_state`
  and `..._compare_shader_state` hash and compare all of
  `sizeof(PshState)`, so the new field keys the shader. Its inputs are
  TEXFMT (color_format) and TEXFILTER (min/mag). Both already drive
  `conv_tex`, `tex_signed` and `snorm_tex`, so they are already dirty
  registers. Disabled stages `continue` before the new code, so the field
  stays zero for them, like its siblings.
- **Point-sampling gate against the host sampler.** In `vk/texture.c` the
  host filter comes from the same MIN/MAG fields, through
  `pgraph_texture_min_filter_vk_map`. BOX_LOD0 and BOX_NEARESTLOD map to
  `VK_FILTER_NEAREST`, and NEARESTLOD sets `mipmapMode NEAREST`. Every
  fetch the gate admits is therefore a single texel, and splitting it is
  exact. TENT and convolution are excluded.
- **Where the split is emitted.** It is emitted only when `sampler_type != NULL`.
  DOTPRODUCT, CLIPPLANE and PASSTHRU get a NULL sampler, so their
  synthetic `t` is never split. A texel that a later bump, dot or dependent
  stage consumes is skipped through `stage_consumed_raw`, the same
  predicate the signing block uses. That keeps #10's HILO paths on fields.
- **Ordering with signing.** The split runs before the per-channel
  `signed_channel` block. All-flags-signed (SNORM) is excluded from the
  split. Partial flags now sign bytes rather than a narrowed field, which is
  no worse than master.
- **Index.** `nv2a_index.json` changes are line-number shifts in `psh.c`.
- **Prediction.** It registers against b_ref `a5b4141064`, and the head has
  not changed `psh.c/.h` since then. The `[job.arms]` verdict passed
  (label `verified`): better=2, worse=0, 186/186 scored, and every
  must_not_move leg held, including Texture_format and both bump suites.

## Findings

### LOW-1: the split does not account for guest anisotropy on the host sampler

`max_anisotropy` comes from the guest's `TEXCTL0_0_MAX_ANISOTROPY`
(`vk/texture.c:1756`). When it is above 1, `anisotropyEnable` is set even
with NEAREST filters, and Vulkan leaves anisotropic filtering
implementation-defined. **Scenario:** a guest point-samples a Y16 colour
texture with MAX_ANISOTROPY > 0, and the host driver averages several
nearest texels anyway. Take the blend of 0x00FF and 0x0100. Split into bytes
it gives B = 0x00 or 0xFF, where a per-byte blend gives about 0x80. On
master the same blend was off by under one level. This depends on the
driver and needs a rare guest state, so it is LOW. **Fix:** add
`GET_MASK(ctl_0, NV_PGRAPH_TEXCTL0_0_MAX_ANISOTROPY) == 0` to
`point_sampled`, which costs one line.

### LOW-2: a texel that a later stage consumes, and that the combiner also reads, keeps its fields

When stage 0 is R16B16, stage 1 bump-maps from it, and a combiner also reads
`t0`, the combiner gets the narrowed fields. It does not get the bytes that
the #283 model says silicon gives. This is master's behaviour unchanged, so
it is not a regression. The comment states the exclusion, but it could
also say that the combiner-side read is knowingly left on the old model.

### LOW-3: 2D behaviour is extrapolated from the volume capture

The PR says every 2D capture is blind, because the converter writes lo == hi
bytes. The change applies to 2D, cube and 3D alike, but only the 3D
(volume) path has discriminating evidence. Treating the texture unit as
dimension-agnostic is plausible, and nothing refutes it. A 2D Y16 texture
with lo != hi (a real game's 16-bit luminance) is the untested case. It
should be recorded as an open leg in NOTES, not left implied by "every 2D
capture is blind".

## Recorded, not a finding

- The Y16 residual of 2,604 px, all off by one in the low byte, is disclosed
  in the PR body and NOTES. The prose estimate was about 100 px, but the
  prediction's machine-checked legs (better/worse, must_not_move) passed.
