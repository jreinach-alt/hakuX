# Audit pass 1: PR #594, lane.gpl569 (#569 P5, Vulkan graphics pipeline libraries)

Head audited: `4011dc3e9b` (the diff against `origin/master` at that sha).
Verdict: **no HIGH, no MEDIUM; five LOW.** The PR goes to `needs-audit-2`.

## Scope

Code: `hw/xbox/nv2a/pgraph/vk/{compile_worker.c,draw.c,instance.c,renderer.h}`.
Lane material: `docs/lanes/gpl569/*` and three predictions under
`docs/testing/predictions/gpl569-*.json`.

## The default (off) path is structurally inert

`HAKUX_GPL_DEFAULT` is 0, so `r->gpl.mode` is 0 unless `HAKUX_GPL` is 1 or 2.
With the mode at 0 the diff does this:

- `add_optional_device_extension_names()` enables no new extension and chains
  no new feature struct, so the device is created as before.
- `create_logical_device()` makes two extra `vkGetPhysical*2` queries and
  prints one `[gpl569]` line, but only when the driver lists the extension.
- `gpl_init()` runs from `pgraph_vk_compile_worker_init()`. That call has no
  guard on `xemu_get_async_compile()` (`shaders.c:1535`), so the lock and the
  tables exist on both the sync and the async path.
- `pipeline_cache_pre_evict()` also reads `gpl_lto_pending`, which is always
  false here.
- `post_evict`'s `snode->layout == r->gpl.layout` compares against
  `VK_NULL_HANDLE`, so it can only clear a handle that is already null.
- `push_template_index()` is gated on `r->gpl.layout != VK_NULL_HANDLE`.
- `finalize_pipeline_cache()` waits on `lto_inflight`, which stays 0.

## Mode 1/2 correctness checks that passed

- **Library keys cover every state each library's create reads.**
  - VI: bindings, attrs, topology and dynamic states.
  - PR: vs/gs SPIR-V ids and every rasterizer field. `depthBiasEnable` is
    fixed at false (`draw.c`), so the omitted bias factors cannot vary.
    `rasterizer.pNext` is always NULL (`rasterizer_next_struct`), so the
    assert cannot fire.
  - FS: fs id, `has_zeta`, and the whole depth/stencil struct from `flags` on.
    All of those fields are 4 bytes wide, so there is no padding.
  - FO: blend attachment, plus blend constants when they are not dynamic.
  - Formats are in every key, and each key is built on a memset struct.
  - Over-keying (dynamic depth/stencil and EDS3 blend fields still in the key)
    costs hit rate only.
- **Dynamic-state capacity.** At most 8+5+3 = 16 states, against
  `GplDynKey.states[20]`.
- **Layout compatibility.**
  - `r->gpl.layout` has the geom range plus the vertex range at 16 attributes,
    and the vertex range is guarded by `use_push_constants_for_uniform_attrs`.
    That is the same shape as `push_template_layout[16]` in
    `shaders.c:300-350`.
  - When the flag is off, both the GPL layout and template 0 have the geom
    range only.
  - So set-0 compatibility (#34 finding 3) holds.
  - The pixel arm (mode 1 vs off, 1059/1059) is consistent with this.
- **Render pass.** The libraries and the link use a formats-only render pass.
  The draw binds the key's own render pass. Vulkan render-pass compatibility
  ignores load/store ops, so the two are compatible even if the comment's
  claim about `create_render_pass()` ever stops being true.
- **Lifetimes.**
  - A `GplLib` is refcounted. A build holds one reference per library across
    the unlocked link, and an LTO job keeps those references until it has run.
    The shutdown drain drops the references of queued LTO jobs.
  - Linked pipelines survive their libraries being destroyed.
  - Shutdown order is right. `finalize_pipelines()` runs before
    `finalize_shaders()` (`renderer.c:511-512`), so entries see
    `r->gpl.layout` still set and do not destroy the shared layout; the worker
    shutdown destroys it once afterwards.
- **The mode 2 swap.**
  - `gpl_lto_pending` is set before `pending` is cleared, whether the job was
    queued from the worker or the render thread, so eviction never sees both
    flags false while an LTO job still holds `target`.
  - The fast-linked pipeline is kept in `gpl_retired_pipeline` until eviction,
    so a command buffer in flight never loses it.

## Findings

### LOW 1: the LTO swap reads the handle before the flag
`draw.c`, cache-hit path. The code reads `snode->gpl_lto_pipeline` first,
then `gpl_lto_pending`, then issues `smp_rmb()`. The worker writes
`gpl_lto_pipeline` as a plain store before its `smp_wmb()`. There is exactly
one write per entry and it is an aligned 64-bit handle, so a non-null read is
already the final value, and this does no harm on arm64 or x86-64. The code
is still in the wrong order and formally a data race. **Scenario:** none on
the shipped targets. A compiler or target that tears or reorders the plain
access could swap in a half-written handle. **Fix:** read `gpl_lto_pending`
with `qatomic_load_acquire` first, then the handle with `qatomic_read`.

### LOW 2: one full table flushes all four
`gpl_get_lib()` calls `gpl_flush_locked()`, which empties every kind when any
one table reaches `GPL_MAX_LIBS`. **Scenario:** a title with many
vertex-layout or topology variants fills the VI table (whose libraries are
cheap). The flush also drops every PR library, and each of those cost about
1.6 s to build on T30 (PR body). The next misses then rebuild them. This is a
performance cost only, and the path is opt-in. **Fix:** flush only the table
that filled.

### LOW 3: `HAKUX_GPL=2` has no pixel evidence
The pixels-inert prediction compares off against mode 1 only. The B2 soaks
ran with the LTO-linked pipelines swapped in, but a soak writes no captures.
**Scenario:** a later change makes mode 2 the default, or builds on it
(uberspike569 D-series), and quotes the 1059/1059 pass as cover. That pass
never drew through an LTO-linked pipeline. This is a limit of what the
evidence shows, not a defect in the code. It matters only if mode 2 is
promoted.

### LOW 4: shutdown under async compile plus mode 2 extends an existing hazard
`finalize_pipeline_cache()` waits for `lto_inflight == 0` and then calls
`lru_flush()`. `lru_flush()` skips any entry whose `pre_evict` refuses it
(`include/qemu/lru.h:229`). **Scenario:** at shutdown, a
`COMPILE_JOB_PIPELINE` for a GPL entry is still queued. `lto_inflight` is 0,
so the wait returns. The flush skips the pending entry, and the cache is torn
down. The worker then writes `target->pipeline` and enqueues a new LTO job
against that entry. `master` already has the `target->pipeline` write for
pending monolithic jobs; this diff adds a second job with the same shape.
The window is shutdown-only and needs an opt-in mode. **Fix, if taken:** have
the shutdown path drain the compile worker queue (both job types) before
`lru_flush()`.

### LOW 5: the DOA soak's device does not match its registration
`gpl569-doa-soak.json` registers `"device": "nova"` and orders all three
arms on the Nova. The PR body reports the DOA soaks as "Thor, cold". The
verdict is a refutation, with S1 at 1.17 and S2 at 16.6 against 0.70, so the
device swap cannot turn it into a pass. D1 and D2 are already void (Thor
thermal pause). **Scenario:** a reader compares these ms figures with the
Nova-registered P1 (#574) numbers as if they came from the same device.
**Fix:** state the device the soaks ran on in NOTES beside the registration,
or add a re-registration note.

## Not findings

- `gpljudge.py` is lane tooling that has already been used to score the
  soaks. It is not on any product path, and I did not audit it line by line.
- `gpl569-blinx-soak.json` stays registered even though its runs were never
  made. The arms job does not run title soaks automatically (they are read by
  hand), so leaving the file registered costs no device time.
