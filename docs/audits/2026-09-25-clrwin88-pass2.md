## The pass-1 reading, re-derived from the code at this head

The claim: after the decline, a stale `pg->surface_zeta.draw_dirty` re-enters
`update_surface_part()`. Once colour has left the address, that re-entry
creates a zeta surface. The claim is that the tail's
`download_surface_deferred()` on that new surface writes nothing to VRAM.

Checked in `hw/xbox/nv2a/pgraph/vk/surface.c`:

- `populate_surface_binding_target_sized()` sets `target->draw_dirty = false`
  (next to `upload_pending = true`).
- Every creation path (unshelve, reuse an invalid surface, fresh `g_malloc`)
  runs `*surface = target;`. That copy overwrites any `draw_dirty` carried
  by a shelved or recycled binding.
- The code between that copy and the tail does not set `draw_dirty` on the
  new surface. That code is `set_surface_label`, the unshelved block (only
  `upload_pending`/`initialized`), `surface_put` (map insert,
  `invalidate_overlapping_surfaces` on other surfaces, CPU-access callback),
  and `bind_surface` (binding pointer, `*_drawn_in_cb`).
- `download_surface_deferred()` returns at its first line when
  `!surface->draw_dirty`.

So the tail's download is a no-op on the new surface. The tail then clears
`pg->surface_zeta.draw_dirty`. The colour surface at that address is evicted
through the incompatible branch. If it is dirty it downloads its own
content first, and then it is shelved. No path writes stale or empty zeta
data over guest VRAM. L1 stays LOW.
