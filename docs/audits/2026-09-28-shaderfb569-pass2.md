## Pass-1 findings, re-checked

### L1: the display pipeline create is not wrapped. Still present, still LOW.

`display.c:622` still calls `vkCreateGraphicsPipelines` directly. The
wrapper `pgraph_vk_create_graphics_pipeline_fb` has three callers:
`draw.c:2041` (clear), `draw.c:2852` (sync) and `compile_worker.c:237` (worker).
The scenario can still occur: a display create inside a scored window goes
uncounted, so dpc reads low by one create. That is bounded. The display pipeline
is created at init and when the mode changes, and it is not on the fight load's
miss path. No verdict in the PR depends on counting it.

### L2: new counters are written from two threads without the lock. Still present, still LOW.

`glsl.c:462/473/485` still add to `glslang_us` and `shader_module_us` with no
lock. `profile.c:967/1050` add to `instr_ns` outside `pcfb_lock`, and
`compile_worker.c:124` adds to it under the lock. The bias is unchanged: a lost
increment makes `dgl_ms` read low, by tens of ms against a create of hundreds of
ms. It could decide C2 only if C2 were marginal. The PR's C2 reading is not
marginal.

### L3: module handles are never forgotten. Still present, still LOW.

`pcfb_modules` (`compile_worker.c:42`) only has entries added
(`:120`). `pgraph_vk_destroy_shader_module` (`glsl.c:516`) does not remove the
handle. A reused handle can still be counted as "reused" in a long session.
The measured soak had 164 creates against a 50K-entry module LRU, so no module
could have been evicted, and the 246/246 C3 reading does not rely on this path.
