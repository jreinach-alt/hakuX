## H1 — CLOSED. The third outcome is excluded by the refs, and the path table matches the code line for line

Pass 1's scenario: the arm is queued on a desktop GL build with
`surface_scale_factor != 1`, aborts on the assert keyed on the undersized
condition itself, and `expect_counts.better = 1` fails for a reason that is
neither model — in a prediction claiming "either outcome settles it".

Both refs now read `4129a349e6 with xemu.toml [display] renderer = OpenGL |
Vulkan, [display.quality] surface_scale = 1`. That key path is real:
`config_spec.yml:226-239` is `display: renderer: {NULL, OPENGL, VULKAN}` and
`display: quality: surface_scale: integer, default 1`. With the scale at 1,
`downscale &= (pg->surface_scale_factor != 1)` (`gl/surface.c:2322`) clears
`downscale`, and the assert lives inside `if (downscale)` at `:2472-2473`. Path
C is unreachable under the registration as written, which is what the finding
asked for.

I re-derived the whole A/B/C table against `origin/master` rather than taking
it, since it is the artifact's new load-bearing claim:

| path | gate in the tree | what the artifact says | holds |
|---|---|---|---|
| A | `#ifdef __ANDROID__` + `android_surface_uses_rgba8_transfer()`, `:2394` | Model E via `android_surface_rgba8_to_guest(..., linear_guest, surface->pitch)` then `swizzle_rect(..., surface->pitch, ...)` into `g_malloc(surface->size)` | yes — `:2424-2432`; branch ends `goto cleanup` at `:2436`, so C is unreachable behind it, exactly as claimed |
| B | otherwise, `surface_scale_factor == 1` | Model E via `glo_readpixels(..., pg->surface_scale_factor * surface->pitch, ...)` | yes — `:2460-2467` |
| C | otherwise, `surface_scale_factor != 1` | `assert(surface->pitch >= surface->width * surface->fmt.bytes_per_pixel)` — abort | yes — `:2473`, inside `if (downscale)` |

`surface_download()` passes `downscale = true` unconditionally at `:2524`, and
nothing in `populate_surface_binding_entry_sized()` forbids `pitch <
width*bpp` — `:2850` is the DMA limit, `:2851` the `pitch % bpp` — so Path C is
live in the tree and the pin, not the code, is what excludes it. The crash-path
list now carries it: the prediction says "(3) IS NOT THE ONLY CRASH PATH AND IS
THE LESS URGENT ONE: `surface_download_to_buffer`'s Path C assert fires on
`pitch < width*bpp` ITSELF", and the investigation doc carries the same table.

The one thing no artifact can enforce is that whoever builds the renderer
override honours the pin. The prediction says so in the imperative ("WHATEVER
SETS THE RENDERER MUST SET `quality.surface_scale = 1` IN THE SAME PLACE"), in
the PR body, and in the doc. For a registration that is deliberately not
queueable, that is the strongest form available; see N3 for the one wrinkle.

## N1 — LOW. The grep is published and the counts beside it are off by one in two places

The remediation replaced "seven sites" with the grep, then wrote three counts
next to it: "seventeen", "fourteen in `vk/surface.c` and three in
`gl/surface.c`", "eight functions". The grep returns **eighteen** lines, **four**
in `gl/surface.c`, across **nine** distinct functions.

The extra gl line is `:2247`, `swizzle_buf = g_malloc(output_pitch *
output_height)` inside `android_surface_download_z24s8_to_guest` — a local
scaled-download buffer, not a surface-extent site, so the enumeration's "three"
is the right count of *sites* and the grep simply over-returns by one. The
ninth function is arithmetic: the artifacts name nine distinct functions and
then say eight.

This cannot reproduce M2's failure. The direction is over-return, so a lane
working the grep sees every site the prose lists plus one to dismiss; nothing
can be missed. Worth a line because the parent finding was precisely "a hand
count beside the code drifts", and three hand counts were re-introduced beside
the grep that was meant to retire them.

## N2 — LOW. "The only GL numbers … are race-affected" omits a race-free GL number that the cited tracker row records two sentences from the text quoted

The prediction and the doc say: *"the only GL numbers (13,160 / 14,848 /
15,360) predate `c807592d02` and are race-affected"*, and the doc says *"Every
clean number on this capture is from the path that does not [use pitch]"*.

`nv2a_issues.toml` #87 — the row the same paragraph quotes — opens with: *"#39's
skew-bound run recorded **both renderers at 10,240 px with one digest**,
`15845fa9e1e40032`"*. That is a GL number on this capture, it is race-free (the
bound is what made it so), and it is byte-identical to Vulkan's. The row's title
is "a swizzled render-target layout **both renderers share**".

**The conclusion is unaffected**, which is why this is LOW and not a reopening
of M5: that run also predates `c807592d02`, so GL was still on the
surface-to-texture fast path and never reached the pitch-using CPU download.
It is not a measurement of Model E either. But the argument as written rests on
"every clean number is Vulkan", and the true premise is the narrower "every
clean number predates the commit that routes GL into the pitch-using code" —
which the artifacts also state, one bullet later, and which is the one that
survives contact with #87's own text.

**Failure scenario, such as it is:** a reader checks "the only GL numbers" against
#87, finds a race-free GL 10,240 sharing Vulkan's digest, and concludes the
survey behind the "unmeasured" verdict was careless — when the verdict is right
and only the premise is overstated. One clause fixes it.

abort instead of either model.
