# Audit pass 1: PR #264 (lane/vtxarr262), #262

Head audited: `e1a710abff`. Diff read: `hw/xbox/nv2a/pgraph/vk/draw.c`
(+113/-1), `docs/lanes/vtxarr262/score_console.py`,
`docs/testing/predictions/vtxarr262-surface-vertex-refetch.json`, the lane
NOTES and the regenerated `docs/testing/nv2a_index.json`.

**Verdict: no HIGH, no MEDIUM. Three LOWs.** Label → `needs-audit-2`.

## What the change does, checked against the code it relies on

`vertex_range_gpu_stale()` calls a vertex range stale when it overlaps a
surface (live, shelved or invalid) that is `draw_dirty`, or whose
`draw_generation` differs from the one recorded when that range was last
copied. The check runs in two places: at the head of
`has_dirty_vertex_pages()` (which gates the `all_uploaded && !dirty` early
exit and the three `OPT_SYNC_RANGE_SKIP` fast paths) and for each merged
range in `sync_vertex_ram_buffer()`. After each copy, the overlapping
surfaces are recorded at their current generation.

I checked the parts that could go wrong:

- **The download comes before the copy.** `pgraph_vk_update_vertex_ram_buffer`
  (`vk/vertex.c:45`) calls `pgraph_vk_download_surfaces_in_range_if_dirty`
  first. That function completes its deferred downloads before it returns
  (`surface.c:432`), and only then runs the `memcpy`. The record step runs
  after the update, so the generation it stores is one whose data is already
  in the vertex buffer.
- **No surface stays stale forever.** A permanently stale surface would copy
  its range on every draw and switch off the skip paths. That needs a surface
  with `draw_dirty` set that the in-range download never retires. I found
  none:
  - A shelved surface is downloaded only if `shelved_dirty && draw_dirty`.
    Eviction sets `shelved_dirty = false` only after it has called
    `download_surface_deferred` (`surface.c:3713-3717`), and that download
    clears `draw_dirty` when it completes, because a shelved surface's
    generation does not move.
  - `download_surface_deferred` returns early when
    `download_generation == draw_generation`. Every full download that sets
    those two equal also clears `draw_dirty` (`surface.c:912-916`, `1583`,
    `1784`, `1868`).
  - A partial download (`download_row_count` from a CPU read) does not clear
    `draw_dirty`. But it resets `download_row_count` to 0, so the next in-range
    download is a full one and does clear it.
- **Threads.** Every caller of the new list walk (`try_snapshot_*`,
  `flush_draw_queue_internal`, `flush_draw_one_pass`, `sync_vertex_ram_buffer`)
  runs where `pgraph_vk_update_vertex_ram_buffer` already runs, and that
  function already walks the same three lists. The change adds no thread to
  the lists.
- **Not setting DIRTY_MEMORY_NV2A.** The PR body says `update_surface_part`
  reads that bit as a guest overwrite. Setting it from a draw would make the
  next surface bind upload VRAM over the render. Keeping the tracking
  read-only is correct.
- **Range width.** `sync_vertex_ram_buffer` checks page-rounded merged ranges.
  `has_dirty_vertex_pages` checks the exact ones. The rounded check covers
  more than the exact one, so the mismatch can only add copies. It cannot
  miss one.

The arm backs this up. 73/73 machine legs are byte-identical between the two
arms, and DynamicUpdateLoop goes from 96,000 px to 0 against the console root.
The other four Surface-as-vertex-array tests do not change.

## Findings

### LOW-1: the generation table is keyed by a pointer that the allocator reuses

`vtx_surf_gen[]` stores `(SurfaceBinding *, gen)`. Bindings are created with
`g_malloc0` (`surface.c:3741`), so `draw_generation` starts at 0, and they are
freed with `g_free` when pruned (`surface.c:2714`, `2764`). No entry is
removed when its binding is freed. The table is also file-static, so it
outlives a renderer finalize/init (`surface.c:4109`).

**Failure scenario:** binding S1 covers address X and is drawn k times. The
flip downloads it, and a vertex draw from X copies the range and records
(S1, k). S1 is pruned. A new binding S2 gets the same block from the
allocator, is bound at X, and is drawn k times. The flip or a texture
download retires it (`draw_dirty` false) before the next vertex draw from X.
`vtx_surface_stale(S2)` finds the entry with gen k, which matches, and
reports the range fresh. The draw uses the previous contents. The loop
pattern that needs this fix, with the same number of draws each pass, is
also the pattern where k matches.

**Bound:** the result is the pre-fix behaviour for that draw, not a new wrong
result. It also needs a prune, a same-block allocation and an outside
download to line up. **Fix:** clear the entry wherever a binding is freed, or
key it on something that is never reused (a per-binding serial, or the pointer
plus `vram_addr`).

### LOW-2: a per-draw download is now possible whenever a live render target overlaps a vertex range, and no leg measures its cost

Each colour or zeta draw sets `draw_dirty` and advances `draw_generation`
(`draw.c:7410-7422`). So when the bound target overlaps a sourced vertex
range, every later sync of that range downloads the target and waits on a
fence (`pgraph_vk_download_surface_complete_deferred`). For true
render-to-vertex-buffer that is the correct cost, and DynamicUpdateLoop needs
it. Before this change, a target that overlapped a vertex range without being
used as one cost nothing unless the guest wrote the range.

**Failure scenario:** a title whose enabled attribute range (offset + stride ×
(max_element + 1)) covers part of a live render target it never reads as
vertices would lose frame rate after this change. Its pixels would not change,
so the machine legs, which are suites only, cannot see it. I know of no title
that does this, so this is LOW. A single `gfps` soak of one title over the
fix ref would settle it. Consider an `OPT_STAT_INC` on the `gpu_stale` branch
so a later soak can count how often it fires.

### LOW-3: the new walk sits in front of every fast path

`has_dirty_vertex_pages` now walks all three surface lists for every pending
sync range (up to 16) before it reads the bitmap, and this happens on the
`OPT_SYNC_RANGE_SKIP` paths, which exist to be cheap. The cost is linear:
ranges × surfaces, plus a 64-slot scan for each overlapping surface. Shelved
is capped at 20 and invalid at 10. Correctness is fine, and no measurement
shows a cost. It is noted because the fast path was built to avoid exactly
this kind of per-draw work.

### Not a defect of this diff

The PR says GL has the same defect (`gl/vertex.c` never downloads surfaces
that overlap a vertex range) and leaves it unfixed. That is outside this
diff. It should be its own issue if it does not already have one.

`score_console.py` hard-codes the host paths of this run. It is a record of
the hand-score, not a reusable tool, and that is fine for a lane directory.
