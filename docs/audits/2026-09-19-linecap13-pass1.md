commits over its stated base **`415dcc6997`** (master merged forward at

**Date** 2026-09-19. **Records** `2026-09-19-linecap13-pass1.{md,json}`.

**2 HIGH. 3 MEDIUM. 3 LOW.**

The diff is +1250/−27 over eleven files. The behaviour change is 253 lines in
`hw/xbox/nv2a/pgraph/glsl/geom.c` — a Sutherland-Hodgman clip of the widened
line footprint against two minor-axis half-planes, plus a new
`emit_line_vertex()` that has to synthesise a vertex where the clip cuts a long
edge — and 16 lines of constants and comment in `vk/instance.c`. Everything
else is offline tooling, notes, the prediction and a line-number-only index
regeneration.

The derivation, the clip geometry and the strip order are right. **Both HIGHs
are in the new synthesised vertex**: the clip cuts a corner off each tip, and
the two or three vertices that replace it carry a depth and a varying set that
the unclipped parallelogram did not have. Neither is reachable from anything
this lane measured — the offline model scores ink coverage, so it is blind to
`gl_Position.z` and to every varying — which is why both survived a green
`--shader` check and green CI.

## What I checked and found correct, so remediation does not re-derive it

* **The clip planes implement the stated rule.** The rule is "minor index `i`
  is lit only if `floor(m_min − w/2) <= i <= ceil(m_max + w/2)`". The GLSL
  (`geom.c:677-684`) clips the polygon to the coordinate span
  `[floor(m_min − w/2), ceil(m_max + w/2) + 1]`. A pixel centre `i + 0.5` lies
  in that closed span exactly when `i >= floor(...)` and `i <= ceil(...)`,
  because both bounds are integers. Correct, including the `+ 1.0`.
* **`lineHalfExtentScale` really is `w/2`, not `E/2`.** `geom.c:238` defines it
  as `0.5 * lineParams.z` and `lineParams.z` is the line width; `E` is formed
  separately at `:591` from the same macro times `(max + min/2)/|d|²`. The
  comment's insistence on "the WIDTH, not the widened extent `E`" matches what
  is written.
* **Clipping the planes from `v_vtxPos` rather than from the tie-shifted
  corners is sound, and the tie bias cannot reach them.** The polygon carries
  `+tie` on the minor axis and is tested against unshifted integer planes; the
  rasteriser's centre test against the shifted polygon then yields exactly the
  index rule above, and a `1/256` shift cannot move a bound that sits half a
  pixel from any centre.
* **Six is the true maximum.** Sutherland-Hodgman against one half-plane takes
  a convex `n`-gon to at most `n + 1` vertices, so 4 → 5 → 6. I also checked
  the case the bound-by-induction argument hides: when the line's minor extent
  is shorter than `E/2 − w/2`, a single plane cuts *two* vertices and adds two,
  so `np` stays 4. The `< 6` guards are therefore dead in exact arithmetic and
  are the right shape for the float case, since an out-of-range GLSL array
  write is undefined rather than trapping.
* **The strip order is a valid cover of the convex polygon and is backward
  compatible.** `j = (k even) ? k/2 : np−1−k/2` gives `0,3,1,2` at `np == 4`,
  which is the order `emit_line()` emitted before this change, and
  `0,5,1,4,2,3` at `np == 6`, whose four triangles tile the hexagon without
  overlap. At `np == 4` all `T` are still exactly `0.0`/`1.0`, so every vertex
  takes `emit_line_vertex()`'s early-out into the old `emit_vertex()` path and
  the "byte for byte the one this shader emitted before" claim holds.
* **`T` is the right parameter.** The corner offset `n` is purely
  perpendicular to `delta`, so both corners at an endpoint have line-parameter
  0 or 1; `cap_clip()` interpolates `T` with the same screen-space fraction it
  interpolates `P` with, and the long edges are parallel to the line, so the
  cut point's `T` is its fraction along the line. Correct.
* **`line_lerp_t()` is correct.** `(t·i_b)/mix(i_a, i_b, t)` is the
  perspective-correct line parameter for screen fraction `t`; it is the
  standard formula specialised to attribute endpoints 0 and 1.
* **The `1/w` half of `line_clip_lerp()` is correct.** `1/w` is affine in
  screen space, so `w = 1/mix(ia, ib, t)` is exact.
* **The component budget in `vk/instance.c` is arithmetically right.**
  `18 × (48 + 5) = 954 ≤ 1024`, `53 ≤ 64`, `18 ≤ 256`; the "70 of headroom,
  not enough for another varying" line is right too (a further `vec4` costs
  `4 × 18 = 72`). All four `QEMU_BUILD_BUG_ON`s still fire on the case they
  were written for.
* **The prediction's refs are live and correctly ordered.** `a_ref
  415dcc6997` is the stated base; `b_ref c8d2c22e14` is an ancestor of the tip
  and is *after* the master merge `5b908c1da6` and after the shader commit
  `7ce57a799b`, so the arm will build the code under test. The two commits
  after `b_ref` touch only `docs/`.
* **`C1` is honestly a bound and not a value.** The reasoning in the
  prediction — that 21 px and 544 px both clear 600 while arm A's ~908 does
  not — is stated before the arm, and registering 544 as a value would indeed
  convert an ordinary model-device gap into a violated check. The `vs_goldens`
  leg reads only the two capture sets, never the model, and prints a "READ
  NOTHING" line so an unfindable capture set cannot score a perfect zero.
* **`carve.py` preserves line numbers** (`"\n" * cut.count("\n")` plus the
  newline that remains at the head of `text[k:]` reproduces the original line
  count exactly), and `geom_dump/build/` is now correctly untracked.
* **`nv2a_index.json` is a line-number-and-provenance change only** — 10
  locations moved, no site added or deleted, `sites` and `gaps` unchanged. No
  suite was dropped by an older tests tree.

## HIGH

### H1 — `line_clip_lerp()` computes the wrong clip-space `z` whenever `w0 != w1`

`geom.c:337-339`:

```
float z = mix(pa.z * ia * ia, pb.z * ib * ib, t) * w * w;
```

`z_clip` is linear in the 3D segment parameter, so `z_ndc = z_clip/w` is
affine in window space and the value at screen fraction `t` is

```
z_clip = w * mix(za*ia, zb*ib, t)
```

— one factor of `ia`/`ib` inside and one `w` outside, not two of each. The two
agree only when `ia == ib`, i.e. `w0 == w1`, which is the 2D case the lane
measured; the comment directly above asserts the general case is handled
("perspective-correct interpolation is affine in `(a/w, 1/w)`") and the code
does not do that.

The comment is also the reason this is not merely cosmetic: it tells the next
reader the subdivision is invisible, so nobody will look here again.

**Failure scenario.** A wide line (`w >= ~24`, where the clip bites) drawn in
perspective with `w_a = 1`, `w_b = 4` and endpoint NDC depths 0.2 and 0.8. At
the cut vertex at screen fraction 0.5 the true NDC depth is 0.5; the shipped
expression yields `z/w = 0.32`. I evaluated the two expressions at
`t = 0.25/0.5/0.75`: NDC depth 0.246 / 0.320 / 0.457 against the correct
0.350 / 0.500 / 0.650. Depth across the two sub-polygons nearest each cap is
then wrong by up to ~0.18 in NDC, which shows as the cap of a wide line
sorting in front of or behind geometry the body of the same line sorts
correctly against, and can push `z` outside `[-w, w]` and invoke near/far
clipping that the unclipped parallelogram did not. No golden and no leg in
this prediction reads depth.

**Remediation.** `float z = mix(pa.z * ia, pb.z * ib, t) * w;`. Worth adding a
host-side check in `line_cap_phase.py`'s shader transliteration that evaluates
`z` at the cut points for a `w0 != w1` pair and compares against the endpoint
lerp, so the next change here is not measured only by ink.

### H2 — under flat shading the synthesised vertex pins six *interpolated* varyings to endpoint `i0`

`geom.c:435-445`, the `else` arm of `state->smooth_shading`:

```
vtxFog = v_vtxFog[i0];
vtxT0 = v_vtxT0[i0];   ... vtxT3 = v_vtxT3[i0];
vtxPointSize = v_vtxPointSize[i0];
```

The premise in the comment at `:392-394` — "EVERY FLAT VARYING HERE COMES FROM
i0. Under flat shading that is all of them" — is false.
`pgraph_glsl_get_vtx_header()` (`glsl/common.c:56-71`) gives `vtxD0`, `vtxD1`,
`vtxB0`, `vtxB1` the shade-mode-dependent qualifier and gives **`vtxFog`,
`vtxT0`..`vtxT3` and `vtxPointSize` `smooth_s` unconditionally**. They are
interpolated in every shade mode. `emit_vertex()` agrees: it reads `vtxD*`/
`vtxB*` through `provoking_index` (`"0"` under flat) but reads
`vtxFog`/`vtxT*`/`vtxPointSize` through `index`, the emitted vertex. The new
flat arm assigns them a constant instead, and also drops the `cylWrap()`
adjustment that `tex_lines[]` applies for every wrapped coordinate — `tex_lerp[]`
is built for all four units but referenced only from the smooth arm.

**Failure scenario.** A flat-shaded, textured wide line, `w = 32`, whose
higher-minor endpoint is `i1`. The high plane cuts corner `P1 = i1 + n`,
producing a cut vertex on the long edge `P0→P1` at `T` close to 1 and a second
on the short cap edge `P1→P2` whose `T` is `mix(1,1,f)`, i.e. `1 - ε` in
float rather than exactly 1, so it too misses the `tl >= 1.0` early-out. Both
vertices sit at the `i1` tip and both are given `i0`'s texture coordinates —
the value from the *far* end of the line. For a 20 px line at 45° the long-edge
cut lands near `T = 0.5`, so the error is a large fraction of the whole
line's texcoord span; at the short-edge vertex it is the entire span. The
texture over the two triangles touching the cap is sheared, and the same
happens to fog. The offline model scores ink masks only, so `--vs-goldens`,
`--rivals` and `--shader` are all blind to it, and `Line_width` has no
textured flat-shaded wide line to catch it either.

**Remediation.** Interpolate them exactly as the smooth arm does — emit
`tex_lerp[]` and `mix(v_vtxFog[i0], v_vtxFog[i1], t)` etc. in both arms — and
keep only `vtxD0`/`vtxD1`/`vtxB0`/`vtxB1` pinned to `gl_in[0]` under flat.
That also makes `tex_lerp[]` live on both paths. The comment at `:390-399`
needs rewriting from the real qualifier table, not from the shade mode.

## MEDIUM

### M1 — the invariant H2's comment promises is not achieved for `vtxFogSpecial` either, because the endpoint vertices still go through `emit_vertex(index)`

`vtxFogSpecial` is `flat` in every shade mode (`common.c:61`) and
`emit_vertex()` reads it through `index` (`geom.c:366`), so a strip vertex
emitted at `T == 1` supplies `v_vtxFogSpecial[i1]`. `emit_line_vertex()` pins
it to `i0` only on the interpolated path. Which vertex is provoking therefore
moves with the clip, which is what the comment says the design prevents.

**Failure scenario.** Take the mirror of H2's case, where the *lower*-minor
endpoint is `i1` — then the low plane cuts `P3` and the high plane cuts `P0`,
and the resulting strip order `0,5,1,4,2,3` puts the surviving original corner
`P1 = i1 + n` (emitted via `emit_vertex(i1)`) into a provoking position under
Vulkan's default first-vertex convention. Before this change both triangles of
the 4-vertex strip provoked from the `i0` side. Independently, the pipeline can
be built with `last_provoking` set from
`NV_PGRAPH_CONTROL_3_PROVOKING_VERTEX_LAST` (`vk/draw.c:5078-5080`): under that
convention the old strip provoked from `i1` for *both* triangles, while the
hexagon's last vertices are three interpolated ones (pinned to `i0`) and one
`i1`. So a flat-shaded wide line's `vtxFogSpecial` — and, under
last-provoking, its flat colours by way of the same asymmetry — changes
depending on whether the cap clip bit, for the full range of widths above the
bite threshold.

**Remediation.** Decide the flat source once for the whole primitive and apply
it on both paths. If `i0` is the intended answer, `emit_line()` must stop
routing `T == 0/1` vertices through `emit_vertex(index)` for the flat
varyings; if the answer is "whatever the provoking vertex would have been",
say which convention and derive it. Either way the comment must state the
convention it depends on.

### M2 — the synthesised vertex uses the perspective-correct parameter for varyings that may be declared `noperspective`

`geom.c:409` computes `t = line_lerp_t(i0, i1, tl)` and every varying mix uses
it. That is right for the default `smooth` interpolation. But `smooth_s` in
`common.c:45` is `"NOPERSPECTIVE "` whenever `state->noperspective` is set,
which `geom.c:46` drives from `NV_PGRAPH_CONTROL_0` — the Texture_perspective
state bit. Under `noperspective` the rasteriser interpolates linearly in
screen space, so the value the old unclipped parallelogram produced at the cut
point is `mix(A0, A1, tl)`, the *screen* fraction, and giving the vertex
`mix(A0, A1, t)` makes the sub-polygons reproduce a different function.

**Failure scenario.** Perspective-disabled texturing (`Texture_perspective`'s
`tex_*_pers_n` cases) on a wide line with `w_a != w_b`: with `w_a = 1`,
`w_b = 4` a cut at screen fraction 0.5 gets the varying value for parameter
0.8 instead of 0.5. Bounded — it needs the perspective bit off, a genuine `w`
difference and a width above the bite threshold at once — but it is a wrong
value on a path the diff introduces, and the same `docs/investigations/`
measurement that established `noperspective` matters (159,574 px across six
captures) says the state is exercised.

**Remediation.** Pass both parameters into the varying mixes and select on
`state->noperspective`, which the generator already has in hand at this point.

### M3 — `controls()` measures the rejected rival's blast radius, not the shipped rule's

`line_cap_phase.py:476-506` is explicitly the "what the instrument cannot see"
section. It unions `cap="perp", clip=1.0` (`:494`) — the *centre-sampled band*,
listed in `VARIANTS` as `"pen, centre band"` and rejected in the write-up for
scoring 497 px — and reports how many pixels that removes and how many the
goldens agree with. The shipped rule is `pen=1.0, tie="ceil"`, which is what
`shader_check()` compares the transliterated shader against (`:344`). The tie
count at `:501-503` has the same problem: it counts boundaries landing on a
half-integer (`abs(v − floor(v) − 0.5) < 1e-9`), which is the population that
separates low-open from closed for the `clip=` variant. The population that
separates the shipped outward rounding from its nearest rival `tie="floor1"`
is boundaries landing on an exact **integer**, and nothing counts it.

**Failure scenario.** The control exists so that a score which did not move
can be told from a rule with nothing to act on. As written it answers that
question for a rule that was not adopted, so the reader of `--controls` gets a
touchable-pixel population and a tie count that are not the shipped rule's.
Concretely: `tie="floor1"` and `tie="ceil"` differ by one pixel row on the high
side exactly when `m_max + w/2` is an integer, and every corner in the NOTES
table (`318.9375`, `508.9375`, `387.9375`, `356.0625`…) is non-integer, so the
six readings the rounding was chosen from cannot distinguish the two. Whether
any golden edge can is unmeasured, and `--controls` is the place that was
supposed to say.

**Remediation.** Score `controls()` on `pen=1.0, tie="ceil"` and add a tie
count for `abs(v − round(v)) < 1e-9` on `m_min − w/2` and `m_max + w/2`. If
that count is zero, say so: it means the goldens do not select the outward
rounding over `floor + 1`, which is a fact the next lane needs and which the
current write-up asserts the opposite of.

### L2 — the shipped comment quotes a different before/after pair from every other artifact

`geom.c:644-646` says the clip takes the residual "from 495 mismatched px to
102", and `:652-653` says the centre-sampled rival scores "497 px, worse than
the 495 it was meant to fix". The prediction, the PR body and NOTES.md all say
497 is worse than **412**, and quote 414 → 21 at the epsilon tie and 935 → 544
at the device tie. 102 appears nowhere else in the diff. Three different
baselines (412, 495, 935) and two different "after" numbers are in play for
what reads as one measurement, with no instrument named at any of them. Since
these numbers *are* the evidence for the rule, each quotation should name
which instrument produced it (analytic model, polygon rasterisation at
`tie=1e-9`, polygon rasterisation at `tie=1/256`) or be dropped.

### L3 — two stale references left behind by the constant bump

`vk/instance.c:751` still reasons about "`assert(limits.maxGeometryOutputVertices
>= 12)`" after the constant moved to 18 (the argument is unaffected; the number
is now wrong). `line_cap_phase.py:76` labels `tie == "floor1"` as "the measured
rule", but the rule that ships, and the one `shader_check()` validates against,
is `tie="ceil"` — see M3. A reader picking a variant from that comment picks the

## Disposition

HIGH present → **`needs-remediation`**. H1 and H2 are both one-site fixes in
`emit_line_vertex()`/`line_clip_lerp()`; M1 and M2 are in the same function and
are cheapest to take in the same pass. Pass 2 will check that each scenario
above can no longer occur, not that a commit exists.
