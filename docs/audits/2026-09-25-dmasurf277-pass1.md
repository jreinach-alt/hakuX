`origin/master` merge base `fab230935e`.

**Verdict: no HIGH, no MEDIUM. Three LOWs.** The hunk is correct for the
failure it targets. The arm isolates exactly the hunk
(`git diff 7f6b5e3473 c49955975b` is `system/physmem.c` +16 only), and both refs
are ancestors of the head. Next state: `needs-audit-2`.

## What was checked

- **Address arithmetic.** `memory_region_get_ram_addr(mr) + xlat` is the same
  ram_addr form that `flatview_write_continue` builds (`mr_addr +
  memory_region_get_ram_addr(mr)`, physmem.c:3447). `flatview_translate`
  returns the terminal RAM region, so aliases are already resolved.
  `memory_access_is_direct()` has already rejected ROM and MMIO writes (they
  take the bounce branch), so `RAM_ADDR_INVALID` cannot reach the call. The
  length is `*plen` after `flatview_extend_translation`, and that is the
  mapped length. `qemu_ram_ptr_length` can clamp it further; the clamped length
  is never larger, so the callback covers at least the bytes the device writes.
- **Callback semantics.** For a write, `surface_access_callback` (vk
  surface.c:1877; the gl sibling works the same way) downloads a dirty surface
  and sets `upload_pending`. Doing this before the device write matches the
  bounce and `address_space_write` paths: they call the watch at physmem.c:3448
  before the bytes land.
- **Re-entrancy.** No code under `hw/xbox` calls `address_space_map`,
  `dma_memory_map`, `cpu_physical_memory_map` or `pci_dma_map`. The surface
  download writes through a host pointer, so the new call cannot recurse into
  itself through a download.
- **Arm.** The must-move leg is the right leg. Wildcard must-not-move legs are
  an existing format (for example `2026-09-20-gl-x1a7-read-side.json`). The
  disc suites cover every leg named.

## Findings

### LOW-1: IDE DMA can now wait on the pfifo thread while holding the BQL

`surface_access_callback` does `qemu_event_wait(&r->downloads_complete)`, and
the pfifo thread sets that event. IDE DMA completion and `dma_blk_cb` run on
the main loop with the BQL held. The pgraph thread takes the BQL for context
switches (pgraph.c:1062) and error or NOP interrupts (pgraph.c:2263).

**Scenario:** a game streams a file into memory that is still a dirty,
watched surface. The pgraph thread reaches `bql_lock()` at 2263 while the main
loop is inside the new call and waiting. The main loop then waits for a
download that the blocked thread will never post, and the emulator hangs.

This is not a new class of hazard. Every BQL-holding device writer through
`flatview_write_continue` (OHCI, nvnet) already has it, and the lane's NOTES
records it. What the patch adds is exposure: IDE loads into
former-render-target memory are the case this fix exists for. The arm detects
a hang only if the race fires during the run, which is unlikely. A clean arm
therefore does not show the hazard is absent. Fixing it belongs in the
callback (drop the BQL around the wait when it is held), not in this hunk.

### LOW-2: the callback list is walked off the vCPU thread

`mem_access_callback_insert` and `_remove_by_ref` change
`cpu->mem_access_callbacks` in `async_safe_run_on_cpu` work.
`remove_by_ref` calls `g_free`. That work runs in an exclusive section which
excludes vCPUs but not the main loop. The new call walks the list from the
main loop.

**Scenario:** the pgraph thread retires a watch while an IDE map walks the
list. The walk then reads a freed `MemAccessCallback`.

This is pre-existing: `flatview_write_continue` and `flatview_read_continue`
already walk the list from the same thread for every OHCI and nvnet access,
far more often than IDE maps. The hunk adds no new thread and no new kind of
race. Record it only.

### LOW-3: the watch fires at map time, but the write lands at unmap

The direct path reports the write before the block I/O runs, and the I/O can
take milliseconds. The bounce path reports it at unmap time.

**Scenario:** the surface is re-bound during that window, and
`upload_pending` is consumed before the file data lands. Rebinding is covered:
`address_space_unmap` sets the NV2A dirty bits, and the rebind path ORs them
back in (`upload_pending |= mem_dirty`, vk surface.c:3649). A guest that
renders into the surface during its own DMA is racing on hardware too. The
hunk's comment says "as the bounce path does", which is loose about the
timing and should say map time. Quality only.

## Not a finding

The lane deliberately leaves out the symmetric `BP_MEM_READ` for direct-map
reads (NOTES, "Not done: the read leg"). It is out of scope for #277 and has
no failing capture yet.
