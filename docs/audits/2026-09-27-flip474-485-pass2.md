### L1: `cbl_pct` reports a censored p90 as a value: stands, perflog readout only

`cbl_pct` (`pfifo.c:988-1000`) still returns `(CBL_BUCKETS + 1) *
CBL_BUCKET_NS` for any latency past the last bin, and `cbl_maybe_dump`
(`:1038-1039`) prints it without a marker. The code is inside
`#if defined(__ANDROID__) && NV2A_PERF_LOG` (`:770`), so no default or
shipping build runs it. As pass 1 found, no verdict in NOTES §15 rests on
p90: S1 and the levers read the span and the split. The scenario (a later
before/after reading 100.3 → 100.3 as "unchanged") needs a future reader,
not this diff. **Follow-up:** print `>=100.25` for the overflow bin, and mark
AUF's p90 cell in §15 as censored, the next time either file is touched.

### L2: the cost comment understates the clock reads: stands, comment only

`pfifo.c:767-768` still says "a clock read per method dispatch and per
park, which the perf log's own `_meth_t0` already pays". It is a comment in
a perflog-only block, so there is no run-time scenario. The P legs bound the
real cost on the two titles measured (14 vs 14.96 and 16 vs 17.32 gfps).
**Follow-up:** correct the comment to two reads per method and two per park,
neither shared with `_meth_t0`.

### L3: `o4clock.py` has no self-test and a zero `sxx`: stands, lane tool

`docs/lanes/flip474/o4clock.py:58` still guards on `len(rows) < 20`, and
`:74-75` still divide by `sxx`, so a sub-5 s `--from/--to` window still
raises ZeroDivisionError. That is a loud crash in a lane analysis script, not
a wrong answer: nothing silently gets the period wrong, and the headline
figure (33.11 / 0.636 = 52.08 ns, 19.2 MHz) comes from a full-run fit
with many bins. No job or gate imports the script. **Follow-up:** require
`n >= 3` bins and add a synthetic self-test with a known period, in whichever
lane first reruns the fit (for example, the Thor check).

### L4: the 19.2 MHz correction has no issue of its own: stands, board action

The correction is still in lane NOTES §15 and comments on #474, #462, #425
and #414. On 2026-09-27 an issue search for `timestampPeriod`,
`gpu_ts_period_ns` and `19.2 MHz` found no dedicated issue. This is not a
code defect in the diff, and a lane may not file tracker rows. **Recommend:**
the board files a "calibrate `gpu_ts_period_ns` in `renderer.c` on the Nova"
issue. Until then, every Nova `hakuX-phase` GPU/R/X figure reads 0.636 of
the true value.
