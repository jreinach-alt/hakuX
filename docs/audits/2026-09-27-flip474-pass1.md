# Audit pass 1 -- PR #475 lane.flip474 (#474, pgraph.lock released across the deferred-download fence wait)

Head audited: `628c96a51f` (`lane/flip474`), diffed against its merge base
with master, `6e4dee6a28`. The C diff comes from four commits: `523612b5de`
and `7f13054916` (the `[lock474]` counter), `16b7e14ec9` (settle-aware lock
takers, inert) and `ef66174066` (the release). It covers `pgraph.c`,
`pgraph.h` and `vk/surface.c`. I also read NOTES §1-§8, the four prediction
files and `lockread.py`. `nv2a_index.json` is generated, and its rebuild is
checked by preflight and CI, so it was not reviewed line by line.

**Verdict: no HIGH, no MEDIUM, four LOW. The PR goes to `needs-audit-2`.**
Each LOW needs a logged decision: fix it, or say why not.

## What was checked and holds

- **Lock order and deadlock.** The release happens only on the PFIFO thread,
  inside `pgraph_method` (or the diag flip path, `pfifo.c:1798`). Every such
  caller holds `pgraph.lock` and not `pfifo.lock`: both puller variants
  (`pfifo.c:1356`, `:1427`) drop `pfifo.lock` before the method runs.
  - The exempt `pgraph_write` cases (INTR, INCREMENT) take `pfifo.lock` and
    then `pgraph.lock`, which is the documented order. Neither can wait on
    the fence-waiting thread.
  - `pfifo_kick` takes no lock.
  - The retake takes only `pgraph.lock`.
  - No new lock edge exists.
- **Settled waiters.**
  - The flag is read and written only under `pg->lock`.
  - The retake clears it and broadcasts under the lock.
  - Waiters loop on the flag, so a wakeup cannot be lost and a spurious one
    is harmless.
  - A waiter that holds the BQL, `pfifo.lock` or the exclusive section
    (`surface_watch_rearmed`) blocks exactly where it blocked on the mutex
    before. The PFIFO thread needs none of those during
    `vkWaitForFences`.
  - After the broadcast the waiter competes for the mutex as before, so the
    existing unlock-to-take-the-BQL dances (NO_OPERATION, context switch) are
    unaffected.
- **Other `pgraph.lock` takers left unconverted.** None can run in the
  window:
  - `pfifo.c`'s takers and the renderer switch are the PFIFO thread itself.
  - `nv2a_lock_fifo` runs only after `fifo_idle_cond`.
  - The GL and null renderers never release.
  - The lockless fast dispatch (`pgraph_method_try_fast`) is the PFIFO
    thread and never reaches `surface_update`.
- **What the exempt accesses can change.** The only writes that can land in
  the window are `pending_interrupts`, `enabled_interrupts`,
  `waiting_for_nop`, `waiting_for_context_switch` and `NV_PGRAPH_SURFACE`
  READ_3D.
  - The fence-waiting method writes none of these after its wait.
  - Flip completion is state-based (`pfifo_stall_for_flip` re-reads
    READ_3D/WRITE_3D), so an INCREMENT that lands before FLIP_STALL sets
    `waiting_for_flip` loses no flip.
  - `FLIP_INCREMENT_WRITE`'s WRITE_3D RMW after the retake and the guest's
    READ_3D RMW in the window are serialised by the lock, and they commute.
- **VRAM.** `surface_access_callback` settles, so a trapped guest write cannot
  land before the staged copy into VRAM.
  - Unwatched VRAM writes during the fence wait were already possible before
    this PR, whenever the vCPU was not blocked in `pgraph_read`. That race is
    not introduced here. The PR only makes the vCPU less often blocked.
- **Scope of the release.** `qemu_thread_is_self(&d->pfifo.thread)` limits
  the release to the PFIFO thread. The public
  `pgraph_vk_download_surface_complete_deferred` keeps the locked wait, and
  so does the third branch (`pgraph_vk_finish(SURFACE_DOWN)`).
- **Builds.**
  - In non-perf builds, `pgraph_mmio_lock` reduces to the plain or settled
    lock.
  - `LOCK474` keeps `t0`/`t1` referenced, so there are no unused-variable
    warnings.
  - `nv2a_clock_ns` is defined in every build.
  - `pgraph_init` and `pgraph_destroy` pair the cond.
  - CI is green on the head.

## LOW-1: two comments name the wrong register as the one DOA waited on

`pgraph.c:1075-1082` says "the ISR's INTR, NSOURCE and TRAPPED_* reads are
what DOA Ultimate's vCPU waited ~50 ms a frame for". `vk/surface.c:933-934`
says "The guest's interrupt handler reads PGRAPH_INTR in that window and its
vCPU blocked ~50 ms a frame on the lock".

NOTES §8 measured something else. `0x0b10 PATT_COLOR0` carried 0.55 and 0.65
of arm A's read wait, at about one read per frame, and it is not an
interrupt-service register. The pilot's INTR share was 0.36.

**Failure scenario.** None at run time. A reader deciding whether the read
exemption can be narrowed to "interrupt registers only" would take these
comments at their word. That narrowing would put PATT_COLOR0 back behind the
fence and undo the result. This is a premise corrected in NOTES but not where
it is read.

**Remedy.** Name PATT_COLOR0 (and the ISR reads as the minority) in both
comments.

## LOW-2: `pgraph_lock_release_for_fence` assumes the caller holds the lock, and nothing checks it

`pgraph.h:422`, reached from `vk/surface.c:4674`. The release is gated on
"this is the PFIFO thread", not on "this thread holds `pgraph.lock`". Today the
two are the same: every PFIFO-thread caller of `surface_update` is a method
or the diag flip path, and all of them hold the lock (checked above).

**Failure scenario.** Not reachable today. Suppose a future PFIFO-thread path
reaches `pgraph_vk_surface_update` without the lock: a fast-table entry that
does more than write registers, or a process-pending path moved off the
render thread. The release would then unlock a mutex the thread does not
own, which is undefined behaviour for a default pthread mutex. The retake
would then leave the lock held when the caller returns, which is a hang.

This is the same unguarded assumption `pgraph_context_switch` and
NO_OPERATION already make when they drop the lock mid-method. That is why it
is LOW and not MEDIUM: the PR adds a third instance of an existing pattern,
not a new class of risk.

**Remedy (optional).** Add `assert(!pg->lock_released_for_fence)` at release.
That catches the nesting case but not "lock not held". A cheap owner check
could be a PFIFO-thread-only `bool pfifo_holds_lock` set and cleared around
`pgraph_method`. Alternatively, record in NOTES why no guard is added.

## LOW-3: `lock474_log` accumulates `snprintf`'s return into `len` unchecked

`pgraph.c:1013-1019`. `len += snprintf(regs + len, sizeof(regs) - len, ...)`
adds the would-be length. If the output were ever truncated, `len` would pass
`sizeof(regs)`. The next `sizeof(regs) - len` would then wrap to a huge
`size_t`, and the next write would land past the stack buffer.

**Failure scenario.** Not reachable with the current fields. The six entries
peak at about 31 characters each (a PGRAPH offset of at most 4 hex digits, a
`%u` count, a millisecond wait), about 186 bytes against a 256-byte buffer.
The wait could exceed 9 digits only if a window lasted about 11 days.
Perf-only builds.

**Remedy.** Break when `len >= sizeof(regs)`, or clamp. Or record that the
widths bound it.

## LOW-4: the read exemption is "every register but two", not a named set

`pgraph.c:1083-1084`. NOTES §1 and "Do not repeat" say not to make PGRAPH
reads lockless without knowing which register is polled, because STATUS is
not the only register a guest could use to infer progress. The fix exempts
every register except RDI_DATA and 0x700.

A read in the window returns the register as the method left it before its
wait. The methods that call `surface_update` write registers on one side of
it only:

- `SET_CONTROL0` (`pgraph.c:2873`) calls `surface_update` first, then writes
  CONTROL_0 and SETUPRASTER. A window read of those registers returns the
  pre-method value.
- The diag branch of FLIP_INCREMENT_WRITE updates WRITE_3D before its
  `surface_update`. A window read returns the post-method value.

In both cases a read linearises cleanly before or after the method, and
neither register is one a guest polls for progress. NOTES §5 argues it
differently ("the puller writes none of them while it waits"). That is true
but weaker: it does not cover a method that writes on both sides of the wait.

**Failure scenario.** None found. This is an opinion about robustness.
Suppose a future method writes a register before `surface_update` and a
related one after it. A read in the window would then show a state that is
neither before nor after the method. That matters only if a guest reads the
pair as a unit. Record the invariant next to the exemption: "a method writes
PGRAPH registers on one side of `surface_update` only". Then a change that
breaks it can see it.

## Outside the diff (not a finding against this PR)

- `SET_FLIP_READ/WRITE/MODULO` (0x120-0x128) are fast-table entries
  (`pgraph.c:567-571`). The PFIFO thread applies them lockless as an RMW of
  `NV_PGRAPH_SURFACE`. The vCPU's INCREMENT RMWs the same word under the lock,
  so the two can race.
- That race predates this PR. The window does not widen it, because the
  PFIFO thread is parked in the fence wait.
