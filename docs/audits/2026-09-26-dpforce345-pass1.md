## What was checked

- **Finite dots don't change.** `_DotZeroForced` returns `d` unchanged unless `isnan(d)`. In IEEE
  arithmetic, a zero factor changes a sum only through a 0 x inf or 0 x NaN term, and any such
  term makes the plain `dot()` NaN. So every non-NaN dot keeps the bits it had before. Lit paths
  and rounding paths run the old code.
- **The NaN path applies the silicon rule.** `_MUL` zeroes a component when
  `sign(NaNToOne(a)) * sign(NaNToOne(b)) == 0`, so 0 x inf -> 0 and 0 x NaN -> 0. A NaN or inf
  times a non-zero value stays NaN or inf. `_MUL` runs `_PosNaN` on its result, and so do the DP
  wrappers. `dp_model.py` reproduces all 5 silicon DP rows (5/5).
- **DP3 padding.** The w lane is `0 x 0 = +0`, and adding +0 to the sum is harmless. On the NaN
  path every zero product comes out +0 (from `_MUL`'s forced write), and that matches silicon row
  `(-0,0,0).(5,5,5) = +0`.
- **DPH.** Its implicit w term is `1 x b.w`. `sign(1) != 0`, so the term is never forced, and a
  NaN in `b.w` still gives NaN. The model row `(1,0,0).(1,1,1,NaN) = NaN` agrees.
- **Definition order.** `_DotZeroForced` comes after `_MUL`, and `NaNToOne` is defined in
  `vsh.c` ahead of the prelude. CI built both targets (`build` x2 SUCCESS, `check` SUCCESS). Both
  arms rendered, which rules out a compile failure on the device.
- **Sibling sites.** Grepping `dot(` in `glsl/` finds no other vertex-program DP emitter. The
  psh/geom/vsh-ff `dot()` calls are fixed-function or pixel-side and belong to different rules.
  The nv2a_vsh_cpu evaluator is out of scope: it is #345 half 2, and the PR body says so.
- **Arm evidence.** The arm-2 verdict reads `PASS -- all 291 registered checks hold`. Before
  unguarding the 9 GeometrySuperscreen captures, I checked `superscreen_hashes_arm2.txt`:
  - the master base apk `cb97387981` is off the modal image on 4 of 9 in arm 1 and 5 of 9 in
    arm 2, and the two arms disagree on which captures;
  - the vshnobegin242 base arms drift the same way.

  This nondeterminism predates the hunk, so unguarding those captures is justified by data
  without the hunk rather than being a post-hoc fit. The other rounding captures stay guarded.

## Findings

### LOW 1: the fallback re-associates a NaN dot that has no zero factor
The fallback runs on every NaN `dot()`, not only one caused by a zero factor. It re-sums the
products in the order `x+y+z+w`, while the driver's `dot()` order is implementation-defined (it
may be an fma chain or a tree).

- **Scenario:** DP3 products `(3e38, 3e38, -inf)` with no zero factor. A driver `dot()` that adds
  x+y first gets `inf + -inf = NaN`. The fallback uses the same order and also gets NaN. A driver
  that adds y+z first gets `3e38 + -inf = -inf`, then `-inf + 3e38 = -inf`, so it never sees NaN
  and the fallback never runs.
- **Where results can move:** a NaN caused by order-dependent overflow can have a
  different value after the fallback's re-sum, but only on drivers whose `dot()` order differs
  from the fallback's.
- **Blast radius:** only dots that overflow to opposite infinities. No golden exercises this,
  silicon's value for it is unmeasured, and the result was already NaN or ±inf before the change.
  Recorded, not asked to fix. Gating the fallback on "some term is 0 x non-finite" would
  close it, at the cost of a wider helper.

### LOW 2: the comment's claim assumes IEEE inf/NaN
The comment says a 0 x inf/NaN term "always makes dot() NaN". GLSL ES does not require inf or NaN
to be produced or preserved. A driver that flushes or folds `isnan` to false simply runs the old
path, so it cannot regress. `_PosNaN` and `_MUL` make the same assumption, so this is a
documentation nit only.
