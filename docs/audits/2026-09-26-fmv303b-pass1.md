## What was checked

1. **The hunk** (`android/app/src/main/cpp/xemu_android.cpp:975-976`). `HAKUX_TIER1_THRESHOLD`, when it is set and not
   empty, overrides the `tier1_threshold` pref. This happens before `xemu_set_tier1_threshold()` and before the
   `tier1 threshold: %d` log line, so the log shows the value that was applied. When the variable is unset or empty,
   behaviour is unchanged, which makes the hunk default-inert. The only other writer is
   `SettingsActivity.nativeSetTier1Threshold`. It fires only when a user edits the setting, which a soak never does.
   `xemu_set_tier1_threshold(0)` sets the threshold to `0x7FFFFFFF` (`accel/tcg/cpu-exec.c:74-77`), which disables
   promotion.
2. **Tier1 was really off in the OFF arm**, and not just requested off. The judge's M0 reads the requested value. The
   audit counted `hakuX-tier1` promote/dedup lines in each arm's logcat:
   - ON `…2431986`: 29
   - ON `…2432336`: present (from `promote #0` on)
   - OFF `…2432129`: 0
   - OFF `…2432888`: 0

   So the independent variable took effect on the device.
3. **The verdict reproduces.** `sh docs/lanes/fmv303b/judge_arms.sh` on the host gives per-run means 0.70 / 0.68 (ON)
   and 0.68 / 0.68 (OFF), pooled ON 0.6881 and OFF 0.6804, all four runs OK, and `VERDICT NOT_TIER1`. This matches
   the PR table. P2 holds: the ON mean 0.688 is inside [0.3, 0.8].
4. **The prediction cannot jam the arms job.** It has `a_ref == b_ref`, and `arms.sh:792` skips that case as
   structural. Once folded, the arms job will not queue or judge it, and the `expect_note` says the prediction is
   hand-read. The prediction was committed in `dcb65090c2` at 14:32:17Z. The first arm's request id `1790433154`
works out to 14:32:34Z, so the prediction was registered before any arm was queued.
5. The lane edited no board files. `surface.c` was not touched: the step-2a hunk is a board request
   (`board_request_surface.md`). The notes are per-lane (`docs/lanes/fmv303b/`).

## Findings

**LOW-1: M0 gates on the requested threshold, not on the effective state.**
`tier1_judge.py:44` accepts a run if its `tier1 threshold:` line matches the arm. The logcat also carries direct
evidence: `D/hakuX-tier1 … promote #N` lines, which are present in ON runs and absent in OFF runs.
- Failure scenario: a later change re-enables promotion under threshold 0. One way is the pre-existing signed
  overflow in `(uint32_t)g_tier1_threshold * 2` at `cpu-exec.c:1798`, which is not in this diff. The judge would
  still pass M0 on OFF runs, and an OFF arm that really ran tier1 would read as NOT_TIER1.
- This did not happen here (item 2). Suggest a leg of the form "OFF promote lines == 0 and ON > 0".

**LOW-2: a non-numeric value silently disables tier1.**
`atoi("abc")` is 0, and `xemu_set_tier1_threshold(0)` means disabled.
- Failure scenario: someone sets `HAKUX_TIER1_THRESHOLD=default` intending "leave it alone" and gets tier1 off.
- The blast radius is bounded: the variable only comes from test env, and the log line shows 0. `strtol` with an
  end-pointer check would reject such values.

**LOW-3: `judge_arms.sh` hardcodes host paths and request ids.**
It hardcodes `/home/justin/hakux-work/dispatch/results` and the four request ids. It is a lane-local record of how
the verdict was produced, so this is acceptable. It will not run anywhere else, and it is not a reusable tool.

**LOW-4: the NOT_TIER1 band is wide.**
`|OFF - ON| <= 0.2` against an ON mean near 0.69 allows a partial tier1 effect of up to about 29% relative to be
called NOT_TIER1.
- Failure scenario: tier1 accounts for part of the tint (ON 0.69, OFF 0.50), and the verdict still reads NOT_TIER1
  instead of flagging a partial effect.
- The observed gap is 0.008, so this verdict does not depend on where the band is drawn. It matters only if the judge
  is reused.
