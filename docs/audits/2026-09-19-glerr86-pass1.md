## What I checked and found correct, so remediation does not re-derive it

* **The drain is preserved exactly.** `android_report_pending_gl_errors`
  (`shaders.c:137`) loops `while ((err = glGetError()) != GL_NO_ERROR)` and
  leaves on `GL_NO_ERROR`, so the context is as empty on exit as the old
  `while (glGetError() != GL_NO_ERROR) {}` left it. That matters for the
  reason the PR gives: `glGetError` eleven lines below at the
  `glProgramBinary()` check cannot distinguish a stale error from its own, so
  a surviving backlog would be charged to the binary. The selftest asserts it
  directly (`the backlog is fully drained`) rather than leaving it to the
  inertness leg — correct, and the prediction says so in its own text.
* **The non-Android path is byte-identical.** The `#else assert(glGetError()
  == GL_NO_ERROR);` arm is untouched, and all three new functions are inside
  the pre-existing `#ifdef __ANDROID__` region that closes at `:179`. Desktop
  CI is green.
* **`is_power_of_ten` is right**, including the two cases that usually get it
  wrong: `0` returns false (the loop does not run and `0 == 1` is false), and
  `10^k` for k up to 18 returns true. Checked at 0, 1, 2, 10, 99999999999,
  1000000.
* **No new thread hazard.** `android_report_pending_gl_errors` holds static
  mutable state where the old code held none, but its only caller
  (`shaders.c:1003`) runs under `qemu_mutex_lock(&r->shader_cache_lock)`
  (`:995`), so the table is not raced.
* **The `#ifdef` guards around `GL_STACK_OVERFLOW`, `GL_STACK_UNDERFLOW` and
  `GL_CONTEXT_LOST` are necessary and sufficient.** The five unguarded codes
  are defined by every GLES3 and desktop header set; the three guarded ones
  have distinct values (0x503, 0x504, 0x507) from the rest, so no header set
  can produce a duplicate `case`.
* **Every symbol the block needs is already in scope.** `<android/log.h>` at
  `:32-34`, `ARRAY_SIZE` from `qemu/osdep.h` (already used at `:270`),
  `binding->node.hash` is `uint64_t` (`include/qemu/lru.h:38`) and is cast for
  the `%llu`/`%llx` conversions. `binding` at the call site comes from
  `container_of(node, ShaderBinding, node)` and cannot be NULL.
* **The selftest does what it claims.** I ran
  `docs/testing/glerr_report_selftest.sh` on this tree: exit 0, `desktop`
  18/18, `gles` 18/18, and the `silent` falsification build fails 10 legs by

* **The arm ran and passed.** `[job.arms] VERDICT: PASS`, 568 checks, 566
  captures, `better 0 worse 0 same 566`, and **every checked capture

* **No drift against current master.** `shaders.c` is unmodified on

## M1 — MEDIUM. The shared last slot of `seen[]` does not aggregate, it resets, so the one case the suppression was built for is the one case that floods

`shaders.c:139-143` states the design:

> the scan stops at a match, at the first unused slot, or at the last slot,
> which is shared. Only a vendor code beyond the eight GL defines can reach
> the shared slot, and **aggregating those costs a suppression nobody will
> miss.**

The code does not aggregate. The scan at `:155` runs `i` over `0 ..
ARRAY_SIZE(seen) - 2`, i.e. slots 0–6 only, so a miss leaves `i == 7`. Then
`:160-163`:

```c
if (seen[i].err != err) {
    seen[i].err = err;
    seen[i].count = 0;
}
count = ++seen[i].count;
```

Two distinct enums alternating in slot 7 each find the other's code there,
**reset the count to 0**, and print with `occurrence=1` — every time, forever.
The shared slot does not cost a suppression; it removes suppression entirely
for whatever lands in it.

I confirmed this rather than reasoning about it. Compiling the live sliced
block against the selftest's stubs and driving it:

```
after seven distinct enums: lines=7 (expect 7)
200 alternating loads into the shared slot: lines=200
last line: [glerr] GL_ERROR_UNRECOGNISED (0x8000) was already pending on entry
           to pgraph_gl_shader_load_from_memory shader=1 occurrence=1
100 loads of ONE enum resident in the shared slot: lines=3
```

200 loads, 200 lines, every one of them `occurrence=1`. A single enum resident
alone in slot 7 behaves correctly (3 lines for 100 loads), so the defect is
specifically the alternation.

**Failure scenario.** A device run in which eight or more distinct GL error
enums occur across the process lifetime — the full desktop-GL set is exactly
eight, and a GLES driver reaching six standard codes plus two vendor codes is
the same arithmetic. Slots 0–6 fill with the first seven; the eighth and any
further code then alternate through slot 7, and every shader load that drains
one emits a line. That is the logcat flood the power-of-ten rule exists to
prevent, arriving precisely in the badly-broken-renderer case where a readable
log matters most, and reporting `occurrence=1` for each so the log also
understates the count.

**Remediation.** Either make the shared slot genuinely aggregate (scan `0 ..
ARRAY_SIZE(seen) - 1`, and on a miss at the last slot keep counting under a
sentinel rather than re-keying), or size `seen[]` so no slot is shared and
drop the sentence at `:141-143`. Whichever is chosen, the comment and the code
must agree, and the selftest must exercise it — see L1.

## M2 — MEDIUM. Both factual premises the suppression is sized from are false, and one of them is false 400 lines up in this same file

The docstring at `:116-135` and the PR body rest on two claims. Neither holds.

**(a) "The Android arm drained the same backlog in silence, which left the
shipping renderer with no error-reporting path at all"** (`:123-124`; the PR
body says "the shipping GL renderer had no way to report a GL error at all").

`shaders.c` already contains three ungated Android GL-error reporters, added
before this PR:

| helper | defined | called | gate |
|---|---|---|---|
| `android_log_shader_stage_errors` | `:49` | `:1025`, `:1037` | `#ifdef __ANDROID__` only |
| `android_log_apply_uniform_entry_errors` | `:59` | `:901` | `#ifdef __ANDROID__` only |
| `android_log_uniform_update_errors` | `:70` | `:944` | `#ifdef __ANDROID__` only |

None is behind `DEBUG_NV2A_GL`. All three print `GL error 0x%X …` to logcat
under the same `"hakuX"` tag, **one line per error, with no suppression at
all**, and `:944` fires per uniform per apply. `NOTES.md:127` describes
these as "existing (debug-logging-gated)"; for the `shaders.c` ones that is
wrong.

**(b) "A shader load happens many times a frame"** (`:131`), the sole
justification for the power-of-ten machinery.

`pgraph_gl_shader_load_from_memory` has exactly one caller, `shaders.c:1003`,
and it is guarded: `if (!binding->initialized && !pgraph_gl_shader_load_from_memory(binding))`.
`initialized` is cleared only in `shader_cache_entry_init` (`:700`), i.e. when
an LRU node is freshly claimed, against a cache of `50*1024` = 51 200 entries
(`:746-752`). The function therefore runs **once per distinct shader state per
run**, on a cache miss — hundreds of times over a whole run, front-loaded into
the first seconds, not many times a frame. A line per load per error could not
produce the thousands `NOTES.md:122` guards against.

**Failure scenario.** The suppression built on (b) discards exactly what the
feature exists to publish. An error found pending at between 2 and 9 shader
loads prints one line, reporting `occurrence=1` and the **first** load's
shader hash; the other loads and their hashes never appear. At the real call
frequency most counts live in 1..9, so in the common case the counter is
printed once and never updated, and a recurring pending error is
indistinguishable in the log from a single one. The docstring itself says the
hash is the point of the line ("the shader hash names where it was *found*",
`NOTES.md:125-126`), and the suppression is what removes it.

(a) compounds this and narrows the window further. `update_shader_uniforms` runs
on **every** `pgraph_gl_bind_shaders` (`:1039`, reached by both the
`goto update_uniforms` fast path and the full path) and calls
`apply_uniform_updates` twice (`:962`, `:974`), each of which begins by
draining and printing the whole backlog at `:901`. So when a later,
cache-missing bind reaches `:1003`, the backlog is at most one draw deep — the
new report can only ever see errors raised since the previous bind's uniform
updates, not "whatever ran before the load" as `:119-120` says. The report is
not inert, but it is much narrower than advertised, and the guidance in
`NOTES.md` ("An empty grep … says no GL error was pending at any shader load
in the run") is read by the next lane as a statement about the run when it is
a statement about that narrow window. An error raised and reported by `:901`
leaves no `[glerr]` line at all.

**Remediation.** Correct both claims in the docstring, `NOTES.md` and the PR
body: say that Android already reports GL errors ungated at `:901`/`:944`/
`:1025`/`:1037`, and that this change adds a report at the one Android site
that was silent. Then re-decide the suppression on the true frequency — at
one call per cache miss, printing every occurrence is affordable and keeps the
per-load shader hash, which is the diagnostic. If suppression is kept anyway,
say what it is protecting against, since it is not the frame rate. `NOTES.md`
should also drop "(debug-logging-gated)" for the `shaders.c` helpers and state
that an empty `[glerr]` grep does not mean the run was GL-error-free — the
`GL error 0x%X before apply_uniform_updates:` lines are where an earlier error
will have been reported.

## M3 — MEDIUM. `NOTES.md` is added at the branch root, which `origin/master` forbids by name

`origin/master:docs/testing/jobs/roles/lane.md:48-53` requires
`docs/lanes/<lane name>/NOTES.md` and says **"Not the branch root"**, with the
reason. `origin/master:docs/lanes/notespath/NOTES.md` is the record of the
lane that made that change: "the first lane to fold landed one on master,
after which every fold conflicted on that exact path." Master carries
seventeen `docs/lanes/<name>/` directories today and **no root `NOTES.md`**.

This worktree is 150 commits behind and its local `roles/lane.md` still says
"branch root", so the lane followed the rule it was given. The consequence is
a property of the fold, not of the intent.

**Failure scenario.** `fold.sh`'s `resolve_root_notes` fires only when root
`NOTES.md` is an *unmerged* path. Master has none, so folding #128 is a clean
add and the guard never runs: `lane.glerr86`'s notes land at the repository
root permanently. The next lane still carrying a root `NOTES.md` then
conflicts, `resolve_root_notes` fires, moves the *newcomer's* copy to
`docs/lanes/<lane>/` and keeps **master's** — glerr86's — at the root. That is
the steady state the `notespath` lane was opened to remove, reseeded by this
PR and thereafter permanent, with one lane's record occupying a
repository-root path and this lane's notes absent from the set where every
other lane's are readable.

**Remediation.** `git mv NOTES.md docs/lanes/glerr86/NOTES.md` and update the
PR body's `Files:` line. One commit, no content change. Cheapest of the three.

## L1 — LOW. The selftest never reaches the stateful part of the code it tests

`seen[]` is the only state in the change, and its capacity behaviour is the
only way the block can misbehave (M1). `glerr_report_selftest.c` uses five
distinct enums across its whole run — `GL_INVALID_OPERATION`,
`GL_OUT_OF_MEMORY`, `GL_INVALID_VALUE`, `GL_INVALID_ENUM`, `0x8000` — so slots
5, 6 and the shared slot 7 are never touched in either build. Eighteen legs
pass, and none of them could have caught M1.

Separately, and correctly flagged by the lane itself: the two suppression legs
pass vacuously against the silent build. The harness says so where they are
written, which is the right handling; I note it only so pass 2 does not count
sixteen discriminating legs as eighteen.

**Remediation.** Add a leg that drives eight or more distinct enums and
asserts the total line count for a repeated pair, alongside whichever fix M1
takes. It is the same probe shape I used above.

## L2 — LOW. The record understates its own strongest evidence: the Android arm *was* built by the shipping toolchain, by this repository's CI, on this head

The PR body's "What is not proved" says "This lane has no NDK, no device and
no arm64 build", `NOTES.md:55-58` repeats it, and the header line reads
`Needs NDK: no to review, yes to build the arm`. True of the worktree, and not
true of the PR.

`.github/workflows/android.yml` runs on every `pull_request`, installs
`ndk;29.0.14206865`, and runs `./gradlew assembleDebug`, which drives
`android/app/src/main/cpp/CMakeLists.txt` through `externalNativeBuild`
(`android/app/build.gradle.kts:119-122`). That CMake build compiles
`XEMU_CORE_SOURCES` into `xemu_core`, which includes
`hw/xbox/nv2a/pgraph/gl/shaders.c` with `__ANDROID__` defined against the real
GLES header set. The Android check on this head completed **SUCCESS** at
2026-09-19T06:27:32Z.

So the check the lane names as missing — "If the dispatcher builds arm B for
Android, that build is the missing check and is worth more than the pixel
comparison" — has already been performed, by CI, and it discharges the
`<android/log.h>` / `ARRAY_SIZE` / GLES-header questions the selftest could
only approximate. Not a defect; the opposite. But left as written, the next
lane inherits a "we have no NDK" caveat that the repository stopped being
subject to.

**Remediation.** Replace the caveat with what is actually unproven: the block
compiles and links for arm64 under the shipping NDK (CI, this head), and what
remains unverified is only that a `[glerr]` line reaches logcat on a device
and that the report fires on a real pending error.

## Disposition

Three MEDIUM findings, no HIGH. Under `roles/cloud.md` this goes to
**`needs-remediation`**. M3 is a `git mv`; M1 is a scan bound and a comment;
M2 is prose plus one design decision to re-take now that the call frequency is
known. Pass 2 should check that the scenarios above can no longer occur — in
particular that the eight-distinct-enum probe in L1 exists and passes, not
merely that a commit touching `seen[]` exists.
