# Audit pass 1: PR #440, lane.doa413b (#413)

Head audited: `b3d58d997e`. Diff read: `origin/master...lane/doa413b` (8 files, +696/-1).

This replaces the pass-1 audit of `6acb0048db`. That head carried the lazy-completion path
behind `XEMU_SURF_LAZY_COMPLETE`. The lane has since removed it (14ed3ff573), so the earlier
findings L1 (the dormant path's CPU-write claim) and L2 (the superseded `doa413b-lazy-mnm`
prediction) no longer apply. Neither the lazy code nor either old prediction file is in the
diff now.

**Result: no HIGH, no MEDIUM, three LOW.** The only code that ships is the `[surf413]`
probe. Outside `NV2A_PERF_LOG && __ANDROID__` builds, it compiles to nothing.

## What was checked

- **Non-perflog builds.** `SURF413_T`, `_FIN`, `_ACC`, `_DO` and `SURF413_HASHED` all expand
  to `((void)0)`, and every use is a whole statement. `g_surf413`, `surf413_log` and the two
  resume counters live inside the `#if`. With the probe off, `pgraph_vk_surface_update` and
  `surface_watch_resume` compile to master's statements in master's order.
- **Perflog Android builds.** Each macro argument passed to `SURF413_DO` has no top-level
  comma, so none is split. The probe only reads `nv2a_clock_ns()` and
  `g_nv2a_stats.phase_working.finish_ns`, and it only writes its own statics. The two
  `upload_pending` reads come before `pgraph_vk_upload_surface_data`, which is where that
  flag is cleared, so `realupl` counts the real uploads. `pgraph_vk_surface_update` has no
  early return, so every call accumulates and reaches `surf413_log`. `surf413_log` returns
  until 60 guest frames have passed, then resets everything, `frame0` included.
- **Probe's claim about `Surf`.** `NV2A_PHASE_TIMER_END_EXCL` (debug.h:486) subtracts the
  `finish_ns` nested since BEGIN. So "sum(segments) - fin is what `Surf` reports" holds, up
  to the few clock reads that fall outside the segments.
- **`surface_watch_resume` counters.** Both callers (surface.c:2042, :3158) hold
  `surface_watch_lock`, so the two counters are not written concurrently with each other.
  `surf413_log` resets them without the lock. The worst case is one lost count in a 60-frame
  window, and this happens only in perflog builds.
- **`dispatcher.sh`.** The change adds `xemu-surf:I` to the default `LOGCAT_SPEC`. It adds
  log volume and nothing else. The PR body states correctly that it goes live only at the
  host's dispatcher update window.
- **Prediction `doa413b-instr-mnm.json`.** It names e5db66fa37 as A (master) and 14ed3ff573
  as B, and B is the probe-only commit. `expect` is empty and `must_not_move` is populated,
  so the file is a real must-not-move guard. The file leaves one row unguarded,
  `Blend_surface/R5G6B5_Add_SrcA_DstA`, and gives the reason (byte-identical to two
  unrelated base legs).

## Findings

### L1 (LOW): host-absolute paths in committed lane tools

`register_instr.py` `BASE`, `cc_surface.py` `SHARED`, and the prediction's `disc.source`
hard-code `/home/justin/...`. **Scenario:** the two scripts fail on any host other than this
one. CI and the arms job never run them, and `disc.source` is provenance only. No action is
needed for this PR.

### L2 (LOW): the new block splits `surface_watch_resume`'s doc comment from its function

The `SURF413_HASHED` block (surface.c:1998-2004) sits between the comment "If the watch is
suspended, re-arm it ..." and `static void surface_watch_resume`. **Scenario:** someone
reading the file takes that comment as documentation for the macro block. **Fix:** move the
block above the comment.

### L3 (LOW, pre-existing, outside the diff): display pre-download flags can stick on master

Carried forward from the previous pass 1, and still true on master. When the draw.c frame
ring completes a display pre-download batch through `pgraph_vk_complete_staged_downloads`,
`display_predownload_pending` stays set. The next `complete_deferred` sees
`num_deferred_downloads == 0` and returns before it clears the flag. **Scenario:** from then
on, the pre-download optimisation stays off for the rest of the run. This costs performance
only, and it belongs to the next #413 lane, which will be working in `complete_deferred`.

## Verdict

LOW only, so the PR moves to `needs-audit-2`. Pass 2 should check L2. L1 and L3 need no
action for this PR. The `[job.arms]` verdict on `doa413b-instr-mnm.json` and CI on
`b3d58d997e` are still pending, and the fold gates on them, not this audit.
