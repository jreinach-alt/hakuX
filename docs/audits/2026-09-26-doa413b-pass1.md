# Audit pass 1: PR #440, lane.doa413b (#413)

Head audited: `6acb0048db`. Diff read: `origin/master...lane/doa413b` (8 files, +745/-3).

**Result: no HIGH, no MEDIUM, four LOW.** The code that ships does nothing unless an
environment variable turns it on. With the flag off, each changed control path does
exactly what master does. The `[job.arms]` PASS on `doa413b-defoff-mnm.json` (205 of 205,
a593d8eb85 vs 6cd9507d07) confirms this on the device.

## What was checked

With `XEMU_SURF_LAZY_COMPLETE` unset (`surf_lazy_complete()` false), every changed site:

| site | flag off |
|---|---|
| `complete_submitted_downloads()` (called from `download_surface_record_deferred`, `pgraph_vk_prerecord_display_download`, `pgraph_vk_upload_surface_data`) | returns at once; the `&&` short-circuits before `deferred_downloads_submitted` |
| `pgraph_vk_download_surface_complete_deferred`, `num_deferred_downloads == 0` | returns early, as on master |
| same function, tail | takes the `else if (r->display_predownload_pending)` branch, byte-for-byte master's block |
| `pgraph_vk_prerecord_display_download` | the new `if (surf_lazy_complete())` is skipped |
| `pgraph_vk_surface_update` completion | `upload && surf_lazy_complete() && ...` is false, so it calls `pgraph_vk_download_surface_complete_deferred(d)` unconditionally, as before |
| `[lazy413]` line in `surface_watch_log_periodic` | one more log line on the existing 5 s gate; reads two statics |

The `[surf413]` probe compiles only under `NV2A_PERF_LOG && __ANDROID__`. In other builds,
`SURF413_T`/`_FIN`/`_ACC`/`_DO` expand to `((void)0)` statements, and `SURF413_HASHED` does
the same. In perflog builds the probe reads clocks and counters and writes nothing the
renderer reads. `pg->frame_time` is reset only in `pgraph_init`, so `frames` in
`surf413_log` cannot go negative within a run.

`dispatcher.sh` adds `xemu-surf:I` to the default `LOGCAT_SPEC`. This adds log volume only.
The PR body states correctly that the change goes live only at the host's dispatcher update
window.

## Findings

### L1 (LOW): the dormant lazy path's claim about CPU writes is unverified

`surface.c`'s comment above `surf_lazy_complete` lists "a guest CPU access" among the
readers that complete a pending batch first. A CPU access is trapped only while the
surface's access callback is armed, and `surface_watch_suspended` (#382) disarms it. With
the flag on, a guest CPU write to a suspended surface between the flip and the lazy
completion would be overwritten by the batch's staging `memcpy`. The window with the flag
off is the same shape but shorter. This pass did not confirm that the scenario is
reachable, and the flag-on arm (`doa413b-lazy-mnm`) did not move `Texture_CPU_Update/*`.
**Scenario:** only with `XEMU_SURF_LAZY_COMPLETE=1`. No default build reaches it.
**Fix:** before anyone enables the flag, add a line to the comment or to NOTES.md naming
the suspended-watch case as open.

### L2 (LOW): a superseded, FAILed prediction stays registered

`docs/testing/predictions/doa413b-lazy-mnm.json` describes the lazy path as the default
(B = 7f01f7f157), and its arm FAILed 1 of 206. `doa413b-defoff-mnm.json` supersedes it,
but after the fold master would hold a registered prediction that describes behaviour
master does not have. **Scenario:** someone reading `predictions/` for #413 takes the
lazy-mnm file as the guard of record. **Fix:** delete the file, or add a `superseded_by`
note to it (if the prediction schema allows one).

### L3 (LOW): host-absolute paths in committed files

`doa413b-defoff-mnm.json` `disc.source`, `register_defoff.py` `BASE`, and `cc_surface.py`
`SHARED` hard-code `/home/justin/...`. The `disc.source` field is provenance, and the
scripts are lane tools. **Scenario:** both scripts fail anywhere other than this host.
Nothing in CI or the arms job runs them.

### L4 (LOW, pre-existing, outside the diff): display pre-download flags can stick on master

When the frame ring completes a display pre-download batch through
`pgraph_vk_complete_staged_downloads` (draw.c ring reuse), `display_predownload_pending`
stays set. The next `complete_deferred` then sees `num_deferred_downloads == 0` and
returns before it clears the flag, so `pgraph_vk_prerecord_display_download` returns
false from then on. The lane added `display_predownload_forget_if_drained` for this case,
but only under the flag. **Scenario:** the guest flips `NUM_SUBMIT_FRAMES` times with no
surface_update in between, and the pre-download optimisation turns off for the rest of the
run. This costs performance only. The lane did not introduce it; it is recorded here for
the next #413 lane.

## Verdict

LOW only, so the PR moves to `needs-audit-2`. Pass 2 should check L1 and L2 (a comment or
NOTES line for L1; the lazy-mnm file removed or marked superseded for L2). L3 and L4 need
no action for this PR.
