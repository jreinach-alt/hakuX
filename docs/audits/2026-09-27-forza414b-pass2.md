## M1: the per-draw diag dump overwrote the pending batch's staging

The pass-1 scenario needed a per-draw dump to write `BUFFER_STAGING_DST`
while `num_deferred_downloads > 0`. That can no longer happen:

- `diag_download_surface` (`renderer.c:580`) is the only diag writer of
  `BUFFER_STAGING_DST`. Its one use of the buffer is `renderer.c:604`. Its
  only caller is the per-draw dump at `renderer.c:1625`.
  `dump_surface_ppm` does not touch the staging buffer.
- The early returns (`renderer.c:584-587`, non-colour or swizzled surfaces)
  come before any copy. The new call to
  `pgraph_vk_download_surface_complete_deferred(d)` (`renderer.c:594`) comes
  before `begin_single_time_commands` and before the staging copy.
- That call reaches `download_surface_complete_deferred_at`
  (`surface.c:1194`). It returns only when `num_deferred_downloads == 0`.
  Otherwise it waits on the batch's fence, whichever slot recorded it: the
  pre-download's `display_predownload_frame_index`, a submitted batch's
  `deferred_downloads_frame`, or a finish for an unsubmitted one. It then
  runs `complete_staged_downloads`, so the batch is empty when control
  returns. The "earlier frame slot" condition that let the batch survive the
  caller's `pgraph_vk_finish` does not gate this path.
- Nothing records a download between that completion and the staging copy.
  The copy is a synchronous single-time command, so no batch can later write
  C's pixels into D's VRAM and retire D at the captured generation.

Scenario closed.
