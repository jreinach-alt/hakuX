## Findings

### LOW-1 — "the value a guest reads before it writes anything" overstates the measurement

`pmc.c` `pmc_reset()` comment, and the `case NV_PMC_ENABLE` read comment
("pmc_reset() gives the idle value silicon reads").

The idle word was read by `tools/nv2a_probe` launched from the dashboard.
"No write issued" means the **probe** issued none. The kernel and the
dashboard (a D3D title) had both run on that boot. So `0x01110000` is the
value **after the guest's boot path**, not a power-on value that nothing has
written. Under a pure-storage model the emulator matches silicon at that
point only if the emulated boot path leaves the same word, either by writing
nothing (then reset carries it) or by writing `0x01110000 & mask`. Before this
PR the constant matched there by construction; now the match depends on the
guest.

Failure scenario: the emulated kernel or dashboard writes the register during
boot (for example to bring up PFIFO/PGRAPH) and silicon's return to
`0x01110000` comes from something the model does not have, such as a
hardware-side reset on XBE launch or a non-storage bit. The emulated probe
would then read `X & 0x13111113 ≠ 0x01110000` in the one state that was
measured. I have no evidence that this happens: if silicon is storage and both
run the same guest writes, they agree. So this is LOW, and the fix is in the
wording. Say "the value read after boot with no write by the reading program",
and list "the emulated boot leaves 0x01110000" as an unverified premise beside
the 16/20/24 falsifier. A probe run under the emulator would settle it at no
risk the next time one is going anyway.

### LOW-2 — the always-sent subsection makes new savestates unloadable on older builds

`nv2a.c` `vmstate_nv2a_pmc_enable` has no `.needed`. A state saved by this
build carries `nv2a/pmc-enable` every time, and a pre-#188 build refuses an
unknown subsection. The QEMU convention is
`.needed = enable != 0x01110000`, which keeps states saved at the reset value
loadable backwards. Bounded: only a downgrade with a newer savestate is
affected, and nothing rides on it today.

### LOW-3 — the proof guards nothing after fold, and two historical suites now disagree

`pmc_enable_selftest.sh` is not run by CI, `preflight.sh` or the jobs
selftest. That was already true before this PR, but it means the 38 checks
and the 14 mutants protect nothing once this lands. The PR body says
`docs/lanes/pmc188/mutants.py` M1–M3 now disagree and
`docs/lanes/cloud190/mutants.py` cannot start. That is honest, and those are
historical records. The live suite for this register is the one in
`docs/testing/`. Wiring it into `check` would be the durable fix, and
belongs to a harness lane, not this one.
