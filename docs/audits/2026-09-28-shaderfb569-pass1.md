## Findings

### L1 (LOW): the display pipeline create is not wrapped, but the text says every create is

`display.c:622` still calls `vkCreateGraphicsPipelines` directly. The
`debug.h` comment ("Every graphics pipeline create counts, sync, worker and
clear"), the PR body and the pixels-inert prediction all say that every graphics
pipeline create goes through the wrapper.
**Failure scenario:** a display-pipeline create (display init or a mode change)
is left out of `pc_ms`/`dpn`/`dfb`. If that create lands in a scored window, dpc
understates that window by one create. This is bounded: the create is rare and
not in the fight load's miss path. Fix: wrap it with `draw=false`, or narrow the
claim to "every PGRAPH draw, clear and worker create".

### L2 (LOW): new counters are written from two threads, some without the lock

`glslang_us` and `shader_module_us` (`vk/glsl.c`) run "on the PFIFO thread or
the async worker" (the patch's own comment) and are written with no lock.
`instr_ns` is written under `pcfb_lock` in the wrapper but without it in
`nv2a_profile_shader_keydiff` (PFIFO thread). The `[shd413]` reader copies the
whole struct without the lock.
**Failure scenario:** with async compile on, the worker and the PFIFO thread
build modules at the same time. A `+=` on `glslang_us` loses one side's
increment, and that window's `dgl_ms` reads low, which biases C2 toward PASS.
A lost increment is only ever tens of ms against a create of hundreds of ms, and
the unlocked `spv_cache_*` counters already have the same pattern. Fix: move these
under `pcfb_lock` (or use `qatomic_add`) if C2 ever becomes marginal.

### L3 (LOW): module handles are remembered forever, so a reused handle reads as "reused"

The lane states this in the code comment and in NOTES. It is recorded here
because the C3 verdict ("P5 stays") depends on it.
**Failure scenario:** in a long session, the shader-module LRU (50K entries)
evicts a module, and the driver returns the freed object's address for a new
module (common with malloc). The new stage is counted in `dsru`/`dsrum`, not in
`dsnu`, which pushes C3 toward ">= 50%". This does not affect the soak: 164
creates cannot evict from a 50K-entry cache, so the 246/246 reading stands. The
set also grows without bound (one small key per module ever created). Fix, if
the instrument is kept on for long runs: remove the handle in
`pgraph_vk_destroy_shader_module`.

## Not findings

- C1 fails low on size (dpc 8.3 s vs the registered 14.8 s). That is a
  measured result, and the PR reports it as one.
- Whether Turnip's per-stage `APPLICATION_PIPELINE_CACHE_HIT` can fire for a
  stage that is shared across pipelines depends on how the driver keys its
  cache. The registered duration cross-check (164 ms per reused stage vs 109
  ms per new one) shows that the misses are real compiles, as the leg requires.
  How this bears on GPL is the lane's reading, and NOTES "C3 limit" states it.
