## MEDIUM-1: an oversized duty got past the refusal. No longer occurs.

`fan_check` now refuses a `FAN_DUTY` longer than 9 digits before any
arithmetic (`[ "${#FAN_DUTY}" -gt 9 ]`). This check comes after the
`*[!0-9]*` case, so by then the value holds only digits. Nine digits fit a
64-bit integer, so the later `$((10#…))` and `[ "$FAN_DUTY" -gt
"$FAN_PERIOD" ]` cannot hit the "integer expression expected" path that
the `if` read as accepted. An empty value returns first, at
`[ -n "$FAN_DUTY" ] || return 0`, so `$((10#))` never runs on an empty string.
`fan_check` is called as `if ! fan_check`, in the current shell rather than a
subshell, so the refusal and the normalised value both reach the rest of the
script.

Pass 1's scenario, re-run: the refusal loop in `99-fan-duty.sh` now includes
`99999999999999999999`. At this head,
`SELFTEST_ONLY=99-fan-duty selftest.sh` gives `ok refused:
FAN_DUTY=99999999999999999999 exits 6 with fan-duty-refused: fan_duty
99999999999999999999 is more than 9 digits`, with no `am start` and no mode
or duty write. At `19227ec4c7` the same input gave `rc=0; started=yes`, as
pass 1 recorded. So if the bound is removed, this leg fails.

## LOW-1: leading zeros were misread as "moved". Fixed.

`FAN_DUTY=$((10#$FAN_DUTY))` runs after the length bound and before the
period read. `fan_enter`, `fan_hold` and `perf_write_result` all read the
normalised value, so `0050000` is written and compared as `50000`. `10#`
also stops bash from reading the value as octal (`08` does not error). The
new `zeros` leg passes: `FAN_DUTY=0050000 starts at 6/50000, reads back,
moved 0`.

## LOW-2: a failed initial write still runs the arm. Not changed.

Pass 1 marked this optional. `fan_duty.ran` still records what the node
held, and a verdict that voids the run can read it. It remains open as
quality, not as a finding.

## LOW-3: `FAN_DUTY=0` is accepted. Documented.

NOTES now says zero is allowed on purpose, as a control, and that the
kernel's thermal trips stay armed.
