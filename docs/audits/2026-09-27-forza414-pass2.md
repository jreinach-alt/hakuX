# Audit pass 2: PR #479 (lane/forza414), 2026-09-27

Remediation read: `f65175f993` ("keep a pending download's struct out of reuse
and prune"), `hw/xbox/nv2a/pgraph/vk/surface.c` only. Result: **clean**. Both
pass-1 scenarios can no longer occur, and LOW 1 remains as quality work that
does not block → `fold-ready`.

## HIGH 1: a pending download's struct is reused: closed

The shelf path in `update_surface_part` now calls
`deferred_downloads_reference(r, surface)` after `get_shelved_surface` has
taken the struct and before `*surface = target`. If a pending entry names it,
`download_surface_complete_deferred(d, SDC_REUSE)` retires the whole batch
first.

Replaying the pass-1 scenario: in step 2 (F1 comes back before a finish), the
completion runs while the struct still holds S's fields. It credits
`dl->draw_generation` to S, marks the dirty range over S's `vram_addr`, and
empties `num_deferred_downloads`. Only then does the assignment make the struct
T with `draw_generation` 0. In step 4 no entry names T, so no completion can
mark T clean. The scenario cannot fire.

I checked the order against `migrate_surface_image`, which runs before the
completion and moves the VkImage handles to `target`. That is safe because
`pgraph_vk_complete_staged_downloads` reads only the staging buffer, `dl->*`
and the struct's address, pitch, height and flags, never `surface->image`. The
recorded copy is already in a command buffer, and image destruction is
fence-deferred. The struct is on no list during the finish, so nothing the
finish walks can reach it. A finish in the middle of `surface_update` already
happens on the `SDC_DEFER_FULL` path.

`display_predownload_surface` is covered too. `pgraph_vk_prerecord_display_download`
records through `download_surface_record_deferred`, which sets `dl->surface`,
so the reference test sees it, and the completion clears
`display_predownload_pending`/`_surface` before the reuse.

The invalid-list path (`get_any_compatible_invalid_surface`) skips any struct a
pending entry names, so it can no longer be reused. That closes (a), the
dropped watch; (b), dirty marks over the wrong range; and (c), the generation
collision.

## MEDIUM 1: prune frees a pending download's surface: closed

`prune_invalid_surfaces` skips a referenced struct with the same test, so the
watch stays until the batch retires and the completion marks dirty through the
live binding. The skipped struct stays on the invalid list and is pruned on a
later update, so nothing leaks. `pgraph_vk_surface_flush`'s
`prune_invalid_surfaces(r, 0)` behaves the same way.

The second half of the remedy is also in. A download whose `dl->surface` is
NULL now marks VGA and NV2A_TEX dirty over `dl->dest_ptr - vram_ptr` for the
length it wrote. That formula is the same one `deferred_downloads_overlap_range`
uses: swizzled `w*h*bpp`, linear `pitch*height`.

Every other site that frees a struct still completes the batch before it calls
`deferred_downloads_clear_surface`:
- `invalidate_overlapping_surfaces`, shelved branch, line ~2816:
  `download_if_dirty` runs first.
- `expire_old_surfaces`, line ~3314: it runs `SDC_EXPIRE` first.
- `pgraph_vk_surface_flush`, line ~5142: `download_if_dirty` runs first.

So the NULL branch is a backstop that no current path reaches with a live
batch. Even if one did, the worst it would add is a redundant dirty mark.

The `SDC_REUSE` enum entry sits before `SDC_EXTERNAL`, and `sdcall_log`'s name
table adds "reuse" at the matching index, so the probe's labels stay aligned.
