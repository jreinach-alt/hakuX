## What I checked and found correct, so remediation does not re-derive it

* **The edge-list rotation argument holds.** `glsl/geom.c:207-210` emits
  `emit_line(1,2)`, `emit_line(2,0)`, `emit_line(0,1)` for a triangle under

  `(C,A),(A,B),(B,C)` — the same three **ordered** pairs, rotated. The paint
  order moves and nothing else does. Confirmed against the source, not taken
  from the PR body.
* **`vtxFogSpecial` really is per-edge.** It is `flat` in every shade mode, but
  the non-widened path assigns it in `emit_vertex()` from the vertex being

  `geom.c:535`). Both are functions of the edge, not of the triangle's index 0,
  so a rotation of the edge list leaves every edge's value where it was. The
  lane's step 4 is correct.

## MEDIUM 1 — `cylWrap()` reads `gl_in[0]` under `POLY_MODE_LINE`, so the enumeration is incomplete

`prim_rewrite.c:88` asks "**Does anything downstream actually READ index 0 of a
rewritten triangle?**" and answers it with `provoking_index`, `vtxFogSpecial`
and (in the prediction) `calc_triz`. There is a fourth reader, and it is a
literal `[0]`, not a `provoking_index`:

```
geom.c:294   vtxT%d = cylWrap(v_vtxT%d[0], v_vtxT%d[index], bvec4(...));
geom.c:297   vtxT%d = mix(cylWrap(v_vtxT%d[0], v_vtxT%d[i0], ...),
geom.c:298                cylWrap(v_vtxT%d[0], v_vtxT%d[i1], ...), t);
```

Cylinder wrap adjusts each vertex's texture coordinate by a whole turn relative
to **the input primitive's vertex 0**, and it is emitted whenever
`state->cylinder_wrap[i]` is non-zero — i.e. whenever a texture unit is in WRAP
address mode with a `NV_PGRAPH_TEXADDRESS0_WRAP_U/V/P/Q` bit set. It is in
`emit_vertex()`, `emit_vertex_fs()` and `emit_line_vertex()` alike, so both the
GL and the widened Vulkan paths carry it, and it is **independent of the shade
mode** — it is not gated by `provoking_index`.

Before this patch a fan triangle's index 0 was `v1` or `v2`; after it, it is the
fan hub. So the cylinder-wrap reference vertex moves.

**Failure scenario.** A guest draws a `TRIANGLE_FAN` under
`NV097_SET_FRONT_POLYGON_MODE_V_LINE` with `SHADEMODE_SMOOTH`, texturing, and
`NV097_SET_TEXTURE_ADDRESS` in WRAP mode with `WRAP_U` set — a textured
wireframe fan. A vertex whose U lies more than half a turn from the new
reference but less than half a turn from the old one (or the reverse) is now
adjusted by a whole turn where it was not, so its texture coordinate moves by
1.0 and the two triangles that touch it sample a different part of the texture.
No golden covers this: `Shade_model`'s line-mode prefix is `kUntexturedLM`, and
`Line width` is untextured, so every leg in the prediction is silent on it and
the arm will come back clean.

**I am not claiming the new value is wrong** — the hub is arguably the better
reference, because it is the same vertex for every triangle of the fan where
the old one varied per triangle. I am claiming the diff asserts, in the comment
that is the entire safety argument for the change, that nothing under
`POLY_MODE_LINE` reads index 0, and that is false. Remediation: name this
reader in the comment and in the prediction, say which way it moves, and say
whether the change is intended or merely tolerated. The predicate does not need
to change for that.

## MEDIUM 2 — `geom.c:197-206` becomes actively false on fold, and the reason given for leaving it is wrong

The PR body routes this itself, which is good, and then gives a reason that
does not hold:

> **`glsl/geom.c` untouched** (another lane's territory).

`origin/board:territory.toml` puts `hw/xbox/nv2a/pgraph/glsl/geom.c` in the
**`[free]`** array (line 618); `[retired.linecap13]` released it there at
`2026-09-20T14:57:11Z`, five hours before this lane opened. It is claimed by
nobody. What is true is narrower and different: `[lane.primpv13]`'s `files` is
`["hw/xbox/nv2a/pgraph/prim_rewrite.c"]` and a lane may not widen its own
territory row, so the lane could not simply take it — but that is a request to
the board, not another lane's claim, and the two have different remedies.

Meanwhile the comment this patch invalidates ships to master:

```
geom.c:197-206  Note this also reorders TRIANGLE_STRIP and TRIANGLE_FAN ...
                The fan arrives here already rotated by emit_tri_pv() ...
                so this takes the Tri class to 100.00% ... and TFan only to
                70.36%; the rest of TFan is rewrite_triangle_fan()'s rotation
                to undo, and undoing it there collides with flat shading's
                need for the provoking vertex at index 0.
```

After this fold all three of those sentences are false on the path they
describe: the fan does **not** arrive rotated under `POLY_MODE_LINE`, TFan is
no longer 70.36%, and "undoing it there collides with flat shading" is refuted
by the first term of the predicate this very patch adds.

**Failure scenario.** The next lane on #13 reads `geom.c` — the file where the
edge order actually lives — believes the TFan residue is still open and still
blocked by a flat-shading collision, and either re-derives work that is already
in the tree or prices a trade that no longer exists. This repo has paid for
exactly that twice: it is why `line_priority.py`'s hand-listed `ours` table had
to be rewritten in this very diff, and the lane says so in its own notes.
Routing it in a PR body is not routing: the PR body is deleted from the reader's
view the moment it merges, and no issue, label or territory note carries it.

Remediation, either of: (a) post a `[lane.primpv13]` PR comment asking the board
for `glsl/geom.c` — it is free — add it to `Files:`, and correct the six lines;
or (b) leave the file alone and make the routing something an actor will find
(an issue, or a line the board can put on `geom.c`'s territory note), rather
than a paragraph in a merged PR body.

## MEDIUM 3 — nothing automated evaluates legs 1–4 or 7, and a `PASS` will read as though something did

`docs/testing/predictions/line-prim-rewrite-fan-provoking.json` has
`"expect": {}`, `"expect_counts": {}` and `"must_not_regress": []`. The entire
machine-judged content is the nine `must_not_move` globs — 167 capture checks,
all of them **scoping** legs. Legs 1, 2, 3, 4 and 7 — the claim the arm exists
to test — live only in the `prediction` prose string, and `ab_compare.judge()`
never reads that string.

`ab_compare.py` has guards for a post-hoc prediction, a tampered one and an
unbound one; it has **no** guard for an empty `expect`. So if the scoping legs
hold, the `[job.arms]` comment on this PR will end:

```
VERDICT: PASS -- all 167 registered checks hold.
```

with the full prose printed above it, including "TFan 11,636 px 73.20% →
100.00%".

**Failure scenario.** The board reads `VERDICT: PASS`, labels the PR
`fold-ready` and folds. The arm has confirmed that the patch did not touch
`Shade_model`'s other 154 captures — which is real, and is not the claim. TFan
could have landed at 73.20% (the patch never reached the binary), at 47.57%
(the composition undone rather than completed), or anywhere else, and the
verdict line would be identical. That is the same shape as the three VBLANK
judges that scored constants in code without opening their prediction.

Remediation is cheap and does not need a new leg: say **in the prediction
itself** that legs 1–4 and 7 are not machine-judged, that the `PASS`/`FAIL`
line covers only the scoping legs, and name who runs
`line_priority_arms.py --a <A> --b <B> --extent-rule --min-width 8
--max-width 63.875` and where the answer gets written. If a capture-keyed leg
is wanted as well, `Shade_model/ProgLM_TriFan_Smooth_{First,Last}` is the only
capture pair outside `Line width` that the patch can move — but note it is
drawn at the default line width, where paint order is visible on a handful of
corner pixels at most, so `must_not_regress` on it may fail for reasons this
lane did not model. The disclosure is the part that matters.

## LOW 1 — "Both renderers rasterise first-vertex-provoking" is false on Android

`prim_rewrite.c:90-92`, the PR body, the notes and the prediction all assert it,
citing `gl/draw.c`. The call is guarded:

```
gl/draw.c:535  #ifndef __ANDROID__ /* glProvokingVertex not available in GLES 3.x */
gl/draw.c:537      glProvokingVertex(GL_FIRST_VERTEX_CONVENTION);
```

On Android the GL renderer keeps GLES 3.x's default, which is **last**-vertex.
The conclusion survives untouched — the rotation changes no edge's `(i0, i1)`
pair, so whichever endpoint a `flat` varying is taken from is the same endpoint
on both arms — and every device arm here is Vulkan anyway. But the sentence is
load-bearing prose repeated in four places, and it is wrong in one build.

## LOW 2 — the derived model still hard-codes one provoking convention, for `LLoop`

`line_priority.py`'s new `prim_rewrite()` takes `fan_pv_rotate` and derives
everything else from the C — except `LLoop`, which returns `(i, (i+1) % n)`
unconditionally. `rewrite_line_loop()` calls `emit_line_pv(v0, v1, pv)` with
`pv = last_provoking ? v1 : v0`, and the docstring states the suite is
`PROVOKING_VERTEX_LAST`, so the C emits **`(v1, v0)`** — the pairs are reversed.

This is inert for the score: the tie-shifted parallelogram, the cap bounds and
`lerp(c_a, c_b, t)` are all symmetric under swapping a segment's endpoints, and
`LLoop`'s `ours` order is `range(n)` either way. LLoop reproduces the device arm
at 99.53%, which is the evidence. But the docstring's whole justification is
"derived from the two files that decide it rather than listed, because listing
it is what went stale", and this is the one place a listed value survived. If
`last_provoking` ever becomes a variable of an arm, it will go stale silently in
exactly the way the rewrite was meant to prevent.

## LOW 3 — "a guess scored by nothing" overstates the strip's evidence gap

`prim_rewrite.c:281-290` declines the same treatment for
`rewrite_triangle_strip()` because "the `Line width` corpus ... draws no
`TRIANGLE_STRIP` at all under `POLY_MODE_LINE`. Changing it here would be a
guess scored by nothing."

The first clause is true — `line_priority.py`'s `BLOCKS` is `LLoop, Tri, QStrip,
TFan, Poly, Quad`. The second is too strong. `Shade_model/ProgLM_TriStrip_*`
(four captures: Flat/Smooth × First/Last) **is** a `TRIANGLE_STRIP` under
`POLY_MODE_LINE`, in this arm's own registered disc, and the lane registered it
under `must_not_move`. It is weak evidence — default line width, so overlap is
confined to the corners — but it is not nothing, and the reflection-vs-rotation
half of the argument stands on its own without the overstatement.

The risk is the one this repo keeps paying for: a blocker written into a code
comment is read as settled. Say "not decisively scored by the `Line width`
corpus, and only weakly by `Shade_model/ProgLM_TriStrip_*` at width 1" and the
next lane can price it instead of believing it is priced.
