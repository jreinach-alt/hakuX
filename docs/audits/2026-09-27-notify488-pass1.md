# Audit pass 1 -- PR #490, lane.notify488 (#488)

Head audited: `9b347631dc` (17 commits over master, MERGEABLE, CI build/build/check green).

**Verdict: no HIGH, no MEDIUM. Three LOWs. -> `needs-audit-2`.**

## What the diff ships

Only code: `hw/xbox/nv2a/nv2a_regs.h`, `pgraph/methods.h.inc`, `pgraph/pgraph.c`.

- `NV097_NOTIFY` (0x104) and its two parameter values, and a `DEF_METHOD(NV097, NOTIFY)` table entry. Before the PR,
  0x104 had no kelvin handler and went to `unhandled`, so no notifier was ever written.
- The handler maps `pg->dma_notifies` and returns if it is unset or its inclusive limit is below 15. It then writes
  PTIMER time into words 0-1, 0 into info32, and after `smp_wmb()` status 0 into word 3. For WRITE_THEN_AWAKEN it also
  sets TRAPPED_ADDR/DATA and `INTR_NOTIFY` and calls `nv2a_update_irq` under the BQL, following NO_OPERATION's
  lock-drop pattern. It does not set `waiting_for_nop`, so the FIFO is not stalled.
- An always-on `[notify488] sem_release N notify N` line in `pgraph_method_histogram_log_and_reset`. It sits inside
  `#if NV2A_PERF_LOG` (`debug.h:192` defaults it to 0) and under `__ANDROID__`, so a shipping build does not log it.
- The semaphore-release change was reverted (`0b3d108e1b`). `BACK_END_WRITE_SEMAPHORE_RELEASE` matches master,
  `surface_update` included.

Checked and correct:
- **Timestamp.** `ptimer_time = ptimer_get_clock() << 5`. The low word equals `TIME_0` (`(clk & 0x7ffffff) << 5`) and
  `(ptimer_time >> 32) & 0x1fffffff` equals `TIME_1` (`(clk >> 27) & 0x1fffffff`), so the notifier carries exactly
  TIME_1:TIME_0 (`ptimer.c:53-56`). The `numerator == 0` guard avoids the divide-by-zero that `ptimer_get_clock` would
  hit before the guest programs PTIMER.
- **Interrupt path.** `nv2a_update_irq` masks with `enabled_interrupts`, so a guest that never enables NOTIFY only sees
  a pending bit, which is harmless. The only other readers of `pending_interrupts` test `INTR_ERROR` and
  `INTR_CONTEXT_SWITCH` (`pfifo.c:1963`, `pgraph.c:1195-1199`, `pgraph.c:2526`), so `INTR_NOTIFY` cannot set off the
  NOP stall or the Android duplicate-NOP skip. A NOTIFY cannot overwrite TRAPPED_ADDR/DATA of a pending NOP trap,
  because `waiting_for_nop` stalls the puller before the NOTIFY is processed.
- **Dispatch.** The kelvin method table is indexed by `METHOD_ADDR_TO_INDEX` (`pgraph.c:1717`), so inserting an entry
  into `methods.h.inc` does not shift any other handler.

## Findings

### LOW-1: the notifier can be written before earlier draws reach guest memory
`pgraph.c` NOTIFY handler, and its comment ("every method before it has been processed").
Scenario: a guest draws to a surface, pushes NOTIFY + NO_OPERATION, polls status == 0, then reads the surface with the
CPU. The semaphore release calls `surface_update(d, false, true, true)` before it writes. NOTIFY does not, so the poll
can succeed before the rendered pixels are in guest RAM. This is **not a regression**: on master the notifier is never
written, so such a guest reached the same read after a timeout, with no download either. No title on disk sends 0x104
(NOTES section 1), and xemu's surface-memory watch may already cover the read.
Fix: reword the comment to say the handler orders method processing, not pixel availability.
It is not a correctness requirement for this PR.

### LOW-2: the end of the notification is not bounds-checked against VRAM
Scenario: `nv_dma_map` asserts only `dma.address < vram size` (its end-of-object assert is commented out, `nv2a.c:126`).
If a guest binds a notifies object whose masked base lies within 15 bytes of the end of `vram_ptr`, the 16-byte write
runs past the mapping. A base beyond VRAM aborts on the assert, which is live in Android release builds. The semaphore
release has the same exposure, so the PR only reaches an existing hazard through a new method. Only a malformed guest
DMA object can trigger it.
Fix: `if (dma_base + 16 > memory_region_size(d->vram)) return;`, or a shared helper for both handlers.

### LOW-3: WRITE_THEN_AWAKEN does not set NSOURCE
NO_OPERATION writes `NV_PGRAPH_NSOURCE` before it raises its trap. NOTIFY raises `INTR_NOTIFY` and leaves NSOURCE at
its previous value. pbkit's ISR (nxdk `pbkit.c:398-404`, cited in NOTES) keys on the INTR bit, and there is no
measurement of what silicon puts in NSOURCE for a NOTIFY. There is no failure scenario, which makes this an opinion.
It is recorded so that pass 2 or a later lane does not treat the value as measured.

## Not audited as shipping code

`docs/lanes/notify488/*.py`/`.sh` are lane instruments. The three predictions are registered data. The 3947-line
`nv2a_index.json` diff is a regeneration, and CI `check` gates it on this head.
