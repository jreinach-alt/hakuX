## H1 — `vk/shaders.c:309` — CLOSED

**The scenario cannot recur.** `want_vtx_range` is
`r->use_push_constants_for_uniform_attrs && n > 0`, and the flag is true only
when `maxPushConstantsSize >= GEOM_PUSH_CONSTANT_SIZE + MAX_UNIFORM_ATTR_VALUES_SIZE`
= 16 + 256 = 272. A device reporting 256 therefore never has the vertex range
declared on any of the 17 template layouts, so the 272-byte range that violated
`VUID-VkPipelineLayoutCreateInfo-pPushConstantRanges-00294` is not built.

**The guard matches, which is the part that actually had to be checked.** A gate
that merely exists would have been the worse bug. `create_pipeline()`
(`draw.c:2290`) declares the range iff the flag is set **and**
`__builtin_popcount(uniform_attrs) != 0`. `push_template_index()`
(`draw.c:2526`) returns that same popcount when the flag is set and `0` when it
is not. So template `n` is selected exactly for a pipeline with `n` uniform
attributes, and the two sides agree for every `n` — including the flag-false
case, where both declare one range.

**The ordering fix is correct, and I checked what it moved past rather than
taking the commit's word.**

- `device_props` is written only at `instance.c:581` and `:610`, and
  `pgraph_vk_init_instance()` runs at `renderer.c:187` against
  `pgraph_vk_init_shaders()` at `renderer.c:229`. The value is available at the
  new computation point.
- The flag's only other readers are `draw.c` (all per-draw) and `shaders.c:833`
  in `shader_binding_build_module_keys()`. No init step between the new
  computation point and `create_push_descriptor_resources()` reads it.
- The computation now precedes `shader_cache_init()` and
  `pgraph_vk_compile_worker_init()`, where before it followed them. That turns
  out to change nothing: `shader_cache_init()`'s warmup (`shaders.c:1153+`)
  replays `ShaderModuleCacheKey` blobs read from `shader_module_keys.bin` and
  does not rebuild keys, so it never reaches `shaders.c:833`. Moving the write
  earlier also strictly narrows the window against the compile worker thread
  rather than widening it.
- Only two sites build a layout carrying this range, so the fix is complete:
  `display.c:589` is fragment-stage and sized by reflection,
  `surface-compute.c:305`/`:938` are 16 bytes of compute.

**One claim in the fix is weaker than stated.** The `assert` at `shaders.c:328`
is implied by the flag it sits under — `offset` is `GEOM_PUSH_CONSTANT_SIZE`
and `size` is at most `MAX_UNIFORM_ATTR_VALUES_SIZE`, which is exactly the sum
the flag tests — so it can never fire. The commit says it "makes the next offset
change fail loudly here"; that holds only for a change that moves the vertex
offset to something *other than* `GEOM_PUSH_CONSTANT_SIZE`. A change made
through that constant — the likely shape, since both sides use it — moves the
flag's threshold in lockstep and the assert stays tautological. This does not
weaken H1's closure, which rests on the gate.

## M1 — `vk/draw.c:5622` — CLOSED

Both halves of pass 1's scenario are closed, and either one alone would have
been insufficient.

**Push half.** The `vkCmdPushConstants` is out of the `if (pipeline_changed)`
block. For the second of two line draws sharing a pipeline,
`e->has_dynamic_line_width` is true, `prev->has_dynamic_line_width` is true, and
`e->line_width != prev->line_width`, so `width_changed` is true and the push is
issued. The `!prev || !prev->has_dynamic_line_width` terms correctly handle the
stale-entry hazard the comment describes — `w->entries[]` is reused in place
and not cleared between windows.

**Merge half.** `check_draw_mergeable()` returns false on
`pg->line_width != q->line_width`, so the two draws never reach one draw call.

**What I checked beyond the diff.** The new `DrawQueue` field is initialised at
*every* activation site, not only the ones the diff touched: all four
`q->active = true` sites (`4670`, `4780`, `6069`, `6126`) are immediately
preceded by `q->line_width = pg->line_width`. The fifth `active = true` at
`6006` is `w->active` on `ReorderWindow`, a different struct. Types are exact —
`pg->line_width` and `DrawQueue::line_width` are both `uint32_t`, so the
comparison is on the raw 1/8-px register with no conversion, while
`ReorderWindowEntry::line_width` is a separate `float` in guest px used only for
the push. And the justification for adding a field rather than reusing a
generation counter checks out at the source: `DEF_METHOD(NV097, SET_LINE_WIDTH)`
(`pgraph.c:3045-3055`) assigns `pg->line_width` directly, writes no register and
bumps no generation, so every existing member of the comparison set is genuinely
blind to it.

**Two side effects pass 1 could not have seen, neither a defect.**

1. The push moved out of the `if (pipeline_changed)` block, and the
   uncompiled-pipeline early return is *inside* that block. When an entry is
   skipped for an uncompiled pipeline the caller still does `prev = e`
   (`draw.c:5897-5898`), so a following entry with the same binding now issues a
   push where it previously issued none. `e->layout` is still a valid
   `VkPipelineLayout` there (assigned at `draw.c:5527` from a binding that is
   never NULL), and `vkCmdPushConstants` does not require a bound pipeline, so
   this is a wasted call rather than an invalid one. The underlying problem —
   that such an entry proceeds to draw with no pipeline bound — is pre-existing
   and untouched by this commit.
2. The merge check is unconditional rather than line-primitive-only, which the
   comment states as a deliberate choice. A title that writes `SET_LINE_WIDTH`
   between triangle draws now loses draw merging where it did not before. A
   throughput cost, not a correctness one, and the stated reasoning for
   preferring it is sound.

## M3 — `vk/draw.c:599` — CLOSED, and pass 1's overstatement is confirmed

**No pixel change was expected and none was found.** All three
`pgraph_vk_get_clear_color()` call sites (`6509`, `6599`, `6604`) are inside
`pgraph_vk_clear_surface()` (`6367`), whose `pgraph_vk_surface_update()` at
`6396` precedes them — so the register and the binding hold the same value at
every reachable call today. The fix is structural, exactly as the
`pass1_overstated` field said.

**The scenario is closed.** Both sides now read the same `SurfaceBinding`. I
verified the load-bearing claim at the source rather than in the commit message:
`drawn_format`, `fmt` and `host_fmt` are assigned adjacently from the same
`target` on the create path (`surface.c:3119-3123`) **and** on the
compatible-reuse path (`surface.c:3340-3342`). A binding cannot report one
format to the clear and another to the sampler.

**I also checked something the fix silently depends on and does not claim** —
that the two *derivations* agree, not just the two state reads.
`pgraph_glsl_surface_pad_alpha_mode()` (`psh.c:187-199`) returns `ZERO` for
`X1R5G5B5_Z` and `X8R8G8B8_Z`, `ONE` for both `_O` twins, `NONE` otherwise;
`kelvin_surface_color_format_vk_map` (`constants.h:497+`) carries
`SWIZZLE_ZERO`/`SWIZZLE_ONE` on exactly those four entries, with
`X1A7R8G8B8_{Z,O}` deliberately left without an override on both sides because
its readback is not a constant. They agree for every colour format. That they
are still two tables is recorded as **P4**.

**Route taken.** Pass 1 proposed resolving the clear stamp "through
`surface->host_fmt` like the sampler does". The fix instead reads
`binding->drawn_format` — a sibling field of the same struct, refreshed by the
same assignments. Equivalent for the scenario and better typed:
`drawn_format` is the guest format enum the pad-mode helper already takes, where
`host_fmt.sampled_pad_alpha` is a `VkComponentSwizzle`. Recording it as a
slightly different route than proposed.

**Pass 1's overstatement is confirmed as overstatement.** `psh.c:180-186`'s "a
binding reused across a format change reports whichever format first created it"
is contradicted by `surface.c:3340-3342` in this tree. The correction stands.

**L8 — the feared scenario is refuted, and the residual is the real finding.**
Pass 1 could not tell whether `sizeof(PshState)` changed when
`bool tex_comp0_const[4]` was added, and its scenario depended on it *not*
having changed. It did. I compiled the before/after struct prefix rather than
reasoning about padding: **sizeof 180 → 184, and `tex_signed` moves from offset
164 to 168.** The `bool[4]` at 157-160 left three padding bytes before a
4-aligned `uint32_t[4]`, and the new `bool[4]` needed four — so it consumed the
padding plus one byte and grew the struct. Both weighted `sizeof` terms in the
fingerprint changed, the cache was wiped automatically, and the reinterpretation
pass 1 feared cannot have happened. (Computed on x86-64; `bool` is one byte and
`uint32_t` 4-aligned on aarch64 too, so the arithmetic is identical on the
target.) A version bump is now a no-op for correctness.

The residual is real and still open, and it is the half pass 1 flagged in
passing: the stamp sizeofs only `ShaderState`, `PshState` and `VshState`, while

is covered by no term, and its `vertex_push_offset` changed from 0 to 16 in this
window. This time the `PshState` size change wiped that file too, by luck rather
than by design. **Requested: add `sizeof(ShaderModuleCacheKey)` to the
fingerprint.**

**L10 is the most substantive of the twelve** and the only one whose scenario is

in this renderer is a silent "draws nothing" rather than a build error, and the
headroom shrank in this window, an assert at device init is cheap insurance.

**L6 was re-tested rather than inherited.** Pass 1 said it had checked that

holds at HEAD. `fesetround`/`fegetround` appear only under `tests/`, `fenv.h` is

because the residual exposure is to third-party libraries this tree cannot see,

### P2 — MEDIUM — no x87 exception flag is raised on the hard-FPU path, and M2's remediation is half-effective as written

L7 is broader than pass 1 recorded. `merge_exception_flags()`
(`fpu_helper.c:722-734`) has its entire body inside `#ifndef USE_HARD_FPU`, so on
the hard-FPU path it is an **empty function**. No status-word exception bit —
IE, ZE, OE, UE, PE, DE — is ever raised by *any* helper there, not only PE from
FRNDINT. Every helper still brackets its work with
`save_exception_flags`/`merge_exception_flags`, so the code reads as though it
maintains the status word; `save_exception_flags` even still clears the flags to
zero.

This is the live path on the Android target, and the build log confirms it:
`fpu_helper.c` **and** `fpu_helper_hard.c` are both compiled, the latter
defining `USE_HARD_FPU 1`, with runtime dispatch through
`MAP_HELPER_SOFT_HARD`.

**This makes pass 1's own M2 remediation only half-work, and M2 has not been
executed yet — so this is worth saying before it is.** M2 says to "set
`float_flag_invalid` on out-of-range and NaN so the existing guards in
`helper_fist*_ST0` become live". That half is sound: `helper_fistl_ST0`'s guard
at `fpu_helper.c:911` reads `get_float_exception_flags()` **directly**, not via
`merge_exception_flags`, so the integer-indefinite `0x80000000` would be stored
correctly. But the guest's status word would still never show IE, because the
merge is compiled out. Whoever takes M2 should either restore the merge on the
hard path or state at the top of the `USE_HARD_FPU` block that x87 exception
flags are deliberately out of scope for it — L7's second option, now known to
apply to the whole block rather than to one function. The file already carries a
bare `FIXME: rounding and exceptions` at `:391` for the x86_64 variant of the
same class.
