# Audit pass 1: PR #416, lane.aufire412 (#412 Agent Under Fire UBO ring grow)

Head audited: `2d04cbb9de`. Diff read: `hw/xbox/nv2a/pgraph/vk/shaders.c`,
`docs/lanes/aufire412/splitread.py`, the two prediction files, NOTES.

**Verdict: no HIGH, no MEDIUM. Three LOWs.** The code hunk is correct on every
path I could construct. Next state: `needs-audit-2`.

## What the hunk does

`make_room_in_ubo_ring()` replaces the two inline ring-full finishes in
`pgraph_vk_update_descriptor_sets`. It grows `push_ubo_sets` by one
4,096-set overflow pool through the existing `grow_descriptor_ring()`, up to
16 pools. If the cap is reached or pool creation fails, it falls back to the
old finish + `flush_all_frames` + index reset.

## Paths checked and cleared

1. **Can grown sets alias live work?** No. Growing appends fresh sets at
   `[old_count, old_count+4096)` and leaves the index alone, so no set that a
   recorded draw holds is rewritten. This is the #34 finding 1 invariant, and
   the hunk keeps it.
2. **Can `g_realloc` of `push_ubo_sets` dangle a pointer?** No. Every reader
   either copies the handle (`draw.c:5913`, `draw.c:6053`, `e->descriptor_set = ...`)
   or passes `&push_ubo_sets[i-1]` straight into `vkCmdBindDescriptorSets`
   in the same statement (`draw.c:2909`, `draw.c:5220`). Nothing holds the
   array address across a grow.
3. **Can overflow pools be destroyed while in use?** No. The only runtime
   reclaim is `pgraph_vk_flush_all_frames` (`draw.c:3323`). It runs after
   every submitted fence is waited, and only when `!r->in_command_buffer`.
   The per-flip index rewinds (`draw.c:3543`, `3610`, `3718`) reset the
   index and keep the pools, which is why P6 read a single pool.
4. **Shared pool array.** `descriptor_overflow_pools` also serves the gfx
   ring, and reclaim truncates both rings. The gfx ring is still never grown
   (no `grow_descriptor_ring` call with `descriptor_sets`), so reclaim leaves
   the gfx ring's count unchanged.
5. **Teardown with pools live.** `destroy_ubo_descriptor_resources` frees
   `push_ubo_set_count` sets from `push_ubo_pool` after `finalize_shaders`
   has destroyed the overflow pools without resetting the count. If the
   count were still grown, that call would free handles from a destroyed
   pool, which is invalid usage. It cannot happen today: `pgraph_vk_finalize`
   calls `pgraph_vk_finalize_textures` first (`renderer.c:306`), which
   asserts `!in_command_buffer` and calls `flush_all_frames`
   (`texture.c:3311`), and that reclaims the pools and restores the base
   count. See L1.
6. **Grow twice in one call.** The first site (`shaders.c:555`) grows. The
   second (`:633`) then sees `index < count` and does not run, so the
   `assert` holds on both the grow path and the fallback path.

## Findings

### L1 (LOW): teardown is correct only because of call order

`pgraph_vk_finalize_shaders` (`shaders.c:1549-1557`) destroys the overflow
pools but does not reset `push_ubo_set_count` to `push_ubo_set_base_count`.
`destroy_ubo_descriptor_resources` then frees `push_ubo_set_count` handles
from `push_ubo_pool`. This is safe today only because
`finalize_textures` runs earlier and reclaims. **Failure scenario:** a future
reorder of `pgraph_vk_finalize`, or a finalize path that skips textures,
would pass 4,096+ handles from a destroyed pool to `vkFreeDescriptorSets`.
Before this PR the count could not grow, so the latent hazard is new with
the hunk. A one-line fix: call `pgraph_vk_reclaim_descriptor_overflow(r)` in
place of the open-coded loop there, or reset the count.

### L2 (LOW): P6 reads the pool count from rate-limited lines

`splitread.py --judge` takes P6's maximum from `ubo_ring_grow` lines. Those
lines print only for grows 1-16 and every 256th after that, so the maximum
it reports is a lower bound. **Failure scenario:** a session that reclaims
and regrows many times would reach `pools2` on an unprinted grow, and P6
would still pass at 1. This does not affect the reported result: B printed
a single grow and pools1. P6 is also labelled a guess.

### L3 (LOW): `static int grows` counts for the whole process

The counter is never reset, not on reclaim and not across renderer re-init.
After 16 grows in a process, a later scene's grows print only at multiples
of 256. **Failure scenario:** a long multi-title session judged by M1
(`grow_lines_b_min`) on a later window could read B as inert although it
grew. It does not bite the registered soak, which is a fresh boot where
the first grow always prints.

## Claims in the PR body

The body reports the fps legs as FAILED (P3, P4, P5) and keeps the hunk for
its mechanism and GPU-time win. It does not claim a #412 fix. The golden arm
is correctly described as inert (99/99 identical, no grow line in either
logcat), so no claim overreaches the evidence.

## For pass 2

There is no HIGH or MEDIUM scenario to re-verify. If the lane fixes L1,
pass 2 should confirm that `finalize_shaders` leaves `push_ubo_set_count ==
push_ubo_set_base_count` before `destroy_ubo_descriptor_resources`, whatever
