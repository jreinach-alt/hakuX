## Findings

### LOW 1: a GPU with a fast round trip never reaches the second half, so it cannot be measured

`renderer.c`, the sampling loop: `while (n < GPU_TS_CAL_MAX_SAMPLES)`, with
`split` set at `SPAN/2` of elapsed time.

**Failure scenario.** Each sample in the first half costs one submit-and-wait,
and there is no sleep. If that round trip is under about 58.6 us
(60 ms / 1024), all 1024 samples fill before 60 ms. When that happens:

1. The loop exits with `split = -1`.
2. `kept_split = kept`, so the second half has 0 samples.
3. The function refuses with "too few samples".

This is reproduced with the lane's own `caltest.py`, with the stub latencies
cut to a round trip of about 15 us (begin 2 us, lat 3-6 us, work 6-10 us), in
the free-running world:

```
reported=33.113 ns measured=0.000 ns (+-0.00%, span 0.0 ms, samples 1024 of 1024,
halves differ 0.00%) using=33.113 ns (reported; not measured: too few samples)
```

The line also contradicts itself: it reports "samples 1024 of 1024" and gives
the reason "too few samples".

**Why LOW.** The fallback is the reported period, which is exactly what master
uses. The effect is limited to perflog phase stats. The fleet's round trip is
about 300 us: the Thor took 319 samples and the Nova 372. No current device
reaches this. It matters only for a faster GPU whose driver also misreports
the period.

**Fix (optional).** Bound each half separately, for example
`MAX_SAMPLES / 2` per half. Or switch to the gapped half on
`n >= MAX_SAMPLES / 2` as well as on elapsed time. Then the refusal reason
would name the real cause.

### LOW 2: the window filter spans both halves, so slower wake-ups in the gapped half can starve it

`narrowest` is taken over all samples, and a sample is kept if its window is
at most `4 * narrowest`. The gapped half idles the GPU for 300 us before each
submit.

**Failure scenario.** A GPU whose wake latency after 300 us of idle is more than
four times its busy round trip loses its whole second half to the filter. The
function then refuses with "too few samples" and keeps the reported period.
On the devices this did not happen: the Thor kept 316 of 319 samples and the
Nova 371 of 372. The consequence is the same fallback to master's behaviour.

**Fix (optional).** Take `narrowest` per half.
