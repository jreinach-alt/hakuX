# Audit pass 1: PR #336, lane/nanfix281 (#281)

Head audited: `8289ffaccb`. Diff: `hw/xbox/nv2a/pgraph/glsl/vsh.c`,
`hw/xbox/nv2a/pgraph/glsl/vsh-prog.c`, the prediction file and lane notes.

**Result: 1 MEDIUM, 2 LOW → needs-remediation.**

The arm passes on the two predicted figures, and the code does what the PR
says for `MOV` and `MUL`. The MEDIUM is about every other op that can write a
NaN colour. Before this PR they all drew white. After it, their colour depends
on the sign the host GPU happens to give the NaN. The one hardware model the PR
measured says arithmetic NaNs come out positive, and the PR applies that model
to `_MUL` only.

## MEDIUM-1: `_ADD`, the add half of `_MAD`, and `_DP3/_DP4/_DPH` now pass a host-signed NaN into the sign-reading colour map

`vsh.c:962-981` swaps `NaNToOne` for `NaNToSignedOne` on every colour output,
so a colour NaN's sign bit now decides black or white. `vsh-prog.c:654` makes
the sign positive only for a `_MUL` product. Every other op still hands its
NaN to the output map with whatever sign the host produced:

- `_MAD` is `_MUL(src0, src1) + src2` (`vsh-prog.c:667`). A NaN product is now
  +NaN, but a finite product plus a -NaN `src2` gives the host's propagated
  NaN, and most hosts keep the input's sign. The PR body's "`_MAD` inherits it"
  holds for the multiply half and not for the add.
- `_ADD`, `_DP3`, `_DP4`, `_DPH` have no canonicalisation at all.

Failure scenario: a vertex program with `MAD oD0, v0, c[k], v3` (the usual
shape for lighting-plus-ambient), fed a -NaN in `v3`, or `ADD oD0, r0, v3` with
the same input. Today on master, `NaNToOne` draws that vertex white. With this
PR, a sign-propagating host GPU gives -NaN → `NaNToSignedOne` → -1 → clamped
to 0, so it draws black. The only NaN-arithmetic behaviour the PR measured
(`-NaN x 1.0`, `x -INF` and `x -NaN` all draw white on hardware) says the
hardware's arithmetic results are +NaN. The likely correct answer for the
`ADD`/`MAD` case is therefore white, the pre-PR output. A host that generates
a negative default NaN (for example 0xFFC00000 from `INF + -INF`) flips
`ADD`/`DP*` colours the same way.

No golden exercises these ops with a NaN (NOTES: "unchanged and unmeasured"),
so the arm cannot see this. That is the reason it is a finding: the regression
sits outside what the goldens exercise. It is only MEDIUM, not HIGH, because a
NaN reaching a colour through ADD/MAD/DP in shipped titles is rare.

Remedy (no device needed to keep the rest of the PR's behaviour): apply the
same `isnan → +NaN` map to the results of `_ADD`, `_MAD` (after the add) and
`_DP3/_DP4/_DPH`. For those ops that restores exactly the pre-PR output
(white), and it matches the only NaN-sign model the lane measured. Or keep the
sign reading to the passthrough case. `_MIN/_MAX` return an operand rather
than computing a new value, so the lane may reasonably leave them as they are.
Whichever you choose, write down that choice and the reason in the PR body.
The prediction's must_not_move legs stay valid under either remedy. None of
those captures feeds ADD/MAD/DP a NaN, and those columns are MUL by constants.

## LOW-1: fixed-function lit colours now read the host's NaN sign as well

`NaNToSignedOne` also sits on the fixed-function outputs (`vsh-ff.c` writes
`oD0/oD1/oB0/oB1` and shares the map in `vsh.c`). `ltMulCore` returns a
positive `LT_NAN` (0x7FFFFC00), so the lighting multiplier is safe. Any native
float add in the lighting accumulation of a NaN material or vertex colour
still reaches the map with the host's sign. NOTES already records this as a
known, unmeasured change ("a -NaN colour from FF lighting now draws 0 where it
drew 1"). It is LOW because no capture is known to produce one. If you apply
MEDIUM-1's remedy, check whether the FF accumulation needs the same map.

## LOW-2: the PR body overstates `_MAD`

"`_MAD` inherits it" should read "the product half of `_MAD`". Fix the wording
together with MEDIUM-1.

## Checked and clean

- `NaNToSignedOne`: `floatBitsToInt(src) < 0` reads the sign bit of a NaN
  correctly, `mix(..., bvec4)` selects without doing arithmetic, and `clamp`
  then gives 0/1. For non-NaN inputs it returns `src` unchanged, so the
  `-INF_INF` and finite legs cannot move from this function.
- The `_MUL` forcing runs after the zero forcing, so `NaN x 0 = 0` is kept (the
  zero test still uses `NaNToOne`, which is why `NaNToOne` stays). `mix` with
  an `isnan` mask leaves non-NaN lanes bit-identical.
- GLSL: `uintBitsToFloat`, `floatBitsToInt`, `lessThan(ivec4)`, `isnan`, `mix`
  with a bvec4 are all ES 3.00 / GLSL 3.30 builtins, and the same shaders
  already use them. The arm's device build compiled and the finite 0-px legs
  held, so no compile failure blanked the captures.
- `_MUL` now also feeds `oPos`, the texcoords and fog. A NaN's sign has no
  effect there: `geom.c` and the fog path test `isnan` and not the sign.
- The prediction was registered on `b_ref 2bedc113aa`, which is the code
  commit, and the arm verdict matches the two `expect` figures exactly.
