# Audit pass 1: PR #563, lane fanduty507 (#507 per-request fan duty)

Head audited: `19227ec4c7`. Read: the diff of `docs/testing/soak_title.sh`,
`docs/testing/devices.sh`, `docs/testing/jobs/selftest.d/99-fan-duty.sh`,
and the lane's notes and proof files.

**Verdict: one MEDIUM, three LOW. Needs remediation.**

## MEDIUM-1: an oversized duty gets past the refusal, and the soak runs

`fan_check` (soak_title.sh, "fan_check") compares with
`[ "$FAN_DUTY" -gt "$FAN_PERIOD" ]`. When `FAN_DUTY` is a string of digits
too large for a 64-bit integer, `test` prints "integer expression expected"
and returns 2. The `if` treats that as false and `fan_check` returns 0, so the
duty is accepted.

Failure scenario, reproduced: add `99999999999999999999` to the refusal leg's
`for want in 60000 fast` loop in `99-fan-duty.sh` and run
`SELFTEST_ONLY=99-fan-duty selftest.sh`. The result is
`FAIL refused: FAN_DUTY=99999999999999999999 rc=0; ; started=yes`. The soak
starts the title instead of exiting 6. On a device the sysfs write of that
value fails, so `fan_mode` is CUSTOM with the firmware's fixed 25000 duty.
That is slower than SPORT's fan. The whole soak runs as a "fan_duty"
arm at a fan below the one MAX would have given it, and every re-write counts as
`moved`. Nothing reads `fan_duty.ran` yet, so nothing voids the run. This is
exactly the case the code comment says the refusal exists for: "a run at a
fan other than the one asked for measures the wrong arm and looks like the
right one."

The input can arrive from the request's top-level `fan_duty` (a JSON integer
of any size) or from `--env FAN_DUTY=`. The blast radius is bounded because
it takes a malformed request. The contract is still stated in the code and in
the PR body, and it does not hold.

Fix: bound the length before any arithmetic (for example, refuse more than
six digits, or compare with `python3`/`awk`). Add
`99999999999999999999` to the selftest refusal loop so the leg holds it.

## LOW-1: leading zeros are accepted and then misread as "moved"

`FAN_DUTY=0050000` passes `fan_check`, since it is a whole number and not
above the period. The same probe run shows `FAIL refused:
FAN_DUTY=0050000 rc=0; started=yes`, and here accepting it is within the
contract. After that, `device_fan_duty_set` and `fan_hold` compare the
read-back string `50000` with the request string `0050000`. So the run logs
"did NOT read back", and every hold sample counts as `moved`, even though the
node holds the duty. If the OEM node parses with base 0 (as the kernel's
`kstrtou*(…, 0, …)` does), the value is also taken as octal (20480).
Normalise the value (`FAN_DUTY=$((10#$FAN_DUTY))` after the length bound) or
refuse a leading zero.

## LOW-2: a failed initial write still runs the arm

When `device_fan_duty_set` does not read back, `fan_enter` logs "did NOT
read back" and the soak goes on. If the failure was in the `fan_mode 6` write
(for example a vsock drop), later `fan_hold` re-writes only the duty, never
the mode. The firmware then keeps the node for the whole run. This matches
how `perf_enter` handles a failed regimen write, and `fan_duty.ran` records
the truth, so this is quality, not a defect. It is still the one path to a
mislabelled arm that remains after MEDIUM-1 is fixed. Consider re-asserting
the mode in `fan_hold` when the read-back mode is not CUSTOM, or voiding the
run through the verdict.

## LOW-3: `FAN_DUTY=0` stops the fan and is accepted

Zero is a whole number no higher than the period, so the soak runs a title
under MAX with the fan stopped. This is explicit and may be wanted for a
control, and the kernel's thermal trips remain. The NOTES should still say
it is allowed on purpose. Otherwise a floor should refuse it.

## Checked and clean

- Refusal runs after `trap release EXIT`. With `FAN_SET=0` and `PERF_SET=0`,
  `release()` does only its force-stop, sleep and lease removal. Nothing is
  left set. Exit 6 has no other meaning in soak_title.sh.
- `fan_leave` runs before `perf_leave` in `release()`, it is idempotent, and
  it writes no duty. Under the `max`/`rest`/`default` regimens, `perf_leave`
  sets `fan_mode` REST again afterwards, which is harmless. Under `off`,
  `fan_leave` leaves REST, not the mode found (`PERF_BEFORE`). That is a minor
  asymmetry, and REST is the documented resting state.
- Moving `PERF_REQUEST` out of the `if` changes nothing for PERF_REGIMEN. It
  is computed either way and read only when the variable is unset.
- `perf_write_result` argv indices (`sys.argv[12:20]`) match the eight new
  positional arguments. `fan_duty` is `null` when no duty was asked for.
- `fan_hold` runs only from the hold loop's thermal branch. It uses the
  loop's `$s`, which is in scope.
- Selftest `99-fan-duty` at this head: all 24 existing legs passed in the
  probe run above. The only failures were the two added inputs.

## To remediate
