## What was checked

1. **The fix is correct against the code it repairs.** In
   `pgraph_vk_upload_surface_data()` (`surface.c:2865`) `regions[0]` is built
   with `.bufferOffset = staging_base`. On the Z24S8/D32S8 path the copy
   source becomes `BUFFER_COMPUTE_SRC` (`surface.c:3004`).
   `pgraph_vk_unpack_depth_stencil()` binds that buffer's depth plane at
   `.offset = 0` (`surface-compute.c`, the first `VkDescriptorBufferInfo`) and
   the stencil plane at `ROUND_UP(depth_size, minStorageBufferOffsetAlignment)`,
   which matches the `regions[1]` rewrite. So `regions[0].bufferOffset = 0`
   is the offset the unpack wrote to. The unpack's input is also fine: the
   `vkCmdCopyBuffer` into `BUFFER_COMPUTE_DST` uses `srcOffset = staging_base`
   and an implicit `dstOffset = 0`, and the unpack reads `COMPUTE_DST` from
   offset 0.
2. **`regions[1]` is always populated on this path.** Both formats that
   select the compute path carry `VK_IMAGE_ASPECT_STENCIL_BIT`, so
   `num_regions == 2` and the existing `regions[1]` writes are not
   uninitialised. The diff doesn't change this.
3. **The arm measured the shipped change.** `git diff 9c5f7416d8 9de95de849`
   touches only `surface.c`, and its only non-comment line is
   `regions[0].bufferOffset = 0;`. `9de95de849` is an ancestor of the head.
   The net diff of `surface.c` against master is that same hunk. The
   decline scaffolding is withdrawn, and master was merged in, not rebased.
4. **The prediction is not tautological.** Leg (1) can fail in both
   directions. Leg (2) names a third background value as the refuting
   world. The Adjacent* must_not_move legs are live, because the lane's own
   trace shows those zeta uploads following a colour upload in the same
   staging window, so the fix does change what they receive.
   `[job.arms]` PASS, 13/13, 0 unreadable. The PR body reports a histogram of
   the arm's PNGs as the mechanism leg's evidence.
5. CI is green on the head (build ×2, check), the PR is MERGEABLE and not

## Findings

### LOW-1: the same offset defect survives in the swizzled-colour path of the same function (pre-existing, not in the diff)

`surface.c:3007-3059`, `use_compute_to_unswizzle` (swizzled, 4 bpp, colour).
It copies `staging_base..+size` into `COMPUTE_DST` at offset 0, and
`pgraph_vk_compute_swizzle()` writes its output to `COMPUTE_SRC` at
`.offset = 0` (all three descriptors in `surface-compute.c` bind offset 0).
Then `copy_buffer` becomes `COMPUTE_SRC`, but `regions[0].bufferOffset` is
never rewritten and still equals `staging_base`.

*Failure scenario:* a swizzled A8R8G8B8/X8R8G8B8 colour surface (a
render-to-texture target) gets uploaded after another upload in the same
staging window. `staging_base != 0`, so `vkCmdCopyBufferToImage` reads
`size` bytes at `COMPUTE_SRC + staging_base`. Those bytes are stale output
of an earlier compute pass, not this surface's unswizzled texels, and the
host image gets garbage. It is not out of bounds: `compute_size >=
staging_size` in `buffer.c`.

This is the defect class the PR names ("a copy offset… `60bc72faed`
introduced `staging_base` and missed this region"), in the sibling branch
where `876942ca09` added the unswizzle path. It is pre-existing and this
diff leaves it unchanged, so it does not block this fold. Fixing it here
would move the shipped diff off the arm's b_ref. **Recommend the board
open a follow-up** for the one-line `regions[0].bufferOffset = 0` in the
unswizzle block, with its own arm on a disc that has swizzled render
targets, e.g. suites exercising `SURFACE_FORMAT` swizzle.

### LOW-2: the in-code comment will go stale once the sibling is fixed

`surface.c:2987-2998` explains the depth offset by reference to "the copy
now reads unpack_buffer". That is accurate. When LOW-1 is fixed, putting
the reset in one place after both compute branches (e.g. "any compute path
leaves its output at offset 0 of `COMPUTE_SRC`") would stop the next
compute path from repeating the omission. This is a quality note only.

### LOW-3: reach under master's policy is unmeasured (stated in the PR)

The arm carries #88's decline in both refs. The shipped change lands on
master's policy, where the lane expects it to be inert on this disc. The
defect is generic, so depth-heavy suites outside the three-suite disc may
move. The PR's Limits section says this and asks for a master →
master+fix sweep. The change makes the upload read the bytes the unpack
wrote, so a move there should be toward correctness. Still, a suite whose
goldens were matched under the wrong depth plane would read as a
regression. There is no failure scenario on the measured disc, so this is
LOW. The sweep belongs to whoever claims the fix's reach.
