# Audit pass 1: PR #401 (lane.flatlm13, #13 class C)

Head audited: `49ecb3e0e7`. Diff read against `origin/master`: `prim_rewrite.c`
(+55/-9), `docs/testing/predictions/flatlm13-orient.json`, and the lane's
`docs/lanes/flatlm13/` tools and notes.

**Verdict: 1 MEDIUM, 2 LOW → needs-remediation.**

The hunk does what it says on the path the arm measured. On the Vulkan and
desktop GL paths every line goes through geom.c, which pins a flat line's
varyings to input index 0 (`provoking_index = "0"`, geom.c:349). There, emitting
(v3,v2) / (v3,v1) / (v0,v4) moves the colour vertex into slot 0. I traced all
three loops: the quad's (v3,v0), the strip's (v3,v2) and the polygon's (v0,v1)
already start from the colour vertex. So the flip covers every edge an index
rewrite can fix, and the paint order is unchanged. The count==2 and count==3
polygon cases are correct. Smooth output is untouched, because the flip is
gated on `flat_shading`.

## M1: MEDIUM. The flip is wrong where no geometry shader exists

`prim_rewrite.c` `emit_edge_flat()`, called from `rewrite_quads_line()`,
`rewrite_quad_strip_line()` and `rewrite_polygon_line()`.

The hunk assumes that the colour of a flat LINE comes from index 0. That
holds only when geom.c runs. On Android GL, a GLES device without
`GL_EXT/OES_geometry_shader` does not attach the geometry stage
(`gl/shaders.c:372`, `need_geometry_shader = false`). The draw then sets
`no_adjacency = true` (`gl/draw.c:830`). With no geometry stage, the `flat`
varyings (glsl/common.c:46) come from the rasteriser's provoking vertex.
GLES 3.x has no `glProvokingVertex` (`gl/draw.c:588`), so that is the LAST
vertex, index 1.

**Failure scenario.** Android GL renderer, GPU without geometry shaders. A
guest draws a flat-shaded QUADS in POLY_MODE_LINE. Before this PR, the edge
(v2,v3) provoked from v3, the golden's colour, correct by accident. After it,
the edge is emitted as (v3,v2) and provokes from v2, which is wrong. The same
happens to the strip's (v1,v3)→(v3,v1) and the polygon's (v4,v0)→(v0,v4). All
three edges the hunk sets out to fix had been correct on this path, and all
three are now wrong. No arm sees this: the arms run Vulkan on a device with
geometry shaders.

**Remedy (one token).** `PrimAssemblyState` already carries the discriminator.
Pass `mode->flat_shading && !mode->no_adjacency` into the three `*_line()`
calls, or test it inside `emit_edge_flat()`. The comment in `gl/shaders.c`
already declares the no-GS path degraded for flat shading, so the aim is only
to leave it as it was. The prediction's `must_not_move` is unaffected. Add
one sentence to the FLAT COLOUR comment saying why the gate is there. The
comment at `pv_placement_observable()` records that "both renderers are
first-provoking" is false in one build, and this is the same trap.

## L1: LOW. `emit_edge_flat()` duplicates `emit_line_pv()`

`emit_line_pv(r, a, b, p)` (prim_rewrite.c:291) already emits the edge from
`p`. `emit_edge_flat` is `flat ? emit_line_pv(r, a, b, p) : emit_line(r, a, b)`
apart from the `b == p` / `p == a` phrasing, which gives the same result for
every call site here (p is always one of a, b). A helper written in terms of
the other would avoid a second copy of the orientation rule. There is no
failure scenario, so this is quality only.

## L2: LOW. Reversal coverage is measured only on the widened Vulkan path

`price.py --verify` measured 0 px of coverage change from reversal, on the
Thor, where geom.c widens lines to triangle strips (geom.c:407, `opts.vulkan`)
and the result is symmetric. On desktop GL, `layout(line_strip)` goes to the
driver's line rasteriser. There the diamond-exit rule can drop a different
endpoint pixel when an edge is reversed. Adjacent edges share that endpoint
and paint order is unchanged, so the worst case is one pixel per corner taking
a neighbour's colour. That is bounded and unmeasured, and the gate is not
desktop GL. It is recorded so that a desktop GL report of corner pixels on
flat wireframes points here.

## Not findings

- The prediction's `must_not_move` globs exclude exactly the six Flat
  line-mode captures. `expect_counts` better=6 / worse=0 matches the PR body's
  arm table, and `expect` is empty, which is allowed because `expect_counts` is
  set.
- The strip's shared edge is emitted twice: quad k emits (v3,v2), and quad k+1
  emits (v2,v3) as its (v0',v1'). The later quad's emission paints last and
  takes its colour from v2 = v0'. That is neither endpoint of the golden's
  v(2k+5), so no index rewrite can fix it. The PR says so, and that is the
  "whole rule (needs geom.c)" column.
