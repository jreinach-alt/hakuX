## What was checked

- **Ordering.** `dispatcher.sh:1587` serves `reqs=("$D"/queue/*.req)` in glob
  order. `fleet.py:226` records that the workers run with `LANG=C.UTF-8`
  (codepoint order). `1-<epoch>` sorts after `0-*` and `0-0-x-*`, since `'0' < '1'`.
  It sorts ahead of `17…`/`18…` epochs because `'-'` (0x2d) is below every digit, and
  ahead of `z-*`. The same order holds under a glibc locale that ignores
  punctuation at the first level (`11790…` < `1790…`). Plain ids start with
  `1` until 2033, which does not change the result.
- **Readers of ids.** None of these search patterns found anything in
  `docs/testing` or `host-tools`: `\d{10}`, `(\d+)-`, `^[0-9]+-`, or a
  `results/` listing sorted by name to pick the newest. `arms.sh` reads ids
  only from `request.sh`'s `queued <id>` line (`${qa##* }`), stores them in
  `pairs/<sha>.json` and opens `results/$ida` by exact name. The queue
  counts (`arms.sh:828`, `status.sh:123`, `board-status.sh:57`) separate
  `z-*` from everything else, so they count a `1-` request as waiting,
  which is correct.
- **`release_prio` output.** `say` is `echo | tee -a "$LOG"`. Inside the
  function it is redirected `>&2`, so the "could not read" line goes to the
  tick log and never ends up in `prio=$(...)`. The function always exits 0,
  so a failed read cannot hit `refused` or `continue`.
- **Label match.** `grep -qxF` matches the whole line, so `0.5-candidate`
  and `blocked:after-0.5` do not match. The fragment tests the first of these.
- **The fragment was run.** `bash docs/lanes/relprio432/prove.sh` on this
  host passed 9 of 9. It showed `1-1790466475-arms-relprio-base-…` and
  `1-…-fix-…` on the labelled read, and plain ids for the unlabelled and
  failed reads, with 3 reads of #7 in 3 ticks.
- **gh without a timeout.** The new `gh api` call has no `timeout`, but
  neither do the other gh calls in `arms.sh` (lines 123, 416, 420). The new
  call does not add a new way for the tick to hang.

## Findings

### LOW-1: any non-empty `HAKUX_RELEASE_PRIO` turns priority on, including `0`
`request.sh:707` uses `${HAKUX_RELEASE_PRIO:+1-}`. `ab_run.sh`
(`PRIO="${HAKUX_RELEASE_PRIO:-}"`) and `release_prio` (`[ -z … ] || echo 1`)
also treat any non-empty value as on.
*Scenario:* a lane shell runs `export HAKUX_RELEASE_PRIO=0`, expecting that
to turn it off, or inherits the variable from an earlier `0.5` session.
Every request.sh call from that shell is then queued `1-`, ahead of every
plain request. The limit on the damage is that only callers who set the
variable are affected, and nothing in the repo sets it except the two
readers. Fix: test `= 1` in all three places.

### LOW-2: the new block separates `ab_run.sh`'s arm-order comment from its code
The block is inserted right after "Concrete shas, never a name. The
baseline goes first so that…". That comment is about the arm order in the
`request.sh` calls further down, but it now sits above the
release-priority reader. This affects readability only.

### LOW-3: two copies of the label reader
`ab_run.sh` and `arms.sh` each contain the same loop (split on `,#`,
numeric filter, `gh api … --jq '.labels[].name'`, `grep -qxF`). The only
thing keeping them in step is a comment that says "change both". The
fragment tests only the `arms.sh` copy. If someone later changes the label
rule in `arms.sh` alone, `ab_run.sh` keeps the old rule and no test fails.
Fix: move the reader into a sourced helper (like `gh-label.sh`) or give
`ab_run.sh --dry-run` a check of its own.

### Not a finding
`titles/table.py:48` breaks a `judged_utc` tie by comparing request-id
strings. The PR body already says so, and no soak is queued with the
variable. It is out of this diff's files.
