## What the diff does, checked

- In `wbufSlopeStep` the row anchor now takes the 4-grid when
  `!cut || (topCut && !(flatTop && mod(clip.y, 8.0) == 0.0))`.  Before the
  patch it was `!cut`.  The column is untouched.
- **Units.** `clip` arrives as `vec4(clipRegion[0]) / surfaceScale`.
  `clipRegion` (psh.c:4043-4062) applies the AA factor and the scaling factor,
  and `surfaceScale` (psh.c:4031-4037) is the product of the same two.  So
  `clip.y` is in unscaled guest pixels, the same space as `vtxPos*.y`.
  `mod(clip.y, 8.0)` therefore does not flip with resolution scale or AA.
  Both factors are integer multiples, so the division is exact.
- **With no window clip, nothing changes.** An exclusive clip passes
  `vec4(-1e9, ...)`, so `clip.y > 0.0` is false.  With no clipping rectangle
  at all (`window_clip_count == 0`), region 0 covers the surface (psh.c:63-72),
  so `clip.y == 0` and `topCut` is false.  In both cases
  `grid == !cut`, which is the shipped expression.  The PR body's claim holds.
- **GLSL.** `(a ? 1 : 0) + (b ? 1 : 0) + (c ? 1 : 0) > 1` parses as
  `(sum) > 1`, because `+` binds tighter than `>`.  Every construct is valid
  in GLSL 1.30+ and in ESSL 3.x.  The arm compiled and ran it on the Thor, and
  the ZS0 and Depth_Clamp guards that would catch a compile failure held.
- **Parity with the model.** `anchor(..., "sel")` in
  `wbuf_anchor_recover.py` is term-for-term the shader expression (`ytop`,
  flat count > 1, `clip[1] > 0 and ytop < clip[1]`, `% 8.0`).
- **Prediction.** It is registered with `expect: {}` and
  `must_not_regress` on the three movers, and every `must_not_move` glob names
  the patch change that would move it.  The verdict is PASS, 371/371
  (`verified` label).  Leg M is prose, and the PR body reports it landing
  within 0.15.
- **nv2a_index.json.** Only line shifts: `psh.c` locs +12, matching the
  diff's net line count.  The PR says it was regenerated from pinned trees.
- **CI.** build ×2 and check are green on this head.  The branch is 11

## Findings

### LOW 1: the rule is one of 93 fits; it has one untested literal and one known separating capture

`flatTop && ct % 8 == 0` rests on four flat-topped data points, all from the
same ClipF floor triangle t0.  The PR says so plainly: NOTES names the capture
that separates the 93 survivors (ClipF, clip_left 300, clip_top 8).

**Failure scenario.** A game draws a flat-topped triangle that a window clip
cuts at the top, with the clip edge on the 8-row grid, and the true selector
is one of the other 92.  Then the anchor sits one grid rung off, and the slope
offset is off by roughly a rung's worth of W.  At ct 32 that is about 1,700
units.

This is LOW because no capture shows it wrong, and every one of the 93 gives
the same answer on every capture that exists.  It is disclosed, and the
separating run is named.  No remediation is asked; the follow-up is that
silicon run.

### LOW 2: the investigation doc still says the ClipF anchor cannot be selected

The deleted psh.c comment used to point readers to
`docs/investigations/wbuffer-slope-offset.md` for "no rule ... separates
them".  That doc still argues it:

- Pair A (line ~300): "no function of (plane, clip rect, first covered pixel,
  top vertex) can reproduce the table".
- Line ~355: ClipF t1 is "unselectable per Pair A/Pair B".

This PR ships a selector that separates them by reading one more fact, the
flat top.  The header comment at psh.c:~2371 still cites that doc.

**Failure scenario.** A later lane reads the doc from psh.c, concludes that
the shipped selector cannot be right, and reverts or "fixes" it.

Fix: put one dated line at the top of that doc saying Pair A is resolved by
flatness plus the clip edge's alignment, with a pointer to
`docs/lanes/wbuf31fix/NOTES.md`.  That follows the rule to correct the premise
where it is read.  This is LOW because it is documentation only.

### LOW 3: `features()` can crash with TypeError in `--selectors`

`r0 = _first_span(wide)[0] if wide else r`: `_first_span` returns `None` when
no row in its four-row search has a covered span.  `wide` can be non-empty
while that is true, for example a sliver thinner than a pixel between centres.
Then `None[0]` raises TypeError.

A second difference: `_span` does not handle a horizontal edge lying exactly
on a row centre, and the shader's span loop does (`a.y == yc && b.y == yc`).
So `features()` can pick a different first row from the shader for a
flat-edged triangle whose edge is exactly on `r + 0.5`.

**Failure scenario.** `--selectors` is run with an extra `PRIMS` entry holding
a sub-pixel sliver, and it aborts before printing the table.  No current
capture reaches this path, and the shipped shader is unaffected.  LOW: it is
an offline tool.
