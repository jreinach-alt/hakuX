# Audit pass 1: PR #364, lane.zrtz272 (round-toward-zero fixed-function screen z, #272 #275)

Head audited: `37e68c70b1`. Auditor: job.cloud, 2026-09-26.

**Result: no HIGH, no MEDIUM, four LOW.** Next state: `needs-audit-2`.

## What the diff does

`hw/xbox/nv2a/pgraph/glsl/vsh-ff.c` is the only code change. It adds GLSL
helpers to the FF vertex header (`ffRtz`, `ffTwoProd`, `ffMulRtz`,
`ffAddRtz`, `ffDotRtz`, `ffAboveOne`, `ffRcpRtz`, `ffScreenZ`). It also adds
one body statement after the `carry` block: when `clipRange.y <= 2^24` and
`tPosition` is finite, `vtxPos.z = ffScreenZ(tPosition)`. `oPos`,
`vtxPos.xyw` and the GL clip z are unchanged. The rest of the diff is lane
notes, `check_rtz.py` and three prediction files.

## What I checked, and how

1. **Column convention.** `oPos = tPosition * compositeMat` gives
   `oPos[j] = dot(tPosition, cm[j])`, and the existing non-finite path already
   uses `cm[j]` that way. `ffScreenZ` takes z from `cm[2]` and w from `cm[3]`,
   so it computes the same quantity as the `oPos.z / oPos.w` it replaces.
   `GLSL_C_MAT4` builds the matrix from four consecutive constants as columns.
2. **Arithmetic is what it claims.** I wrote a float32 model of the helpers
   (numpy, one rounding per statement, no FMA) and compared it with exact
   rational round-toward-zero. Over 100,000 random pairs with exponents
   2^-40..2^40, I found **0 mismatches** each for `ffMulRtz`, `ffAddRtz` (and
   another 100,000 near-cancelling sums) and `ffRcpRtz`. `ffRcpRtz(1) = 1`
   exactly, as the comment requires. The model's premise is that `precise`
   prevents FMA contraction of the Dekker and Knuth sequences. That holds in
   SPIR-V (NoContraction), and `psh.c` and `geom.c` already rely on it.
3. **Range guards.** `w` goes through `clampAwayZeroInf` (±[2^-64, 2^64])
   before `ffRcpRtz`, so it is never 0 or inf. The Veltkamp split (4097·a)
   cannot overflow under `ffMulRtz`'s `< 1e34` guard. An overflowing product
   gives `r = inf`, and `ffRtz` passes it through unchanged.
4. **Gate.** `clipRange.y` (`common.c:pgraph_glsl_set_clip_range_uniform_value`)
   is 0xFFFF for Z16 fixed, 511.9375 for Z16 float, 0xFFFFFF or 0x1000000 for
   Z24 fixed, and `f24_max` for Z24 float. The `<= 16777216.0` gate therefore
   excludes F24 only, and it includes the stored-as-float Z24 case (0x1000000),
   as the comment says. The gate is a uniform, so the shader key does not
   change.
5. **Compile.** I ran `docs/lanes/wparamcode223/vshemit/build.sh`, then
   `python3 docs/lanes/zrtz272/check_rtz.py` on this head. All 8 variants
   compiled (skinning × lighting × vulkan/opengl), the helpers and statement
   are present in each, and all 3 mutants were rejected: `ALL OK`.
6. **Consumers of `vtxPos.z`.** Only the geometry shader passes it through
   (`vtxPos0..2`), and `psh.c` uses it for the depth plane. W-buffering reads
   `vtxPos.w`, which the hunk does not touch.
7. **Merge.** `git merge-tree` against `origin/master` (146 commits ahead of
   this branch's base) is clean.
8. **Evidence.** Arm 3 (`zrtz272-rtz3.json`) PASS 1,253/1,253 on the same
   binaries as arm 2. Removing the arm-2 guard on `X_O1RGB5_Add_SrcA_DstA` /
   `R5G6B5_Add_SrcA_DstA` is justified in the PR body: the test disables the
   depth test, the block flips within one apk, and the image matches builds
   without this hunk. This is dropping a guard, not fitting one to the data,
   because the draw cannot read vertex z.

## Findings

### LOW-1: dead range guard in `ffRcpRtz`
`if (aw > 1e-34 && aw < 1e34)` is always true, because `ffScreenZ` is its
only caller and it passes a `clampAwayZeroInf`'d w (|w| in [2^-64, 2^64]).
Scenario: none today. If a future caller passes an unclamped w outside that
range, the reciprocal silently falls back to round-to-nearest. Either drop
the guard or comment that it exists for other callers.

### LOW-2: `ffRtz` steps on a NaN error term
`e != 0.0` is true for NaN and `(e < 0.0)` is false. So with `r < 0` and a
NaN `e`, `ffRtz` moves `r` one ulp toward zero. Scenario: a composite matrix
entry of ±inf with a finite `tPosition`. `ffMulRtz` returns `a*b` for it,
and a later `ffAddRtz` can produce a finite `s` with a NaN `e` only if one
operand is already non-finite, and then `s` is non-finite too. So I could
not build a finite-output case. The fix is `!isnan(e)` in the condition, or
a note that the case is unreachable.

### LOW-3: per-vertex cost is unmeasured
On every non-F24 FF draw, `ffScreenZ` runs 8 `ffTwoProd` calls for the dot
products, 1 for the final multiply and up to 6 for the reciprocal
correction: roughly 15 × 17 flops per vertex. The gate is dynamically
uniform, so F24 pays nothing. Scenario: a vertex-bound FF title slows down
on a handheld. No arm measured fps, and the goldens cannot. This is a
bounded cost with no correctness impact.

### LOW-4: superseded predictions remain registered
`zrtz272-rtz.json` (arm 1, FAIL) and `zrtz272-rtz2.json` (arm 2, FAIL)
remain in `docs/testing/predictions/` next to `zrtz272-rtz3.json`. The PR
body names arm 3 as the prediction of record. Scenario: a reader or tool
that treats every registered file for #272 as live sees two FAILs. The PR
already carries `verified`, so the arms job has resolved this. The files
are history, not a defect.
