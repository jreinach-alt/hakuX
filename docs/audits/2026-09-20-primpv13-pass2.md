## The pass-1 scenarios, re-tested

### MEDIUM 1 — `cylWrap()` reads `gl_in[0]`, so the enumeration was incomplete → **CLOSED**

Pass 1's scenario was that `prim_rewrite.c`'s comment — the entire safety
argument for the change — asserts an enumeration of index-0 readers that omits
a fourth, so a reader takes "nothing downstream reads index 0" as settled.

`prim_rewrite.c:122-165` now asks the question and answers it with three
numbered readers, and `(3)` is `cylWrap`, named as a literal `[0]` rather than
a `provoking_index`, in both `emit_vertex()` and `emit_vertex_fs()`, in both
the GL and widened Vulkan paths, and independent of the shade mode. The
direction is stated and it is **correct**: I checked `emit_tri_pv()` rather
than taking it — `p == c` emits `(c, a, b)`, so a fan triangle `(hub, v1, v2)`
with `pv = v2` put `v2` at index 0 and with `pv = v1` put `v1` there, both rim
vertices varying per triangle; unrotated, index 0 is the hub, one per fan.
The same paragraph appears in the prediction and in `NOTES.md:291-300`, so it
survives the PR body's deletion at merge.

The "tolerated, not measured" claim is **stronger than the remediation argued
and I confirmed it independently**, because the prediction only justified it
for `Shade_model` and `Line width` while the disc has five more suites. Over
`~/nxdk_pgraph_tests/src/tests/`: exactly three files draw a `TRIANGLE_FAN`
under a LINE polygon mode — `edge_flag_tests.cpp`, `line_width_tests.cpp`,
`shade_model_tests.cpp` — and **none of the three contains `TEXTURE_ADDRESS`,
`WRAP`, or any texture-stage call at all**; the only files that set a WRAP
address mode are `texture_border_tests.cpp` and `texture_wrap_mode_tests.cpp`,
neither of which draws a line-mode fan and neither of which is in the disc.
So `state->cylinder_wrap[i]` is zero on every fan capture the arm will take,
and the disclosure is accurate rather than merely cautious.

`calc_triz` and the widened path's flat block are both re-checked in the same
comment and both hold: the flat block is inside `if (state->smooth_shading)
{...} else {...}`'s else arm, reached only under FLAT shading, where the
predicate's first term keeps the rotation.

## NEW MEDIUM 1 — the `+12 / +10` correction reached four places that state the tool's output and not six

`f2433a8909` changed what `line_priority.py` prints: `225,558 → 225,570` under
`--extent-rule` and `198,880 → 198,890` under the default. It propagated that
to the registered prediction, the PR body, `line_priority.py`'s own docstring,
and two of the three tables in `NOTES.md` — each of the two with an explicit
`SUPERSEDED`-style note, which is the right pattern and is why the omissions
stand out. Three statements of the same numbers were left asserting the old
ones, and one of them is inside the prediction that was re-registered to fix
exactly this.

**(a) `docs/testing/line_priority_arms.py:34-38`** — the docstring of the tool
the prediction names as *the judged command*:

```
The default is left alone rather than flipped, so that arms already judged
against it (#13's geom.c arm, 198,880 decisive px) stay reproducible.  But a
new arm should pass `--extent-rule` ... over widths 8-63.875 the perpendicular
set is 198,880 px and the derived-extent set is 225,558
```

Both figures are present-tense claims about what this tool computes today, and
the same commit made both false by +10 and +12. The first is worse than stale:
it is the stated *reason* for a design decision — leaving the default alone so
#13's geom.c arm stays reproducible — and re-running that arm against the
default on this tip gives 198,890, not the 198,880 the sentence promises.

**(b) `docs/lanes/primpv13/NOTES.md:185-195`**, the lane's leg table, which is
where a reader of the merged tree goes after the PR body is gone:

| class | n (recorded) | n (this tip) | |
|---|---:|---:|---|
| nine others | 189,913 | **189,925** | leg 3 |
| **ALL** | **225,558** | **225,570** | advisory |

and the prose beneath it, "ALL 198,880 px 95.85% -> 99.93%", now 198,890. The
tables immediately above (`:112-124`) and below (`:146-174`) each carry a
blockquote saying the totals moved; this one, between them, does not — so a
reader who checks the neighbours concludes this table was reviewed and found
unaffected.

**(c) the registered prediction, calibration 1**, which reads:

> `line_priority.py --rules --extent-rule …` gives **225,570** decisive pixels
> … That is **exactly the figure and the phrasing** prim_rewrite.c's own file
> comment carries from #13's original derivation — same instrument, same
> window, **same answer**.

`prim_rewrite.c:424` carries `100.00% of 225,558 decisive pixels`, and
`geom.c:184` carries `225,558` too. The figures differ by 12, so the identity
the sentence asserts — offered as one of three calibrations "none of them
fitted" — is no longer an identity. The cause is documented two sections
earlier in the same file, so a careful reader reconciles it; the sentence still
claims exactness it does not have.

**Failure scenario.** MEDIUM 3's remediation appoints a hand-judge who runs
`line_priority_arms.py --extent-rule --min-width 8 --max-width 63.875` over the
two arms *before* `fold-ready` goes on. That judge reads the tool's own
docstring (`the derived-extent set is 225,558`), then the lane's leg table
(`nine others 189,913`, `ALL 225,558`), then gets 189,925 and 225,570 from the
run. Leg 3's claim is that *"the nine other classes are UNCHANGED and `moved`
is 0 on each one"* — so a 12-pixel discrepancy in the size of exactly that
group is the shape of the thing leg 3 forbids, arriving with no note beside it
and with the two adjacent tables explicitly annotated as *having* moved. Either
the judge spends the session separating an instrument change from a device
change, or they record leg 3 as failed. The one judge who is safe is the one
who reads only the registered prediction's per-class list, which is correct —
but the prediction is also the file that points them at `NOTES.md` and at the
tool.

**Blast radius, stated so this is not escalated past what it is:** twelve
pixels and ten pixels, in a class that reads 100.00% under every rule before
and after. No percentage moves, no code is affected, no leg's *verdict*
changes, and the prediction's own per-class numbers for leg 3 are right. This
is a MEDIUM because three shipped artifacts state a false number about the
instrument, not because any measurement is wrong.

**Remediation.** Three sentence-edits — `line_priority_arms.py:34-38` to
198,890 / 225,570 (and say plainly that the default's totals moved by +10 in
this lane's LOW-2 fix, so #13's geom.c arm re-runs at 198,890 with every
percentage unchanged); `NOTES.md:185-195` to 189,925 / 225,570 / 198,890, or a
blockquote matching the two beside it; and calibration 1 in the prediction to
say the figure is `225,570` **against the 225,558 `prim_rewrite.c:424` and
`geom.c:184` carry from #13's derivation, the 12-px difference being this
lane's own LOW-2 correction** — which is the honest version of the calibration
and is still a calibration. **Do this before the arm fires.** The arms job runs
every registered prediction whose refs are live, and `40ca2bcb22` is live now;
once a verdict exists, editing the prediction is post-hoc and `ab_compare`'s
tamper guard is the least of the problems. It is free this minute and
impossible an hour after.
