## Per-finding verification

### LOW-1: comments name INTR, not PATT_COLOR0: stands, harmless at run time

The comments at `pgraph.c:1075-1082` and `vk/surface.c:933-934` are unchanged.
They are comments, and there is no run-time scenario. The exemption they
describe still covers PATT_COLOR0: `pgraph_read` settles only for
`NV_PGRAPH_RDI_DATA` and `0x700` (`pgraph.c:1083-1084`), so the measured
register is inside the exemption.

The narrowing risk pass 1 named stays open until the comments are corrected.
It would take a future edit that trusts them. **Recommended follow-up:**
name PATT_COLOR0 in both comments, in any later touch of these files.

### LOW-2: release assumes the lock is held: still unreachable

The release is still gated on `qemu_thread_is_self(&d->pfifo.thread)`
(`vk/surface.c:4673-4674`), with no owner check (`pgraph.h:420-426`). I
re-enumerated the `surface_update` callers on this head:

- `pgraph.c` has twelve method handlers, all of them under `pgraph_method`'s
  lock.
- `pfifo.c:1800` is the diag flip path, which holds the lock.
- `vk/blit.c:446` and `:861` are reached from methods.
- `vk/draw.c:1260` and `:7242` are draw methods.

The set is the one pass 1 checked. No PFIFO-thread path reaches the release
without the lock, so the unlock-of-an-unowned-mutex scenario cannot occur on
this head.

### LOW-3: `lock474_log` `snprintf` accumulation: still bounded

`pgraph.c:1013-1019` is unchanged. A worst-case entry is
`" r5=0x" + 4 hex + ":" + 10-digit %u + ":" + ms`, about 35 characters for
any wait under about 10^9 ms. Six entries come to about 210 bytes against the
256-byte buffer. The counters reset each log interval
(`memset(&lock474, ...)`), and the code is perf builds only. Truncation, and
so the `size_t` wrap, cannot occur.

### LOW-4: the exemption is "all but two" and the invariant is not recorded: no scenario

The exemption and its comment are unchanged. Pass 1 found no failure
scenario, and on an identical tree there is still none. The two methods it
named (`SET_CONTROL0` at `pgraph.c:2875`, and the diag FLIP_INCREMENT_WRITE)
still write on one side of `surface_update` only. **Recommended follow-up:**
record the one-side invariant beside the exemption.
