## The eight pass-1 findings, each verified closed

### H1 — `line_clip_lerp()`'s `z` — **CLOSED**

`geom.c:356` is now `float z = mix(pa.z * ia, pb.z * ib, t) * w;`. `pa.z * ia`
is the endpoint's window-space depth, the mix is taken at the screen fraction
`tl` the caller passes, and multiplying by `w` puts it back in clip space, so
`z/w` at the cut point is `mix(za/wa, zb/wb, t)` — what the rasteriser
interpolates across the parallelogram this vertex replaces.

Pass 1's scenario (`wa = 1, wb = 4`, NDC depths 0.2 and 0.8) cannot occur: run
here, `line_cap_phase.py --depth` reproduces the audit's own arithmetic and
reports

```
75 cases.  shipped worst |error| 1.11e-16, mutant worst |error| 0.583
shipped expression reproduces the parallelogram's depth: PASS
the pre-remediation expression trips this check: PASS
```

The mutant lives inside the check and the check reports FAIL *about itself* if
the old expression does not trip it, so this is not a green that discriminates
nothing — I confirmed the second line is a real leg by reading `depth_check()`,
not only by seeing PASS.

### H2 — the flat arm pinning six interpolated varyings to `i0` — **CLOSED**

`vtxFog`, `vtxT0..T3` and `vtxPointSize` are now emitted from a single
`mstring_append_fmt()` **below** both shade-mode arms (`geom.c:501-509`), and
only `vtxD0/D1/B0/B1` remain inside them. That matches the qualifier table I
re-read at `glsl/common.c:56-71`: `qualifier_s` (shade-mode-dependent) on
`vtxD*`/`vtxB*`, `smooth_s` unconditionally on `vtxFog`, `vtxT0..T3` and
`vtxPointSize`.

Verified on the emitted shader, not the generator. `lines_flat_vk` from
`geom_dump` now reads

```
  vtxD0 = v_vtxD0[0];   …   vtxB1 = v_vtxB1[0];
  vtxFog = mix(v_vtxFog[i0], v_vtxFog[i1], t);
  vtxT0 = mix(v_vtxT0[i0], v_vtxT0[i1], t);   … vtxT3 …
  vtxPointSize = mix(v_vtxPointSize[i0], v_vtxPointSize[i1], t);
```

so the flat-shaded textured wide line of pass 1's scenario gets the cut
vertex's own texcoord rather than the far endpoint's. The `cylWrap()` half is
closed too: `tex_lerp[]` is now referenced from the common block, and
`lines_smooth_zpersp_cylwrap_vk` emits
`vtxT0 = mix(cylWrap(v_vtxT0[0], v_vtxT0[i0], …), cylWrap(v_vtxT0[0],
v_vtxT0[i1], …), t)` — the two adjusted values interpolated, which is what the
rasteriser does between two adjusted corners. The 320-byte `tex_lerp[]` buffer
is not truncated at its longest expansion (~175 chars).

### M1 — `vtxFogSpecial` moving with the clip — **CLOSED**

`emit_vertex()` is generated as `emit_vertex_fs(int index, int fs, …)` when
`widen_lines`, with `vtxFogSpecial = v_vtxFogSpecial[fs]`, and every call in
the widened path passes `fs = i0`: both early-outs in `emit_line_vertex()`
(`geom.c:474, :478`) and the interpolated path's own
`vtxFogSpecial = v_vtxFogSpecial[i0]` (`:509`). One footprint therefore carries
one value on every vertex, so no output convention can observe which vertex
provokes, and pass 1's mirror-case scenario cannot fire.

Two things I checked rather than accepted:

* **The rename cannot leave a stray three-argument call.** When `widen_lines`
  is set, the only bodies generated are `emit_line(0, 1, 0.0)` and the three
  `emit_line()` calls of `POLY_MODE_LINE`; the `emit_vertex(…)` call sites at
  `geom.c:145-147` and `:202-206` are `POLY_MODE_FILL` and `POLY_MODE_POINT`,
  and `widen_lines` (`:124-127`) requires `PRIM_TYPE_LINES` or
  `POLY_MODE_LINE`. All six Vulkan cases compile (below), which is the check
  that would have caught it anyway.
* **The comment's claim about the convention is true.** Nothing under
  `hw/xbox/nv2a/pgraph/vk/` enables `VK_EXT_provoking_vertex`; every
  `last_provoking` in `vk/draw.c` (`:5078`, `:5408`, `:5728`, `:5856`, `:7465`)
  feeds `PrimAssemblyState`, and `prim_rewrite.c:81` rewrites a `LINES` draw
  exactly when `last_provoking && flat_shading`. So the pipeline convention is
  first-vertex and `gl_in[0]` is the guest's provoking vertex, as written.

### The defect the remediation found on its own — **verified correct**

`cap_clip()`'s `S[nq] = (T[i] == T[j]) ? T[i] : mix(T[i], T[j], f);` is right
and is not a float-equality trap. `T` starts as exactly `0.0`/`1.0`; the only
non-endpoint value a first pass can introduce comes from cutting a *long* edge,
whose two ends have different `T`, so the two branches never disagree about
which case they are in. On a short cap edge the exact endpoint parameter is
taken and the `tl >= 1.0` early-out fires as intended.

## HIGH

### N1 — the clip is not inert below `w = 24`; it bites on hundreds of narrow-line edges, and the device scored 8 of them worse

`geom.c:719` tells the reader: *"It is inert below w = 24, where E/2 - w/2 is
under a pixel."* `emit_line_vertex()`'s comment (`:428-433`) adds that the
unclipped four-corner case "emits exactly what it emitted before, bit for bit".
Both are true of the *pixels the offline model scores* and false of *the
geometry the device is handed*.

`E/2 - w/2` being under a pixel does not stop the clip biting: the bounds are
`floor(m_min - w/2)` and `ceil(m_max + w/2) + 1`, arbitrary reals rounded to
integers, so an overhang of a tenth of a pixel crosses one whenever the corner
lands near it. Counting how many of each capture's 57 edges come back from
`shader_poly()` with more than four vertices at the shipped 1/256 tie:

| capture | w | edges clipped (of 57) | deepest sliver (px) |
|---|---:|---:|---:|
| `Line_0000.5` | 0.625 | 3 | 0.005 |
| `Line_0001.0` | 1.000 | 9 | 0.020 |
| `Line_0004.0` | 4.000 | 17 | 0.114 |
| `Line_0008.0` | 8.000 | 18 | 0.232 |
| `Line_0013.0` | 13.000 | 11 | 0.301 |
| `Line_0016.0` | 16.000 | 20 | 0.468 |
| `Line_0024.0` | 24.000 | 25 | 0.704 |
| `Line_0063.7` | 63.875 | 32 | 1.818 |

Every capture from `w = 0.625` up is clipped on between 3 and 20 edges before
`w` reaches 24. Below 24 the sliver removed is under half a pixel, so **no
pixel centre changes side in float64** — which is why `--rivals`, `--controls`
and `--shader` all report the change as inert there, and why I could reproduce
that: rasterising the clipped and unclipped polygons against the goldens
capture by capture, the first row that moves at all is `Line_0024.0`.

The device does not work in float64. It computes the cut fraction
`f = da / (da - db)` in float32 from a `da` that is a sliver depth, snaps every
emitted vertex to 1/256 of a pixel, and then decides centre membership. A
centre sitting a thousandth of a pixel inside a cut edge goes one way in the
model and the other on silicon.

**Failure scenario, already measured.** `[job.arms] VERDICT: FAIL` on this PR,
`a_ref 2e1c5790aa` (master) against `b_ref 9fdc6b5d70` (this branch), one run
each, `Line_width`:

| worse | w | Δ | | better | w | Δ |
|---|---:|---:|---|---|---:|---:|
| `Line_0004.0` | 4 | +1 | | `Line_0001.0` | 1 | −1 |
| `Line_0006.0` | 6 | +2 | | `Line_0008.0` | 8 | −1 |
| `Line_0007.0` | 7 | +2 | | `Line_0011.0` | 11 | −1 |
| `Line_0009.0` | 9 | +1 | | `Line_0015.0` | 15 | −5 |
| `Line_0010.0` | 10 | +2 | | `Line_0016.0` | 16 | −1 |
| `Line_0012.0` | 12 | +5 | | | | |
| `Line_0013.0` | 13 | +9 | | | | |
| `Line_0014.0` | 14 | +1 | | | | |

Thirteen scored captures below `w = 24` moved, eight of them away from the
goldens, where all three of this lane's instruments say not one pixel can
change. `Line_0064.0` through `.7` and `Line_FFFFFFFF` each moved
`1,402 → 1,401` as well — the same value, the same direction, nine captures at
once, which is not the shape of a single-run flake. The prediction's own
machine-read leg was `expect_counts: {"worse": 0}`, and it failed; the PR
carries `regressed`; nothing on the PR has answered it.

This is the same failure pass 1 raised H1 for, one level up: the comment tells
the next reader the change cannot reach narrow lines, so a narrow-line
regression will not be traced here — and eight of them are already on the
board.

**Remediation.** Three things, and the first is the cheap one:

1. **Stop the clip biting where it cannot matter.** A cut shallower than the
   device's own vertex quantum can only move pixels by re-quantising an edge
   that was previously exact. Skipping `cap_clip()` on a plane the polygon
   violates by less than one quantum (`lineTieBias` is already in the push
   constant) leaves the `w >= 24` result untouched — the deepest sliver there
   is 0.70 px and up — and restores the bit-for-bit claim everywhere below it.
   Whatever threshold is chosen, derive it and say what it is; do not pick 24.
2. **Make an instrument see it.** `shader_poly()` rasterises in double
   precision and never snaps a vertex to the 1/256 grid, so it is blind to
   exactly the class of change the arm measured. Quantising each emitted
   vertex to `lineTieBias` before the coverage test — and reporting the bite
   count per capture, which is the number above — would have caught this
   offline. `--depth` is the model for how to do this: an explicit check with
   a mutant inside it.
3. **Re-register and let the arms job re-judge.** The verdict is the gate of
   record for `regressed`, and `arms.sh` clears the label from the verdicts
   rather than by hand. A second pair also settles the residual question of how
   much of the ±1 px is run-to-run: `noise 0` in that verdict is one run per
   arm with nothing to estimate from, not a measured zero.

Correct the two comments either way. If the decision is that the narrow-line
movement is an acceptable price for −391 px at the wide end, that is a
`regression-accepted` argument for the owner on #13, not a comment that says it
did not happen.

## LOW

### N2 — `--controls`' integer-boundary count includes the boundary that cannot separate the two rules

`controls()` counts both `m_min - w/2` and `m_max + w/2` into `ties_int` and
prints the total as "the population that separates tie=ceil from tie=floor1".
Only the high boundary does: `edge_mask()` computes `plo` with `np.floor(...)`
for every `tie` value, and the `tie` switch reaches `phi` alone. Split over the
same captures, the 1,104 is 617 low-side and **487 high-side**. The
conclusion survives — 487 is not zero, so the goldens do select the outward
rounding — but the figure quoted on the PR is 2.3× the population it names.
Count `m_max + w/2` alone, or print both halves.

### N3 — the PR body still asserts the two figures it later retires

The body's appendix says 497 and 412 are retired and "neither reproduces on
this tree". Sixty lines above it, the original text still reads: *"A
centre-sampled `±w/2` band scores 497 px, worse than the 412 px it was meant to
fix."* A reader who stops at the derivation gets the retired number. `geom.c`
and `NOTES.md` were both corrected; the body was not, which is what
`gh pr edit` silently failing on this host looks like — use the REST `PATCH`
through `gh api` and read the body back.
