# Audit pass 1: PR #543 (lane/forza414-c)

PR: #543, "lane.forza414: hunk 5 (covering clear drops the upload) and the dirty-draw uniform hash skip (#414, #474)"
Head audited: d433d6af74
Scope: the diff against master: `hw/xbox/nv2a/pgraph/vk/{draw.c,renderer.h,shaders.c,surface.c}`,
three predictions under `docs/testing/predictions/forza414-{clrskip,uhash}-*.json`,
the regenerated `docs/testing/nv2a_index.json`, and `docs/lanes/forza414/NOTES.md`.

Verdict: **no HIGH, no MEDIUM, two LOW. needs-audit-2.**

## What the change does

1. **Hunk 5 (surface.c, draw.c).** In a clearing `pgraph_vk_surface_update`,
   `surface_drop_covered_upload` drops the pending upload of a bound binding
   that the coming clear overwrites whole. It still does the upload's
   bookkeeping: it re-arms the CPU-write watch under `surface_watch_lock`,
   clears `upload_pending`, sets `draw_time` and marks the binding
   `initialized`. It does not copy the VRAM. Because the binding no longer
   uploads, `surface_update_may_defer_downloads` can defer the pending
   downloads instead of forcing a completion.
2. **The coverage rule** moves out of `mark_clear_full` into
   `pgraph_vk_clear_covers_binding`, and the clip-bounding of the clear rect
   into `clear_rect_clipped`. Both callers use it: `mark_clear_full` after the
   clear, and the drop before it. `r->clear_parameter` is now set before the
   update rather than after it.
3. **Uniform hash skip (shaders.c).** A draw with dirty constant or light flags
   no longer hashes the two uniform layouts. It sets `uniform_hashes_stale`,
   and the next clean draw counts as changed whatever its hash is.

## Checked and found sound

- **Every return between the drop and the clear.** Frame skip returns before
  the update, so nothing is dropped. After the update there are two returns.
  "No binding" cannot happen once a binding has been dropped. "Entirely
  outside the clip" runs the same `clear_rect_clipped` that
  `clear_covers_binding` returned false on, so no binding was dropped either.
  Every binding that is dropped is therefore cleared in the same method.
- **The rect the clear writes is at least the rect the rule tested.** Both
  paths (inline `vkCmdClearAttachments` and pipeline) clamp the clip-bounded
  rect to `binding->width-1`, then apply the AA factor and then the scale
  factor. The rule compares the unclamped AA-scaled rect against `b->width`,
  which is in AA units (`populate_surface_binding_target` applies the factor).
  `!x && !y` rules out the unscaled `clip_x`/`clip_y` term that the linear
  width includes. When a colour binding is bound, the zeta binding is forced
  to the colour binding's width and height (`EVICT_WHY_ZDIM`). So the
  zeta clear clamped to the colour binding's size still covers zeta whole. A
  compatible colour binding that is *larger* than the target fails the
  `w >= b->width` test, so it keeps its upload. That is the conservative
  direction.
- **Channel and aspect coverage.** A colour binding needs all four channel
  bits. A partial clear takes the blend-constant quad path, and the rule
  rejects it. A zeta binding needs Z, plus stencil when the host format has a
  stencil aspect. Both clear paths build the same aspect mask from the same
  test.
- **Image layout and load op.** The layout is set at image creation (`UNDEFINED`
  → `GENERAL` / `DEPTH_STENCIL_ATTACHMENT_OPTIMAL`), not by the upload, so a
  dropped upload leaves the layout valid. With `initialized = true`, the
  render pass picks `LOAD` on undefined texels. The clear then overwrites all
  of them, as the comment says.
- **Upload bookkeeping.** The tail of `pgraph_vk_upload_surface_data` does
  nothing else a later reader depends on: no dirty-bitmap reset, and no
  generation or `vram_newer` update. The drop's lock sequence mirrors the
  upload's head.
- **Watch gap check versus deferred downloads.** The drop now hashes VRAM
  while downloads to that range may still be pending. The gap check
  `surface_watch_rearmed` might then see a changed hash. But it takes
  `pgraph_lock_settled`, which waits out a lock released for a fence, so it
  runs only after the clear method has returned. By then
  `pgraph_vk_set_surface_dirty` has set `draw_dirty`, and the change is
  counted as lost rather than setting `upload_pending` over the clear.
- **`clear_parameter` moved earlier.** It is read only by the clear-pipeline
  key and state (`draw.c:1860-1974`), under `pg->clearing`. Setting it
  before the update means that any clear pipeline built during the update
  sees the current parameter rather than the previous clear's.
- **Uniform skip.** `last_*_uniform_hash` has no reader other than the
  clean-path compare. The skip trades "the next clean draw with unchanged
  content skips the upload" for "uploads once". That is correct by
  construction. The save/restore of `uniforms_changed` at `draw.c:5456/5710`
  does not interact: a nested dirty call leaves the flag stale, which can
  only force an extra upload.
- **Post-arm code.** The arms ran on B = 79f0102478. The only lane code
  commit after it is 24f56f1981, and it only makes `clear_rect_clipped` read
  into locals. It is equivalent by reading. The other hw/ deltas since B came
  from master merges (#413's pipeline counters and a diag-dump completion).
- **Index.** `nv2a_index.json` changes only by the removed FIXME entry
  (draw.c:7285) and line shifts, as expected for the code move.

## Findings

### LOW 1: `uniform_hashes_stale` is file-static; the hashes it qualifies are per-renderer

`shaders.c:1352`. The flag describes `r->last_vsh_uniform_hash` and
`r->last_psh_uniform_hash`, but it lives outside `PGRAPHVkState`. A renderer
torn down and rebuilt (for example a renderer switch or reinit) starts with
zeroed hashes and whatever flag the old one left. Failure scenario: none that
renders wrong. With the flag false, the first clean draw compares against 0,
which a real hash almost never equals, so it uploads anyway. This is a
quality point: a field next to the two hashes would keep the three in one
place.

### LOW 2: the arms did not run the head's code

The verdicts attached to the three predictions are for 79f0102478. The head
adds 24f56f1981 (a refactor of `clear_rect_clipped` into locals, checked
equivalent above) and master merges. Failure scenario: only if the refactor
changed a value. Reading it, it does not: the same four GET_MASKs, the same
clip, and the same return. Pass 2 can confirm this with the line-by-line
comparison. No new arm is needed.
