## HIGH

### H1 — `translate-all.c:445` — the recycle path `siglongjmp`s into a returned stack frame

`tb_lock_page1()` has a contention path. When the two pages must be locked out
of index order and the second page's spinlock is already held, it cannot block
without risking deadlock, so it drops page 0, re-takes both in the right order,
and restarts translation:

```c
    /* Incorrect locking order, we cannot block lest we deadlock. */
    if (!page_trylock(pd1)) {
        return;
    }
    /*
     * Drop the lock on page0 and get both page locks in the right order.
     * Restart translation via longjmp.
     */
    pd0 = page_find_alloc(pindex0, false);
    page_unlock(pd0);
    page_lock(pd1);
    page_lock(pd0);
    siglongjmp(tcg_ctx->jmp_trans, -3);
```
— `tb-maint.c:580-593`

`tcg_ctx->jmp_trans` is armed in exactly two places: `setjmp_gen_code()`
(`translate-all.c:263`) and `tb_gen_superblock()` (`:1166`). Upstream's only
caller of `tb_lock_page1()` is `translator.c:353`, which runs inside
`translate_code()` inside `setjmp_gen_code()` — the jump target is a live frame
and `setjmp_gen_code` returns `-3`, which `:584`'s switch turns into
`goto restart_translate`.

The fork's recycle path calls it from a different place entirely:

```c
        recycled = true;                     /* translate-all.c:415-450 */
        ...
        if (phys_pc != -1) {
            tb_lock_page0(phys_pc);
            if (tb->page_addr[1] != -1) {
                tb_lock_page1(phys_pc, tb->page_addr[1]);   /* :445 */
            }
        }
        goto recycle_tb;
```

This block runs near the *top* of `tb_gen_code()`, before `setjmp_gen_code()`
is reached on this call — and the recycle path never reaches it at all, that
being the point of recycling. So `tcg_ctx->jmp_trans` still holds the context
of some *earlier* `tb_gen_code()` call whose frame has long since returned.
`siglongjmp` into it is undefined behaviour: in practice a jump through a stale
frame pointer, with two page spinlocks held.

Introduced by `255d110496` (xemu, 2025-01-06, *accel/tcg: Lock tb page when
recycling for link*), which added the locking without the setjmp context the
locking depends on.

**Scenario.** All three must hold:

1. the recycled TB spans two pages (`tb->page_addr[1] != -1`) — ordinary;
2. the second page's *physical* index is lower than the first's — ordinary
   under scattered guest paging, and precisely the case the out-of-order branch
   exists to serve;
3. another thread holds that page's spinlock at that instant.

(3) is the interesting one, and it is **not** a second vCPU.
`assert_memory_lock()` is empty in softmmu (`internal-common.h:181`), and
`do_tb_phys_invalidate` is reachable from `system/physmem.c:3297`
`invalidate_and_set_dirty` → `tb_invalidate_phys_range` → `page_collection_lock`
on whatever thread performs a device write. On Xbox that is IDE/DVD DMA — the
overlay load that `2af6def68a` names as its own correctness payoff.
`tb_invalidate_phys_range_fast`'s own comment (`tb-maint.c:1605`) says it is
called "with iothread mutex not held".

No soak and no test disc can produce this: it needs cross-thread contention on
one specific page at one specific instant, and the corpus is nearly all static
content read by the vCPU. This is the shape the calibration asked for — wrong
outside the cases the goldens exercise, and unreachable by any arm we can run.

`tb_gen_superblock()` has the same defect at `:1156-1158`, where it locks
*before* arming `jmp_trans` at `:1166`. It is dead while
`XBOX_SUPERBLOCK_ENABLED == 0`, and is recorded as L4-equivalent inside H1's
remediation rather than as its own row, because the fix is the same fix.

## MEDIUM

### M1 — `tb-maint.c:1525` — the #73 fix silently broke `ws`, which was correct only by accident

```c
            tbs_seen++;
            if (tb_cflags(tb) & CF_INVALID) {
                hakux_inval_already++;
            } else {
                tbs_live++;
                tbs_overlap += tb_overlaps_written_range(tb, n, start, last);
            }
```
— `:1467-1472`, with a comment that is explicit about *why* the overlap
question is asked only of live blocks: asking it of dead ones "would report 'a
range test would have spared this' for a block that is already dead — which is
how the first run produced `sp_share = 1.000` in every window."

Fifty lines later:

```c
        if (!p->first_tb) {
            hakux_inval_emptied++;
            if (tbs_overlap < tbs_seen) {       /* :1525 */
                hakux_inval_would_survive++;
```

`tbs_overlap` is live-only. `tbs_seen` includes the dead. **Before**
`2af6def68a` that mismatch could not bite, by accident: an already-invalid TB
took `do_tb_phys_invalidate`'s early return *before* `tb_remove()`, so it stayed
on the page list, so `!p->first_tb` was false for any event that visited one.
`em` therefore implied `tbs_seen == tbs_live`, and the comparison was made on a
clean population.

The #73 fix removes exactly that implication. Already-invalid TBs are now
really unlinked, so a page can empty while dead blocks were visited — and every
such block contributes 1 to `tbs_seen` and 0 to `tbs_overlap`.

**Scenario.** Any post-fix run on a page carrying a tier-1-promoted block. The
page empties, `em` fires, and `ws` fires with it — even when every live block
overlapped the written range and the range test would have spared nothing. `ws`
is the counter `profile.c`'s own legend calls "the prize", and it is the number
#68's held arm will be judged on. The bias is one-directional: `ws` over-reports,
crediting the arm with survivals that cannot occur.

Separately, `em` changes population across the fix too, so the six Crimson
Skies soaks of 2026-09-13 are not comparable with any post-fix run on either
counter. `2af6def68a`'s "WHAT THIS COUNTS CHANGED" note (`tb-maint.c:79-95`) is
careful and correct about `ai`, and silent about `em` and `ws`.

### M2 — `cpu-exec.c:192` — tier-1 requests do not sit in their slot, they multiply

`tb_request_tier1_promotion()` takes the first free slot with no check for an
existing request on the same `(pc, cs_base, flags)`, and
`tier1_consume_request()` clears only one matching slot. Three things then
compose:

- the masked `tb_lookup_cmp` (`:546`) keeps the promoted, `CF_INVALID`-carrying
  TB findable and executable, so `tb_gen_code()` is never called for that pc —
  the commit's own "WHAT IS NOT FIXED";
- `tb->tier` is set on the **new** block; the old one keeps `tier == 0` forever;
- `exec_count` is clamped at `threshold * 2` (`:1421`) rather than reset, so
  `tb->exec_count >= g_tier1_threshold` stays true forever.

So the promotion re-fires on every subsequent execution of that block.
`2af6def68a` states this as "the request sits in its slot, and 64 such slots
exist". It does not sit.

**Scenario.** A hot block on a code page the guest never writes — the common
case. It re-requests once per execution up to the budget
(`TIER1_PROMOTION_BUDGET` 8 per `TIER1_BUDGET_RESET_INTERVAL` 100000 loop
iterations), so all 64 slots fill with duplicates of a handful of pcs within
~800k TB executions: seconds. From then on `requests FULL: dropped` and tier-1
promotion is dead for every other block until the next `tb_flush` (which calls
`tier1_clear_all_requests`, `tb-maint.c:960`). The duplicates also make
`tier1_has_pending_request()` permanently true for those pcs, so
`translate-all.c:424` refuses to recycle them from `inv_htable` on every
regeneration, draining one duplicate per full retranslation.

#73's fix *reduces* this — a store to the page now really removes the stranded
block — but only for pages the guest writes. A never-written code page is
unaffected, and that is where hot blocks live.

Nothing measures it: `g_tier1_promotions_total` / `_dropped` are not on the
`hakuX-pages` line, and the `hakuX-tier1` lines are DEBUG and dropped by every
dispatcher logcat spec, which the commit itself says.

### M3 — `tb-maint.c:167` — the impossible row's caveat names the wrong second writer

> One caveat for whoever ports this to a target with more than one vCPU: the
> check reads `hakux_tb_discarded` either side of the call, so a concurrent
> discard on another vCPU would show up here as a violation. The Xbox has one
> CPU and the invalidation path holds the page locks, so there is no second
> writer on this tree.

One vCPU is not the same claim as one writer, and only the former is
established. `assert_memory_lock()` is empty in softmmu; the page locks are
per-page while `hakux_tb_discarded` is a global non-atomic `uint64_t`; and
`do_tb_phys_invalidate` is reachable **today** from a non-vCPU thread via
`invalidate_and_set_dirty` (`system/physmem.c:3297`).

**Scenario.** The vCPU thread is at `:1498-1502`, holding page P's lock, having
read `discarded_before`. An IDE/DVD DMA completion on the main loop
concurrently invalidates a TB on page Q and increments the same global. The
vCPU's post-call read then differs from `discarded_before` even though *its* TB
was not discarded, so a genuine model violation is **not** counted. The failure
direction is the one that reads as healthy: `xx` stays 0 while the model is
broken. The same race tears `visits`, `ai` and `di` themselves, so every ratio
on the line is approximate in a way nothing on the line declares.

### M4 — `tb-maint.c:96` — the fix's registered falsifier is not falsifiable

> ai should fall from ~0.9 of visits to the tier-1 promotion rate. If it does
> not, the #73 model is wrong and the mask did not reach the population it was
> aimed at.

`hakux_inval_already` counts promoted TBs that an invalidation **visits**. That
is bounded above by the number of promotions and has no reason to equal it — a
promoted block on a page the guest never writes is never visited and never
counted. The prediction names a bound as a value.

And the comparison cannot be made at all from the instruments that exist. There
is no promotion counter on the `hakuX-pages` line; `g_tier1_promotions_total`
is emitted only by a `qemu_printf` inside `tier1_maybe_reset_budget`
(`cpu-exec.c:379`) and by `hakuX-tier1` DEBUG lines the specs drop.

**Scenario.** The fold is judged on a soak. `ai/visits` falls from 0.90 to 0.04.
There is nothing on the line to compare 0.04 against, so it reads as
confirmation — and would read as confirmation for 0.30 or 0.001 equally, and
also if the fall came from something else entirely (a change in page-write mix,
or fewer promotions because the 64-slot table saturated, M2). The half of the
impossible-row model that `2af6def68a` deliberately dropped was moved onto this
counter. It did not survive the move.

### M5 — `cpu-exec.c:605` — `inv_htable` has no eviction path, and each stale entry costs a full guest-memory hash

Entries enter `tb_ctx.inv_htable` at `tb-maint.c:1155` for every discarded TB.
They leave on a successful recycle (`translate-all.c:440`), on the pending-tier-1
drop (`:430`), or on `tb_flush`. Nothing else.

An entry whose guest bytes have since changed can never be recycled —
`inv_tb_lookup_cmp` requires `tb->ihash` to equal a hash recomputed over
*current* memory — so it stays. `ihash` is not part of the qht bucket hash, so
every superseded entry for one `(pc, cflags, page)` key lands in the **same
bucket**, and `inv_tb_lookup_cmp` calls `tb_code_hash_func` once per candidate.
That function reads guest bytes one at a time through `cpu_ldub_code` →
`cpu_ldb_code_mmu`, up to ~4000 of them.

**Scenario.** A page the guest rewrites repeatedly — self-modifying or
overlay-loaded code, which is exactly the #73/#68 workload. Each distinct byte
content ever translated leaves one permanently unrecyclable entry in that
bucket. Every later `tb_gen_code` call for that pc walks them all and performs a
full byte-at-a-time guest-memory hash per entry before falling through to
generation. The cost of a translation on a thrashing page therefore grows
linearly in how many times that page has been rewritten since the last
`tb_flush`.

Nothing measures it. The work happens inside `qht_lookup_custom`, before
`hakux_tb_codegen` is incremented, so it is charged to neither calls nor
generations — and the "about five to one" recycle rate quoted at
`translate-all.c:319` does not price it.

### M6 — `hw/xbox/nv2a/pgraph/profile.c:412` — the log line still documents the model the fix abandoned

`tb-maint.c`'s comment and the code were updated by `2af6def68a`. The legend on
the log line — which is what a reader of a soak actually reads — was not:

```c
            /* xx is the impossible row: a visit that was live and was not
             * discarded, or was already invalid and was. Anything but 0 voids
             * every ratio on this line. */
```
— `:412`, and the prose legend at `:352` says the same ("Visits where
live-ness and discard-ness disagreed").

The second clause is now the fix's *intended* behaviour. `tb-maint.c:143-155`
calls it "the entire point": a tier-1-promoted TB is already invalid and is now
really discarded.

**Scenario.** Someone reads a post-fix soak to decide whether #73 landed. The
legend says `xx` counts, among other things, already-invalid TBs that *were*
discarded. They see `xx = 0` and conclude that no already-invalid TB was
discarded — that the fix did not reach its population — which is the exact
opposite of what `xx = 0` now means. The same legend tells them "anything but 0
voids every ratio on this line", so the reading is treated as authoritative.

Outside this lane's territory; routed via the board request, together with the
`em`/`ws` caveat M1 needs in the same legend.

## Verdict on the things this pass was sent to test

### `2af6def68a` — the hash fix itself is **correct**

`tb_link_page()` (`tb-maint.c:1227`) is the only insertion site into
`tb_ctx.htable`; it asserts `!(tb->cflags & CF_INVALID)` and hashes
`tb->cflags` verbatim. `CF_INVALID` therefore cannot be an input to any
insertion hash, `qht_remove` requires the insertion hash, and masking it off at
`:1150` is the right correction. For a **live** TB the mask is a no-op, so the
fix does not disturb the population the old model was built on.

Verified alongside it: the recycle-side removal hash (`translate-all.c:437-440`)
clears `CF_INVALID` before hashing and so agrees with the new insertion hash;
the pending-request drop (`:427-430`) masks it explicitly and also agrees; and
`CF_TIER1` is stripped before `tb_link_page` hashes (`:816`), so the only cflag
that ever differs between link time and invalidate time is `CF_INVALID` itself.

### The restated `hakux_inval_impossible` model **survives**

`live && !discarded` is not a tautology of the patch. For a live TB the two
hashes are computed from identical inputs by construction, so the check does
what it claims — it fires if a live block on a page list is absent from the
table, or if the two hash derivations ever diverge again. This is the shape
audit pass 2 caught last time (an assert implied by its own condition); here it
is genuinely a regression guard on a future divergence, not on the present one.

What does **not** survive is the claim that the dropped half was safely rehomed:
see M4.

### The masked pair — **claims 1 and 3 survive, claim 2 is half-shown**

- **Claim 1, load-bearing for the recycle cache: holds.**
  `tb_htable_lookup_common` computes the bucket hash from `s.cflags`, which is
  `CF_INVALID`-free (`tb_lookup` asserts it; `tb_gen_code` derives it from
  `curr_cflags`), while every entry in `inv_htable` carries `CF_INVALID` by
  construction — `do_tb_phys_invalidate` sets the bit before inserting. Make
  `tb_lookup_cmp` exact and `inv_tb_htable_lookup()` matches nothing, ever.
  Confirmed.
- **Claim 2, "unmasking either one alone is worse than unmasking neither":
  one direction traced, one not.** `tb_lookup_cmp` exact + `tb_cmp` masked is
  as described: the lookup misses, `tb_gen_code` runs, `tb_link_page`'s
  `qht_insert` returns the old `CF_INVALID` TB as `existing_tb`
  (`tb-maint.c:1241-1246`), `translate-all.c:829` throws the fresh block away
  and returns the stale one — on every lookup. Confirmed, and it is worse.
  The other direction I could not reproduce: with `tb_cmp` exact and
  `tb_lookup_cmp` masked, the lookup still finds the promoted TB, so
  `tb_gen_code` is never called for that pc and the dedup never sees the pair;
  `inv_tb_cmp` is unaffected because both operands carry the bit; `qht_remove`
  is pointer-identity. That reads **inert**, not worse. Recorded as a LOW
  against the comment, not against the code.
- **Claim 3, the correctness scenario is closed at its source: holds.** A
  `CF_INVALID` TB found in `htable` is dangerous only if stale, and staleness
  needs a write to its bytes. Both write paths reach
  `tb_invalidate_phys_page_range__locked`: CPU stores via `notdirty_write` /
  `tb_invalidate_phys_range_fast`, and device/DMA writes via
  `invalidate_and_set_dirty` → `tb_invalidate_phys_range`. I could not find a
  third. Post-fix both really remove the block.

**So the decision to leave both masked stands on correctness** — and M2 is its
price, which the commit's own "WHAT IS NOT FIXED" paragraph understates.

## What could not be audited, and why

- **Nothing was built.** Desktop is the known, named gap
  (`libcurl4-openssl-dev` absent, sudo unavailable) — I did not run it and am
  not claiming it. Android was not built either: this pass changed no code
  under `accel/`, and building would have required dirtying a tree that
  `lane.tcginval` holds.
- **Nothing was run on a device.** Every finding above is by reading.
- **H1's reachability is argued, not measured.** Whether Xbox guest paging
  actually produces two-page TBs with descending physical order, and how often
  the iothread holds a page lock the vCPU then wants, needs two counters that do
  not exist. I can show the branch is reachable in principle and that the second
  thread exists; I cannot give a rate. That gap is the finding's, not the
  scenario's — the code is wrong whether or not this corpus hits it.
- **`g_assert(existing == NULL)` at `tb-maint.c:1156` is unresolved.** The #73
  fix newly routes tier-1-promoted TBs into `inv_htable`, so the assert now sees
  a population it never saw. I built four candidate sequences that would put two
  `inv_tb_cmp`-equal TBs in the table at once; every one was blocked, either by
  `ihash` (a superseded translation always differs) or by whole-page
  invalidation removing the incumbent first. **I could not prove it
  unreachable.** Per the standard, a suspicion with no scenario is not a
  finding, so it is recorded here rather than in the JSON — but it is the thing
  I would look at first if this code aborts in the field.
- **`tb_code_hash_func` faulting mid-lookup.** It reads guest memory from inside
  a qht lookup callback, and a fault there would longjmp out of `tb_gen_code`
  with `qemu_thread_jit_write()` unpaired. I believe it cannot fault, because
  `tb_lookup_cmp` has already resolved both pages through `get_page_addr_code`
  before the `ihash` test runs. I could not rule out an exotic path where a
  non-vCPU thread invalidates the TLB entry between the resolve and the read.
  Not filed.
- **`937848c9e7` (#68) was not audited.** It is held pending its arm and is not
  landed code, per the brief. It is worth saying that M1 changes what that arm
  will measure, so the two should be sequenced.
- **No spec exists for the tier-1 mechanism.** M2's remediation is my reading of
  what the code is trying to do from its comments; whether re-promotion on every
  execution was *intended* as a cheap retry is not recorded anywhere. If it was,
  M2 is a design question rather than a defect, and the 64-slot saturation is
  still real either way.
