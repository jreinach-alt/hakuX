## What I checked and found correct, so remediation does not re-derive it

* **Every number in both documents re-runs.** I ran
  `python3 docs/testing/bump_y16_class.py --all` against the committed
  defaults. 22,374 / 1,576 / 0 / 21,472; per-quad 5,340 / 5,398 / 5,336 /
  5,398 in columns 44..102 with 0 outside; `BumpEnvLum_Y16` at 1,576; the
  non-blindness profile 4,872 / 4,770 / 5,880. All exact.
* **The identity claim is the strong one and it holds.** Our `BumpMap_Y16` is
  byte-identical to our `BumpMap_Y8`, `Y8_L`, `AY8`, `AY8_L` and `A8Y8` inside
  the four quads, and the goldens' `Y16` is identical to nothing but its own
  `_L`. It is also derivable from current master rather than from the capture
  alone: SZ_Y16 is `GL_R16` with `{ONE, RED, RED, ONE}`
  (`gl/constants.h:349`, `vk/constants.h:347`), a stored `Y8 * 257` samples to
  exactly `Y8/255`, and `bump_signed` (`psh.c:2100`) does `round(x * 255.0)`,
  which lands on the same byte a Y8 source gives. Every code citation in the
  document is accurate: `psh.c:3045-3046` are the two `append_bump_channel`
  calls for BUMPENVMAP, components 2 and 1, as claimed.
* **The `Y8 * 257` arithmetic is exact in float32, and not only for 82/83.**
  `int(f32(f32(y)/f32(255)) * f32(65535)) == y * 257` for all 256 values of
  `y`, so the byte-replication argument that kills the byte-order and
  channel-assignment rivals is sound as stated and would stay sound for any
  other test's colours.
* **The control is a real control, and its premise checks out.** SZ_A8 is
  `{ONE, ONE, ONE, RED}` (`gl/constants.h:287`), so component 0 — the
  luminance channel `append_bump_channel` reads at `psh.c:3082` — is the same
  `ONE` literal for A8 and for Y16; the two differ in the offset channels
  only. Our `BumpEnvLum_A8` is itself at the 1,576 floor, so the comparison is
  not resting on an unvalidated model of what A8 means.
* **The staleness argument, as far as it goes, is true.** `git diff
  c866527e03 origin/master -- hw/xbox/nv2a/pgraph/glsl/psh.c` contains zero
  occurrences of "bump", and `z-repeat-c866527e03-011-Bump_map` (2026-09-13)
  is the newest `Bump_map` capture set that exists on this host — there are
  six, and no lane could have produced a newer one without a device. See L5
  for what the argument does not cover.
* **The inversion observation is true, and stronger than stated.** I measured
  it independently: in quad g0 b0, every one of the 33 differing columns has
  **100% of its differing pixels swapping red for grey**, and the vertical
  transition rows are bit-identical between the two goldens (column 60: 5, 11,
  16, 21, 26, 32, 37, 42, ... in both). The 15-run decomposition quoted in the
  document is exactly the run structure of the differing-column list the tool
  prints. So "inverted, not displaced" is established.
* **The refutation of "read the filtered value at more than eight bits" is
  sound.** At most half a byte unit is 0.3 texel of 256, ~1/26 of a checker
  cell; a shift that small inverts only those columns whose base phase lies
  within 1/26 of a cell boundary, i.e. ~4% of the band. 56% of the band's
  columns (33 of 59) are inverted. The conclusion holds; only its stated
  reason is loose (see L4).

## MEDIUM

### M1 — the "~200 byte units" lower bound is not derivable from the toggle count

`docs/investigations/bump-y16-class.md:98-106`, repeated at
`docs/lanes/cloud-10/NOTES.md:28-29` and in the PR body.

The document converts "the inversion toggles 30 times" into "at least fifteen
cells, i.e. hardware's Y16 offset sweeps at least ~200 byte units", and then
says "the parity is blind to even multiples of a cell, so the true swing can
only be larger". Neither step survives.

* **The halving is backwards.** Under the document's own model, each parity
  toggle needs the relative cell index to change by an odd number, so ≥ 1
  cell. Thirty toggles bound the *cumulative* movement at ≥ 30 cells ≈ 400
  byte units, not 15 ≈ 200. Nothing in the data licenses dividing by two.
* **Some of those toggles are the base texture's, not hardware's.** Parity
  flips whenever *either* `floor(u·32)` or `floor((u+Δ)·32)` crosses an
  integer. I measured the base checkerboard's own horizontal period in the
  gold `BumpMap_Y8` quad: boundaries at columns 3, 8, 14, 19, 24, 29, 35, 40,
  45, 50, 56, 61, 66, 71, 77 — period 5.29 columns — which contributes ~6
  toggles inside columns 44..77 with Δ held perfectly constant. The derivation
  charges all 30 to hardware.
* **"Can only be larger" is false for the quantity the sentence names.** A
  swing (an excursion, max − min) is not bounded below by a flip count at all:
  a Δ oscillating between two adjacent cells produces arbitrarily many
  toggles with a range of one cell ≈ 13 byte units. Only the cumulative travel
  is bounded, and only under the correction above.

**Failure scenario.** The next lane reads "hardware's offset sweeps at least
~200 byte units" — from the PR body, the investigation and `NOTES.md`, all
three — and uses it as a sieve. A candidate whose excursion is ~40 units is
discarded as too small although the data does not exclude it (it needs
cumulative travel, which oscillation supplies); a candidate with a ~200-unit
excursion is accepted although the monotone reading of the same data demands
~400. The document states this figure as "the size of the thing", so it is the
one number that survives into the next session.

**Remediation.** State which quantity is bounded and derive it once. The
defensible sentence is: 30 parity toggles across columns 44..102, of which ~6
are attributable to the base checkerboard's own 5.29-column period, leave ~24
attributable to Δ, so Δ's *cumulative* movement is ≥ ~24 cells ≈ 320 byte
units, while its *excursion* is bounded below only by one cell ≈ 13 units
without a monotonicity assumption this data does not supply. Then say which
one the rival-sizing argument needs. Making the tool compute the toggle count
and the base period (L2) is what stops the next reader re-deriving it by eye.

### M2 — the tool prints a mechanism that contradicts the document and the data

`docs/testing/bump_y16_class.py:199-203` prints "A whole-column inversion needs
the horizontal offset to move by about half a checker cell", while
`bump-y16-class.md:92-93` says the differing columns' "horizontal checker cell
index differs by an odd number". These are different claims with different
per-toggle costs — about 6.7 byte units against 13.3 — and the tool's is the
one wrong.

Within a column the sampled `u` is essentially constant, so a shift of Δ cells
inverts the whole column exactly when `floor(p + Δ) − floor(p)` is odd. Half a
cell therefore inverts *some* columns (those whose phase `p` is in the upper
half of their cell) and leaves the rest untouched — and it would do so with
exactly the base texture's period, 5.29 columns, and only where that period
exists.

I measured the region where it does not: beyond column ~77 the gold `Y8` quad
has **no horizontal colour transitions at all** along a row (row 20 and row 160
both end their transition list at column 77), so a constant half-cell offset
predicts no alternation whatever in columns 78..102. Five inverted runs are
observed there (82-83, 87-88, 92-93, 96-98, 101-102). A constant offset
difference is excluded by that sub-band, which is a stronger statement than the
document makes and belongs in it.

**Failure scenario.** A reader who runs `--columns` and does not also read the
investigation takes "about half a checker cell" as the minimum offset
movement, gets ~6.7 byte units, and sizes rivals against a figure 30× smaller
than the one the same lane published in the PR body. Both texts ship in this
PR and nothing in either tells the reader which to believe.

**Remediation.** Make the printed prose say what the document says — an odd
number of whole cells — and add the sub-band fact, which is the evidence that
kills the constant-offset reading.

## LOW

### L1 — `--columns` crashes on the capture set a fix would produce

`docs/testing/bump_y16_class.py:191-196`. `nz = np.flatnonzero(p2)` is followed
by `nz.min()` / `nz.max()` with no guard, so a capture whose `BumpMap_Y16`
matches the golden inside quad g0 b0 gets a `ValueError: zero-size array
reduction` instead of "0 px". The loop fifteen lines above (`:181-185`) guards
exactly this case with `nz.min() if len(nz) else -1`, so the intent is clear.
Reachable only when this defect *and* #38's positional floor are both gone in
that quad, which is why it is LOW rather than MEDIUM — but that is the state
the tool exists to recognise.

### L2 — "every number re-runs with `--all`" is not true of the inversion evidence

`bump-y16-class.md:15`, `NOTES.md:11`. `--all` computes and prints the
identity table, the per-quad column profile, the differing-column list and the
control. It does not compute the swap fraction (">95%"), the vertical
transition rows ("4, 10, 15, 20, 25, 31, ..."), the 15-run decomposition, the
toggle count or the cell arithmetic — those are prose. I verified all of them
by hand and they are true, so this is a verifiability defect rather than a
wrong claim: the next reader who tries to re-derive M1 has to rebuild the
instrument. A `--parity` report printing per-column swap fraction, the run
structure, the toggle count and the measured base period would make the
document's load-bearing half re-runnable.

### L3 — the ">95%" figure is below 95% for 15 of the 33 columns

`bump-y16-class.md:88-92`. Measured per-column: the differing pixels swap red
for grey **100%** of the time, but the number of differing pixels per column
runs 152..168 of 168, i.e. 90.5%–100% of the column, and 15 of the 33 columns
are under 95%. The claim is true under one reading of "its pixels" and false
under the other. Say "every differing pixel, 90.5%–100% of each column".

### L4 — the eight-bit rival is refuted by duty cycle, not by "cannot invert"

`bump-y16-class.md:117-124` argues a sub-half-byte shift "cannot invert, let
alone invert a whole column". It can: any nonzero shift inverts whole columns
whose base phase lies within the shift of a cell boundary. The refutation is
sound for the right reason — ~1/26 of a cell inverts ~4% of the band's columns
and 56% are inverted — and it should be written that way, because the
"cannot invert a column" form is the same reasoning error M2 is made of.

### L5 — the currency argument covers one file of the several that moved

`bump-y16-class.md:8-13` and `NOTES.md:3-8` justify a 2026-09-13 capture set
by `psh.c` alone. Between `c866527e03` and `origin/master`, 23 files under
`hw/xbox/nv2a` changed by ~4,800 lines, including `gl/texture.c` (+87, texture
cache invalidation and surface writeback), `gl/surface.c`, `gl/draw.c`,
`gl/shaders.c` and `glsl/common.c`. None of them is obviously in this suite's
path and no newer `Bump_map` capture exists to re-measure against, so this is
not fixable by measuring — it is fixable by saying what was checked. The
document's conclusion does not actually depend on the capture being current
(see the code-side derivation in the correct-findings list above); saying so
is worth one sentence.

### L6 — two small tool blemishes

`bump_y16_class.py:131-132`: the family filter `any(k in n for k in (..., "_A8"))`
also matches `BumpMap_A8R8G8B8` and `BumpMap_A8B8G8R8`, so four non-Y formats
appear in a table headed "the Y family". Harmless, and their rows are
informative, but the header is wrong. `:140-142`: the `if c else -1` arms are
dead — `--cap` has a non-empty default and `capdir` is never falsy — and if
they were ever reached they would print `-1` as a pixel count.

## Verdict

Two MEDIUM, so **`needs-remediation`**. Both live in the same derived
quantity and its explanation; the measurements, the identity finding, the
rival refutations and the control are correct and reproduce exactly, and
remediation should not touch them.
