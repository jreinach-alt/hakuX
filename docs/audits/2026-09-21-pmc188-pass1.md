**0 HIGH. 3 MEDIUM. 6 LOW.**

The diff is +369/−0 across four files: **20 lines of emulator code** (one `case`
in `pmc_read`, 18 of which are comment), a 209-line committed falsifier
(`docs/testing/pmc_enable_selftest.{sh,c}`) and 140 lines of `NOTES.md`.

**The change itself is right and must not be reverted.** `pmc_read` had no case
for `NV_PMC_ENABLE` and fell to `default: r = 0`; silicon reads `0x01110000`;
the case returns it. All three MEDIUMs are about what the tree *says* around
that value, not about the value: the one check this PR ships has a hole I
reproduced, the tree's own gap list will assert the opposite of the tree the
moment this folds, and the "these two facts do not reconcile" framing — which
appears in the emulator source, the PR body and `NOTES.md` — is contradicted by
two other documents in this same repository, in a direction that matters for
the follow-up work #188 asks for.

## What I checked and found correct, so remediation does not re-derive it

* **I ran the falsifier both ways myself.** Green on this tree (8 checks, 0
  failures, exit 0). Red on the parent commit `68a18b35d7^` in a scratch tree —
  `FAIL NV_PMC_ENABLE addr=0x200 got=0x00000000 want=0x01110000`, **8 checks, 1
  failure, exit 1**, the other seven green. The red is one line, for the stated
  reason, not a build error. The red/green table in the PR body and `NOTES.md`
  is accurate as written.
* **`pmc_write` is untouched.** The diff has a single hunk and its `@@` header
  names `uint64_t pmc_read`; `pmc_write` (`pmc.c:109-128`) is byte-identical.
  The lane's `sha256`-of-the-function claim is an honest way to say this.
* **Nothing else in the tree reads this register.** `git grep NV_PMC_ENABLE`
  over `hw/` returns the header declaration (`nv2a_regs.h:72`) and the new case
  and nothing else, so the blast radius of the value change is guest-visible
  only — no internal consumer changes behaviour.
* **The endian rival is already dead, and the next reader will not know that.**
  `0x01110000` byte-swapped is `0x00001101` — bits 0, 8 and 12, which is
  *exactly* the header's `_PFIFO`/`_PGRAPH` pair plus bit 0. That coincidence is
  arresting, and given that this same sweep already produced two retracted
  findings caused by a byte swap, anyone who notices it will stop and re-check.
  It is refuted, and the refutation is in
  `nv2a-probe-pmc-findings.md`: the clean read sweep issued **no writes at
  all**, so `BOOT_1`'s endian switch was never flipped, and `BOOT_0` read
  `0x02A000A3` in that same run as the control. I am recording this here so the
  next reader finds the answer instead of re-deriving it (see L4 for where it
  should also be written down).
* **`0x01110000` needs no cast and no suffix.** It is `int`-representable and
  positive, so the `uint64_t r` assignment cannot sign-extend.
* **`Files:` matches the diff**, the PR is out of draft, `Prediction: none: no
  arm` is correctly reasoned (no golden can see a PMC read), and `NOTES.md` is
  under `docs/lanes/pmc188/`, not the branch root.

## MEDIUM

### M1 — the write-side guard checks the spelling, not the behaviour: `case 0x200:` in `pmc_write` passes green

`docs/testing/pmc_enable_selftest.sh:62`

This PR's stated verification *is* this script: `Prediction: none: no arm. ...
The check is the committed selftest.` Its most load-bearing half is the pair of
guards that refuse a write model, because "writing 0 halted the physical
console" is the reason the write side is deferred. Mutant M1 in the lane's own
table confirms the guard refuses `case NV_PMC_ENABLE:`. It only ever tested that
spelling.

I built the other spelling. Adding to `pmc_write`

```c
    case 0x200:
        d->pmc.pending_interrupts = val;  /* a bogus write model */
        break;
```

produces **`8 checks, 0 failures`, exit 0** — the script reports the tree as
clean while a write model for the halting register sits in it. Neither grep
fires: `^[[:space:]]*case[[:space:]]+NV_PMC_ENABLE[[:space:]]*:` requires the
macro, and the second grep looks for `0x01110000`, which a write case has no
reason to contain.

That is not a hypothetical spelling. Every other arm in `pmc_write` uses the
macro, so a future editor copying the *offset* out of `nv2a_regs.h` or out of a
probe log — where it appears as `0x200` and `0xFD400200` — is the likely way
this lands.

**Remediation.** Match the offset as well as the name, e.g.
`case[[:space:]]*(NV_PMC_ENABLE|0x0*200)[[:space:]]*:`, and add the mutant
above to the table so the guard has been seen to refuse both spellings. Pass 2
can re-run it verbatim.

### M3 — "those two facts do not reconcile" is contradicted by two documents in this tree, and the direction of the contradiction is the part that matters

`hw/xbox/nv2a/pmc.c:69-75`, repeated in the PR body ("Those two facts do not
reconcile") and `docs/lanes/pmc188/NOTES.md:31-36`

The comment beside the constant says the bit semantics are not established
because the header puts `_PFIFO` at bit 8 and `_PGRAPH` at bit 12 "while the
measured value sets bits 16, 20 and 24", and calls that an unreconciled
contradiction. Two files in this repository say otherwise:

* `docs/testing/nv2a-mapping-programme.md:167` — *"PTIMER is enabled on this
  console (`NV_PMC_ENABLE` bit 16 set; the block reads 992/1024 non-zero)"* —
  and again at :204, *"`NV_PMC_ENABLE` bit 16 is PTIMER, so a blind write there
  stops the system clock"*. The tree already assigns one of the three set bits,
  and cross-checks it against that block reading live in the same survey.
* `docs/testing/nv2a-probe-pmc-findings.md` — *"PGRAPH reading entirely zero is
  consistent with the graphics engine simply not being enabled — `NV_PMC_ENABLE`
  reads `01110000` here"*. The survey table in that file has PGRAPH at
  **0/2048** non-zero and PFIFO at 382/2048.

Put together, the measured word is not in tension with the header at all: bits
8 and 12 are **clear** in it, and the same sweep independently found PGRAPH
silent. A word with `_PFIFO` and `_PGRAPH` clear, read on a machine whose PGRAPH
block reads entirely zero, is what the header predicts, not a refutation of it.
The open question is narrower than the comment states — what bits 20 and 24 are,
and what a *busy* machine reads — and the comment's framing points the next
lane away from it.

Two consequences, and the second is why this is not merely wording:

1. **The reproducibility argument is doing work it cannot do.** "Two
   independent read sweeps, with a reboot between them, 1,024/1,024 identical"
   establishes that the *same machine state* re-reads the same word. Both
   sweeps were the console freshly out of the dashboard with the engines idle.
   That bounds repeatability; it says nothing about state-independence, which is
   the property a hardcoded constant needs. The measuring document says so
   itself, in the paragraph that names this value: *"Values are
   state-dependent... nothing here should be turned into an emulator change
   without a second read in a known state."* The diff turns exactly that reading
   into an emulator change and does not mention the restriction in the comment,
   the PR body or `NOTES.md`.
2. **We now answer "PFIFO and PGRAPH are off" while we are rendering.** If the
   header positions hold — and per the above, this measurement is evidence for
   them rather than against — then the constant reports both engines down at all
   times, including mid-frame. #188's body names precisely that reader: *"A
   guest that reads `PMC_ENABLE` to check whether PFIFO or PGRAPH is up."* This
   is **not a regression** (the previous `0` also reported everything down, and
   is further from silicon in the one state we measured), which is why this is
   MEDIUM and why the value should stay.

**Remediation** (the required part is small): correct the framing where it is
read — `pmc.c`'s comment, the PR body, and `NOTES.md`, whose summary asserts it
near the top as well as in the body — to say that the measured word has bits 8
and 12 *clear*, consistent with both engines being idle when the sweep ran, that
`nv2a-mapping-programme.md` already reads bit 16 as PTIMER, and that what is
unestablished is bits 20/24 and what a busy machine reads. Name the machine
state the word was measured in, beside the constant.

**A remediation is a claim, and this next one is a suggestion the lane may
decline with a reason:** the stateful alternative — return the constant with
the `_PFIFO`/`_PGRAPH` bits reflecting our own always-on engines — is *not*
being asked for here. It would assert the header positions this lane
deliberately refused to assert, and it grows into a `NV2AState` field with a
`vmstate` bump (`nv2a.c:1519`, `version_id = 3`), which is the write lane's
work, not this one's. Correcting the framing is the whole of M3.

## LOW

### L1 — the write extract runs to end-of-file, so an unrelated later function is refused as if it were `pmc_write`

`docs/testing/pmc_enable_selftest.sh:44`

`sed -n "${WSTART},\$p"` takes everything from `^void pmc_write(` to EOF, so
both guards are really "anywhere after `pmc_write` starts". Verified: appending

```c
static uint32_t pmc_enable_debug_mask(void)
{
    return 0x01110000;
}
```

to a copy of `pmc.c` yields `REFUSED: the measured read-back constant appears in
pmc_write.` — a red check against a file where `pmc_write` is untouched. The
same holds for a later helper containing a `case NV_PMC_ENABLE:` (a decoder, a
reset path). It fails loudly rather than silently, and nothing currently follows
`pmc_write`, which is why this is LOW. Bounding the extract at the next
column-0 `}` followed by a top-level definition, or simply at the end of the
function, removes it.

### L2 — the read extract spans to `pmc_write`, so a helper added between the two gets compiled into the test

`docs/testing/pmc_enable_selftest.sh:43`

Anything between `pmc_read` and `pmc_write` is included in
`pmc_read_extract.c`. A future `static` helper that touches a QEMU type the
stubs do not provide makes the script report *"the extracted `pmc_read` did not
compile cleanly"* — a failure about the test's stub set presented as a failure
of `pmc.c`. Again loud, not silent. `NOTES.md` documents the ordering
assumption, which is the right instinct; this is the second half of it.

### L3 — `g_log.size` and `g_log.block` are recorded and never asserted

`docs/testing/pmc_enable_selftest.c:38-44, 76`

The trace check is `g_log.calls != 1 || g_log.val != want || g_log.addr !=
addr`. The struct also captures `size` and `block`, and nothing reads them, so a
case that logged the read under the wrong block or with a corrupted size passes
"the trace is right". `size` is cheap to add (the helper already knows it is
4). `block` is not, because `NV_PMC` comes from `nv2a_int.h`, which the stub
deliberately does not include — worth a one-line comment saying so, so the next
reader does not think it was forgotten.

### L4 — `unmodelled 0x204 == 0` is knowingly contrary to a measurement, and does not say so

`docs/testing/pmc_enable_selftest.c:121`

The control asserts our model returns 0 at `0x204`. Silicon reads
`0x00000001` there and across `0x204`–`0x2FC` — that is open issue **#190**,
row three of the same gap-list section. The assertion is correct *as a scope
control* (the new case must not widen), but a reader meeting it cold will take
it as silicon-backed, and the lane that fixes #190 will see this go red and have
to work out whether it broke something. One clause — "silicon reads 1 here
(#190); this pins the case width, not the value" — fixes it. The same paragraph
is the natural home for the endian refutation recorded above.

### L6 — "nothing differs today" is the one sentence of the PR body that is not true

PR body; `docs/lanes/pmc188/NOTES.md:52-53`

*"The write is still discarded, so nothing differs today — but the two are not
independent the day that path becomes live."* The read differs today, for every
guest read of `0x200`, and that is the only thing this PR changes. `NOTES.md`
says so one sentence earlier and then undercuts it; the PR body keeps only the
undercutting half. Whether any title reads the register is unknown and this
lane could not find out — but "unmeasured" and "nothing differs" are different
claims, and the second is the one a fold reviewer will read. One word ("no
*write* differs today") is the whole fix. Pairs with M3.
