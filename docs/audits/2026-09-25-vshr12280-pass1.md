## What the diff does, checked

- `decode_opcode` now takes an `opos_suffix`.  An output write to register 0
  (`out_reg_name[0] == "oPos"`) goes to `_opos_tmp` when
  `use_temp_var || mask > 0`.  `use_temp_var` means a paired MAC.  `mask > 0`
  means the same unit also writes a temporary.  `decode_token` appends
  `oPos.<m> = _opos_tmp.<m>;` last, after the ILU statement and after
  `mac_suffix`.
- **Every shape the condition admits:**
  - *Unpaired op writing oPos plus a temp R.*  Both statements now read R12
    as the oPos the instruction started with.  This is the Multioutput fix.
  - *Paired MAC writing oPos, ILU reading R12 as input C.*  The ILU now reads
    the original oPos, which matches how `_temp_vec` and `_c_rw_tmp` already
    model pairing.
  - *Paired MAC writing oPos, ILU not reading R12.*  A pure rename, so it
    cannot change a value.
  - *Paired ILU writing oPos with an R1 mask.*  The R1 statement reads the
    original R12.  The MAC statement comes first and writes only `_temp_vec`,
    so this is inert for the MAC.
  - Only one unit owns the output mux (`FLD_OUT_MUX`), so `opos_suffix` never
    gets two lines.
- **Mask string.** The whole block is guarded by `FLD_OUT_O_MASK != 0`, so
  `&mask_str[m][1]` is never empty.  The copy line and the op's write mask
  come from the same field, so exactly the written components are copied, and
  the uninitialised `_opos_tmp` components never reach `oPos`.  `oFog`'s
  `fog_mask_str` path is untouched, because `out_reg == 0` excludes it.
- **Memory.** `opos_suffix` is allocated once per token.  It is appended and
  unref'd on the single return path after allocation.  The early return for
  MAC_NOP+ILU_NOP comes before the allocation.  No leak.
- **Nothing else parses the generated text.**  No `strstr` or other scan over
  the program body looks for `oPos` in `vsh.c`, `gl/` or `vk/`.  The epilogue
  (`vsh-prog.c:874-887`) runs after every token, so it sees the final oPos.
- **Prediction.** a=`d709a8d1fa`, b=`8dce0cf12e`.  The only commits after b
  are docs.  Its one expect leg is Multioutput -> 0.  Each must-not-move glob
  is tied to the one change that could move it: the header global breaking
  compilation.  The `[job.arms]` verdict is PASS, 335/335 (`verified` label).
  The mover went 32768 -> 0, and the count of byte-differing captures is 1,
  which equals the mover count.
- **CI.** build x2 and check are green on this head.  `vsh-prog.c` has no
  commits on master since the branch point, and `git merge-tree` against
  `origin/master` is clean.

## Findings

**LOW-1: an R12 temp destination changes which write lands last, unmeasured.**
Scenario: a paired instruction whose MAC writes temp R12 (so `R12.x =
_temp_vec.x` goes into `mac_suffix`, and that line writes oPos through the
`#define`) and whose ILU writes oPos with a nonzero R1 mask.  Before the patch
the MAC's suffix ran last and won on overlapping components.  Now the ILU's
`_opos_tmp` copy runs last and wins.  There is no silicon measurement either
way, and by the lane's 47-program emitter diff no program in the corpus has
this shape.  NOTES lists "R12 as a temp destination" under "Not chased".  The
blast radius is bounded to a shape nothing exercises, so this is LOW.
Suggestion: add one sentence to the code comment saying that the ordering
against an R12 temp write is unmeasured.

**LOW-2: the unpaired constant-file sibling stays unfixed.**  An unpaired op
that writes `c[n]` and a temp that reads the same `c[n]` still emits the
output write first.  This is outside this PR's scope, NOTES records it, and
the corpus has no program with the shape.  It is recorded here so it is
tracked.  Suggest the board files it as a follow-up, not this lane.

Nothing here blocks: pass 2 has no HIGH or MEDIUM scenario to re-check.  It
should confirm the two LOWs are either addressed or explicitly left alone, and
that the head is still green and current.
