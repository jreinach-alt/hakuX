# Audit pass 1: PR #379, lane.tiecode282 (weight-binade texel-tie rule, #282, #283)

Head audited: `6321ec4477`. Diff read against `origin/master` (merge base `6c25a829ef` + merge `adb573c270`).

**Result: no HIGH, no MEDIUM, three LOW.** The PR goes to pass 2.

## What was checked

- `psh.c` / `psh.h`: the new `PshState::fixed_function`, `texel_tie_rule_stage()`,
  `append_texel_tie_rule()`, the per-stage `texelTieBias0..3` substitutions
  (PROJECT2D sample, hilo16 rebuild, new PROJECT3D sample), and where the new
  code is spliced into `psh_convert()`.
- `differ.c`: the new field row.
- The prediction files, lane tools and `nv2a_index.json` (generated) by inspection only.

### Points that hold

1. **Every `texelTieBias%d` a shader names is declared.** `append_texel_tie_rule()`
   emits all four `texelTieBias0..3` at the top of `main()` in every shader,
   gated or not, and every use (`psh.c` hilo at 1110/1114, PROJECT2D at 3191,
   PROJECT3D at 3241) is in `vars`, which is spliced after them. No helper
   function outside `main()` names a per-stage bias. The shadow path (1461)
   keeps the shared `texelTieBias`, and `texel_tie_rule_stage()` excludes
   shadow stages, so the two stay consistent.
2. **The hilo16 rebuild reads the same coordinate as its source sample.**
   `append_hilo16_texel(k = input_tex[i])` uses `texelTieBias<k>`, the bias of
   stage k's own PROJECT2D fetch. The comment at 1105 ("exactly the coordinate
   the PROJECT2D sample used") is still true.
3. **The rule's arithmetic matches its statement.** `a = x1 - p.x = l0*W` and
   `b = p.y - y0 = l2*H` for the gated UL/UR/LR triangle (y0 == y1 and x1 == x2
   are both enforced). `4a > W && 2a <= W` is `l0 in (1/4, 1/2]`, and
   `2b <= H` is `l2 <= 1/2`, with the closed/open ends as stated.
   `frexp(x) == 0.5` is an exact power-of-two test.
4. **The derivatives are in uniform control flow.** `texelTieV()` is called
   before `clip` (so before any `discard`) and not under any branch, and it
   takes all its `dFdx`/`dFdy` before its only early return.
5. **Every input exists in every shader.** `vtxT0..3` and `vtxPos0..2` are
   in the common varying list (`common.c` 62/66). `surfaceScale` is in the
   uniform DECL list (`psh.h` 218) and includes the AA and scale factors
   (`psh.c` 4329-4334), which is the same frame the depth path already uses.
6. **`fixed_function` is read the same way `vsh.c` reads it** (`vsh.c:92`,
   CSV0_D mode == 0). It adds no shader variants, because `VshState` already
   keys on `is_fixed_function` (`shaders.c:51`). The GL on-disk cache is
   invalidated by xemu version, so the `PshState` layout change cannot read
   stale entries. `differ.c` uses `offsetof`, so the new row is independent
   of field order.
7. **The Vulkan gate is honest.** `frexp(float, out int)` needs GLSL 4.00 or
   ES 3.1, and the rule is emitted only under `opts.vulkan`.
8. CI (`build` x2, `check`) passes on the head.

## Findings

### LOW-1: PROJECT3D volume draws outside the gate change from no bias to "up", which the PR body does not say

`psh.c:3234-3242` now adds `texelTieBias<i> * pT.w` to **every** PROJECT3D
sample of a 3D texture. That includes GL-renderer draws, VS-drawn volumes and
flat-shaded volumes, where `texelTieBias<i>` is the plain "up" bias. On master
these draws had **no** bias. The PR body says "every other draw keeps 'up'",
which is true for 2D but not here: for volumes the change outside the gate is
none → up, on u and v.

**Failure scenario:** a VS-drawn (CSV0_D mode 2) volume-texture draw whose
interpolated u or v lands exactly on a texel boundary now takes the upper
texel where master took the lower one. No silicon capture on disk covers that
configuration.

**Why this is LOW:** only exact ties can change, by one texel. "Up" is also
silicon's direction on every measured non-rule 2D configuration (VS-drawn
checkerboards 32,674 of 32,674), so this is an unmeasured extrapolation, not
a known-wrong result.

**Remedy:** name the none → up change for ungated volumes in the PR body and
in the comment at 3235. Alternatively, restrict the PROJECT3D bias to stages
where `texel_tie_rule_stage()` holds under the gate.

### LOW-2: vertex roles are read from post-assembly order, not submission order

The comment says the rule is taken only where "v0, v1, v2 = upper left, upper
right, lower right". The test (`vtxPos0.y == vtxPos1.y && vtxPos1.x == vtxPos2.x`,
W > 0, H > 0) runs on `vtxPos0..2` as the geometry stage emits them, which is
host primitive-assembly order. For strips, host assembly swaps the first two
vertices of odd triangles. So a guest triangle submitted in a different role
order can reach the rule if assembly lands it in UL/UR/LR order.

**Failure scenario:** a strip whose odd triangle the guest submitted as
(UR, UL, LR), which assembly presents as (UL, UR, LR). The rule then applies
the binade test to a vertex-role assignment silicon was never measured on.
The comment itself says other roles are "not determined by anything on disk".

**Why this is LOW:** the geometric test is still a real narrowing. It needs
equal w, constant q and a right triangle whose v is constant along one leg.
The effect is limited to the direction of exact v ties. No capture on disk is
known to hit this case.

**Remedy:** say in the comment that roles are post-assembly, or note which
primitive types the measured draws used (the goldens' quads/lists).

### LOW-3: the head does not merge cleanly with current master

`gh pr view` reports `CONFLICTING`. `git merge-tree origin/master HEAD`
conflicts only in the generated `docs/testing/nv2a_index.json`. No source file
conflicts. The fold needs a merge of master and an index rebuild (with the
fold pins, as at `adb573c270`) before it can build this head.
