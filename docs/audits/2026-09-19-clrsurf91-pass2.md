## M1 — CLOSED. A download can no longer consume the dirty bits, and the two
consumers are still the only two

Pass 1's scenario: the guest CPU writes the surface's VRAM range; a download
with the binding absent test-and-clears `DIRTY_MEMORY_NV2A` over that range
and hands `mem_dirty` to nobody; the next upload opens the gate on
`!current_binding`, reaches the compatible-hit or unshelve path, computes
`mem_dirty == false` because this call already ate the evidence, leaves
`upload_pending` false and takes the stale host image as-is.

**It can no longer occur.** The scan at `surface.c:3503` is now
`if (upload && !tcg_enabled())`, so no call with `upload == false` reaches
`bitmap_test_and_clear_atomic` at all — the bits survive the download untouched
and are still set when the next upload scans them. I re-derived the consumer
set rather than taking pass 1's word for it: every occurrence of `mem_dirty` in
`update_surface_part()` is at `:3502` (init), `:3518` (the scan), `:3592` (the
gate expression), `:3800` and `:3871`. `:3800`
(`surface->upload_pending |= mem_dirty`) and `:3871`
(`surface->upload_pending = shelf_stale || mem_dirty`) are both at sixteen
spaces of indent inside the `if (gate_open)` block that opens at `:3598`, and
the remaining three are the variable's own plumbing. There is no consumer
outside the gate, so making the *producer* upload-only cannot starve one.

**The widening is monotone, and I checked the one way it could have been
wrong.** Retaining a bit that used to be cleared can only turn
`upload_pending` from false to true (`|=` at `:3800`, and at `:3871` the
right-hand side is a disjunction with `mem_dirty`), so the worst case is a
redundant upload. The way that could still be *wrong* rather than merely
wasteful is if the download itself set the NV2A bit — then every download
would leave the range looking CPU-dirty and the following upload would push
guest RAM over a host image that might be newer. It does not:
`pgraph_vk_download_surface_complete_deferred()` marks `DIRTY_MEMORY_VGA` and
`DIRTY_MEMORY_NV2A_TEX` (`surface.c:1025-1031`) and never `DIRTY_MEMORY_NV2A`.
The only writers of that client bit in `hw/` are `vk/blit.c:757`,
`vk/blit.c:924` and `gl/blit.c:686` — guest-visible blit writes, which is
exactly what the bit is for — plus the guest's own stores via
`memory_region_set_log(d->vram, true, DIRTY_MEMORY_NV2A)` at `nv2a.c:1283`. So
a retained bit means a real CPU write and uploading it is the correct action.

**The comment the finding asked for is there.** `:3471-3499` states that the
scan is a destructive read, names both consumers, gives the failure, and marks
its own scope; `:3581-3589` answers the other half — what a declined download
*is* allowed to consume — and that list is accurate against the tail: the tail
at `:3959-3960` clears `write_enabled_cache` and `draw_dirty` and nothing else.

**One thing the remediation is right about and one it over-claims** — both in
the new LOWs below, neither reopening this finding.

## M2 — CLOSED. `addr=` is emitted, and it is the address the comment names

Pass 1's scenario: `dl91_probe` is the lane's only instrument for a fix that
is a removal, its own header says `addr=` is "the number worth having", and
the log line had no such field, so whoever reads the arm log greps for it,
finds nothing, and either re-runs the arm or concludes the declines were not
address-attributable.

**It can no longer occur.** The signature at `:340` is
`dl91_probe(PGRAPHState const *pg, bool color, hwaddr addr)`, the format at
`:358-361` is `"[dl91] frame=%d declined=%lu f_declined=%lu part=%s addr=0x%08"
HWADDR_PRIx`, and the sole call site at `:3956` passes `target.vram_addr` —
the same expression `surf91_overlap_probe`'s call site at `:3680` passes, and
`target` is populated from the current registers at the top of the function
(`:3466`), so the value is in scope and live at the probe. The format is
`hwaddr` against `HWADDR_PRIx`, matching `surf91_overlap_probe`'s existing
line; both CI builds (Android and Desktop) are SUCCESS on this head, which is
where a `-Wformat` mismatch would have surfaced.

The header at `:314-323` now says which address it is and why, and records
that the field was documented before it was emitted. I did not have to take
"it is the right address" on trust: the declined download's counterfactual is
the old code resolving a binding *at* `target.vram_addr`, so that is precisely
the address the removed download would have gone to.

## New findings

### N1 (LOW) — the M1 comment presents as live a loss that is dead on every
device arm, and never says so

`:3503` is `if (upload && !tcg_enabled())`. The `!tcg_enabled()` half is
pre-existing and `vk/draw.c:115-118` already records what it means: "the
surface upload read is deliberately NOT instrumented: nothing on the device
clears `DIRTY_MEMORY_NV2A` over a surface range — the only clearer is the
vertex sync below, for its own ranges, and `update_surface_part`'s own scan is
behind `!tcg_enabled()` and therefore **dead here**". The device runs TCG, so
the scan has never executed on an arm; M1's lost write was reachable on a
non-TCG host and nowhere else.

The new block at `:3471-3499` describes the failure in the present tense over
eleven lines, says it is "load-bearing rather than tidy", and says the change
"stops eating the bit out from under the vertex-RAM sync" — with no mention
that neither statement is true of the configuration every measurement in this
project is taken in. Pass 1 did not say it either; the finding is against the
comment as it now stands, not against the fix, which is correct and should
stay.

**Failure scenario.** A later lane reading this block takes M1 as a defect the
arms could have caught, goes looking in the `[surf92]`/`[dl91]` logs or in a
score for the lost write it describes, and finds nothing — because on the
device the scan never ran and `mem_dirty` is unconditionally false. That is a
capture set or an arm spent proving an instrument blind, which is the same
class of cost `vk/draw.c` wrote its own paragraph to prevent. Worse, a lane
that *does* believe `mem_dirty` is live on the device may read the gate
`upload && (!current_binding || buffer_dirty || mem_dirty)` as a three-term
condition when on every arm it is a two-term one.

**Remediation:** one sentence in the block saying the scan is behind
`!tcg_enabled()` and therefore dead on the device, so this repairs a non-TCG
host and tightens an invariant everywhere. Cite `vk/draw.c:115-118` rather than
re-deriving it.

### N2 (LOW) — `vk/blit.c`'s justification for its direct `upload_pending`
write is now false about this tree, and invites deleting a write the device
depends on

`blit.c:778-786` explains why `pgraph_vk_solid_line()` writes `upload_pending`
directly instead of relying on the dirty bit:

> marking `DIRTY_MEMORY_NV2A` looks like [a renderer-agnostic equivalent], and
> both renderers do read that bit, but their scans test-and-clear it *before*
> the guard that consumes it, and with `upload == false` on a live binding the
> bit is cleared and discarded — and `upload == false` is what every
> surface_update call in shared code passes.

After this PR that is no longer true of the Vulkan renderer: with the scan
upload-only, `upload == false` clears nothing. It was already untrue of the GL
renderer — `gl/surface.c:2929` records that "THE `mem_dirty` TERM IS GONE" and
why (#85) — so both halves of "both renderers do read that bit" are now stale,
one half by this diff.

**Failure scenario.** A lane sent to simplify `pgraph_vk_solid_line()`, or the
lane that eventually closes #91 and reads every `DIRTY_MEMORY_NV2A` site,
checks the comment's claim against `vk/surface.c`, finds the scan is
upload-only and GL has no surface term at all, concludes the hazard the
comment describes is gone, and replaces the direct `upload_pending` write with
a `memory_region_set_client_dirty(..., DIRTY_MEMORY_NV2A)`. On the device that
route is dead under `!tcg_enabled()` (N1), so the solid line's write reaches no
surface, the `VkImage` keeps stale content, and the symptom is a wrong image
with nothing in the log — the exact failure the comment was written to prevent,
reintroduced by trusting it.

**Remediation:** correct the comment where it is read. The conclusion — keep
the direct write — is still right and the reason is now *stronger* (`upload ==
false` reaches no scan at all, and on the device no scan runs either), so this
is a rewrite of two sentences, not a change of decision.
