The emulator change is `+41/-0` in `hw/xbox/nv2a/pmc.c`: one new arm in
`pmc_read` (`case 0x160:` and `case 0x204 ... 0x2FC:`, returning `1` for
dword-aligned offsets), 34 lines of it comment. The rest is the extended
falsifier, a new mutant suite, a repointed `pmc188` suite, one gap-list row and
the lane's `NOTES.md`.

## What I checked and found correct, so pass 2 does not re-derive it

* **The arm is right against the measurement.** 0x204–0x2FC inclusive is
  `(0x2FC-0x204)/4+1 = 63` dwords; with 0x160 that is the 64 offsets the survey
  reports. 0x200 (`NV_PMC_ENABLE`) is outside the range and still returns
  `0x01110000`; 0x1FC and 0x300 fall to `default` and return 0.
* **The alignment guard is consistent with how the region reaches `pmc_read`.**
  The PMC `MemoryRegionOps` (`nv2a.c:123-127`, via `ENTRY`) set only
  `.read`/`.write`, so QEMU's default access sizes (1–4, no widening) apply and
  a sub-dword read arrives with its own `addr` and `size`. A 1-byte read at
  0x204 returns 1 (the low byte of the measured `0x00000001`); a read at 0x205,
  0x206 or 0x207 returns 0, which is what the high bytes of `0x00000001` are.
  No read that returned non-zero before this change now returns something else;
  the only behavioural change is the 64 aligned offsets going 0 → 1, which the
  PR body states.
* **`pmc_write` is untouched.** The diff to `pmc.c` is one hunk inside
  `pmc_read`; the write path still drops every one of these offsets via
  `default:`.
* **The trailing trace is unaffected.** `nv2a_reg_log_read(NV_PMC, addr, size,
  r)` and the Android `hakuX-mmio` poll log both run after the switch and see
  the new `r`, which is what the selftest's trace assertion checks.
* **I ran every gate the PR names, myself, on the tip.**
  `docs/testing/pmc_enable_selftest.sh`: 16 checks, 0 failures, exit 0.
  `docs/lanes/cloud190/mutants.py`: 24 mutants, 0 unexpected, including `PRE`
  (pmc.c at base `3fe18366cd` goes red) and the two recorded holes `K1`/`K2`
  green as declared. `docs/lanes/pmc188/mutants.py`: 14 mutants, 0 unexpected.
* **The new write guard's reach is as documented.** It refuses any hex
  `0x2xx` / `0x160` / decimal `352` label or range endpoint in `pmc_write`, and
  its two stated holes (a spanning range with both ends outside, decimal
  516–764) are mutants that stay green, so the limit is measured, not asserted.
  It also re-refuses hex `0x200`, which the #188 guard already refuses — an
  overlap, not a conflict.
* **GNU case ranges are fine here.** The tree already uses `case a ... b:`
  (`hw/adc/aspeed_adc.c`, `hw/misc/bcm2835_cprman.c`, others), so this is not a
  new portability dependency for the emulator build.

## Findings

### L1 — two mutant rows now pass only under gcc (LOW)

`docs/lanes/pmc188/mutants.py` M4 was repointed from `FAIL unmodelled 0x204`
(compiler-independent) to the gcc diagnostic text `duplicate (or overlapping)
case value`, and `docs/lanes/cloud190/mutants.py` N4b expects the same text.
`pmc_enable_selftest.sh:147` honours `CC="${CC:-gcc}"`, and clang words the
same refusal `duplicate case value '516'`.

*Scenario, reproduced:* on this host `env CC=clang python3
docs/lanes/pmc188/mutants.py` → `14 mutants, 1 unexpected: ['M4']`, and `env
CC=clang python3 docs/lanes/cloud190/mutants.py` → `24 mutants, 1 unexpected:
['N4b']`. In both cases the mutant *is* refused (clang errors out on the
duplicate case); only the expected-text match fails. So a run on a clang
machine reads as a broken suite when the guard is working — and before this PR
M4 passed under clang.

*Why LOW:* the default is gcc, neither suite is wired into CI, and the failure
is a false red, never a false green.

*Remediation:* match the substring both compilers share — `duplicate` (or the
regex `duplicate( \(or overlapping\))? case value`) — in M4 and N4b. Pass 2
re-runs both suites with `env CC=clang`.

### L2 — the only falsifier is still unwired (LOW, pre-existing, declared)

Nothing in CI runs `pmc_enable_selftest.sh` or either mutant suite
(`jobs-selftest.yml` is scoped to `docs/testing/jobs/**`). The PR says so in
its Gates section. Scenario: a later edit to `pmc_read` that drops the region
arm builds and folds green; the selftest would go red, but only if someone
invokes it. Not this lane's to fix — it is shared with the other unwired
selftests the PR names — and recorded so it is not lost.

2. The selftest and both suites are still green on whatever tip pass 2 reads.
