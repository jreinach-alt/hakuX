## Why this exists

`grep -i audit AGENTS.md` returns nothing: there is no audit protocol in the
canonical file. `preflight.sh` runs six checks and not one of them reads a
diff. So the +1,531 / −539 lines of compiled code in this window were gated on
measurement claims about their *effect*, never on review of the code.

That shapes what this pass looked for. Measurement on `nxdk_pgraph_tests` —
one device, static content, one renderer — cannot see error paths, resource
lifetimes, device-limit violations, host-state assumptions, or a second
device. Those are most of what is below.

## HIGH

### H1 — `vk/shaders.c:284` — push-constant range grew past `maxPushConstantsSize`, and the new guard covers the wrong site

Moving the vertex inline-attribute range up to offset 16 to make room for the
geometry stage's wide-line `vec4` raised the largest range's end from **256 to
272 bytes**.

`pgraph_vk_init_shaders()` gained a guard for exactly this:

```c
r->use_push_constants_for_uniform_attrs =
    (r->device_props.limits.maxPushConstantsSize >=
     GEOM_PUSH_CONSTANT_SIZE + MAX_UNIFORM_ATTR_VALUES_SIZE);
```

That flag is read by `create_pipeline()` in `draw.c`. It is **not** read by
`create_push_descriptor_resources()`, which runs unconditionally whenever push
descriptors are supported and creates all seventeen template layouts, `n = 0`
through `16`, with the vertex range sized `n * 16` at offset 16.

**Scenario.** A device reporting `maxPushConstantsSize == 256` — desktop
NVIDIA, many Mali parts. Before the change the largest range was
`{VERTEX, 0, 256}`, ending at exactly 256 and legal. Now `n = 16` gives
`{VERTEX, 16, 256}`, ending at 272, which violates
`VUID-VkPipelineLayoutCreateInfo-pPushConstantRanges-00294`.
`vkCreatePipelineLayout` is called with it at init. With validation on it is an
error; with a driver that reports failure `VK_CHECK`'s `assert()` aborts at
startup, since QEMU does not define `NDEBUG`; with a driver that accepts it the
handle is undefined.

The blast radius is bounded by an accident: on such a device
`use_push_constants_for_uniform_attrs` is false, `push_template_index()` returns
0, and templates 1–16 are created and then never used. That accident is also
precisely why no golden run could ever surface this.

**Remediation.** Gate the VERTEX range in `create_push_descriptor_resources()`
on `use_push_constants_for_uniform_attrs`, or stop the loop at the largest `n`
that fits, and add `assert(GEOM_PUSH_CONSTANT_SIZE + n * 16 <= maxPushConstantsSize)`
so the next offset change fails loudly rather than quietly.

## MEDIUM

### M1 — `vk/draw.c:5508` — the wide-line push is gated on `pipeline_changed`, and the snapshot it defeats was added to handle that case

`emit_reorder_entry()` issues the geometry push constants only inside
`if (pipeline_changed)`. Two lines above, `try_snapshot_draw_arrays()` and
`try_snapshot_inline_elements()` snapshot `e->line_width` under a comment added
in this same window:

> Snapshotted because SET_LINE_WIDTH can change between draws inside one
> reorder window

The gate drops exactly that. Two line draws in one window sharing a pipeline:
the second gets no push and renders at the first draw's width.
`check_draw_mergeable()` (line 4468) is a second, independent leg — it was
edited in this window for #43 and still does not compare line width, so the two
draws can instead be concatenated into one draw call with one width.

The gating is inherited from the deleted `vkCmdSetLineWidth` call, so the
defect predates the change. What the change did is make it worse in kind: the
width now decides the *geometry the shader emits*, so the failure is a wrong
footprint rather than a wrong thickness — and it added a comment asserting a
guarantee the surrounding code does not provide.

**Remediation.** Push when `pipeline_changed || e->line_width != prev->line_width`;
add `pg->line_width` to `check_draw_mergeable()`.

### M2 — `target/i386/tcg/fpu_helper.c:249` — FRNDINT now honours RC; FIST still does not

The cherry-picked change is sound, and I verified its premise rather than
inheriting it (see *What checked out*, below). But it fixes one half of a macro
table and leaves the sibling half wrong in the same way.

On this hard-FPU path `floatx80_to_int32/int64` are plain C casts. They
truncate toward zero whatever RC says, and they never set `float_flag_invalid`
— so `helper_fistl_ST0`'s out-of-range guard at line 910 and
`helper_fistll_ST0`'s at line 923 are unreachable code.

**Scenario.** A guest sets `RC = round-down` via FLDCW and executes FISTP — the
same x87 idiom the FRNDINT fix was written for, just the other instruction —
and gets truncation. Separately, FISTP of a value outside int32 range: on
aarch64 the cast compiles to `fcvtzs`, which saturates to `INT32_MAX`/`INT32_MIN`
and returns 0 for a NaN, where x87 stores the integer-indefinite `0x80000000`
and raises `#IA`. Neither is visible to a pixel corpus.

Pre-existing, filed because the change made the two halves inconsistent and
because a guest-FPU divergence reaches every title.

### M3 — `vk/draw.c:523` — the clear-side and sample-side pad stamps are keyed on different things

`pgraph_vk_get_clear_color()` keys on `pg->surface_shape.color_format`, the
live guest format. `surface_sampled_pad_alpha()` in `vk/texture.c:1327` keys on
`surface->host_fmt`, the format the *binding* was created with. `psh.c:180-186`
says so itself:

> a binding reused across a format change reports whichever format first
> created it

**Scenario.** A binding created under `X8R8G8B8_Z8R8G8B8` and reused after the
guest switches to the `_O` variant — reuse happens precisely because
`A8R8G8B8`, `X8R8G8B8_{Z,O}` and `X1A7R8G8B8_{Z,O}` all map to one `VkFormat`.
The clear writes pad byte 1 into the image while sampling still returns 0, or
the reverse. Before the change the clear always wrote 1.0 and the two could not
disagree on the clear path. It reaches the guest when the surface is downloaded
to VRAM and read, or re-uploaded as a texture.

### M4 — `gl/texture.c:830` — a `glGetError()` moved into the per-draw path

Replacing the hand-rolled overlap loop with
`pgraph_gl_download_surfaces_in_range_if_dirty()` was a real fix — the old test
used inclusive ends with an exclusive-end comparison, and the new helper also
iterates with `QTAILQ_FOREACH_SAFE` where the old loop did not. But it moved
`android_log_texture_stage_errors()` out of the `if (overlapping)` body.

That function loops on `glGetError()`, a driver synchronisation point. It now
runs on every texture bind taking the `!surf_to_tex` path, where it previously
ran only on the rare actual overlap. The stage label `"download_overlap"` is
now also printed when nothing overlapped.

AGENTS.md records this exact class: an added per-call probe in an inner loop
that "throttled the emulator so badly it presented as a renderer deadlock".
This arrived via the 53-commit remote-lane merge, measured on that branch under
the GL renderer, so the Vulkan measurements gating this window could not see it.

**Remediation** is a one-liner: the helper already returns `found_overlap` and
the caller discards it.

### M5 — unconditional instrumentation, against a stated non-negotiable

Three diagnostic facilities landed in this window with no flag, no runtime
switch and no removal plan:

- the **#54 VRAM-race probe** — `draw.c:39-160`, call sites at 3568 and 6169;
- the **#43 `[signfold]` counters** — `draw.c:7285-7365`;
- the **TCG counters** in `accel/tcg/tb-maint.c` and `translate-all.c`, under
  `#ifdef XBOX`, which is always defined here.

AGENTS.md: *"Instrumentation is not free … Profile-grade tracing belongs behind
a flag."* The VRAM probe adds an RCU read plus a dirty-bitmap scan to every
vertex-range copy and every `begin_pre_draw` window — both per-draw. None of it
can be switched off, so any later timing measurement on this branch measures
the probe too. Each probe's own comment says it exists to answer one bounded
question, so each has an end date that nothing records.

## LOW

Twelve, in the JSON with full scenarios. Grouped:

**Contracts kept in sync by hand.** `GEOM_PUSH_CONSTANT_SIZE` is defined twice
(`draw.c:830`, `shaders.c:50`); the widening predicate exists twice
(`geom_widens_lines()` at `draw.c:839`, `widen_lines` at `geom.c:123`). I
checked all four and they agree today. Both carry comments saying they MUST
agree — the correct diagnosis, not a fix. Related: both copies of the
push-constant comment still call `lineParams.w` "unused" when it is the tie
bias the whole #13 derivation turns on.

**Comments that describe a superseded revision.** `psh.c:3576` says the
selector is left at LOW; `draw.c:7373` resets it to NONE and explains why LOW
was wrong.

**Diagnostics that go quiet.** `draw.c:2401` keys its one-shot on
`subPixelPrecisionBits`, which never changes, but prints
`surface_scale_factor` and the derived tie bias, which do. The comment directly
above it is about a diagnostic that "reads as having been checked".

**FPU leftovers.** `floatx80_round` kept as an alias for round-to-integer when
softfloat's means round-to-*precision* (deleting it would make a future caller
a compile error, since `floatx80` is `double` here); `rint()` in the `default:`
arm still following the host FP environment; PE/C1 never raised by FRNDINT
(pre-existing).

**Cache-identity bookkeeping.** `SHADER_STATE_LAYOUT_VERSION` is still 1 though
`PshState` gained `tex_comp0_const[4]` in this window, in exactly the slot
where padding could absorb it. The file's own comment requires a manual bump in
that case. Separately, `GenVshGlslOptions` is not one of the three structs the
fingerprint covers, and its `vertex_push_offset` moved from 0 to 16 here.

**Geometry modelling choices stated as facts.** Zero-length lines now emit
nothing (`geom.c:407`); `max_vertices` doubled to 12 with no assert on the
geometry limits (`geom.c:152`); the 45-degree tie-axis choice is arbitrary and
not flagged as one (`geom.c:444`); the pad stamp on the partial-clear path is
undetermined for a clear that does not enable alpha (`draw.c:6480`).

## What checked out — claims I tested rather than inherited

Recorded because a passing check is evidence too, and because several of these
were the obvious places for this window to have gone wrong.

- **`line_clip()` inverts vsh's map exactly.** `vsh-prog.c:760` and
  `vsh-ff.c:886` both compute `clip.xy = ((2·screen − surfaceSize)/surfaceSize)·w`,
  and `line_clip` computes `(screen · lineNdcScale − 1)·p.w` with
  `lineNdcScale = 2/surfaceSize`. Identical, and identical for **w < 0** too,
  because both go through the same expression — so a line crossing the near
  plane is not a special case. `clampAwayZeroInf(oPos.w)` removes `w == 0`.
- **Units are consistent under surface scaling.** `surfaceSize` is
  `surface_binding_dim / aa`, in guest pixels; the line width is in guest
  pixels; the scale factor genuinely cancels, as `geom_line_params()` claims.
- **No line draw can reach the rasteriser without a geometry shader.**
  `pgraph_glsl_need_geom()` returns true for exactly the two primitive modes
  `geom_widens_lines()` tests, and `primitive_mode` is the *rewritten* output
  mode, so LINE_STRIP and LINE_LOOP cannot leak past it.
- **Culling is cleared on all three paths** — static pipeline (`create_pipeline`),
  eds3 dynamic (`begin_draw`), and the reorder snapshot
  (`snapshot_dynamic_state`). A widened line's winding depends on the sign of
  the perpendicular offset, so a miss on any one path would have dropped half
  the lines.
- **The FRNDINT fix's premise holds.** `update_fp_status()` is reached from
  every fpuc write live under TCG, including `cpu_post_load` (`machine.c:392`),
  so `float_rounding_mode` is never stale when the new switch reads it. The
  direct `env->fpuc =` writes in `xsave_helper.c`, `whpx-all.c` and
  `nvmm-all.c` are not TCG paths. The x86_64 hard-FPU block never defined
  `floatx80_round_to_int`, so it always used real softfloat and never had the
  bug — the aarch64-only fix is correctly scoped.
- **The #59 write-side stamp and the #43 sign fold do not collide.** Both
  rewrite `fragColor.a`, and their composition under ONE/ONE two-pass blending
  would have destroyed the pad byte. The write-side half was withdrawn
  (`55de5edfff`) before the fold landed, so the interaction does not exist in
  HEAD. Only the clear-side stamp remains.
- **The GL renderer is unaffected by the sign fold.** `signedBlendPass` is
  emitted unconditionally but gated on the uniform, `NONE == 0` is the
  identity, and `gl/draw.c` never sets the selector.
- **The #54 probe's "impossible row" premise holds.** Its claim is that the
  only code clearing `DIRTY_MEMORY_NV2A` is the vertex sync and
  `check_texture_dirty`. The other candidate, `update_surface_part` in
  `vk/surface.c:3187`, is behind `!tcg_enabled()` and is dead in every build we
  run. The claim is correct.
- **The triangle-strip vertex order is right.** `P0+n, P0−n, P1+n, P1−n` is the
  standard zigzag and covers the parallelogram; attributes are constant across
  the width and linear along the length, which is what a wide line wants.
