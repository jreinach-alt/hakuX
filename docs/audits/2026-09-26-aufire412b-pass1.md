# Audit pass 1: PR #451, lane.aufire412b (#412, AUF vCPU-side frame pacing)

Head audited: `619fe7a7f2`. Files: `hw/xbox/nv2a/pgraph/profile.c`,
`docs/lanes/aufire412b/{NOTES.md,capture_p1p2.sh,pace.py,vbl.py,vcpucount.py}`.

**Result: 1 MEDIUM, 4 LOW. Goes to `needs-remediation`.**

The code change is correct. The MEDIUM is in the analysis that the PR hands to
lane.jcache425. Its list of reasons a TB returns to the loop is incomplete, and
the counter it specifies cannot separate the missing reason from the one it
blames.

## What was checked and holds

- **profile.c `Lw:%.1f`.** `lock_wait_ms` is a `float` (debug.h:309),
  EMA-smoothed from `cpu_working.lock_wait_ns` (profile.c:121) and zeroed at
  profile.c:158. The accumulator is `user_write` (user.c:82-85). The line is
  about 150 chars into `buf[512]` (profile.c:646), so it does not truncate. It
  is only printed under `NV2A_PERF_LOG`. Every consumer of `hakuX-cpu` parses
  by key: `splitread.py` `cpu()` uses `NUM.findall`, and `work_table.py` does
  `re.search('Mth:')`. `run_perf.sh` and `dispatcher.sh` only name the tag. So
  the added field breaks nothing positional.
- **vbl.py regexes against nv2a.c.** `vbl n=... max=%lld src(...) coal=%u def=%u`
  (nv2a.c:681-683) and `vblphase ... nodef(n= mean= max=) def(n= mean= max=) ... clamp=%u`
  (nv2a.c:659-662) both match. `vbl n=` does not match `vblphase n=`.
- **pace.py against `hakuX-pace`** (`f= v0..v4= vb= max=%.1f ms=%.1f`) and
  `[tlb68]` `dt=`/`cpu=` (cputlb.c:260): the keys and types match.
- **capture_p1p2.sh.** The hold is check-then-noclobber, it waits for any
  claimed request before install, and it releases only its own tag. Every exit
  force-stops the app and clears the caches. `soak_title.sh` traps TERM
  (soak_title.sh:219-221), so killing the setsid leader cleans up its
  children.
- **vcpucount.py.** It uses plain `report-sample` as the denominator. `addr2line -f -i` prints the
  innermost inlined frame first, and `o[0]`/`o[1]` read that frame.
- **The arithmetic.** 37.4% x 54.0 = 20.2 ms. (54.1+7.4+7.1)% x 54.0 = 37.0 ms.
  Both are labelled as bounds.
- **cpu-exec.c:1770-1772** (page-spanning target clears `last_tb`) is as
  cited.

## MEDIUM

### M1. The "three ways a TB returns" list misses the i386 translator's own `exit_tb(NULL, 0)`, and the proposed counter would book those exits as lookup misses

NOTES "Why the TBs return" and the PR body both say a return with
`last_tb == NULL` "happens three ways": an indirect-jump lookup miss,
`TB_EXIT_REQUESTED`, and a page-spanning target. On this target there is a
fourth way. `gen_eob()` (target/i386/tcg/translate.c:2883-2913) ends the block
with a plain `tcg_gen_exit_tb(NULL, 0)` for every mode except an uninhibited
`DISAS_JUMP`. These instructions all end their TB that way:

- `STI` (`DISAS_EOB_INHIBIT_IRQ`, emit.c.inc:4117)
- `POPF` (`DISAS_EOB_NEXT`, emit.c.inc:3101)
- `IRET` (`DISAS_EOB_ONLY`, emit.c.inc:2303)
- segment-register writes (emit.c.inc:369/374)
- `CLTS`, `WRMSR` and CR writes (translate.c:3829-4079)
- any `DISAS_JUMP` that follows an interrupt shadow (`inhibit_reset`)

Every one of these exits returns to `cpu_exec_loop` and pays the
`cpu_handle_interrupt` barrier that the profile prices at 20.2 ms per frame.

Failure scenario: suppose AUF's hot path is the kernel's
`pushfd; cli; ...; popfd` spinlock and IRQL idiom (HAL and Kf* routines), or
the IRET at the end of each interrupt. Then every iteration returns via
`gen_eob`. The counter the NOTES specifies for lane.jcache425 has four parts:
`tb_exit` value, `last_tb` NULL by cause, page-spanning target, and
`interrupt_request` non-zero. A `gen_eob` exit and a `helper_lookup_tb_ptr`
miss look the same to that counter. Both come back as ret 0 through the
epilogue (`helper_lookup_tb_ptr` returns `tcg_code_gen_epilogue` on a miss,
cpu-exec.c:1135-1136) with `tb_exit` 0 and `last_tb` NULL. So the counter
reads those exits as "lookup miss", and lane.jcache425 enlarges or re-hashes
the jump cache. That cannot move a return that no cache lookup ever made.

The NOTES' own fps conclusion has the same gap. The poll-vs-real-work split
("a poll returns from a handful of guest PCs") does not separate the cases
either, because a handful of IRQL/spinlock PCs is exactly what the missing
cause looks like.

Remediation:
- NOTES and the PR body: list the fourth cause.
- The counter spec: count misses inside `helper_lookup_tb_ptr` itself, and
  count translator-generated `exit_tb(NULL, 0)` separately. A per-TB flag set
  at `gen_eob`, or the guest opcode at the returning TB's last instruction,
  would do it.
- The hand-off comment to lane.jcache425: correct it where they read it
 .

## LOW

- **L1. "`tb_add_jump` never runs" (PR body).** The profile shows zero
  samples. That is not zero calls. `tb_add_jump` runs once per
  (TB, exit) link, so a loop that chains perfectly also samples it at zero in
  steady state. The claim that TBs return rests on the barrier's volume, not
  on this absence. Reword it to "zero
  samples". The conclusion does not change.
- **L2. vcpucount.py cannot reproduce two rows its table is credited with.**
  The NOTES table is headed "(`vcpucount.py`, ...)". It has rows for TB lookup
  (7.8/7.1%), #424 invalidation (0.74/0.59%) and host runtime (1.08%). The
  script only emits JIT, loop self, `cpu_tb_exec` self and "other". The PR's
  37.0 ms bound includes the lookup row. Either add those symbol classes to
  the script, or say which command produced them.
- **L3. `Lw` is a per-snapshot EMA (alpha 0.2), not a window total.** It is
  printed every 60 flips but smoothed once per snapshot, so it reads roughly
  the last five snapshots. The NOTES' "the guest's `pfifo.lock` wait" should
  say "ms per frame, smoothed", so the outstanding read on request
  `1790470425` is not summed as a total. There is also a pre-existing race
  that this line only exposes: `user_write` does a plain `+=` on the vCPU
  thread and profile.c:158 zeroes the value on another thread, so a window can
  lose or double-count one increment. The effect is bounded and perflog-only.
- **L4. Tool hygiene.**
  - `pace.py`/`vbl.py` hard-code the year `2026-`, and would fail on a Feb 29
    logcat or one crossing New Year.
  - `vbl.py` divides by `n`/`win` unguarded.
  - `vcpucount.py` indexes the NDK glob at import, so it dies with no NDK
    installed.
  - `pace.py` includes a pace line whose 60 flips began up to ~4 s before
    `lo`.
  - The pace.py docstring cites `profile.c:628`. That is a line number that
    drifts. Cite the tag instead.

## Prediction

"none: no arm" is justified. The only code change is a perflog-gated log
field, and it has no pixel leg.
