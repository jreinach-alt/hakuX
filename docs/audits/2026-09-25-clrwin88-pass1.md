## The open reading, checked instead of carried

Under the withdrawn patch, the previous lane's comment said a known defect
"has to be fixed before it re-lands". The scenario: the early return skips the
download tail, so `pg->surface_zeta.draw_dirty` stays set. Once colour moves
off the address, a zeta surface is then "created and downloaded over VRAM the
guest never rendered". This PR downgrades that to "a reading, not a
measurement" and ships it unchanged. That needed checking, because a
data-corruption path would be HIGH.

**Reading the code does not support the "downloads over VRAM" half.** A
creation path cannot write guest VRAM:

- All three creation paths in `update_surface_part()` (unshelve, reuse an
  invalid surface, fresh `g_malloc`) end in `*surface = target;`.
- `target` comes from `populate_surface_binding_target()`, which sets
  `target->draw_dirty = false` (surface.c, near `target->upload_pending = true`).
- The tail calls `download_surface_deferred(d, r->zeta_binding)`, and that
  function returns at its first line when `!surface->draw_dirty`.

So the tail's download is a no-op on the surface just created. The tail then
clears `pg->surface_zeta.draw_dirty` and the stale flag is gone.

What does happen on that re-entry:

1. The colour surface is still registered at the old address. The re-entry
   finds it, it is incompatible (colour vs zeta), and it is evicted and
   shelved. If it is `draw_dirty`, it is downloaded first, which writes its
   own correct content.
2. An empty zeta surface with `upload_pending` is bound during a
   download-path call.
3. On the next upload, that zeta surface uploads guest VRAM, which is what
   the hardware would hold.

That is extra work and an early shelve of colour. It does not lose data.

## Findings

### L1 (LOW, accuracy): the comment and the prediction describe a download that cannot happen

`vk/surface.c` (the paragraph beginning "Zeta declines by clearing
buffer_dirty"), `NOTES.md` "Open reading", and the prediction's OPEN READING
sentence all say the re-entry "creates a zeta surface and downloads it". Per
the reading above, the created surface has `draw_dirty = false`, so the
download is a no-op. Failure scenario: the next lane reads this comment,
believes a VRAM-clobber path exists, and changes the decline to guard against
it. It then chases a defect that is not there, or rules out the decline for a
depth-heavy regression it cannot cause. Fix: reword to "creates and binds an
empty zeta surface and shelves the colour surface at that address". Or clear
`pg->surface_zeta.draw_dirty` on the decline, which removes the re-entry
entirely; the arm's registered legs cannot see that edit.

### L2 (LOW, efficiency): render-pass break on every draw while overlapped

While colour holds the overlap address, `r->zeta_binding` is NULL, so
`gate_open = !current_binding` is true on every `pgraph_vk_surface_update(d,
true, ...)` with `zeta_write`. The gate-open body calls
`pgraph_vk_ensure_not_in_render_pass()` and `unbind_surface()` before it
reaches the decline. The download branch does the same while
`write_enabled_cache` and the stale `draw_dirty` keep it entering. Failure
scenario: a title that aliases colour and zeta for many draws ends the render
pass on every draw. Correctness is unaffected and the cost is bounded to that
configuration. Before the patch, master unbound colour and kept zeta, so the
gate closed on later draws. Moving the decline check ahead of
`ensure_not_in_render_pass` would avoid this, but that is a separate change
and needs its own measurement.

### L3 (LOW, stats): the decline is counted in neither hit nor miss

The early return skips the `create_count`/`hit_count` accounting. `[surf91]`
counts declines separately, so nothing is lost. `surf_working` totals just no
longer sum to `update_calls`. No behaviour depends on this, as far as I read.

## Not measurable here

The Khronos validation layer run the original registration asked for is
still not done. This host has no desktop build. The colour-only framebuffer
this path produces is the ordinary z-writes-off case on master, so the class
is not new, and I do not raise it as a finding.
