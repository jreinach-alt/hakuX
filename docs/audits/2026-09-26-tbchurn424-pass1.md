# Audit pass 1: PR #434, lane.tbchurn424 (#424)

Head audited: `8616f42e2c`. Diff read: `accel/tcg/tb-maint.c`, `accel/tcg/cputlb.c`,
`docs/lanes/tbchurn424/{NOTES.md,churn.py,queue_soaks.sh}`, the two predictions.

**Verdict: one MEDIUM, four LOW, no HIGH. The code is correct as far as this
pass can trace it. The MEDIUM is the registered must-not-regress leg (M4) that
failed and is still unresolved.** Label: `needs-remediation`.

## What was checked and holds

- **Bitmap is a superset of the range test.** `tb_page_code_extent()` gives the
  same interval as `tb_overlaps_written_range()` for both `n == 0` and `n == 1`.
  For n == 1 it covers `[0, (addr0 + size - 1) & ~MASK]`, which is the range
  test's `[page_addr1, page_addr1 + off]`. `MAX(size, 1)` only widens the
  `size == 0` case. Superblocks and `tier >= 2` get the whole page, matching the
  loop's unconditional discard. So "no bit set in [off, off+len)" means the
  range test would spare every live block on the page.
- **Every list insertion updates the bitmap.** The only writer of
  `p->first_tb` that adds a block is `tb_page_add()` (tb-maint.c:1216-1223),
  and it sets bits whenever the bitmap exists. A build walks the whole list,
  dead blocks included, under `p->lock`. The bitmap never clears bits except
  in a rebuild from the list, and the rebuild runs inside
  `tb_invalidate_phys_page_range__locked()` with `p` locked by the page
  collection, before the precise-SMC `cpu_loop_exit_noexc`.
  `tb_remove_all_1()` frees it under the page lock during an exclusive flush.
- **A skipped walk cannot leave a stale block.** A store touching a live
  block's bytes, a dead block's bytes or a superblock's page finds a bit and
  walks. The dead-block case matters because `tb_lookup_cmp` masks CF_INVALID
  (cpu-exec.c:709), so dead blocks are still executed. The walk discards them
  (`!tb_live` clause).
- **Store sizes stay in bounds.** `notdirty_write` callers pass per-page sizes.
  `probe_access_*` sizes are page-bounded and `__locked` asserts
  `start`/`last` share a page. So `off + len <= TARGET_PAGE_SIZE` and
  `find_next_bit(bitmap, off + len, off)` stays inside the 4096-bit map. The
  old "len <= 8" comment on the fast path is stale, but the bitmap does not
  depend on it.
- **No new lock nesting.** `page_code_bitmap_misses()` takes and drops the single
  page lock before `page_collection_lock()`. The store path holds no page lock
  on entry.
- **Arming behaviour is unchanged when a page is empty.** The fast path answers
  only when `p->first_tb` is set. A store to an empty armed page still walks,
  so #311's `armed_idle` fallback still counts it.
- **Counters.** `visited` now counts before the predicate, so
  `visited == ov + sp + ai` holds on both predicates. The comment states the
  whole-page-only identity correctly.
- **The pixels leg:** `[job.arms]` 593/593 byte-identical. The PR states it as
  weak evidence for self-modifying code, which is correct.

## MEDIUM

### M1. The registered must-not-regress leg (M4, Blinx) failed, and the only gameplay data leans toward a regression

`tbchurn424-soak.json` M4: "Blinx, survey route: B's median gfps >= A's - 1."
Result: B 30.0 against A 43.25. **FAILED.** The lane's diagnosis is that the
survey route's span median follows how much of the span is menus. That is
plausible: A r2's 56 comes from menu samples. But the post-hoc gameplay-tail
reader (NOTES.md:140-152) gives **A 9 / 9, B 7 / 9**. So the only data aimed
at Blinx gameplay speed shows one B run 22% below both A runs. The cost-side
counters did move on this title: slow stores went from 67k/s to 101k/s and
invalidator entries from 396/s to 33.5k/s (85x).

**Failure scenario:** the PR folds, and the fork's default flips to the range
test for every title. If Blinx gameplay is 7 gfps where it was 9, a 0.5
release title has regressed. The PR's own registered instrument flagged it,
and nothing registered has cleared it. The kill switch exists, but nothing
would tell anyone to use it.

This is not a code defect. The mechanism argument against a large cost is
reasonable: vCPU CPU did not rise (A 190k/202k ms, B 188k/195k ms), and each
bitmap answer is one page lock plus a bit scan. But the purpose of a
must-not-regress leg is that a failed one is not waved through on a post-hoc
reader and two runs. NOTES says so itself ("cannot rule out a 1-2 fps one").

**Remedy (any one):**
1. Register a new prediction **before** the runs. It names the gameplay-tail
   reader (median of hakuX-perf gfps after the last sample >= 40, already
   written up in NOTES) as the M4 reader, with >= 3 interleaved runs per arm
   on the same A/B refs, or on a Blinx route with a gameplay mark if #397 has
   one. Pass criterion as before: B >= A - 1. Commit it and let the arms job
   run it.
2. Or keep the fix in with the default flipped: whole-page stays the default,
   and `HAKUX_TCG424_RANGE=1` opts in. Crimson's win then waits for the Blinx
   measurement, and nothing ships unmeasured.

Pass 2 checks for a registered and passed gameplay-phase Blinx leg, or for
the default flip.

## LOW

- **L1. `hakux_tcg424_cbb++` is a plain increment from more than one
  thread.** `page_code_bitmap_build()` runs under the lock of *its own* page.
  DMA and watchpoint invalidations (`tb_invalidate_phys_range`, device
  threads) and the vCPU hold different page locks, so two builds can race on
  the counter. Lost counts only. The comment at tb-maint.c:84-88 ("by whoever
  holds the page lock") suggests the lock serialises it, which it does not.
  Use `qatomic_inc`, or reword the comment.
- **L2. `hakux_tcg424_range_on` is declared in two .c files instead of a
  header** (cputlb.c:150, tb-maint.c:777). If the signature changes in one
  place, the compiler will not flag the mismatch across translation units.
  Move it to `tb-internal.h`, next to `tb_invalidate_phys_range_fast`.
- **L3. Bitmaps can outlive a page's code.** A page emptied through its
  *other* page (`tb_page_remove` from a walk of the neighbour) keeps its
  512-byte bitmap and its stale bits. It is freed only by a later walk that
  finds the page empty, or by `tb_flush`. The worst case is 512 B for every
  page that ever took 10 code-write traps: 8 MB for 64 MiB of RAM, 16 MB for
  128 MiB. This costs memory, not correctness.
- **L4. Stores that hit code bytes now pay two list passes.** On a page
  where the bitmap says "walk", the walk is followed by a full rebuild.
  Self-modifying pages that are stored to repeatedly pay this every time,
  where A paid only the walk (and B, without the bitmap, the same walk). No
  title is measured as doing this. This is a pricing note for the corpus
  survey the prediction's `what_this_cannot_see` already names.

## Not findings

- M2's Blinx failure: the lane's diagnosis checks out against the counters it
  cites. On both arms, most of Blinx's slow stores never enter
  `tb_invalidate_phys_range_fast`, and `cb/inv = 1.00` on both titles. The leg
  used the wrong denominator. The 20x stop clause on slow/s did not fire
  (1.5x). This is reported, not refitted, and it is correctly recorded for the
  next lane.
- Correctness against self-modifying code beyond what pgraph and two soaks
  exercise is the prediction's own named limit (`what_this_cannot_see`). This
  pass does not raise it as a finding.
