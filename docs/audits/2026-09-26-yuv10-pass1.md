# Audit pass 1 -- PR #419 lane.yuv10 (#10 SET_CONTROL0 colour-space conversion)

Head audited: `c3d401ad6b` (`lane/yuv10`), diffed against its merge base with
master, `5dcb482dfd`. The C diff covers `nv2a_regs.h`, `pgraph.c` (the
SET_CONTROL0 handler), `psh.h`, `psh.c` and `texture.c`. The docs and
prediction were read as well.

**Verdict: one MEDIUM, four LOW. The PR goes to `needs-remediation`.**

The measured rules in `docs/testing/xbox-csc-2026-09-26.md` are implemented
as written:

- The field is global.
- The converter runs after the texture shader.
- The converter is util.h's, with kr = 128.
- YUY2/UYVY upload raw.
- The BUMPENVMAP_LUM product is truncated when the field is on.

I checked the following and found them correct:

- **Raw upload offsets.** YUY2 reads Y0 Cb Y1 Cr and UYVY reads Cb Y0 Cr Y1,
  the same bytes util.h's decoders read.
- **Invalidation.** CONTROL_0 is a `REG_CAT_SHADER` and `REG_CAT_PIPELINE`
  register. Bits 30-31 are not in `pgraph_reg_dynamic_mask_table`, so a write
  moves `shader_state_gen`.
- **Shader cache.** `PshState` grows by 4 bytes with no padding. The hash and
  memcmp in `glsl/shaders.c` and the `sizeof(PshState)` term in
  `vk/renderer.c` all see the change.
- **GLSL.** Signed `>>` sign-extends, as util.h's C does. `clamp(ivec3, int,
  int)` exists in GLSL 1.30+ and ES 3.0. `highp int` is declared for GLES.
- **Arm.** It passes, 84 of 84 checks.

## MEDIUM-1: SCRYSCB_TO_RGB (value 2) now leaves a YUV texture unconverted

`psh.c` (the `else if` after `csc_crycb`) logs `NV2A_UNIMPLEMENTED` for field
value 2 and emits no conversion. `texture.c` now uploads YUY2/UYVY raw
whatever the field says.

**Failure scenario.** A guest binds a YUY2 or UYVY texture and writes
SET_CONTROL0 with bits 28-31 = 2 (`SCRYSCB_TO_RGB`).

- Before this PR, the upload decoded the texture to studio-range RGB, which is
  approximately right.
- After this PR, the stage outputs (Y, Cb, Cr, 255) as colour: the green and
  magenta image that raw YCbCr gives.

This is a regression on a path the goldens do not exercise. No test sets value
2, and silicon measured only values 0 and 1. The tree has no evidence about
which value XDK D3D's YUV enable writes. The blast radius is bounded to titles
that write value 2 and sample a YUV texture. Nothing shows that such titles
exist, but nothing rules them out either. The pre-PR behaviour was the safe one.

**Remedy.** Under value 2, convert as CRYCB_TO_RGB does and keep the
`NV2A_UNIMPLEMENTED` log. That restores at least the pre-PR output for a YUV
source. If converting non-YUV stages under an unmeasured value is unwanted,
convert only the stages whose format is YUY2/UYVY. That is the exact pre-PR
behaviour, and it needs a per-stage "is YUV" bit in `PshState`. Either choice
closes the scenario. Neither needs a device arm, because no golden writes
value 2. Record the choice in NOTES.

## LOW-1: field values 4-15 are masked into 0-3

`pgraph.c` stores `csc & 3`.

- A method value of 5 is stored as 1 and converts.
- A method value of 4 is stored as 0. It passes through silently, and the
  `NV2A_UNIMPLEMENTED` log never fires.

Only 0-2 are defined, so no known guest writes these values. The fix is to
store 3 (a sentinel that reaches the unimplemented branch) when `csc > 3`.

## LOW-2: colour key and alphakill now compare raw YCbCr

For a YUV texture, the colour-key comparison and alphakill now run on the raw
(Y, Cb, Cr, A) fetch, because the conversion comes after the stage loop.
Before this PR they compared decoded RGB. Hardware plausibly keys in the
texture unit, before the converter, but nobody measured it.

The scenario: a title colour-keys a YUV texture with an RGB key. It would stop
keying in hakuX, and hardware might agree. Record it as unmeasured in NOTES.
Do not change the code without a measurement.

## LOW-3: signed channels are clamped to 0..1 before conversion

`crycb_to_rgb` clamps `t.rgb` to [0, 1]. A stage with `tex_signed` or SNORM
channels under the field therefore loses its negative values before
conversion. Nobody measured this, and no known workload does it. A NOTES line
is enough.

## LOW-4: NOTES misstates where the field sits

`docs/lanes/yuv10/NOTES.md` says `PshState.color_space_convert` is "at the
front of the struct". The diff puts it after `final_inputs_1`. This has no
effect on behaviour.

## Not findings

- The BUMPENVMAP_LUM truncation applies only under the field, so Lum_Off still
  rounds where silicon truncates. The PR scopes this out on purpose, because
  those captures must not move. It is a later lane's arm and not a defect of
  this diff.
- Stages that do not fetch (NONE, PASSTHRU, CLIPPLANE, DOTPRODUCT) are not
  converted. That is unmeasured, and NOTES says so.
