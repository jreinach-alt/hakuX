# Audit pass 1: PR #334 (lane/fix311, issue #311)

Head audited: `24a7a0c866`. Read: `gh pr diff 334` (surface.c, prediction,
NOTES, read_soak.py, nv2a_index.json), plus the surrounding code in
`hw/xbox/nv2a/pgraph/vk/surface.c` and `system/physmem.c` that the hunk calls.

**Verdict: no HIGH, no MEDIUM. Three LOWs.** Next state: `needs-audit-2`.

## What the fix does, checked against the code

`update_surface_part()` takes a slot from `get_shelved_surface()` or
`get_any_compatible_invalid_surface()`; both `QTAILQ_REMOVE` it from their list
before returning. A slot retired dirty keeps `access_cb`
(`unregister_cpu_access_callback_if_clean`, surface.c:2074). Before this PR,
`*surface = target` overwrote that pointer with `target.access_cb`, which is
NULL (`memset(&target, 0, ...)` at surface.c:3464), so `surface_put()` ->
`register_cpu_access_callback()` -> `unregister_cpu_access_callback()` saw
NULL and the old `MemAccessCallback` stayed on `cpu->mem_access_callbacks`
for the life of the process. The diagnosis in the PR body is correct.

The new `unregister_cpu_access_callback(surface)` before the assignment:

- **Cannot remove someone else's watch.** `mem_access_callback_insert()`
  (physmem.c:880) allocates a fresh node per call and never deduplicates
  ranges; `remove_by_ref` frees exactly that node.
- **Cannot drop a watch another binding relies on.** `surface_access_callback`
  is registered with `opaque = d`, not the surface, and on a write walks the
  shelved and invalid lists by address. The reused slot has already left both
  lists, and every dirty binding that remains on them holds its own watch.
  The old writeback the watch guarded is discarded by `*surface = target`
  (it replaces `draw_dirty`), which is pre-existing behaviour this PR does not
  change.
- **Reads no uninitialised memory.** The fresh-slot path now uses
  `g_malloc0`, so `access_cb` is NULL there; without that change the new call
  would have passed heap garbage to `remove_by_ref`. Both halves are needed
  and both are present.
- **Has no sibling.** `*surface = target` occurs once (surface.c:3761). The GL
  renderer (`pgraph/gl/surface.c`) has no `_if_clean` retention, so it cannot
  leak this way.
- `xbox_ram_fp_cb_count_ptr` is defined under `#ifdef XBOX` in `tcg/tcg.c`
  and already referenced the same way from `system/physmem.c`; the extern
  links on every build that compiles `vk/surface.c`.

## Findings

### L1 (LOW, efficiency): a reuse of a dirty-retired slot now costs two synced TLB flushes

`mem_access_callback_remove_by_ref()` and `mem_access_callback_insert()` each
end in `tlb_flush_all_cpus_synced()`. On the path this PR touches, the remove
(new) is followed within the same `update_surface_part()` by the insert in
`surface_put()`, so a reused slot that still held a watch flushes twice where
it used to flush once. Bounded: only slots retired dirty carry a watch, and the
leak it replaces cost far more (29 vs 2 gfps). Failure scenario: a title that
reuses dirty shelved slots every frame pays one extra full TLB flush per reuse;
no correctness effect.

### L2 (LOW, quality): the `[watch311]` counter ships as a permanent 5 s log line

`surface_watch_log_periodic()` runs on every `pgraph_vk_surface_update()` and
logs every 5 s unconditionally: to logcat on Android, and via `fprintf(stderr)`
on desktop. This follows the `[surf91]`/`[surf92]` precedent in the same file,
and the counter is the only in-tree check that the leak stays closed, so
keeping it is defensible. Failure scenario: a desktop user running from a
terminal gets one stderr line every 5 s for the life of the process.

### L3 (LOW, evidence): two registered sub-legs failed and the dip on the Thor is unexplained

The PR body reports this honestly: arm A's end/30 s ratio is 4.2x and 3.3x
against a registered 5x (the leak is still present: 1,719 and 1,783 live
watches against 14 bindings), and arm B on the Thor has one gfps line at 8
against a registered floor of 15, with 29 on either side. Neither undercuts
the fix: W1's leak/no-leak separation and F1's median hold on both devices.
Failure scenario for the record: if the Thor 8-gfps line recurs on arm B in
later soaks, it is a separate stall not explained by the watch count (live=4
on that run). A second arm-B Thor soak would show whether it recurs.

- The prediction carries `expect` keys but no capture keys; the PR body
