# Audit pass 1: PR #244, lane wbuf31sel (#31)

Head audited: `a105a32af2` (diff against `origin/master`). Auditor: `[job.cloud]`, 2026-09-25.

**Verdict: no HIGH, no MEDIUM. Two LOWs.** The shader change does what the PR
says. The Python oracle computes `first` the same way the shader does, and the
arm result (570/570 byte-identical, status columns checked) is consistent with
the claim that no golden reaches the changed clause.

## What was read

- `hw/xbox/nv2a/pgraph/glsl/psh.c`, `wbufSlopeStep`: `first` hoisted out of the
  span loop; `flatTop` replaced by `first != clip.x` in the top-cut clause.
- `docs/testing/wbuf_anchor_recover.py`: new `span` mode, ClipF-300-008 prim,
  reporting for both modes.
- `docs/testing/predictions/wbuf31sel-spanclip.json`, `docs/lanes/wbuf31sel/NOTES.md`.
- `nv2a_index.json` regeneration and the `fits57.*` / `simulate.out` artifacts,
  which are lane evidence rather than shipped code; not re-derived here.

## Checked and correct

1. **The hoist.** The loop exits on `found` (`k < 4 && !found`), so after it
   `first` is the span start of the row that set `c` and `r`, not a later
   row's. When no row is found the function returns 0.0 before `first` is
   read. The declaration `float c = 0.0, first = 0.0;` is valid GLSL.
2. **Float robustness of `first == clip.x`.** On a left-clipped polygon `lo` is
   a `mix()` result within a few ulp of `clip.x`. For integer `clip.x`,
   `ceil(lo - 0.5)` is `clip.x` for any `lo` in `(clip.x - 0.5, clip.x + 0.5]`,
   so ulp error cannot flip the comparison. `clip` is
   `clipRegion[0] / surfaceScale`, and `clipRegion` is the unscaled rect times
   an integer scale, so `clip.x` is an integer at every scale.
3. **The exclusive-clip path** passes `±1e9`, so `cut` is false and `grid` is
   true before the new literal is read. It is unchanged from master.
4. **The oracle matches the shader.** Python's `anchor()` leaves `first` bound
   to the found row (it `break`s), and it returns before the `span` branch when
   nothing is found. This is the same literal the fit was scored on.
5. **The prediction** names both suites as must_not_move, gives failure worlds
   a golden would show (a broken hoist makes ClipF-150-* t1 read `first == 0`,
   and 0 is not 150), and does not open `expect`. The arm PASS and the status
   columns are recorded in the PR body and NOTES.

## Findings

### LOW-1: the swap also flips master's answer for pointed-top triangles, the common case, and no capture pins either answer

`flatTop` and `span_starts_at_clip` disagree in two quadrants. The PR's
evidence covers one of them (flat-topped with the span at the clip:
ClipF-300-008 t0, which moves from snap to grid). The other is a triangle that
is **not** flat-topped and whose first span starts **right of** the clip's left
edge. Master gives it the 4-grid; this PR gives it the 2x2 snap. No capture has
that shape: ClipF t1 is pointed but its span is at the clip, and every
clip_top 0 capture has `topCut` false.

Failure scenario, from the PR's own oracle: triangle (320,0) (200,300)
(440,300), clip (100, 8, 640, 480). `anchor(..., "sel")` gives row 10 and
`anchor(..., "span")` gives row 8. At clip_top 16 it is 18 against 16, and at
clip_left 0 it is again 10 against 8. In a game, a pointed-top triangle cut by
an 8-aligned scissor top, not touching the left edge, is the ordinary case. So
under W-buffering with a non-zero polygon-offset factor, this PR moves the
slope-offset anchor row by up to 2 for most scissored geometry, and nothing
measured says which row is right.

Why LOW: master's answer in that quadrant is just as unpinned, and the effect
is a one-step slope evaluation at a neighbouring row, so the blast radius is
small. But the PR body's framing, "keep every other term" and "replace flatTop,
keep everything else", reads as a change confined to the refuted case, and it
is not one. The NOTES line "the capture that would separate the 12 computable
fits ... has not been identified" should also name this quadrant. Suggested
fix, no code needed: add one sentence to the psh.c comment and NOTES saying
this quadrant is extrapolated. Name the separating console run: a pointed-top
triangle (a TriH-style primitive) under polygon offset, with the window clip at
clip_top 8 and clip_left well left of the triangle. `flatTop` predicts row 10
and `span` predicts row 8.

### LOW-2: "starts at the clip" also fires for an uncut left edge within half a pixel of `clip.x`

`first == clip.x` holds whenever the first row's `lo` falls in
`(clip.x - 0.5, clip.x + 0.5]`, whether or not the left clip cut the polygon.
The comment calls it "the first covered span starts right of the clip's left
edge", which matches the code. But the NOTES gloss the literal as "the span
begins at the clip", which suggests a cut. The Python oracle and the shader
agree, so no fit was scored on a different literal. Only the prose is loose.
No failure scenario beyond the ambiguity; quality only.
