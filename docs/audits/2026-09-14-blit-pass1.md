## Why this pass exists, and where the effort went

The commit is the best-verified change of the night: its helper was run as real
instructions over all 2²⁴ `(src, dst, β)` triples with 0 mismatches. **That is
the shape that makes a reviewer stop reading the callers**, which is exactly how
tonight's HIGH got in — `2026-09-14-remote-pass1.md` H1, a conversion correct
for the path it was written for and wrong in the one consumer of ten that read
its result unguarded, invisible to any test of the intended path.

So the arithmetic was not re-derived. The effort went to the callers, the
width tail, the type widths, the formats and the paths the sweep's domain does
not contain. The conclusion on the change itself is **clean**, and it is
recorded below as a result rather than padded out with a LOW.

## HIGH

### H1 — `blit.c:128` — `BLEND_AND` hard-codes 32bpp, and unlike the other two paths in this tree it has no `bytes_per_pixel` gate

`perform_blit()`'s `BLEND_AND` branch indexes `s[x * 4 + ch]` and
`d[x * 4 + ch]`, and its NEON body loads and stores 16 bytes per four pixels.
Its caller supports three pixel sizes:

```c
case NV062_SET_COLOR_FORMAT_LE_Y8:      bytes_per_pixel = 1;   /* blit.c:344 */
case NV062_SET_COLOR_FORMAT_LE_R5G6B5:  bytes_per_pixel = 2;   /* blit.c:347 */
case ...A8R8G8B8 / X8R8G8B8 / ..._Z8R8G8B8 / Y32:
                                        bytes_per_pixel = 4;   /* blit.c:350-354 */
```

`SRCCOPY` is format-correct because it `memmove`s `width_bytes`. `BLEND_AND`
takes `width` in **pixels** and multiplies by a hard 4. `bytes_per_pixel` is
threaded into `perform_blit_tiled()` (`blit.c:268`) and **never into
`perform_blit()`**.

**Scenario.** A guest sets `NV062_SET_COLOR_FORMAT` to `LE_R5G6B5`, sets
`NV09F_SET_OPERATION` to `BLEND_AND`, and writes `NV09F_SIZE`. `row_bytes` is
`row_pixels * 2`; the blend walks `row_pixels * 4`. Every row but the last
spills into the next row of the same surface; the last row writes past
`dest_offset + dest_size`, which nothing bounds — `pgraph_vk_image_blit()`
asserts only `dest_offset < dest_dma_len`, and `nv_dma_map()` has its
end-of-object assert **commented out**:

```c
assert(dma.address < memory_region_size(d->vram));
// assert(dma.address + dma.limit < memory_region_size(d->vram));   /* nv2a.c:96 */
```

The surplus bytes are also outside the range given to
`pgraph_vk_download_surfaces_in_range_if_dirty()` and outside the later
invalidate, so the write is invisible to surface coherency as well as being
outside the rect. On `Y8` the factor is four, not two.

**Why no golden sees it.** Every `BLENDAND` capture in the suite is `XRGB` or
`ZRGB` — 12 and 8 of them, all `bytes_per_pixel == 4`. There is no
`ImgBlt_BLENDAND_ARGB` and no 16bpp `BLENDAND` capture at all
(`docs/testing/run-2026-09-07-full-scores.tsv`). This is the rubric's
"wrong outside the cases the goldens exercise", exactly.

**The remediation is already written, 550 lines lower in the same file.**
`pgraph_vk_solid_line()` meets the identical question and answers it:

```c
/*
 * ... Every corpus case is A8R8G8B8, and what a 5-5-5 colour becomes in a
 * 1- or 2-byte destination is unmeasured, so the narrow cases say so rather
 * than inventing an answer.
 */
...
if (bytes_per_pixel != 4) {                     /* blit.c:689 */
    static bool warned;
    if (!warned) { warned = true; fprintf(stderr, "... not implemented\n"); }
    return;
}
```

Thread `bytes_per_pixel` into `perform_blit()` and give `BLEND_AND` the same
warn-once early return. **Do not invent a 565/Y8 blend** — silicon's behaviour
there is not on disk and an expansion would be a fit; a real narrow-format
blend is separate work wanting a capture behind it.

Two of the three paths in this tree that face this question are gated — the
solid line above, and the swizzle compute shader, whose hardcoded 4-byte
element `nv2a_issues.toml:125` records as unreachable because "both callers
gate on `bytes_per_pixel == 4`". `BLEND_AND` is the one that is not.

I did **not** establish that the overrun can leave the VRAM mapping entirely;
that depends on where the guest places the surface. The claim is corruption
beyond the blit rect, not a host-memory escape.

## MEDIUM

### M1 — `blit.c:47` — `blend_and_div()`'s `W < 2¹⁶` precondition is stated in a comment and enforced in a different module

`(W * 0x8081) >> 23 == W / 255` is exact for `W < 2¹⁶` and **silently** stops
being exact above it. `W` is bounded only because `beta_mult ≤ 0x7f80`, and the
only thing that bounds `beta_mult` is one line in another module:

```c
beta->beta = parameter & 0x7f800000;            /* pgraph.c:1951 */
```

Nothing in `blit.c` names that dependency, nothing asserts it, and the two
files carry no cross-reference. The same mask is what keeps
`inv_beta_mult = max_beta_mult - beta_mult` from underflowing — and
`inv_beta_mult` is used **unmasked** by the scalar path while the NEON path
truncates it to `uint16`. So if the invariant broke, the two paths would not
merely be wrong, they would be wrong *differently*.

**The margins, measured rather than argued:**

| | value |
|---|---:|
| largest reachable `W` | **65,152** |
| `W` where `(W * 0x8081) >> 23` first ≠ `W / 255` | 66,299 |
| `W` where `W * 0x8081` first exceeds 2³² | 130,559 |
| largest reachable `W * 0x8081` | 2,143,305,344 (0.19% under 2³¹) |
| results exceeding 255 | **0** — the `uint8_t` store never truncates |

1.76% of headroom, and **the first failure mode is a silently wrong pixel, not
a trap.** `pgraph.c`'s own comment signposts the future world: *"only 8
fractional bits are actually implemented in hardware"* — an invitation to widen
the mask if a later capture says otherwise. One step past it is already
catastrophic: `beta_mult = 0x8000` gives `inv_beta_mult = 0xFFFFFF80`, which the
NEON path narrows to 65,408 and which drives `W` to **195,712** — past both
thresholds above — while the scalar path overflows `uint32` in `b` alone.

**Remediation, and it is checked against the precedent that killed the last
one.** `assert(beta_mult <= max_beta_mult);` at the top of the `BLEND_AND`
branch. Pass 2 of this chain caught a remediation whose assert was *implied by
the condition it sat under* and could never fire. **This one is not implied:**
`beta_mult` is a dereference of state written in another translation unit, and
nothing in `perform_blit()`'s control flow constrains it. Nor is it a
guest-input assert turned into a DoS — the mask means no guest can reach it, so
it is an internal invariant, which is what `assert` is for. A comment in
`blend_and_div()` naming `pgraph.c:1951` as the enforcer is the cheaper
alternative and gives a mask change a thread to pull. **A remediation is a
claim**; the lane may decline the assert for the comment and log the reason.

## LOW

### L1 — `blit.c:49` — the NEON helper re-encodes `max_beta_mult` as four bare literals

`blend_and_div()` uses `0x3FC0` (= `max_beta_mult / 2`), the `>> 7` and the
`0x8081`/`>> 23` pair (= `255 << 7` factored) in a function that cannot see the
`uint32_t max_beta_mult = 0x7f80` at `blit.c:67`. The scalar path derives its
rounding term from the symbol; the NEON path does not.

No current defect — the two paths measure byte-identical. The failure is a
future one, **and it is the same shape as the defect this commit just removed**:
an edit to `max_beta_mult` updates the scalar tail and leaves
`blend_and_div()` dividing by 32,640, reintroducing a seam between the vector
body and the width tail visible only at widths not a multiple of four. That is
not hypothetical for this codebase — `c234c1cc3f` fixed "the NEON 565 body
disagreeing with its own scalar tail" (`nv2a_issues.toml:2869`).

Fix by hoisting the constant, or — better, since the 255-and-128 factoring *is*
the trick — `QEMU_BUILD_BUG_ON(max_beta_mult != (255u << 7))`. Reviewed-and-not-
fixed with that reasoning logged is an acceptable outcome.

## What held up — the clean results

These are the questions the pass was sent to ask, and the answers are all
affirmative. They are recorded because a clean audit is a result.

### The NEON body and the scalar width tail agree, on real instructions

This was the sharpest risk: the NEON path handles the vector body and the
scalar path the tail, a fix applied differently to one shows only at particular
widths, and **this tree has already shipped that exact bug once**
(`c234c1cc3f`). The `BLEND_AND` body of `perform_blit()` was copied verbatim out
of the commit, cross-compiled with NDK 29 clang and run under `qemu-aarch64`,
comparing the NEON-plus-tail row against a scalar-only row:

    rows checked (beta x content x width) : 278528     (256 betas x 64 contents x widths 1..17)
    NEON-body vs scalar-only mismatches   : 0
    alpha bytes changed by NEON path      : 0
    old >>15 vs new, low / high           : 8388608 / 0

Zero at every width from 1 to 17, across all 256 reachable β. The `vbslq_u8`
that restores destination alpha agrees with the scalar loop's `ch < 3`: alpha
never moves on either path.

This matters more than it looks, because **the tiled path is almost entirely
the scalar tail.** `perform_blit_tiled()` calls `perform_blit()` with
`width = chunk / bytes_per_pixel` where `chunk ≤ 16` (`blit.c:284`), so width
is 1–4 and the NEON loop's `x + 4 <= width` fires only on a 16-byte-aligned
full chunk. Before this commit those pixels were divided differently from the
linear path's vector body; now they are not.

### The reachable domain is the swept domain, and the callers add nothing to it

`beta->beta` has exactly **one** write site (`pgraph.c:1943-1951`), is absent
from every vmstate description, and lives inside the QOM-allocated `NV2AState`,
so `0` is its only uninitialised value. Masked values are `k * 0x80` for
`k = 0..255` — 256 of them. The commit's 2²⁴ sweep is `256 × 256 × 256`, i.e.
**exhaustive over the true domain, not a sample of it.**

Entry points enumerated in full: `pgraph.c:2110` → `renderer.c:1757` →
`pgraph_vk_image_blit()` at `blit.c:306`; three direct `perform_blit()` sites
(`blit.c:282`, `496`, `519`) and two `perform_blit_tiled()` sites (`489`,
`510`). None of them reaches the arithmetic with a β outside the mask.

### Empty and degenerate rects cannot reach it

`pgraph.c:2109` gates the whole blit on `if (image_blit->width && image_blit->height)`,
so the `(height - 1)` in `dest_size` cannot underflow and `perform_blit()` is
never entered with a zero extent. The `leftover_bytes > 0` and
`adjusted_height > 0` guards cover the clipped-tile split.

### The half-tie ambiguity is not merely unmeasured — it is unreachable

The investigation and the prediction both say, correctly, that no triple in the
2²⁴ domain is an exact half-tie, so the data cannot distinguish round-half-up
from round-half-even. Both code paths nonetheless *commit* to half-up
(`+ max_beta_mult / 2`, `+ 0x3FC0`). **Nothing justifies half-up over half-even,
and nothing needs to**, because no tie can ever occur while the mask holds:

- β is always `128k`, so `V = src·β + dst·(0x7f80 − β) = 128·(src·k + dst·(255−k))`
  is always a multiple of 128;
- a tie needs `V mod 32640 == 16320`, and `16320 / 128 = 127.5`.

`V mod 32640` is a multiple of 128 and 16320 is not, so the tie set is empty by
construction rather than by luck of the sweep. Confirmed: **0 ties over the full
domain.** This upgrades the doc's "this data cannot distinguish" to "nothing
can, while the mask holds" — and note it rests on the same invariant as M1, so
the mask is load-bearing twice.

### The numbers in the commit message and in the new comment both reproduce

Independently, on this box: the replaced `>> 15` measures **8,388,608 low / 0
high** (commit message), and the replaced truncating scalar divide measures
**8,164,890 low / 0 high** (the new comment at `blit.c:122-125`). Both exact.

### Neither precedent shape is present

- **An assert implied by the condition it sits under.** The commit adds no
  assert. The only one in the function (`assert(false && "Unknown blit
  operation")`) is untouched and reachable, which is the point of it.
- **A hard-coded identity asserted as an invariant.** The identity that *is*
  asserted — `floor(floor(x/128)/255) == floor(x/32640)` — is a true nested-
  division identity for all `x`, not a fitted one. The claim that is assumed
  rather than proved is `W < 2¹⁶`, and that is M1.

### The prediction is well-formed

`expect` names all 20 `ImgBlt_BLENDAND_*` captures in the suite plus
`BlitRenderBlit` — no BLENDAND capture is missing a leg — and every leg is an
absolute the goldens constrain, not a quantity this patch constructs. The eight
`Overlap_*` and the three `SRCCOPY` captures are on `must_not_move`. No leg
names a capture that does not exist.

## Considered and not filed

Recorded so silence is not mistaken for having missed them.

- **`assert(false && "Unknown blit operation")` is guest-reachable.**
  `image_blit->operation` is stored unmasked from the pushbuffer
  (`pgraph.c:2087`), so any third value aborts the emulator. This is the
  established xemu idiom for unhandled guest state throughout this tree and is
  nowhere near this diff; filing it here would be scope creep.
- **`chunk / bytes_per_pixel` truncates in `perform_blit_tiled()`** if a tile
  offset is not pixel-aligned, dropping a partial pixel from a `BLEND_AND`.
  Pre-existing, and I found no path that produces a non-4-aligned offset —
  **no failure scenario, therefore an opinion.** Downgraded out.
- **`unsigned int x` against `size_t width`** in both loops would spin if
  `width > UINT_MAX`. `row_pixels` is bounded by a 16-bit `NV09F_SIZE` field
  and by `pitch / bpp`. Not reachable; an opinion.
- **`nv_dma_map()`'s disabled end-of-object assert** (`nv2a.c:96`) leaves the
  blit extent unbounded for *every* format, not just the narrow ones. It is
  upstream xemu's own TODO and belongs to whoever owns that file; it is cited
  inside H1 as the reason H1's overrun is not caught, not filed separately.

## What could not be audited

- **Neither build was run.** The desktop half is the named, verified gap:
  `dpkg -s libcurl4-openssl-dev` reports *not installed* on this host as of this
  pass, and there is no `build/` tree. **I did not build desktop and am not
  claiming I did.** What I *can* say about desktop is narrower and true: the
  scalar path is the entire path there, the changed expression
  `(a + b + max_beta_mult / 2) / max_beta_mult` introduces no intrinsic, no new
  symbol and no new include, and compiled natively for x86-64 with gcc it
  produces round-half-up with no overflow over the full reachable domain.
  `docs/testing/check_android_guards.py` passes (3,298 files) — that catches the
  Android-only-symbol class, not a link error. The Android build was not run
  either; this is an auditor and holds no files.
- **`BLEND_AND` alpha semantics on `A8R8G8B8` are unverifiable from this
  corpus.** Both paths deliberately preserve the destination alpha. The two
  formats the goldens cover — `XRGB` and `X8R8G8B8_Z8R8G8B8` — have their alpha
  overwritten afterwards by `patch_alpha()` (`blit.c:526-540`, `550`), and there is no
  `ImgBlt_BLENDAND_ARGB` capture. So the investigation's *"alpha differing: 0"*
  row is evidence that `patch_alpha` ran, **not** evidence that the alpha
  handling is right. Whether silicon blends alpha on an alpha-bearing
  `BLEND_AND` is unestablished and cannot be established from anything on disk.
  This is a coverage gap, not a finding — it has no demonstrated failure. It is
  raised in the board request as a candidate capture.
- **Nothing here is a device measurement.** The arm's own result judges the
  pixels; this pass judges the code around them.

## Disposition

The change itself is correct, its two paths agree with each other and with
round-to-nearest over the entire reachable domain, its type widths hold with
measured margin, and its callers introduce no input the sweep did not cover.
**M1 and L1 are against the commit and are cheap.** H1 is against the function
and predates it, and should be routed rather than allowed to hold the fold.
