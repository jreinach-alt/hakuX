## H1 — HIGH. Model E is derived from a path that is compiled out of the build the registered arm runs, and the path that build does take asserts on the undersized condition

The derivation names its mechanism by quoting the write:
`dst_row = linear_guest + y * surface->pitch` (investigation doc, "the
one-paragraph derivation"; repeated in the prediction's `prediction` field).
That string occurs once in the GL renderer, at
**`hw/xbox/nv2a/pgraph/gl/surface.c:2075`**, inside
`android_surface_download_depth16_to_guest()` — an `#ifdef __ANDROID__`
function for **depth16** surfaces. It cannot run for the A8R8G8B8 colour
render target the whole document is about, and it does not exist at all in a
desktop build.

`surface_download_to_buffer()` (`:2310`) has three shapes for a swizzled
download, and the PR treats them as one:

| path | condition | behaviour at `pitch < width*bpp` |
|---|---|---|
| A — Android RGBA8 | `__ANDROID__` **and** `android_surface_uses_rgba8_transfer()` (`:2394`, true for A8R8G8B8, `:154-168`) | Model E, via `android_surface_rgba8_to_guest(..., linear_guest, surface->pitch)` at `:2424`, `dst_row = dst + y*dst_stride` at `:816` |
| B — generic, unscaled | otherwise, `surface_scale_factor == 1` | Model E, via `glo_readpixels(..., surface->pitch, width, height, ...)` at `:2465` |
| C — generic, scaled | otherwise, `surface_scale_factor != 1` | **`assert(surface->pitch >= (surface->width * surface->fmt.bytes_per_pixel));`** at `:2473` |

Path C is not hypothetical. `pgraph_gl_surface_download()` calls
`surface_download_to_buffer(d, surface, true, false, true, ...)` at **`:2524`**
— `downscale` is passed `true` unconditionally for every surface→VRAM
download — and the only thing that turns it off is
`downscale &= (pg->surface_scale_factor != 1);` at **`:2322`**. So on any GL
run with a scale factor other than 1, a swizzled surface whose pitch is
undersized aborts.

Two consequences, and the second is the one that matters for the artifact:

1. The document enumerates crash paths deliberately — it lists `:2851`'s
   `assert(surface->pitch % fmt.bytes_per_pixel == 0)` as "a crash path if
   silicon accepts it" — and misses `:2473`, which asserts the undersized
   condition **itself**, the subject of the entire lane. Nothing anywhere in
   the surface-creation path forbids `pitch < width*bpp`: `:2850`/`:2851`
   check the DMA limit and `pitch % bpp`, not the width relation.
2. The registered arm is a **desktop** pair (`a_ref`/`b_ref` are
   `4129a349e6 with xemu.toml [display] renderer = OpenGL|Vulkan`, and the
   document says the renderer is an `xemu.toml` key). Path A is
   `#ifdef __ANDROID__`, so the desktop GL arm is Path B or C, never the one
   the derivation quotes.

**Failure scenario.** Someone lands the one-line renderer override the PR asks
for and queues the arm on a desktop build with `surface_scale_factor != 1` —
the default for anyone who has ever touched the scale setting, and not pinned
anywhere in the registration. The GL arm aborts inside
`pgraph_gl_surface_download_to_buffer` on the `Surface_pitch/Swizzle` capture.
`expect_counts.better = 1` fails, and it fails for a reason that has nothing to
do with either model. The prediction states flatly: *"Either outcome settles
it; there is no result that leaves the question open, which is the point of
registering it this way."* There is a third result, it is reachable from the
arm as written, and the registration does not exclude it.

**Remediation.** State which of A/B/C the derivation models and which the arm
runs; pin `surface_scale_factor = 1` in the registration (or say the arm is an
Android-device arm, in which case Path A holds and the `xemu.toml` refs are the
wrong refs); and add `:2473` to the crash-path list beside `:2851`, because it
is the assert keyed on this lane's own subject.

## M1 — MEDIUM. Every `vk/surface.c` line citation is already wrong on master, and one of them now points at the opposite of what it claims

The PR cites `vk/surface.c` by line ten times. `hw/xbox/nv2a/pgraph/vk/surface.c`
has changed by **+283 / −4** between this lane's base and `origin/master`, all
of it above the cited region, and every citation is out by roughly 206 lines:

| cited | claimed to be | what is there on `origin/master` | actually at |
|---|---|---|---|
| `:587` | `dl->use_compute_to_swizzle = false` | `vkCmdCopyImageToBuffer(...)` | `:793` |
| `:593` | `surface_vram_written(..., pitch*height, ...)` | inside a barrier struct | `:800` |
| `:650` | `g_malloc(dl->pitch * dl->height)` | `VkBufferCopy buf_copy = {...}` / `vkCmdCopyBuffer` | `:856` |
| `:858` | the `use_compute_to_swizzle` gate, "no pitch anywhere" | **the deferred CPU `swizzle_rect(..., dl->pitch, ...)` block** | `:1064` |
| `:664-669`, `:741-746` | the dirty-range calls | unrelated | `:1551/1554`, `:1749/1752` |

`:858` is the damaging one. The document's load-bearing claim is *"Vulkan's
synchronous download never uses pitch … `vk/surface.c:858` … no pitch
anywhere."* On master that line number lands inside the **deferred** CPU
swizzle, the one place in the file that does take pitch and the one the same
document flags for a tracker row. A reader checking the claim finds the
contradiction of it under the pointer given.

This is not a novel hazard here: `origin/master` carries
**`3c2f6622c5`, "nv2a/vk: cite surface.c by symbol — L4's drift, five more
times"**, committed 2026-09-19 03:05Z — 67 minutes before this prediction's
`registered_utc` of 04:12:36Z — whose message says all five by-line citations
into this file "were correct when written and all five were wrong within a
day". This PR adds ten more.

**Failure scenario.** A remediation lane or the tracker row this PR recommends
opens `vk/surface.c:650` on master, finds `vkCmdCopyBuffer`, and concludes the
over-read was fixed or fabricated — when it is alive at `:856`, byte for byte
as described.

**Remediation.** Cite by symbol, as `3c2f6622c5` did: name
`pgraph_vk_complete_staged_downloads`'s `dl->swizzle` branch, the
`use_compute_to_swizzle` initialiser in the synchronous download, and
`download_surface_record_deferred`'s assignment. The `gl/surface.c` citations
need no change — that file is unmodified since the base.

## M2 — MEDIUM. The "seven sites" `pitch * height` enumeration is presented as complete and is short by at least seven, including the synchronous path's own

The prediction says: *"This is the claim behind **seven sites** that use
`pitch*height` as the surface extent: `gl/surface.c:2850` and
`vk/surface.c:3109` …, `vk/surface.c:593` … and **the four**
`memory_region_set_client_dirty` calls at `vk/surface.c:664-669` and
`:741-746`."* Both "seven" and "the four" read as exhaustive. At the lane's own
base, `grep` for the extent expression in `vk/surface.c` alone returns
**thirteen** sites:

```
594, 650, 665, 668, 742, 745, 1343, 1345, 1348, 1543, 1546, 1627, 1630
```

Seven of those are unlisted, and they are not incidental:

* **`:1343`** — `surface_vram_written(r, surface->vram_addr, surface->pitch * surface->height, surface);`
  immediately after `download_surface_to_buffer()`. This is the *same call, the
  same expression, the same defect* as the enumerated `:593/:594`, on the
  **synchronous** download path — the path this document elsewhere calls
  "Model H by construction". Its extent under-reports exactly as the deferred
  one does.
* **`:1345/:1348`**, **`:1543/:1546`**, **`:1627/:1630`** — three further pairs
  of `memory_region_set_client_dirty(..., pitch * height, ...)`, so the dirty
  range misses the second half in six places, not two.

**Failure scenario.** A lane takes "seven sites" as the fix list for the
extent question — which is precisely how the prediction frames it, as "the
claim behind seven sites" with hardware leg 1 written to settle it. It patches
seven, the arm confirms Model H, and the synchronous download path and three
more dirty-range pairs are left under-reporting. The bug survives a fold that
was reported as closing it, and the next reader has a list that says the work
is done.

**Remediation.** Either enumerate all thirteen (plus the `gl/surface.c` ones),
or replace the count with the grep that produces it, so the list cannot drift
from the code.

`origin/master:docs/testing/jobs/roles/lane.md:48` already reads
`docs/lanes/<your lane name>/NOTES.md`, with the reason on the next line.
`origin/master:docs/lanes/notespath/NOTES.md` is the record of the lane that
changed it: *"`roles/lane.md` item 3 used to ask for `NOTES.md` in the branch
root, and the first lane to fold landed one on master, after which every fold
conflicted on that exact path."* Master now carries fourteen
`docs/lanes/<name>/NOTES.md`, **including the sibling `docs/lanes/cloud-110/`**,
and no root `NOTES.md`.

This lane's worktree is 128 commits behind and read the stale local copy of
`roles/lane.md`, which still says "branch root" — so the lane followed a
written rule. The consequence is a property of the fold, not of the intent.

**Failure scenario.** `fold.sh`'s `resolve_root_notes()`
(`origin/master:docs/testing/jobs/fold.sh:69-90`) fires **only when root
`NOTES.md` is an unmerged path** (`:72`). Master has no root `NOTES.md`, so
folding #115 is a clean add and the guard never runs: `lane/cloud-109`'s notes
land at the repository root permanently. The *next* lane with a root
`NOTES.md` then conflicts, `resolve_root_notes` fires, and `:84-85` keeps
**master's** copy — i.e. cloud-109's — at the root and moves the newcomer's to
`docs/lanes/`. The exact steady state `notespath` was opened to remove, seeded
by this PR, and thereafter permanent.

**Remediation.** `git mv NOTES.md docs/lanes/cloud-109/NOTES.md` and update the
PR body's `Files:` line. One commit; no content change.

## M5 — MEDIUM. The falsifier's negative result is drawn from captures on a path the same document proves cannot exhibit Model E

The PR's headline is *"the undersized-pitch rule does not explain #87's
residual, and #109 should stop claiming it as a lead"* — a conclusion the board
would act on. Three bullets carry it. One of them is sound and one is not:

* **Sound.** The *golden* is identical across the pitch-512 and pitch-256
  members of the same 128×128 surface. That is hardware, and it establishes
  that hardware ignores pitch at the one-half ratio for a power-of-two width.
* **Not discriminating.** *"…and **our capture** [is] identical across that
  pair, 0 px"*, and *"#87's residual was identical on **both** 128-wide
  quads"*. Both are observations about our capture. The same document
  establishes, twice and correctly, that **every clean number on
  `Surface_pitch/Swizzle` is Vulkan**, and that Vulkan's synchronous download
  takes the compute swizzle where *"pitch never enters at all"*, so *"a Vulkan
  0 is consistent with both models and discriminates neither."* On a Model-H
  path the two quads are identical **by construction** — which is exactly what
  was seen. The absence of the asymmetry is entailed by the path, not evidence
  against the rule.

The document never says which renderer produced #87's residual, in a document
whose whole thesis is that the renderer decides which model applies.

**Failure scenario.** The board reads "the rule predicts an asymmetry that was
measured and is not there", drops #109's link to #87, and closes the lead. If
the residual capture was Vulkan — which the document's own survey says every
clean one is — nothing was measured about Model E, and the very GL arm this PR
registers exists because that measurement has never been taken. The
cross-renderer table the PR itself cites shows `Surface_pitch/Swizzle` at
GL 15,360 against VK 10,240 on 2026-09-13: the two renderers **do** differ on
this capture, which is the opposite of reassuring for an argument that rests on
a Vulkan capture standing in for both.

**Remediation.** Name the renderer behind #87's residual. If it is Vulkan, the
headline narrows to what the golden alone supports — hardware ignores pitch at
the 1/2 ratio, so #109's *hardware* rule is confirmed, not refuted, and the
lead on #87 is unsupported-because-unmeasured rather than falsified. That is a
different sentence and a different instruction to the board.

## L3 — LOW. `must_not_move` is byte-exact across two different renderers, on ten controls that are nonzero on both

`ab_compare.py:896-930` treats `must_not_move` as bit-identical, with the byte
leg firing on `pixels_moved_attributable`. Ten of the fourteen controls are
nonzero-but-equal cross-renderer (4,419 … 32,667), and score equality in the

a control violation that masks the discrimination rather than a clean verdict.
Worth registering the expectation that a first run may need the controls
re-scoped to `must_not_regress`.
