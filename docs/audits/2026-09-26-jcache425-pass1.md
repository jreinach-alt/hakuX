# Audit pass 1: PR #443, lane.jcache425 (#425)

Diff audited: `master@9f34d60036..a506db0f94` (6 files). Only
`accel/tcg/cpu-exec.c` ships code; the rest is lane notes, two lane scripts
and two predictions.

**Verdict: no HIGH, no MEDIUM, three LOW.** The PR goes to `needs-audit-2`.

## What the code change does

- `tb_lookup()` gains a `caller` argument. All three call sites pass one
  (`helper_lookup_tb_ptr`, `cpu_exec_step_atomic`, `cpu_exec_loop`), so the
  compiler would catch a missed site.
- Under `XBOX`, each probe increments exactly one outcome counter: hit,
  empty, pc collision, CF_INVALID stale, or key mismatch. Each miss also
  increments one qht counter (found or none). The classification sits after
  the hit test and reads only `tb` and `jc->array[hash].pc`, which the hit
  test already loaded. It changes no control flow, and the fill of the slot
  after a qht hit is untouched.
- `jc425_tick()` is called beside `hakux_tlb68_tick()` inside the existing
  `#ifdef XBOX` block (cpu-exec.c, the tlb68 gate). It rate-limits itself to
  one `[jc425]` line every 2 s.
- Buffer bound: each caller segment is at most 7 x (4 + 20) = 168 bytes, and
  3 segments come to 504 bytes, which is less than the 512-byte `buf`.
  `snprintf` is bounded by `sizeof(buf) - off` in any case, so truncation
  cannot overrun.
- Thread safety: the counters are plain statics, incremented and read on the
  vCPU thread. `cpu_exec_step_atomic` also runs on that thread, under
  exclusive. An Xbox has one vCPU, so there is no second writer.
- Non-XBOX builds: `JC425_COUNT` is empty and `caller` goes unused. QEMU does
  not build with `-Wunused-parameter`, so this raises no warning.

Pixel inertness is evidenced as well as argued. NOTES records both disc
pairs, 593/593 byte-identical: master vs `1b43be6b3a`, and JC off vs JC=1 on
`1b43be6b3a`.

## Findings

### L1 (LOW): the counters and the 2 s WARN line ship unconditionally in every XBOX build

`JC425_COUNT(caller, JC425_HIT)` sits on the hit path of
`helper_lookup_tb_ptr`, which is about 10% of the guest thread on the Crimson
route. It is not gated by an env var. `[jc425]` then logs at WARN every 2 s
for the life of every session.

- **Scenario:** a user build runs for hours and emits a line every 2 s, and
  pays a store to a global array on every indirect branch.
- **Blast radius:** both arms of every A/B carry it, so no measurement in
  this PR is biased. The cost is a single increment.
- **Suggestion:** gate the counters behind the same switch as `[tlb68]`, if
  one exists, or remove them once #425's lever lands.

### L2 (LOW): `perfsum.py` drops the logcat date, so a soak that crosses midnight gets a wrong window

`ts()` parses only `HH:MM:SS.mmm`. If a soak crosses 00:00 device time, then
`t0 + 90 .. t0 + 240` selects nothing after the wrap, and the window is
silently truncated. It still prints numbers, but `n=` shrinks.

- **Scenario:** a run that starts at 23:58.
- **Blast radius:** a lane tool only. None of the six runs cited in NOTES
  crosses midnight, so the reported table stands.

### L3 (LOW): `perfsum.py`'s `[jc425]` sum also totals `w`, `dt` and `jc`

`re.findall(r'\b([a-z]+)=\d+', ...)` picks up the header fields, and the
script prints their sums next to the counters. `w` and `jc` sums are
meaningless. This is harmless because the F2 ratios are computed from the
named counters, but a reader could take `jc=<sum>` for a state.

Nothing in the shipped behaviour needs re-verifying. Pass 2 only checks
