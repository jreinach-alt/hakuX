## Checked, no finding

- **The emitter (`profile.c`).** It sits inside the existing `#ifdef __ANDROID__`,
  `frame_count % 60 == 0` block. `now` is the flip's µs clock, the same one used by
  `pace_max_us`. Every `ShaderPipelineStats` field is `unsigned int` (`debug.h:179`), so `%u`
  is correct. `dt_ms` is cast to `long long` for `%lld`. The first line prints `dt_ms=0`, and its
  deltas equal the totals because `prev` starts at zero. The reader handles this: that window
  cannot be a stall or a base-rate sample (`0 < dt_ms`). The counters only ever increase. The two
  `pipeline_cache_misses++` sites (`vk/draw.c:1882`, `:2323`) run on the thread that calls
  `nv2a_profile_flip_stall` (`pgraph.c:2685/2702`). A concurrent writer can therefore at most drop

## LOW-1: the comment says an async enqueue counts as a miss; the code does not count it

`profile.c`'s new comment and NOTES §1 say "a miss is a `vkCreateGraphicsPipelines`, or an async
enqueue". In `vk/draw.c`, both `OPT_ASYNC_COMPILE` early returns (`snode->pending`, and
`xemu_get_async_compile() && !ready`) come *before* `pipeline_cache_misses++` at `:2323`. Those two
sites are the only increments in `vk/`.

Scenario: someone reruns this instrument with async compile on. `g_xemu_async_compile` defaults to
false, so both of this PR's runs were synchronous. In an async run, a scene load that enqueues its
pipelines shows `dpm` near 0 in the stall window. The misses land in a later window, or never, if
the entry is later found to be a hit. Read through this comment, that looks like P1's "time goes
elsewhere" world, but it is not. Fix: the comment should say a miss is counted only when the
create runs inline.

## LOW-2: `registered_utc` postdates the run it governs

The prediction says `"registered_utc": "2026-09-28T05:05:00Z"`. The pilot was queued at 04:53:10Z,
and the commit that holds the prediction is dated 04:53:04Z. Scenario: a reader checks
pre-registration from the file alone. They see a prediction registered 12 minutes after its pilot
was queued, and they discount the legs. The field should read 04:53Z, or no later than the commit
time.

## LOW-3: P1's rate clause is inert when the base is 0, and co-occurrence cannot separate compile from load work

In both runs the non-stall median miss rate after 60 s is 0 (`infx base` on every stall line).
Any stall with even one miss therefore passes the ">= 5x base" clause, so the only part of P1 that
could discriminate was `dpm >= 30`, and it failed. The NOTES' "the compile explanation for this
load stands" rests on:

- misses occurring together with stalls, and
- doa413c's simpleperf profile, which is outside this PR.

Co-occurrence does not tell apart "the time is the compile" from "a scene load both brings new
shaders and spends its time on something else". The §8 bounds survive this. "Saves <= the excess"
holds whatever the mechanism, because a fix cannot save more than the excess. The per-pipeline
prices are a different matter. 485 ms, 780 ms and 1.24 s are excess divided by `dpm`, so they are
upper bounds on compile cost, not measurements of it. The PR body's table heads that column
"excess / miss", which is accurate, but NOTES §7 calls them "ms per pipeline". The §9 `dpc_ms`
falsifier is what settles this, and the NOTES already name it.

A smaller point in the same section: the title-stage "neighbouring zero-miss" floor of 2105 ms comes
from a window that carries `dpm=2`. It is not zero-miss, though the post-stall windows (1.7-2.5 s)
give nearly the same floor.

## LOW-4: `shdwin.py` breaks if a soak crosses 00:00 on the device clock

`secs()` turns the logcat stamp into seconds of the day and ignores the date. The pilot's lines are
stamped `00:07:55` device time, so a run a few minutes earlier would have crossed midnight. After
the crossing, `t` jumps back by 86400 s. `w["t"] - t0 >= 60` then fails for every later window,
which empties or skews the base rate. Marks after midnight also sort before `t0`, so the
`[after mark ...]` labels are wrong. Scenario: a soak that starts at 23:58 device time reports a
base rate taken only from the first 2 minutes, and puts `mark play` before `booted`. Fix: carry the
`MM-DD` into `secs()`, or add 86400 when `t` goes backwards.
