**Result: no HIGH, no MEDIUM, 3 LOW.** Next state: `needs-audit-2`.

## What was checked, and held

1. **The gate is exact.** `tex_y16[i]` is set only for SZ_Y16 and LU_IMAGE_Y16
   (`psh.c:491`), next to `tex_comp0_const`, inside the per-stage loop that
   writes every other per-texture field. `PshState` is hashed whole
   (`vk/renderer.c` fast_hash over the state), so the new field reaches the
   shader key. No other format can take the new branch.
2. **The branch reads the raw 16-bit value.** Y16 is `R16_UNORM` / `GL_R16`
   with the view swizzle {ONE,R,R,ONE} (`vk/constants.h:347,388`,
   `gl/constants.h:349,357`), so `t<k>.b` is the filtered 16-bit value over
   65535. Two rewrites of `t<k>` could have got in first, and neither does:
   - the `tex_bytes16` byte split (`psh.c` ~:3427) and
   - the per-channel `signed_channel` fixup (~:3449)
   are both skipped under `stage_consumed_raw`, which is true for
   BUMPENVMAP and BUMPENVMAP_LUM consumers. Even if the byte split did run,
   `(b0*257) & 255 == b0`, so the expression still yields the low byte.
   `snorm_tex` is false for Y16 (it has no signed variant), so `t.b` is in
   [0,1] and `uint(round(t.b*65535.0))` never casts a negative float.
3. **Only component 2 changes.** Both call sites (`psh.c:3110`, `:3145`) pass
   comp 2 with `luminance = false`, so skipping the luminance sub-cases in the
   early return loses nothing. Component 1 and component 0 take the old paths
   unchanged.
4. **Deliberately ignoring BSIGNED on Y16 comp 2** is documented in the code
   and NOTES with its silicon basis (the four flag quads differ only by the
   A8 positional floor). This is a claim the measured result is consistent
   with, not a missing case.
5. **Prediction scoping.** `must_not_move` globs (`BumpMap_[!Y]*`, `_Y8*`,
   `_YUY2*`, and the same for BumpEnvLum) leave exactly the four Y16
   captures unscoped. `BumpEnvLum_Y16*` is `must_not_regress`, and
   `expect_counts` is better=2, worse=0. Together the registered checks
   force the two movers to be Y16 captures that did not get worse. The
   `[job.arms]` PASS (a 081dcf4a38 → b 50b46b0495) shows 22,374 → 3,490 on
   BumpMap_Y16 and _Y16_L, with 139 captures the same.
6. **Arm integrity.** a_ref and b_ref are ancestors of the head. NOTES says
   the branch was merged, never rebased, and the only `hw/` difference
   between the refs is the fix. CI `build` ×2 and `check` pass on d2ddc74ad8,
   and GitHub reports the PR MERGEABLE against the current master
   (db73a7fb99).

## Findings

### L1 (LOW): the numeric bounds are prose, not registered legs

`expect` is `{}`. The "< 6,000 px each" bound (in the PR's leg table) and the
"moves but stays above ~15,000 refutes" rule exist only in the `prediction`
string, and `ab_compare.py` does not judge that string. The verdict's "all
141 registered checks hold" is accurate, but it does not cover those two
bounds. **Failure scenario:** a B at 12,000 px would have printed the same
PASS. That did not happen here (3,490), so no conclusion in the PR is wrong.
A future Y16 arm (the vertical-source follow-up) should register the bound as
a capture-keyed `expect` entry, so that it is judged.

### L2 (LOW): the low byte depends on the host's R16_UNORM filter precision

The expression takes bits 0-7 of a *filtered* 16-bit value. A host GPU that
filters 16-bit UNORM through a lower-precision intermediate (for example
fp16, whose ulp near 0.32 is about 16/65535) would quantise the low byte
to coarse steps. The seam sweep would then become a staircase. This has been
measured on the arm device only. **Failure scenario:** a different Vulkan
driver that filters R16 at reduced precision leaves BumpMap_Y16 above 3,490.
There is no evidence that any supported device does this, so this is a note
for the cross-device pass, not a defect.

### L3 (LOW): the 1,914 px residual is attributed but not tested

NOTES and the PR attribute the residual above the 1,576 floor to the vertical
source (full value vs high byte). That is plausible from PR #363's m11-only
figures, but no arm tested it. It is labelled as open, which is correct. It
should be read as a hypothesis for the next lane, not as a finding of this
one.
