# Audit pass 2: PR #336, lane/nanfix281 (#281)

Head audited: `1700e41f63` (code at `a6227fea68`). Pass 1: `2026-09-25-nanfix281-pass1.md`
on `8289ffaccb`.

**Result: clean → fold-ready.** The MEDIUM-1 scenario can no longer occur and
LOW-2 is fixed. LOW-1 is still LOW, and the lane recorded it in NOTES.

## MEDIUM-1: host-signed NaN from ADD/MAD/DP* reaching `NaNToSignedOne`: closed

`vsh-prog.c` now defines one `_PosNaN(v)` helper
(`mix(v, +NaN, isnan(v))`) in `vsh_header`, ahead of every op that uses it.
It wraps the result of `_MUL`, `_ADD`, `_MAD` (after the add), `_DP3`, `_DPH`,
`_DP4`, DST's `y` product, `RCP`, `RCC`, `RSQ`, `EXP`, `LOG` and `LIT`.

Re-running the pass-1 scenarios against the new code:

- `MAD oD0, v0, c[k], v3` with -NaN in `v3`: `_MUL` is finite, `+ src2` gives
  the host's NaN (either sign), and `_PosNaN` makes it +NaN. `NaNToSignedOne`
  gives +1 and the vertex draws white, which is master's output.
- `ADD oD0, r0, v3` with -NaN `v3`: `_PosNaN(src0 + src1)` gives +NaN and
  draws white.
- A host whose default NaN is negative (`INF + -INF` → 0xFFC00000) in
  ADD or DP*: `isnan` is true whatever the sign, so the result is +NaN and
  draws white.

I walked every op in `vsh_header`. The ones left without the helper cannot
produce a new NaN. `MOV`, `MIN` and `MAX` return an operand, which is the
measured passthrough case and a stated choice in the PR body. `SLT` and `SGE`
return 0/1 from a bool vector. `ARL` writes an int address register. `DST`'s
x, z and w components are a constant 1.0 or a copied operand. The early
returns in `RSQ` and `LOG` are ±INF, 0 or 1, never NaN. No op in the
vertex-program path can now hand the colour map a NaN whose sign came from
host arithmetic.

Non-NaN lanes are bit-identical through `mix` with a false mask, so finite and
±INF results cannot move. The `NaN x 0 = 0` forcing in `_MUL` still runs
before `_PosNaN`.

Compile risk: `_PosNaN` uses the same expression that pass 1 checked inside
`_MUL`, and that expression compiled on the device in the first arm.
`_PosNaN` is defined once, only in `vsh_header` (grep: no other definition
in `hw/`), and it precedes its first caller. The re-registered arm on
`a6227fea68` is still queued and will confirm the compile. If the arm fails, the
fold gate refuses the PR anyway.
