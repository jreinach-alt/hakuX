# Audit pass 2 -- PR #419 lane.yuv10 (#10 SET_CONTROL0 colour-space conversion)

Head audited: `268f74d5e5` (`lane/yuv10`). The pass-1 file is
`docs/audits/2026-09-26-yuv10-pass1.md`, written at `c3d401ad6b`. The
remediation is the single commit `268f74d5e5`, which touches `psh.c`,
`pgraph.c` and the lane NOTES.

**Verdict: every pass-1 scenario is closed in the code. The head is NOT
clean, though: the remediation commit moved indexed lines without
regenerating `docs/testing/nv2a_index.json`. CI's `check` job fails on this
head, and fold.sh will not fold a RED head. The PR goes back to
`needs-remediation` for that one mechanical item.**

## Pass-1 scenarios

**MEDIUM-1 (SCRYSCB_TO_RGB left a YUV texture unconverted): closed.**
`csc_crycb()` now returns true for value 1 and value 2. It gates both the
`crycb_to_rgb` preflight and the per-stage `tN = crycb_to_rgb(tN)` lines. A
guest that writes bits 28-31 = 2 and samples a raw-uploaded YUY2/UYVY texture
now gets converted RGB, not (Y, Cb, Cr, 255). The `NV2A_UNIMPLEMENTED` log is
kept: it fires for every value that is neither PASS nor CRYCB_TO_RGB. NOTES
records the choice, and says that non-YUV stages are converted too under
value 2, which is unmeasured.

- A side effect, not a finding: `csc_crycb()` also gates the
  BUMPENVMAP_LUM byte truncation (`psh.c` near line 3530), so value 2
  truncates as well. That is consistent with "value 2 behaves as value 1".
  It is unmeasured, and no golden writes value 2.

**LOW-1 (values 4-15 masked into 0-3): closed.** The handler stores
`csc > 3 ? 3 : csc` into the 2-bit `NV_PGRAPH_CONTROL_0_CSCONVERT` field
(`0xC0000000`). `psh.c` reads the field back as 3. That value is neither PASS
nor CRYCB/SCRYSCB, so it logs `NV2A_UNIMPLEMENTED` and does not convert.
Before the fix, 4 read as PASS with no log, and 5 read as CRYCB_TO_RGB. Both
of those paths are gone.

**LOW-2 (colour key/alphakill compare raw YCbCr): closed as documented.**
NOTES records it as unmeasured, and the code is unchanged, as pass 1 asked.

**LOW-3 (signed channels clamped before conversion): closed as documented.**
There is a NOTES line.

**LOW-4 (NOTES misplaced the field): closed.** NOTES now says "after
`final_inputs_1`", and `psh.h` agrees.

## Still open

**MEDIUM (gate): stale nv2a index on the head.** On `268f74d5e5`, CI run
36278705899, job `check`, step "Check the index matches the tree", fails
with `STALE INDEX`, listing 10 real site changes. They include:

- `NV097_SET_CONTROL0_COLOR_SPACE_CONVERT_SCRYSCB_TO_RGB: new symbol with sites`
- moved REF anchors for `..._CRYCB_TO_RGB`, `..._PASS`, `NV_PGRAPH_CONTROL_0`
  and `NV_PGRAPH_CONTROL_0_CSCONVERT` in `psh.c` and `pgraph.c`

`fold.sh` reads the rollup through `ci_green()`. On RED it posts "Not
folded: CI is red". `stale_red()` does not excuse this failure, because the
failing run belongs to this head and not to an older base. The fold's own
`regen_index` runs only after the CI gate, so it never gets the chance to
repair the index. Labelling this `fold-ready` would park the PR.

**Failure scenario.** Label `fold-ready` at this head. The fold tick sees
`check: FAILURE` on `268f74d5e5` and refuses. The PR waits until someone
pushes a new head.

**Remedy.** On the lane branch, run `nv2a_index.py build` over the pinned
trees, the same way the branch's earlier "nv2a index: regenerate" commits
did. Commit the result and push. Nothing else needs to change. Pass 2 does
not need to rerun for the code: the scenarios above were verified at
`268f74d5e5`. An index-only commit on top leaves them as they are.
