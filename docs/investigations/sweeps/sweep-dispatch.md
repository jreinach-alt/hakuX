## Naming taxonomy

### The five naming families in `nv2a_regs.h`

`hw/xbox/nv2a/nv2a_regs.h` is a flat `#define` file with an indentation convention that
encodes nesting depth. **[V]** The indentation levels are:

| Prefix in file | Meaning |
|---|---|
| `#define NAME` (col 0) | a block/class/register/method **address** or a top-level constant |
| `#   define NAME` (3 sp) | a **field mask** inside the parent, or a **method** inside a class |
| `#       define NAME` (7 sp) | an **enumerated value** of the parent field |
| `#           define NAME` (11 sp) | a value of a value (rare, e.g. `NV097_SET_TEXTURE_FORMAT_COLOR_*`) |

Counts, mechanically: 138 col-0 `NV_PGRAPH_*` register defines, 199 indented
`NV_PGRAPH_*` field/value defines, 215 indented `NV097_*` defines. **[V]** (counts taken
by `grep -c` over `nv2a_regs.h`).

#### 1. `NV_<BLOCK>` — MMIO block selectors

`nv2a_regs.h:37-58` defines 21 block ids (`NV_PMC`=0 … `NV_USER`=20, `NV_NUM_BLOCKS`=21).
These are *array indices*, not addresses. The address/size mapping lives in
`hw/xbox/nv2a/nv2a.c:118-145` (`blocktable[]`), e.g. `ENTRY(PGRAPH, pgraph, 0x400000,
0x002000)` at `nv2a.c:138` and `ENTRY(USER, user, 0x800000, 0x800000)` at `nv2a.c:144`.
Each entry binds `<lname>_read` / `<lname>_write` (macro at `nv2a.c:119-124`), whose
prototypes are generated by `DEFINE_PROTO` in `nv2a_int.h:213-237`. **[V]**

#### 2. `NV_PGRAPH_*` — the hardware register file

`NV_PGRAPH_<REG>` is a **byte offset into the 8 KiB PGRAPH MMIO window**. Examples:
`NV_PGRAPH_INTR 0x00000100` (`nv2a_regs.h:191`), `NV_PGRAPH_BLEND 0x00001804`
(`nv2a_regs.h:359`), `NV_PGRAPH_ZCLIPMAX 0x00001ABC` (`nv2a_regs.h:649`). **[V]**

Backing store: `PGRAPHState.regs_[0x2000]` — a **byte-addressed** `uint32_t` array
(`pgraph/pgraph.h:249`). Accessors `pgraph_reg_r` / `pgraph_reg_w`
(`pgraph/pgraph.h:327-354`) both `assert(r % 4 == 0)` and index `pg->regs_[r]` directly
with the *byte* offset, so only 1 in 4 array slots is ever used. **[V]** — this is a
4x-oversized array by design, not a bug; `regs_dirty` is sized `0x2000/sizeof(uint32_t)`
bits (`pgraph.h:250`) and indexed `r / sizeof(uint32_t)` (`pgraph.h:337`), consistent.

Sub-conventions inside this family **[V]**:

- `NV_PGRAPH_<REG>_<FIELD>` — a **mask** within the register, e.g.
  `NV_PGRAPH_CONTROL_0_ZFUNC 0x000F0000` (`nv2a_regs.h:432`),
  `NV_PGRAPH_BLEND_EN (1 << 3)` (`nv2a_regs.h:361`).
- `NV_PGRAPH_<REG>_<FIELD>_<NAME>` — an **already-shifted-down enum value** for that
  field, e.g. `NV_PGRAPH_CONTROL_0_ZFUNC_LEQUAL 3` (`nv2a_regs.h:436`),
  `NV_PGRAPH_BLEND_SFACTOR_SRC_ALPHA 4` (`nv2a_regs.h:367`).
- **Banked registers** carry a trailing digit: `NV_PGRAPH_TEXFILTER0..3`
  (`nv2a_regs.h:561,579,580,581`), `NV_PGRAPH_WINDOWCLIPX0..7` (`nv2a_regs.h:618-627`),
  `NV_PGRAPH_BORDERCOLOR0..3` (`nv2a_regs.h:397-400`). **Field masks are only spelled out
  for bank 0** (e.g. `NV_PGRAPH_TEXFILTER0_MIN`, `nv2a_regs.h:566`); code applies the
  bank-0 mask names to every bank and computes the address as `BASE0 + slot*4`
  (e.g. `pgraph/pgraph.c:3703`). Some banked registers have no separate defines at all —
  `NV_PGRAPH_COMBINEALPHAI0 0x000018C0` (`nv2a_regs.h:420`) is a single define whose 8
  slots are reached as `+ slot*4` (`pgraph/pgraph.c:2105`).
- Two "colour" spellings coexist and are **channel-swapped**: parameter channels are ABGR,
  PGRAPH channels are ARGB. The fog handler documents and performs the swap at
  `pgraph/pgraph.c:2228-2236` (`NV097_SET_FOG_COLOR_RED 0x000000FF`, `nv2a_regs.h:925`, vs
  `NV_PGRAPH_FOGCOLOR_RED 0x00FF0000`, `nv2a_regs.h:492`). **[V]**

#### 3. `NV<class-hex>_*` — per-graphics-class methods

Graphics classes are declared at col 0 with their **class id**, and their methods are
declared one level in, keyed by the *hex class id* rather than the symbolic name
(`nv2a_regs.h:806-844`) **[V]**:

| Class symbol | id | method prefix | file:line |
|---|---|---|---|
| `NV_SET_OBJECT` (method 0, all classes) | `0x00000000` | — | `nv2a_regs.h:807` |
| `NV_BETA` | `0x0012` | `NV012_` | `nv2a_regs.h:809` |
| `NV_MEMORY_TO_MEMORY_FORMAT` | `0x0039` | *(no methods defined)* | `nv2a_regs.h:813` |
| `NV_CONTEXT_PATTERN` | `0x0044` | `NV044_` | `nv2a_regs.h:815` |
| `NV_CONTEXT_SURFACES_2D` | `0x0062` | `NV062_` | `nv2a_regs.h:818` |
| `NV_KELVIN_PRIMITIVE` | `0x0097` | `NV097_` | `nv2a_regs.h:844` |
| `NV_IMAGE_BLIT` | `0x009F` | `NV09F_` | `nv2a_regs.h:833` |

So **`NV097_*` = methods of the Kelvin 3D class (class id 0x97)**, pushed through the
command FIFO. They are *not* MMIO registers. Their numeric value is a **byte offset in the
class's method space**, always 4-byte aligned, spanning `0x0000`–`0x1EA4`
(`nv2a_regs.h:845` … `nv2a_regs.h:1313`). **[V]**

Method-name sub-conventions **[V]**:

- `NV097_SET_*` — pure state writes (the overwhelming majority).
- Non-`SET_` names are **actions/triggers**, not state: `NO_OPERATION` (`:846`),
  `WAIT_FOR_IDLE` (`:847`), `FLIP_INCREMENT_WRITE` (`:851`), `FLIP_STALL` (`:852`),
  `CLEAR_REPORT_VALUE` (`:1149`), `GET_REPORT` (`:1153`), `ARRAY_ELEMENT16/32`
  (`:1171,:1172`), `DRAW_ARRAYS` (`:1173`), `INLINE_ARRAY` (`:1176`),
  `BACK_END_WRITE_SEMAPHORE_RELEASE` (`:1269`), `CLEAR_SURFACE` (`:1278`),
  `LAUNCH_TRANSFORM_PROGRAM` (`:1306`).
- `NV097_<METHOD>_<FIELD>` at depth 2 — a mask over the 32-bit parameter, e.g.
  `NV097_SET_TEXTURE_FORMAT_COLOR 0x0000FF00` (`nv2a_regs.h:1191`),
  `NV097_DRAW_ARRAYS_COUNT 0xFF000000` (`nv2a_regs.h:1174`).
- `NV097_<METHOD>_<FIELD>_<NAME>` at depth 3 — a **post-shift** enum value for that field,
  e.g. `NV097_SET_TEXTURE_FORMAT_COLOR_SZ_A8R8G8B8 0x06` (`nv2a_regs.h:1198`),
  `NV097_SET_SURFACE_FORMAT_ZETA_Z24S8 2` (`nv2a_regs.h:883`).
- **`_V_` (and `_OP_`) infix means "raw whole-parameter token", not a field value.**
  These are OpenGL/D3D-style tokens compared against the *entire* parameter:
  `NV097_SET_BLEND_FUNC_SFACTOR_V_SRC_ALPHA 0x0302` (`nv2a_regs.h:963`) is matched by
  `switch (parameter)` at `pgraph/pgraph.c:2368,2377`; likewise
  `NV097_SET_STENCIL_OP_V_KEEP 0x1E00` (`nv2a_regs.h:1013`) at `pgraph.c:2538-2539`,
  `NV097_SET_SHADE_MODE_V_FLAT 0x1D00` (`:1022`) at `pgraph.c:2585-2586`,
  `NV097_SET_CULL_FACE_V_FRONT 0x404` (`:1034`) at `pgraph.c:2660-2661` (source line
  numbers verified), and `NV097_SET_BEGIN_END_OP_END 0x00` (`:1160`) at `pgraph.c:3612`.
  **Caveat:** the converse is *not* true — `NV097_SET_TEXGEN_S_EYE_LINEAR 0x2400`
  (`nv2a_regs.h:1051`) carries no `_V_` yet is a raw-parameter token: `kelvin_map_texgen`
  `switch (parameter)`es over it at `pgraph.c:2722-2746`. Likewise
  `NV097_SET_SKIN_MODE_OFF..._4` (`nv2a_regs.h:945-951`) are raw parameters that happen to
  equal their `NV_PGRAPH_CSV0_D_SKIN_*` field values (`nv2a_regs.h:310-316`), so the
  handler can write `parameter` straight through (`pgraph.c:2323-2327`). Do not rely on
  `_V_` absence.

#### 5. Parameter decoding — the `GET_MASK` / `SET_MASK` pattern

```c
#define GET_MASK(v, mask) (((v) & (mask)) >> ctz32(mask))            // nv2a_regs.h:25
#define SET_MASK(v, mask, val) ... (v) &= ~mask; (v) |= (val << ctz32(mask)) & mask;
                                                                      // nv2a_regs.h:27-33
```
The shift is **derived from the mask** via `ctz32`, so a field define never needs a
companion shift constant. `SET_MASK` re-masks after shifting, which silently **truncates**
an over-wide value — this is load-bearing: `SET_ALPHA_FUNC` writes `parameter & 0xF`
explicitly (`pgraph.c:2355-2356`) while the fast path writes the raw parameter through
`NV_PGRAPH_CONTROL_0_ALPHAFUNC` (`pgraph.c:517`) and gets the same 4-bit truncation. **[V]**

Two PGRAPH-scoped conveniences are defined **only in `pgraph.c`** (not in a header):
```c
#define PG_GET_MASK(reg, mask)        GET_MASK(pgraph_reg_r(pg, reg), mask)   // pgraph.c:39
#define PG_SET_MASK(reg, mask, value) { rv = pgraph_reg_r(pg, reg);
                                        SET_MASK(rv, mask, value);
                                        pgraph_reg_w(pg, reg, rv); }          // pgraph.c:40-45
```
Both **capture the identifier `pg` from the enclosing scope** — they are unhygienic and
only usable where a local named `pg` exists (every method handler has one, supplied by
`METHOD_HANDLER_ARG_DECL`, `pgraph.c:1338-1342`). **[V]**

### The exact rule: method name → handler

Given a method symbol `NV097_FOO` **[V]**:

1. **Address.** `NV097_FOO` is defined in `nv2a_regs.h` (lines 845-1313) as a byte offset.
2. **Table slot(s).** Exactly one `DEF_METHOD*` line in `pgraph/pgraph.h.inc`… precisely
   `hw/xbox/nv2a/pgraph/methods.h.inc` names `FOO`. The variant fixes how many slots of the
   2048-entry dispatch table it claims (`pgraph.c:1368-1409`, table declared
   `pgraph_kelvin_methods[0x800]` at `pgraph.c:1367`):
   - `DEF_METHOD(NV097, FOO)` → 1 slot at `NV097_FOO >> 2`.
   - `DEF_METHOD_RANGE(NV097, FOO, N)` → `N` consecutive slots,
     `[NV097_FOO>>2 … (NV097_FOO + 4N - 1)>>2]` (GCC range designator, `pgraph.c:1376-1377`).
   - `DEF_METHOD_CASE_4(NV097, FOO, S)` → 4 slots at `NV097_FOO + {0, S, 2S, 3S}`
     (`pgraph.c:1383-1409`; `S` is the per-texture-unit stride, 64 for texture methods).
   - `DEF_METHOD_CASE_4_OFFSET(NV097, FOO, O, S)` → 4 slots at `NV097_FOO + O + {0,S,2S,3S}`.
3. **Handler symbol.** `METHOD_FUNC_NAME(gclass, name)` = `pgraph_ ## gclass ## _ ## name
   ## _handler` (`pgraph.c:1336-1337`) → **`pgraph_NV097_FOO_handler`**, a `static void`
   with signature `METHOD_HANDLER_ARG_DECL` (`pgraph.c:1338-1342`).
4. **Definition site.** In `pgraph.c` after line 1524 (`#define DEF_METHOD(gclass, name)
   DEF_METHOD_PROTO(gclass, name)`, never re-`#undef`'d), so `DEF_METHOD(NV097, FOO) { … }`
   *is* the function body.
   If the definition uses `DEF_METHOD_INC` / `DEF_METHOD_NON_INC` (`pgraph.c:1526-1543`),
   **two** functions are emitted: the table-visible `pgraph_NV097_FOO_handler` trampoline,
   which calls `pgraph_method_inc`/`pgraph_method_non_inc`, plus the real body
   `pgraph_NV097_FOO_int_handler` (`METHOD_FUNC_NAME_INT`, `pgraph.c:1522-1523`).
5. **Sub-index recovery.** Inside the body the slot is recomputed from the method address:
   `(method - NV097_FOO) / 4` for `RANGE` methods, `/ 64` for texture `CASE_4` methods,
   `/ 16` for texgen.

### Worked example, end to end — `NV097_SET_TEXTURE_FILTER` on texture unit 2

All steps verified.

1. Guest builds a pushbuffer method header word; the pusher decodes it at
   `pfifo.c:572-582`: `method = (word & 0x1fff) >> 2`, `subchannel = (word >> 13) & 7`,
   `count = (word >> 18) & 0x7ff`, type = INC. Stored into `NV_PFIFO_CACHE1_DMA_STATE`.
2. Next iteration, `method_count != 0`, so the data word is packed into a method entry
   (`pfifo.c:504-508`) and handed to the puller
   (`pfifo.c:512-515`, `pfifo_run_puller`).
3. `pfifo_run_puller` recovers `method = method_entry & 0x1FFC` (`pfifo.c:270`),
   `subchannel` (`:271-272`), `inc = !GET_MASK(..., NV_PFIFO_CACHE1_METHOD_TYPE)` (`:273`).
   Since `method >= 0x100` it takes the engine path (`pfifo.c:321`), tries the lockless
   fast path (`pfifo.c:341-355`), else drops `pfifo.lock`, takes `pgraph.lock`, and calls
   `pgraph_method(...)` (`pfifo.c:369-371`).
4. Method address for unit 2: `NV097_SET_TEXTURE_FILTER` = `0x1B14` (`nv2a_regs.h:1245`);
   stride 64 (`methods.h.inc:159`, `DEF_METHOD_CASE_4(NV097, SET_TEXTURE_FILTER, 64)`).
   Unit 2 ⇒ `0x1B14 + 128 = 0x1B94`. Table index `METHOD_ADDR_TO_INDEX(0x1B94)` =
   `0x1B94 >> 2` = **`0x6E5`** (`pgraph.c:1332`).
5. `pgraph_kelvin_methods[0x6E5]` = `{ base 0x1B14, "NV097_SET_TEXTURE_FILTER",
   pgraph_NV097_SET_TEXTURE_FILTER_handler }`, produced by the `DEF_METHOD_CASE_4_OFFSET`
   expansion at `pgraph.c:1396-1401` (the `stride*2` arm).
6. Dispatch: `pgraph_method` looks the handler up at `pgraph.c:1777-1778` and calls it at
   `pgraph.c:1786-1787` with `num_words_consumed` pre-set to 1 (`pgraph.c:1785`).
7. Handler body (`pgraph.c:3700-3707`):
   `slot = (0x1B94 - 0x1B14) / 64 = 2`;
   `reg = NV_PGRAPH_TEXFILTER0 + 2*4 = 0x19F4 + 8 = 0x19FC` = `NV_PGRAPH_TEXFILTER2`
   (`nv2a_regs.h:561`, `:580`);
   `pg->texture_dirty[2] |= (parameter != old)`; `pgraph_reg_w(pg, 0x19FC, parameter)`.
8. `pgraph_reg_w` (`pgraph.h:333-354`) sets `regs_dirty` bit `0x19FC/4`, and because
   `pgraph_reg_category_table[0x19FC/4]` carries both `REG_CAT_SHADER`
   (`pgraph.c:131`) and `REG_CAT_TEXTURE` (`pgraph.c:140`), bumps `shader_state_gen`
   (if a non-dynamic bit changed) and unconditionally `texture_state_gen`, plus
   `any_reg_gen`.
9. The Vulkan backend notices on the next draw: `pg->texture_state_gen !=
   r->last_texture_state_gen` at `pgraph/vk/draw.c:1179` (and the rebind at the following
   lines), and `pg->texture_dirty[2]` at `pgraph/vk/texture.c:1947`. The GL backend reads
   `pg->texture_dirty[i]` at `pgraph/gl/texture.c:765` and clears it at
   `pgraph/gl/texture.c:737,756,951`.

Second worked fragment — parameter *token translation* rather than field decode:
`NV097_SET_BLEND_FUNC_SFACTOR` (`0x0344`, `nv2a_regs.h:958`) is `DEF_METHOD(NV097,
SET_BLEND_FUNC_SFACTOR)` (`methods.h.inc:56`) → `pgraph_NV097_SET_BLEND_FUNC_SFACTOR_handler`

## Dispatch mechanism

### Path 0 — the guest kick

`user_write` (`user.c:73-124`) is the only doorbell. Channel id is `addr >> 16`
(`user.c:79`); a write to `NV_USER_DMA_PUT` (`0x40`, `nv2a_regs.h:769`) stores the new put
pointer into `d->pfifo.regs[NV_PFIFO_CACHE1_DMA_PUT]` (`user.c:97`) and calls
`pfifo_kick(d)` (`user.c:111`), which sets `fifo_kick` and broadcasts `fifo_cond`
(`pfifo.c:185-191`). PIO mode and non-current-channel (ramfc) access are `assert(false)`
(`user.c:60,64,115,119`). **[V]**

### Path 1 — the PFIFO thread

`pfifo_thread` (`pfifo.c:632-…`) loops: `pgraph_process_pending(d)` (`pfifo.c:650`),
`pfifo_run_pusher(d)` (`pfifo.c:658`), `pgraph_process_pending_reports(d)` (`pfifo.c:669`),
then either spins for `FIFO_SPIN_ACTIVE_NS` = 100 µs (`pfifo.c:47`, `pfifo.c:689-700`) or
waits on the condvar. **[V]**

`pfifo_run_pusher` (`pfifo.c:423-630`) maps the pushbuffer DMA object
(`nv_dma_map`, `pfifo.c:464`) and walks words between `DMA_GET` and `DMA_PUT`
(`pfifo.c:468-471`). Command-word decoding (`pfifo.c:534-601`) **[V]**:

| word pattern | meaning | file:line |
|---|---|---|
| `(word & 0xe0000003) == 0x20000000` | old jump | `pfifo.c:535-540` |
| `(word & 3) == 1` | jump | `pfifo.c:541-546` |
| `(word & 3) == 2` | call (1 deep) | `pfifo.c:547-559` |
| `word == 0x00020000` | return | `pfifo.c:560-571` |
| `(word & 0xe0030003) == 0` | **increasing** methods | `pfifo.c:572-582` |
| `(word & 0xe0030003) == 0x40000000` | **non-increasing** methods | `pfifo.c:583-593` |
| otherwise | reserved → `assert(false)` | `pfifo.c:594-601` |

Field layout for a methods header: `method = (word & 0x1fff) >> 2`,
`subchannel = (word >> 13) & 7`, `count = (word >> 18) & 0x7ff` (`pfifo.c:574-579`).

### Path 2 — the puller

`pfifo_run_puller` (`pfifo.c:246-415`) **[V]**:
- Stalls (returns −1) if flip-stall pending, NOP-wait pending, context-switch pending, or
  `NV_PGRAPH_FIFO_ACCESS` is clear (`pfifo.c:239-244`, `can_fifo_access` at `:193-196`).
- `method == 0` → `NV_SET_OBJECT`: RAMHT lookup, bind engine to subchannel, context switch
  (`pfifo.c:276-319`).
- `0x180 <= method < 0x200` → parameter is a handle, replaced by the RAMHT instance
  (`pfifo.c:326-333`).
- `method >= 0x100` → engine path. With `XEMU_OPT_PFIFO_LOCK_BATCH` (default 1,
  `pfifo.c:33-35`) it holds `pfifo.lock` while acquiring `pgraph.lock`, then releases
  `pfifo.lock` (`pfifo.c:359-365`) — the reverse of the non-batched build
  (`pfifo.c:385-386`). Lock order is documented at `nv2a_int.h:70-82`:
  `pfifo.lock → pgraph.lock → pgraph.renderer_lock`.
- Returns `num_proc` = words consumed; the pusher advances `DMA_GET` by
  `(num_words_processed-1)*4` and rewrites `DMA_STATE_METHOD` / `METHOD_COUNT`
  (`pfifo.c:520-529`).

### Path 3a — the lockless fast path (hakuX-specific)

`pgraph_method_try_fast` (`pgraph.c:727-793`), gated by `XEMU_OPT_LOCKLESS_FAST_DISPATCH`
(defaults to `XEMU_OPT_METHOD_FAST_TABLE` = 1, `pgraph.c:154-156`, `:717-719`), is called
**without `pgraph.lock` held** from `pfifo.c:343-345`. It runs only when `method >= 0x100`,
the subchannel is unchanged, and `pg->cached_graphics_class == NV_KELVIN_PRIMITIVE`
(`pgraph.c:734-738`). **[V]**

It consults a second table, `method_fast[0x800]` (`pgraph.c:343-642`), whose entry type is
`{uint16_t reg; uint8_t mask_idx; uint8_t xlat;}` (`pgraph.c:206-210`). Five entry kinds
(constructor macros at `pgraph.c:335-339`):

| macro | behaviour | applied at |
|---|---|---|
| `MF_DIRECT(r)` | `pgraph_reg_w(pg, r, p)` | `pgraph.c:673-674` |
| `MF_MASKED(r, m)` | read-modify-write with `mask_lut[m]` | `pgraph.c:675-679` |
| `MF_XLAT(r, m, x)` | translate `p` via `fast_xlat`, then masked write | `pgraph.c:669-679` |
| `MF_TEX(r, slot)` | set `pg->texture_dirty[slot]`, then direct write | `pgraph.c:654-660` |
| `MF_VTX_OFF(slot)` | write `vertex_attributes[slot].{dma_select,offset}`, bump `vertex_attr_gen` | `pgraph.c:661-668` |

`mask_lut[]` (`pgraph.c:281-333`) is a 51-entry indirection so each `MethodFastPath` fits
in 4 bytes. `fast_xlat` (`pgraph.c:232-279`) reimplements the token→enum translation of the
slow handlers for blend factor/equation, depth func, stencil op, shade mode, polygon mode,
cull face and front face; on an unrecognised token it returns `UINT32_MAX` and the caller
**falls back to the slow path** (`pgraph.c:669-672`, `pgraph.c:746`, `pgraph.c:1561`).

The fast path also **coalesces across command boundaries**: after consuming the current
command's words it peeks at subsequent pushbuffer headers, and if the next header is an
INC methods command on the same subchannel whose whole run is fast-path-eligible, it
consumes that too without returning to the puller (`pgraph.c:761-790`, mirrored in the
locked variant at `pgraph.c:1577-1609`). A mid-command `xlat` failure rewinds
`consumed` by `(i+1)` and lets the puller re-dispatch the remainder (`pgraph.c:784-787`,
comment at `pgraph.c:1601-1604`). **[V]**

Atomicity: the lockless variant uses `fast_entry_apply_atomic` (`pgraph.c:683-713`), which
routes through `pgraph_reg_w_atomic` (`pgraph.h:363-392`) — `qatomic_set` on the register,
`bitmap_set_atomic` on `regs_dirty`, `__atomic_fetch_add(..., __ATOMIC_RELAXED)` on every
generation counter. The header comment (`pgraph.h:356-362`) states relaxed ordering is
sufficient "because the render thread re-validates under `pgraph.lock` at draw time". **[V]**
Note `pg->texture_dirty[slot] |= changed` at `pgraph.c:689` is a **non-atomic** byte RMW on
the otherwise-lockless path.

### Path 3b — the locked slow path

`pgraph_method` (`pgraph.c:1545-1822`) **[V]**:
1. If the fast table is enabled it retries the same fast-table logic *under the lock*
   (`pgraph.c:1554-1616`), falling through to `slow_path:` on miss.
2. **Kelvin fast entry** (`pgraph.c:1621-1625`): if subchannel is unchanged, the cached
   class is Kelvin, and `method != NV_SET_OBJECT`, it jumps straight to `kelvin_dispatch`,
   skipping the `channel_valid` assert, the CTX_CACHE→CTX_SWITCH copy, **and the method
   trace** (`pgraph_method_log` only runs in the full preamble, `pgraph.c:1673-1675`).
3. Otherwise: assert channel valid (`pgraph.c:1627-1629`); on `NV_SET_OBJECT` read the
   5-word object from RAMIN into `NV_PGRAPH_CTX_CACHE1..5 + subchannel*4`
   (`pgraph.c:1637-1653`); on subchannel change copy CACHE→SWITCH
   (`pgraph.c:1655-1667`); read the class from
   `NV_PGRAPH_CTX_SWITCH1_GRCLASS` and cache it (`pgraph.c:1669-1671`).
4. `switch (graphics_class)` (`pgraph.c:1682-1814`): `NV_BETA` (2 methods),
   `NV_CONTEXT_PATTERN` (1), `NV_CONTEXT_SURFACES_2D` (7), `NV_IMAGE_BLIT` (6, and
   `NV09F_SIZE` synchronously calls `renderer->ops.image_blit`, `pgraph.c:1766-1768`), and
   `NV_KELVIN_PRIMITIVE` → the table lookup. Anything else → `goto unhandled`.
5. `kelvin_dispatch` (`pgraph.c:1776-1811`): NULL handler → `unhandled`; otherwise call
   with `num_words_consumed = 1` and read it back into `num_processed`.
6. **BEGIN/DRAW_ARRAYS/END squashing** (`pgraph.c:1789-1807`): after a `DRAW_ARRAYS`, if
   the next 6 words in the pushbuffer are `END`, `BEGIN(same mode)`, `DRAW_ARRAYS`, the
   dispatcher swallows 4 extra words and sets `pg->draw_arrays_prevent_connect`.
7. `unhandled:` (`pgraph.c:1818-1821`) emits `trace_nv2a_pgraph_method_unhandled`
   (`trace-events:12`) and returns 1 — **the drop is silent unless tracing is compiled in.**

### Path 4 — INC / NON_INC batching

`pgraph_method_inc` (`pgraph.c:1480-1500`) loops `MIN(num_words_available, (end - method)/4)`
times, re-loading `parameter` from the word stream and stepping `method += 4`, where `end`
is the compile-time constant `pgraph_NV097_FOO__END` generated by the third
`methods.h.inc` pass (`pgraph.c:1417-1433`; `= base + 4` for `DEF_METHOD`, `base + 4*range`
for `RANGE`, `base + 4*stride` for `CASE_4`). `pgraph_method_non_inc`
(`pgraph.c:1502-1520`) consumes *all* available words at the same address. Handlers defined
with plain `DEF_METHOD` never write `num_words_consumed`, so they consume exactly one word
and the puller re-enters per word. **[V]**

### Path 5 — when the backend sees it

Two distinct mechanisms **[V]**:

- **Synchronous** renderer calls from inside handlers, via `pg->renderer->ops.*`
  (`pgraph.h:100-127`): `surface_update` (e.g. `pgraph.c:2028, 2038, 2048, 2077, 2090,
  2097, 2126, 1878, 1932, 3973`), `draw_begin`/`draw_end` (`pgraph.c:3630`, `:3619`),
  `flush_draw` (`pgraph.c:3793`), `clear_surface` (`pgraph.c:4031`), `get_report`
  (`pgraph.c:3599`), `image_blit` (`pgraph.c:1767`), `flip_stall` (`pgraph.c:1933`),
  `process_pending_reports` (`pgraph.c:2021`).
- **Deferred, generation-counter-driven**: `pgraph_reg_w` bumps
  `shader_state_gen` / `pipeline_state_gen` / `texture_state_gen` / `non_dynamic_reg_gen` /
  `any_reg_gen` (`pgraph.h:341-351`) according to `pgraph_reg_category_table` (built in
  `pgraph_init_reg_category_table`, `pgraph.c:107-152`) and *suppressed* for bits listed in
  `pgraph_reg_dynamic_mask_table` (built in `pgraph_init_reg_dynamic_masks`,
  `pgraph.c:50-105`, taking `eds1`/`eds3` = extended-dynamic-state feature flags). The
  Vulkan backend compares them at draw time: `pgraph/vk/draw.c:1057` (pipeline),
  `pgraph/vk/draw.c:1179-1184` (texture/shader/pipeline early-out),
  `pgraph/vk/draw.c:2697, 2761` (non-dynamic / any), `pgraph/vk/vertex.c:141` (vertex
  attrs), `pgraph/vk/shaders.c:1253` (shader). The Vulkan render thread snapshots the whole
  of `pg->regs_` and the counters into a per-draw snapshot
  (`pgraph/vk/render_thread.c:25-110`).

### `methods.h.inc` — role and maintenance

204 lines, no `#include` guard, no preprocessor logic of its own — a **pure X-macro list**
(`pgraph/methods.h.inc:1-204`). It is `#include`d **three times** by `pgraph.c` with
different macro bindings **[V]**:

| pass | `#include` at | `DEF_METHOD*` bound to | produces |
|---|---|---|---|
| 1 | `pgraph.c:1356` | `pgraph.c:1349-1355` | forward declarations of every handler |
| 2 | `pgraph.c:1410` | `pgraph.c:1368-1409` | the designated initialisers of `pgraph_kelvin_methods[0x800]` |
| 3 | `pgraph.c:1429` | `pgraph.c:1419-1428` | `static const size_t pgraph_NV097_FOO__END` range bounds |

Each pass `#undef`s its bindings afterwards (`pgraph.c:1357-1360`, `:1411-1414`,
`:1430-1433`). In pass 1 and pass 3, `DEF_METHOD_CASE_4_OFFSET` expands to nothing
(`pgraph.c:1353`, `:1425`) so the extra `SET_TEXTURE_SET_BUMP_ENV_MAT` offset lines do not
re-declare the handler or re-define the range constant.

**Maintenance model: hand-maintained, not generated.** **[I, strong]** — no generator
script, meson custom_target, or "generated file, do not edit" banner references it
(`grep -rn methods.h.inc /home/user/hakuX` returns only the three `pgraph.c` includes);
`pgraph/meson.build` does not mention it. Its ordering does not match address order
(e.g. `SET_VERTEX3F` at `methods.h.inc:113` sits between `SET_TRANSFORM_CONSTANT` and
`SET_BACK_LIGHT_AMBIENT_COLOR`, mirroring the same out-of-order placement in
`nv2a_regs.h:1090-1093`), which is what you would expect from a hand-curated list that
grew by appending. Adding a method therefore requires **three** coordinated edits: the
address in `nv2a_regs.h`, the line in `methods.h.inc`, and the body in `pgraph.c`; and
optionally a fourth (`method_fast[]` in `pgraph.c:343-642`) to keep the fast path in sync.

## Uncertainties

Being generous, per instruction. Everything below is something I could **not** settle from
the files in scope.

1. **`methods.h.inc` provenance.** I found no generator and no "do not edit" banner, and its
   ordering is non-monotonic in address — strong evidence it is hand-maintained. But I did
   not search the repo's tooling directories, git history, or upstream xemu for a
   historical generator. Treat "hand-maintained" as **[I]**, not **[V]**.

2. **Which of the 663 uncovered table slots correspond to real hardware methods.** I can
   state that they have no handler and hit the silent `unhandled` path. I cannot say which
   of them a real Xbox title actually pushes, because `nv2a_regs.h` simply does not define
   them and I have no external method map in scope. The isolated single-slot holes at
   `0x1B18` / `+64` / `+128` / `+192` are the most suspicious (they sit *inside* the
   otherwise fully mapped per-unit texture descriptor, between `SET_TEXTURE_FILTER` `0x1B14`
   and `SET_TEXTURE_IMAGE_RECT` `0x1B1C`), and `NV_PGRAPH_TEXCTL2_0/1` exist as
   unreferenced registers — but I am **not** asserting that `0x1B18` is the method that
   would feed them.

3. **Whether the fast-path `SET_DEPTH_MASK` divergence is observable.** The missing
   `write_enabled_cache |=` is a verified code difference. Whether it produces a visible
   artefact depends on how `Surface.write_enabled_cache` is consumed in
   `pgraph/gl/surface.c:2908` and the Vulkan equivalent, and on whether a title ever
   toggles depth-write while relying on the cached value. I did not trace that through.

4. **Whether other `method_fast` entries diverge from their slow handlers.** I checked
   `SET_ALPHA_FUNC`, `SET_STENCIL_FUNC`, `SET_DOT_RGBMAPPING`, `SET_ANTI_ALIASING_CONTROL`,
   `SET_FLIP_*`, the texture `MF_TEX` group, the blend/stencil/polygon `MF_XLAT` group and
   `SET_PROVOKING_VERTEX` and found them equivalent (modulo the noted assert). I did **not**
   audit all 51 `mask_lut` bindings or all ~150 table entries one by one.

5. **`nop_stall_start_ns`** (`pgraph.h:257`) — a hakuX-specific field; I did not locate its
   writer or reader.

6. **`surface_binding_dim`** (`pgraph.h:151-158`) — I found the GL writers
   (`pgraph/gl/surface.c:2794-2799, 2847-2852`) but no reader within the time budget; the
   `// FIXME: Refactor` suggests it is a shim. Do not assume it is dead.

7. **`dma_vertex_a` / `dma_vertex_b` readers** — written at `pgraph.c:2006, 2011`; I did not
   chase the vertex-fetch readers in the GL/Vulkan backends.

8. **`REG_CAT_*` completeness.** `pgraph_init_reg_category_table` (`pgraph.c:107-152`)
   enumerates a fixed list of shader/pipeline/texture registers. Any register a renderer
   reads that is *not* in those lists will not bump a generation counter, so a change to it
   can be missed by the early-out checks. I did not cross-check the renderers' actual
   register reads against these lists. `OPT_VALIDATE_GEN_COUNTERS`
   (`pgraph/vk/draw.c:1062-1072`) exists precisely to catch this class of bug, which
   suggests it has been a real hazard.

9. **`eds1` / `eds3` semantics.** `pgraph_init_reg_dynamic_masks(bool eds1, bool eds3)`
   (`pgraph.c:50`) is clearly about Vulkan extended dynamic state, and it changes which bits
   are treated as "dynamic" (and therefore do *not* bump `shader/pipeline_state_gen`). I did
   not find the call site that supplies those booleans, so I cannot say which configurations
   are exercised.

10. **Thread-safety of the lockless path w.r.t. `texture_dirty`.** `fast_entry_apply_atomic`
    uses atomics for the register and the counters but does a plain `|=` on
    `pg->texture_dirty[slot]` (`pgraph.c:689`). Whether this is safe depends on who else may
    be touching that array concurrently (the render thread clears it, e.g.
    `pgraph/vk/texture.c:2064`). I did not determine the actual concurrency window.

11. **`METHOD_ADDR_TO_INDEX` `#ifndef` guards.** It is defined twice, both times guarded
    (`pgraph.c:1331-1333` and `pgraph.c:723-725`), implying some build may define it
    externally. I found no such definition, but did not search the build system.

12. **`NV_PGRAPH_TEXFMT0_COLOR` is 7 bits (`0x00007F00`, `nv2a_regs.h:589`) while
    `NV097_SET_TEXTURE_FORMAT_COLOR` is 8 bits (`0x0000FF00`, `nv2a_regs.h:1191`), and
    format values up to `0x41` are defined** (`nv2a_regs.h:1233`). `SET_TEXTURE_FORMAT`
    copies the 8-bit method value into the 7-bit register field via `PG_SET_MASK`
    (`pgraph.c:3672`), which truncates. Same shape of mismatch for `DIMENSIONALITY`
    (4 bits method / 2 bits register) and `TEXIMAGERECT` (16 bits method / 13 bits
    register). Whether these are faithful hardware widths or transcription errors in
    `nv2a_regs.h` I cannot determine from the code alone. This is the single finding I
    would most want a second opinion on before treating the register-side widths as
    canonical vocabulary.

13. **Non-Kelvin classes are dispatched by an inline `switch`, not by any table**
    (`pgraph.c:1682-1814`, comment `/* ugly switch for now */` at `pgraph.c:1681`). There is
    no equivalent of `methods.h.inc` for `NV012`/`NV044`/`NV062`/`NV09F`, so the naming
    rule "method name → `pgraph_<CLASS>_<NAME>_handler`" applies to `NV097_*` **only**.

14. **Trace coverage.** I read `trace-events:12` for the unhandled-method event and confirmed
    `pgraph_method_log`'s use of `trace_nv2a_pgraph_method` /
    `trace_nv2a_pgraph_method_abbrev` (`pgraph.c:1446, 1467`), gated by
    `TRACE_NV2A_PGRAPH_METHOD_ENABLED` (`pgraph.c:1435`). I did not check how that symbol is
    produced or whether it is on in any shipped configuration.
