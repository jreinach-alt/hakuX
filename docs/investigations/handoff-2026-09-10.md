### 1. The device hangs, and not only in `Clear` — UNRESOLVED

**There is exactly one confirmed hang, not three. An earlier version of this
section claimed three and was wrong; the reasoning is kept below because the
mistake is easy to repeat.**

Confirmed: the `Clear` disc stopped mid-suite at `Clear::C01010101_Depth_y`,
having written 55 captures (32 `Blend surface`, 22 `Clear`). The watchdog saw
a genuine stall — `get == put`, pushbuffer drained — and stopped the VM
cleanly, which is why extraction worked.

Not confirmed, and previously misread as two more hangs at the same EIP: two
later runs hit the *harness* timeout with "0 files". That was a **tooling
artefact**. `run_disc.sh` used to `exit 1` on timeout without pulling the HDD,
so "0 files" meant "we never looked", not "the guest wrote nothing". Fixed —
the timeout path now force-stops and extracts anyway, and says `PARTIAL`. The
progress log it recovers names the test, which is the fact worth having.

Two further reasons to distrust the discarded reading:

- In those runs `get` and `put` **advanced** between stall reports
  (`0x3e33f10`, `0x3e3175c/0x3e31778`, `0x3e321f0`, ...), so the guest was
  submitting and the pushbuffer was being consumed. That is a working guest,
  not a deadlocked one. The watchdog's STALL warning is a frames-without-flip
  heuristic and fires on both.
- `eip=0x80030e4c` was taken from the CPU heartbeat, which samples every few
  seconds regardless of what the guest is doing. Seeing it in a run that was
  still working is not evidence that it is a hang site. **It was promoted to
  "the highest-value single fact" here and in a message to the remote lane;
  that was not warranted.**

the colour-mask reading below is still the best hypothesis for it. The rule

### 3. #23's biggest class: `3D_primitive` `-ls`/`-ps`, 100 blank frames

**Not about smoothing.** The emulator masks the smooth bits out of the
pipeline key and ignores them. What the test does when either flag is set:
redirect the colour surface to *texture memory* at 2x pitch with
`AA_CENTER_CORNER_2`, draw, then reset the surface to the framebuffer and
draw a full-screen quad sampling stage 0 from that memory as a 1280x480
`LU_IMAGE_A8R8G8B8`. So it is surface-to-texture aliasing of an anti-aliased
surface, and the blank is the quad sampling black.

A first hypothesis -- `check_surface_to_texture_compatiblity()` rejects the
alias because `surface->width` (640) != texture width (1280) -- is **wrong**:
`populate_surface_binding_target()` applies the AA factor before storing, so
`surface->width` is already 1280. Checked before building.

The better reading: when the guest rebinds the framebuffer, the AA surface is
shelved dirty; before `23edc14a3d` that meant never downloaded, so the texture
upload read empty VRAM. The sweep that measured 100 blanks predates that
commit. **Re-run `3D primitive` on `baab7ad5dc` before touching code** -- disc
`~/hakux-work/iso-3d_primitive.iso`, guest dir `p3d`, queued. If the blanks are
gone, the class is closed by #7's fix and needs only recording.

### 4. #20, guest power-off -- explained, experiment queued

`nxdk_pgraph_tests` `Shutdown()` writes SMC `POWER=0x80` directly (its own
comment: `HalInitiateShutdown` never reaches `smc_write_data`), then spins in
`Sleep(30000)`. `smc_write_data` decodes that to
`qemu_system_shutdown_request(GUEST_SHUTDOWN)`; `main_loop_should_exit`
returns true unless `shutdown_action == PAUSE`, and nothing on Android passes
`-no-shutdown`. So either the request never registers, or the loop exits and
`qemu_cleanup()` hangs. Disc `~/hakux-work/iso-shutdown.iso` (`Texture format`,
shutdown-on-completion, 3 s delay) is queued with logcat capture; the
`do_vm_stop new=11` runstate line discriminates without a build. This one is
worth more than its issue: every device run today waited out its full timeout
because the guest never exits.

### 5. #32, depth lands a unit high -- cause found offline, fix built, device run queued

The `+1 on 56,959 / -1 on 781` asymmetry was the clue. Reconstructing the
`Depth buffer` test's geometry in float32 reproduces the golden bit for bit:
**hardware is `floor(z interpolated at the pixel centre)`, nothing more.** A
float32 model of `psh.c`'s own formula reproduces *our* output on 99.1% of
pixels, so the defect could be isolated without the device: every
intermediate is exact, and the rounding is the final `vtxPos0.z + delta`. At
2^20 a float32's ULP is 0.125, so a pixel-centre fraction of `.9375` is a tie,
ties-to-even rounds it to `1.0`, and `floor()` lands one above hardware. Near
2^24 the ULP is a whole unit and *every* fraction is rounded away, which is
why a third of pixels were affected and none went low.

Fix: keep `floor(vtxPos0.z)` aside and let only its fraction ride with the
delta -- `zfloor = zhi + floor(zlo)` -- exact wherever the delta is. In the
model: 0 of 126,796 pixels differ from the golden across three `M` variants,
from 38,235 before. Applied to both the Z and W paths, stores of D16 and D24.
`apk-psh32.apk`; `Depth_buffer`, `Depth_buffer_fixed_function`, `W_buffering`
queued on it. Expect the 151 captures with median error <= 1 to go exact.

### 6. #21, `SZ_R6G5B5` green — read the warning first

Green is unexplained, and **two plausible fixes have already been measured and
rejected**. Bit windows `[8:5]` and `[8:4]` both fit `Texture format`'s

## Device conventions that cost a cycle each when forgotten

- **Force-stop the emulator after every run.** The handheld stops
  trickle-charging while it is up. `run_disc.sh` does this in its exit trap.
- **`run_disc.sh` does not install.** Install the APK yourself first, or you
  will measure the previous build and the numbers will look plausible.
- **The ISO's `--output-dir` must match the guest dir passed to
  `run_disc.sh`.** Mismatched, extraction silently finds nothing.
- One test per disc for anything scored: issue #19 found 328 of 864 tests
  rendering a previous test's image. `Bump map` alone scores 38/40 isolated
  against 36/40 sharing a disc.
- Do not `pkill -f` a pattern that matches your own shell. Kill by PID.
