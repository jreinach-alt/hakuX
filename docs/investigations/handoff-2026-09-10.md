## The three analytical items

### 1. The device hangs, and not only in `Clear` — UNRESOLVED

**Read this before the section below it: the hypothesis recorded there is
probably too narrow.** A second run hung on a *different* disc — `Surface
format` / `Color zeta overlap` / `Texture shadow comparator` — at the **same
guest EIP**:

    Clear disc:  eip=0x80030e4c IF=0  get == put
    rest disc:   eip=0x80030e4c IF=0  get=0x3e2f378 put=0x3e2f48c  pmc_intr=0x1000000

Same address, two discs, five different suites between them. So "the first
fully-unmasked colour and depth state" cannot be the whole explanation, and
may not be any of it. Two things the second signature adds that the first did
not: the pushbuffer is **not** drained (`get != put`, work pending and not
being consumed), and there is a **pending PMC interrupt while the guest has
interrupts disabled** (`pmc_intr=0x1000000`, `IF=0`). A guest waiting on a
completion it can only learn about by interrupt, with interrupts masked,
deadlocks exactly like this.

The two hangs also differ in shape, which may narrow it: the `Clear` disc
wrote 55 captures (32 `Blend surface`, 22 `Clear`) before stopping mid-suite,
while the rest disc ran the full 1800s timeout, rendered ~93,000 frames, and
extracted **zero** captures -- it appears to have hung before anything was
written.

`0x80030e4c` is the thing to identify first. It is reached from both discs and
is the highest-value single fact available. It also comes **before** the
`D24_UNORM` A/B in the start-here list above: that A/B was scoped to a
`Clear`-specific hypothesis that no longer looks right, and is worth doing
only once the address is known.

The rest of this section is the narrower `Clear` case, which is still true as
far as it goes:


Removing the "untested" assert (`baa6c2ace2`) traded an abort for a hang.
`Clear` runs 11 tests and stops on `Clear::C01010101_Depth_y`:

    STALL: frames=1200 ... get=0x3e2f294 put=0x3e2f294    pfifo drained
    hb: can_run=1 halted=0 eip=0x80030e4c IF=0            fixed EIP, interrupts off
    do_vm_stop -> qemu_main returned 0                    our watchdog, clean stop

**The guest and the translation are exonerated.** The remote lane scored the
same suite on lavapipe: 32/32 captured, and `C01010101_Depth_y` is **0
differing pixels** against the golden, as are all 24 `C*_Depth_*` captures.
Only the `SCF_*`/`SFC_*` cases differ there, by the documented 7-bit alpha
defect. So this is device-side.

Two readings, both the remote lane's and both better than the first one
recorded here:

- `get == put` with a fixed EIP and `IF=0` **does not distinguish** a guest
  spin from a vCPU thread blocked inside a VRAM-access hook — the test's
  readback triggers a surface download that waits on the pgraph thread —
  while the pgraph thread sits in `vkWaitForFences` on a GPU that faulted.
  `thread apply all bt` at the stall settles it.
- `C` is `SET_COLOR_MASK`, so `0x01010101` is all four write-enables and
  `Depth_y` the depth mask: **test 12 is the first fully-unmasked colour and
  depth state**. The clear ignores those masks in both paths
  (`pgraph_vk_clear_surface`, `draw.c` ~5140), so if the fault is on the GPU
  it is in what follows the clear with everything writable, not the clear.

### 2. #26, the combiner policy question

55 register values kill the pixel shader generator, in six classes, all with
line numbers in the issue. `f19eb88a16` fixed the stage count. The rest is one
decision, not six bugs: **what should the generator do with a combiner input
register the hardware reserves** — clamp, ignore, or emit something safe and
known-wrong. That decision is the work; the edits after it are mechanical.
Verification is binary, no goldens needed, and it batches into one build with
anything else.

### 3. #21, `SZ_R6G5B5` green — read the warning first

Green is unexplained, and **two plausible fixes have already been measured and
rejected**. Bit windows `[8:5]` and `[8:4]` both fit `Texture format`'s
gradient beautifully and both take `BumpMap_R6G5B5` from 23,793 differing
pixels to 58,317 and 64,214. The two suites want opposite windows, which means
the difference between them is not in the decode. The standing candidate is
what else differs: `Bump map` sets the per-channel signedness bits of
`NV_PGRAPH_TEXFILTER0` and `Texture format` does not.

This issue has cost two overfits. It needs a hypothesis about hardware
behaviour, not another curve fit against one suite.

## Device conventions that cost a cycle each when forgotten

- **Force-stop the emulator after every run.** The handheld stops
  trickle-charging while it is up. `run_disc.sh` does this in its exit trap.
- **`run_disc.sh` does not install.** Install the APK yourself first, or you
  will measure the previous build and the numbers will look plausible.
- **The ISO's `--output-dir` must match the guest dir passed to
  `run_disc.sh`.** Mismatched, extraction silently finds nothing.
- One test per disc for anything scored: issue #19 found 328 of 864 tests
  rendering a previous test's image. `Bump map` alone scores 38/40 isolated
  against 36/40 sharing a disc.
- Do not `pkill -f` a pattern that matches your own shell. Kill by PID.
