### 4. #20, guest power-off -- explained, experiment queued

`nxdk_pgraph_tests` `Shutdown()` writes SMC `POWER=0x80` directly (its own
comment: `HalInitiateShutdown` never reaches `smc_write_data`), then spins in
`Sleep(30000)`. `smc_write_data` decodes that to
`qemu_system_shutdown_request(GUEST_SHUTDOWN)`; `main_loop_should_exit`
returns true unless `shutdown_action == PAUSE`, and nothing on Android passes
`-no-shutdown`. So either the request never registers, or the loop exits and
`qemu_cleanup()` hangs. Disc `~/hakux-work/iso-shutdown.iso` (`Texture format`,
shutdown-on-completion, 3 s delay) is queued with logcat capture; the
`do_vm_stop new=11` runstate line discriminates without a build. This one is
worth more than its issue: every device run today waited out its full timeout
because the guest never exits.

### 5. #32, depth lands a unit high -- cause found offline, fix built, device run queued

The `+1 on 56,959 / -1 on 781` asymmetry was the clue. Reconstructing the
`Depth buffer` test's geometry in float32 reproduces the golden bit for bit:
**hardware is `floor(z interpolated at the pixel centre)`, nothing more.** A
float32 model of `psh.c`'s own formula reproduces *our* output on 99.1% of
pixels, so the defect could be isolated without the device: every
intermediate is exact, and the rounding is the final `vtxPos0.z + delta`. At
2^20 a float32's ULP is 0.125, so a pixel-centre fraction of `.9375` is a tie,
ties-to-even rounds it to `1.0`, and `floor()` lands one above hardware. Near
2^24 the ULP is a whole unit and *every* fraction is rounded away, which is
why a third of pixels were affected and none went low.

Fix: keep `floor(vtxPos0.z)` aside and let only its fraction ride with the
delta -- `zfloor = zhi + floor(zlo)` -- exact wherever the delta is. In the
model: 0 of 126,796 pixels differ from the golden across three `M` variants,
from 38,235 before. Applied to both the Z and W paths, stores of D16 and D24.
`apk-psh32.apk`; `Depth_buffer`, `Depth_buffer_fixed_function`, `W_buffering`
queued on it. Expect the 151 captures with median error <= 1 to go exact.

### 6. The last blank: `Texture CPU Update` -- root-caused, not fixed

`RGBA` rewrites a texture red→green from the CPU between two draws; we render
red. Instrumented on hardware: the generic VRAM-texture dirty path works (a
plain texture re-reads the rewrite), but the failing texture is bound
**surface-to-texture** -- a render surface shadows its VRAM address, so the
bind samples the stale surface image and never re-uploads the CPU-written
texels, even though the write sets `possibly_dirty`. `create_texture` guards
the inverse (`surface->upload_pending` forces a VRAM read), so the fix is
making a CPU write to surface-backed VRAM set `upload_pending` -- but that
lives on the surface-access callback and the aliasing path that has been
fragile, so it needs its own experiment (does the callback fire; does it
regress the loading-screen case the guard exists for). Full trace on #5. Not
attempted. `apk-texdbg.apk` was the instrumented build; the device is back on
the clean one.

### 7. #31, slope-scaled offset under W -- measured, not modelled

`gold(ZS1) - gold(ZS0)` is hardware's offset term. It is **one constant per
triangle**; ours varies per pixel with w^2. `factor x triMZ x w_ref^2` fits
three of five quad triangles to <1% with `w_ref` = w at the triangle's first
visible pixel after clipping (the Roof's second triangle proves it is the
*pixel*, not a vertex). The Wall's second triangle wants its clipped-away apex
instead, and the TriH strip's four congruent triangles get constants 13%
apart. Full table on the issue. Do not fit a rule to this suite; it conflates
x-translation and apex-clipping. A one-variable test would settle it.

### 8. #21, `SZ_R6G5B5` green — read the warning first

Green is unexplained, and **two plausible fixes have already been measured and
rejected**. Bit windows `[8:5]` and `[8:4]` both fit `Texture format`'s
gradient beautifully and both take `BumpMap_R6G5B5` from 23,793 differing
pixels to 58,317 and 64,214. The two suites want opposite windows, which means
the difference between them is not in the decode. The standing candidate is
what else differs: `Bump map` sets the per-channel signedness bits of
`NV_PGRAPH_TEXFILTER0` and `Texture format` does not.

This issue has cost two overfits. It needs a hypothesis about hardware
behaviour, not another curve fit against one suite.

## Device conventions that cost a cycle each when forgotten

- **Force-stop the emulator after every run.** The handheld stops
  trickle-charging while it is up. `run_disc.sh` does this in its exit trap.
- **`run_disc.sh` does not install.** Install the APK yourself first, or you
  will measure the previous build and the numbers will look plausible.
- **The ISO's `--output-dir` must match the guest dir passed to
  `run_disc.sh`.** Mismatched, extraction silently finds nothing.
- One test per disc for anything scored: issue #19 found 328 of 864 tests
  rendering a previous test's image. `Bump map` alone scores 38/40 isolated
  against 36/40 sharing a disc.
- Do not `pkill -f` a pattern that matches your own shell. Kill by PID.
