## 1. #19: with isolation available, contamination is zero

### The two contamination cases were one poisoning test, and one line removes both

`crossmatch.py` on `Texture render target`, same goldens, same tool, two discs:

| disc | binary | checked | failing | **accused of rendering another test's image** |
|---|---|---:|---:|---:|
| loop **included** (`issue59` base, near-tip) | `4cb0903f4b23` | 41 | 40 | **2** |
| loop **skipped** at tip (`--skip-test`) | `cade6d3c9b13` | 40 | **0** | **0** |

The two the loop-included disc accuses are
`Texture_render_target::TexFmt_A8` and `TexFmt_A8_L`, both reproducing
`TexFmt_DXT1` at own-error 67.42 against 17.4 -- **exactly and only the two
cases #19 reports as contamination.**

Why those two and not the other 38: with the stage disabled every `TexFmt_*`
capture holds flat `[0,0,0,255]` across the quad, and flat black is not any
test's golden. `crossmatch` accuses only the captures whose *own* golden is
furthest from black, so it under-counts this by construction and picks out
`A8`/`A8_L`. The accusation was never about A8.

**So #19's contamination count is 2 of 84 with the loop in the disc, and 0 of
40 with it out.** Both entries are resolved by one `skip_tests` line, and by
no code:

```
--skip-tests "Texture render target::RenderTextureLoop"
```

### The suite at tip, for the record

| | captures | exact | differing px |
|---|---:|---:|---:|
| loop included, near-tip | 41 | 1 | 3,209,634 |
| loop skipped, **at tip**, 2 runs | 40 | **11** | **4,235** |

Byte-identical between the two runs. The 3.2M headline was 99.87% disc.

### The other 82 cannot be touched by a skip list, and that is a fact about the classes

This is worth stating plainly because it decides how much re-measurement #19
needs. The two verdicts are defined by the solo arm:

* **contamination** -- the test is *exact alone*. It fails only in company, so
  removing the company fixes it. A `skip_tests` entry can resolve it.
* **missing-state** -- the test is *as wrong alone*. No disc composition
  changes what it renders.

`skip_tests` can therefore only ever resolve contamination, never
missing-state. Re-running the 82 under the new mechanism would answer a
question the definition already settles, and would cost hundreds of device
cycles to reproduce a number measured this morning on one binary with
progress-log proof on every solo run
(`docs/investigations/issue-19-isolation-2026-09-12.md`). The half of #19 that
the new mechanism touches is the half re-measured above, and it is now zero.

## 2. Is there another `RenderTextureLoop`? Two instruments, one answer: no

This is the part worth the most, because a poisoning test inflates the
scoreboard silently and nothing in the harness was looking for one.

### Instrument A -- the capture signature, `docs/testing/poison_scan.py` (new)

`crossmatch` asks "does another golden fit better?", which needs the
substituted image to *be* another test's golden. Poisoning does not have to
look like that. So this scans for the signature itself: many captures in a
suite differing from their goldens on *exactly the same pixels*, with our
content flat across that region while the goldens hold many colours, the
suspect exact, and the suspect sorting first (`RunAll` walks a `std::map`).

Validated on the known positive before being trusted anywhere else:
`Texture_render_target` scores 4 of 4 -- 39 of 40 masks identical, all 39
flat `(0,0,0,255)`, `RenderTextureLoop` first and pixel-exact.

Run over **88 suites / 2,071 captures**, nothing else scores 4. The runners-up
are all explained without poisoning:

| suite | score | what it actually is |
|---|---:|---|
| `Fog_carryover` | 3 | 7 captures share a 16,384-px flat-blue region -- but the test is *about* carryover **within one test** (the right-hand quad deliberately sets no fog coordinate). A real defect, already **#42**. Not order-dependence between tests. |
| `Texture_shadow_comparator` | 3 | 20 captures share a mask of **21 px each**. Below any mechanism. |
| `Texture_BRDF` | 3 | all 3 tests share one 614-px mask, and all 3 run the same `Test()` which sets its own format -- no test is privileged, so no poisoner. |
| `Depth_buffer_fixed_function`, `3D_primitive`, `2D_Lines` | 2 | shared masks of 24, 7 and 200 px. Precision floor. |
| `Material_alpha`, `Alpha_func`, `High_vertex_count` | 1-2 | shared masks but **max delta 1-4** -- a band, not stuck state. |

`Fog_carryover` is the useful negative: it trips every capture-side criterion
and is not poisoning. The tool says so in its own docstring, and the disc is
what settles it.

### Instrument B -- the test sources, independent of any capture

`TestSuite::Initialize()` runs **once per suite**; tests run alphabetically and
inherit whatever the previous test left set. So a poisoner is a test that
mutates state the suite only ever establishes in `Initialize()`. Audited all
**100** suite `.cpp` files for that: 15 have a test touching Initialize-only
state, and of those only three have a setter that **exactly one** test
touches.

| file | test | verdict |
|---|---|---|
| `texture_render_target_tests.cpp` | `TestRenderTextureLoop` sets `SetShaderStageProgram`, Initialize sets it and `SetTextureStageEnabled` | **the known poisoner** |
| `zpass_pixel_count_tests.cpp` | `TestPointSizeProgrammable` sets a shader | **restores it** -- `SetVertexShaderProgram(nullptr)` on its last line (416) |
| `vertex_shader_independence_tests.cpp` | `TestMultiOutput` sets `SRC_SPECULAR` | **restores it** -- `SRC_DIFFUSE` nine lines later |

The other twelve are suites where *every* test sets the state (`W param`,
`Texture perspective`, `Specular`, `Texture cubemap`, ...), which is
self-consistent: nothing is inherited.

The two instruments have different blind spots -- A is blind to the 12 suites
the sweep has not reached yet (`W_param`, `Window_clip`, `ZMinMaxControl`,
`ZPass_pixel_count`, `Volume_texture`, `TextureWrapMode`, `Weight_setter`,
`Zero_stride`, `Texture_render_update_in_place`, and the three
`Vertex_shader_*`), B is blind to poisoning that does not go through a
`host_.Set*` call -- and B covers exactly the suites A is missing.

**On present evidence `RenderTextureLoop` is the only test in the corpus that
poisons its suite, and the skip list should stay one line long.**

### One thing to fix about the sweep that is in flight

The 100 requests of the running full-corpus sweep were queued at 13:31, from
the script as it stood **before** `8da779610b` (20:54). Every one of them
carries **no `skip_tests` key at all**. Its `Texture_render_target` row --
request `z-sweep-085`, which is in neither `queue/`, `running/` nor
`results/` -- must not be quoted whatever it turns out to be. The next sweep
picks the skip up automatically.

### `Context_switch` -- not #19, and fully characterised from one capture

#58 guessed this "may be the same mechanism as #19's 82 missing-state, with a
suite of its own; check that first". **It is not.** #19's population is tests
that render a *sibling's* image; `Context switch` has exactly one test, so
there is no sibling and no substitution. It is an unimplemented register.

The test writes `NV_PGRAPH_CTX_SWITCH1` GRCLASS = 0 partway through a 7-vertex
`PRIMITIVE_POLYGON` and restores it before `End()`. On silicon that stops
pgraph accepting methods. The hypothesis makes three independent predictions,
and a single capture can carry all three:

| prediction | measured |
|---|---|
| **P1** the polygon's lower half (rows 240-431, cols 64-575) is undrawn on hardware, so the golden holds only the checkerboard | golden is `0xFF333333`/`0xFF444444` on **100.00% of 98,304 px** -- 192x512 exactly |
| **P2** we draw the polygon there instead | ours is checkerboard on **0.00%** of the same region |
| **P3** the following triangle takes the last diffuse set *before* the disable, `(0.3,0.4,0.7)`; we take the last set overall, `(1.0,0.9,0.4)` | 3,072 px, all differing. Gold modal `(73,90,140,198)` and `(67,85,135,198)`; ours `(208,189,93,207)` and `(204,184,89,207)` -- **counts match 1560/1560 and 1512/1512**, same geometry, different vertex colour |

Alpha differs by up to 64, which is why this cannot be read as a colour
residual and why the comparison had to be RGBA.

**Mechanism, located.** `hw/xbox/nv2a/pgraph/pgraph.c`, `pgraph_method()`. The
MMIO write does land -- `pgraph_write()`'s `default:` case writes the register
(line ~987). But two fast paths added for performance both gate on the
*cached* class and return before the register is re-read:

* the `XEMU_OPT_METHOD_FAST_TABLE` block (~line 1777): `... && pg->cached_graphics_class == NV_KELVIN_PRIMITIVE`, then `return consumed;`
* the "Kelvin fast entry" (~line 1843): the same test, then `goto kelvin_dispatch;`

`cached_graphics_class` is refreshed from `NV_PGRAPH_CTX_SWITCH1` only at
line ~1895, which both paths skip. With the subchannel unchanged the register
is also never restored from `CTX_CACHE1`, so the guest's write is simply never
observed: every subsequent Kelvin method takes a fast path keyed on the stale
class.

**Not implemented here** -- `hw/` is another stream's territory. The shape of
the fix, for whoever is assigned it: have `pgraph_write()` update
`pg->cached_graphics_class` when `addr == NV_PGRAPH_CTX_SWITCH1`, which drops
both fast paths through to the slow path; the slow path then reads GRCLASS 0
and falls to `default: goto unhandled`, which is the hardware behaviour the
test asserts, and the guest's restore write comes back through the same path.
Do **not** reach for `pg->last_subchannel = UINT_MAX` instead: that forces a
reload from `CTX_CACHE1`, which would overwrite the guest's 0 with 0x97 and
silently undo the very write being emulated.

### `Color_mask_blend` -- the guess was wrong; it is blend precision

#58 guessed it "sits directly on the write-mask/blend interaction that #43 and
#48 both moved today". The measurement says the mask and the factor are both
**right**. The single test is colour mask = RGB enabled with **alpha write
disabled**, `FUNC_ADD`, sfactor `DST_ALPHA` (0x304), dfactor `ZERO`.

* **alpha is pixel-exact** -- 0 differing channels -- exactly as a disabled
  alpha write predicts;
* every one of the 24,963 differing channels is within **2 counts**, and 95.3%
  are within 1. A wrong write mask or a wrong factor zeroes or scales a whole
  channel; it does not produce a band.
* the signs are directional: R reads +1 on 89% of its differing channels, B
  reads -1 on 88%.

That is #14's residual as #14 already describes it -- "one step, led by the
`ONE_MINUS_*` factors, float32 against their fixed point" -- on a `DST_ALPHA`
factor. **No new issue. Assign to #14.**

### `Degenerate_begin_end` -- the semantics are already correct

The test omits `NV097_SET_BEGIN_END_OP_END` on two triangles, so the final quad
must be drawn as a triangle. If we got that wrong the capture would be missing
or gaining a whole primitive. Instead **every one of the 17,502 differing
channels is within 2 counts**, 95.1% within 1, alpha exact, and our modal
colours track the golden's one-for-one (`(0,10,245,255)` x61 against
`(0,9,246,255)` x61).

**We reproduce the degenerate-primitive behaviour correctly**; what is left is
the shading interpolation band. **No new issue. Assign to #12.**

### Both band suites are ordinary members of a large population

Not an outlier pair. Across `run-2026-09-12-corpus-classes.tsv`, **127 of the
578 rows classed `structural`** are >=95% a +-1 band and are called structural
only because a few channels reach 2. `Color_mask_blend` at 95.3% and
`Degenerate_begin_end` at 95.1% sit inside that population alongside `Fog`
(100%), `Lighting_normals` (99.8%), `Fog_vsh` (99.4%) and `Fog_param` (98.2%).

A note for `classify_residuals.py`, not acted on here: a row that is 95% +-1
with a sprinkle of +-2 is reported identically to a row that is 40% +-1 with a
max delta of 255. The one-step classes require *every* differing channel to be
+-1, so a single 2 reclassifies a whole capture as `structural`. The band
fraction is already derivable from the TSV's `plus_one`/`minus_one` columns;
surfacing it would stop this pair looking like a structural defect to the next
audit.

## 4. The standing rule for excluding a test

Proposed, from what this cost:

1. **A test is excluded only when it is shown to poison the tests after it** --
   never because a suite scores badly. The evidence is the suite measured with
   and against the test on **one binary**, progress-log proof on both arms, and
   the difference confined to the tests that sort after it.
2. **Check the goldens' dates first.** `RenderTextureLoop` is new in Aug 2026
   and the `TexFmt_*` goldens are from 2025-02-11, so the goldens cannot
   adjudicate the poisoned tests at all (#27). A poisoning test whose goldens
   *postdate* it is a different situation and may be a real defect.
3. **One machine-readable skip list, read by everything.** Today it lives in
   three places: `queue_full_sweep.sh`'s `skip_tests_for()`, the hand-written
   `docs/testing/configs/texture_render_target-no-loop.json`, and whatever an
   agent types after `--skip-tests`. Three copies of a list whose whole purpose
   is to not be forgotten is the same failure that produced this issue, one
   level up. It belongs next to the suite in `nv2a_issues.toml` or in a file
   both the sweep and `request.sh` read.
4. **`disc_id` folds in the skip list** -- already true, and load-bearing. Two
   discs differing by 9.9x on an unchanged binary must never share an id.
5. **Report it upstream.** The exclusion is a workaround for a bug in the test
   suite: `RenderTextureLoop` should restore the stage, or the format tests
   should set it.
