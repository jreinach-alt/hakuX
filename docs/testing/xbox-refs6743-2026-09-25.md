  directly, so it waits for the owner's power switch under the standing
  safeguards. It is the only test source that writes PMC, PFIFO or PBUS

## First comparison: hakuX against the new references

This compares the Thor dry run's captures (hakuX `84a67b9cf8`) with the
console's. It counts pixels in one run and is not an A/B arm.

| capture | differing px | max delta |
|---|---:|---:|
| `Surface as vertex array::DynamicUpdateLoop` | **96,000** | 255 |
| `Surface as vertex array::RenderScalePattern` | 18,136 | 1 |
| `Fog planar vsh::ZeroPlane_*` (four captures) | 3 each | 93 |
| the other five | 0 | 0 |

**`DynamicUpdateLoop` is a real defect.**

- **What it draws.** Four passes, each of which:
  1. renders a solid colour into `surface_a_`;
  2. draws a quad whose `DIFFUSE` vertex array points at that same memory
     (`UB_D3D`).
- **What silicon shows.** The quads come out red, green, blue and yellow.
- **What hakuX shows.** All four are red, the first pass's colour.
- **The arithmetic.** Three quads of 32,000 px each account exactly for the
  96,000 px.
- **The diagnosis.** hakuX's vertex fetch is not invalidated when the GPU
  renders into memory that is also bound as a vertex array. The test's own
  comment says it was written so that "xemu's internal vertex attribute
  tracking ... cannot mask issues".

No issue owned it before this run. It is routed on #112 for the board.
