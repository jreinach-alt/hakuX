# #10 on silicon: a Y16 bump texel's low byte feeds an offset, and its high byte feeds one too

**Measured 2026-09-25 on the project console.** Registered beforehand in
[`docs/lanes/xbox/y16low-run.md`](../lanes/xbox/y16low-run.md) (`07684e58a8`).
The host routed it on #112 as #10's discriminating retest, after PR #350
showed the old m11 cut and #10's own control were blind.

**Result: M = LOW, with every gate holding.**
- **The low byte is read.** Forcing every low byte of the Y16 bump texture to
  0x00, with the high bytes unchanged, moves the silicon image by 28,336 px
  against Y8. hakuX, which converts the full 16-bit value, moves only the
  112 px of printed text.
- **So PR #187's "dead" rival is the mechanism:** the low byte of the filtered
  16-bit value feeds a bump offset.
- **The high byte is read too.** The zero-low-byte image is not the
  zero-offset image. Silicon splits the texel's bytes between offsets, which
  is consistent with #283's measured byte order for Y16 colour lookups.

## What it settles, and what it does not

**It rules out every model in which both offsets come from the high byte or
the full value.** That covers hakuX's full-value conversion and every other
Y8-like reading.
- **The low byte of the filtered 16-bit value feeds an offset.** A seam
  between byte-replicated texels such as 0x5252 and 0x5353 sweeps that byte
  through about 200 values, which is #10's measured sweep.
- **It is not both offsets from the low byte.** `_lo00` would then equal
  `_zero`, and it differs by 48,342 px. The high byte feeds the other offset.
- **This agrees with #283** (`a5b4141064`), which measured silicon handing a
  Y16 texel's bytes to the combiner separately.

**Not settled: which offset reads which byte.**
- A translation fit against the zero-offset image is too weak to name the
  axis, with agreement of 0.62–0.76. Each quad mixes regions with different
  bump values.
- **The clean follow-up** isolates one axis at a time: `_lo00` against Y8 with
  m11 = 0, so only the horizontal term is live, then with m00 = 0. Each
  variant's seam band gets checked for stripes first.

## For hakuX

hakuX renders a Y16 bump source through its full 16-bit value, so it collapses
onto Y8. Silicon splits the bytes between the offsets. Modelling that is a
change to the bump path in `psh.c`, which belongs to whichever lane the board
assigns. The byte-to-axis assignment above is still open, and a fix needs it
first.
