## What changed

`docs/COMPATIBILITY.md` is now generated by `docs/testing/compat_page.py` from
three inputs: the playable ledger (`pm/playable-accepted.tsv`), a title
registry snapshot (`docs/lanes/compatpage1012/registry.tsv`, built with
`title_registry.py build --no-forge`), and the hand-written
`docs/testing/compat_notes.tsv` (region, region source, notes text, red
reasons, the NFS hand-played figures). It also writes `docs/compatibility.csv`,
a public CSV with the same rows and no run ids or paths. Both regenerate with:

```
python3 docs/testing/compat_page.py \
  --ledger pm/playable-accepted.tsv \
  --registry <a freshly built title_registry.py tsv> \
  --notes docs/testing/compat_notes.tsv
```

`--check` exits non-zero if the committed files differ from what the script
would produce; `docs/testing/compat_page_selftest.py` covers tier assignment,
ledger-wins, the NFS override, the "?" region fallback, and `--check` on a
stale page. Both pass.

## Corrected thresholds

The old page said "at least 30 fps," "no dropouts," and "at least 90% play
share" in a way that didn't match `docs/testing/title_verdict.py`'s actual
constants. The page now says, and the generator's `DEFINITIONS` block
encodes:

- **fps bar**: 28.5 fps (`bar_fps=30` × `fps_tolerance=0.95`), held for at
  least 90% of gameplay time (`fps_share_min=0.90`) — not "30 fps, no
  dropouts."
- **play share**: at least 90% of the scored window must be actual play,
  not menus/loading/cutscenes (`play_share_min=0.90`) — this was already
  roughly right but is now stated against the real constant name.
- Audio-starve and hitch/flicker frame review are unchanged in substance,
  reworded only for the three-section framing.

override: Nova, 2026-10-12, 29.9 median fps, 95% time at bar of a 204 s race,

## Region sourcing

Priority order used, strictly: (1) the tested image's own filename/request
metadata, (2) an exact match in `d-xbox-archives.txt`, (3) `library-gaps.html`'s
`DATA` array, (4) xemu's compatibility list / web search (xemu.app itself is
GitHub-Pages-hosted and is on the WebFetch deny list; `reports.xemu.app` is
Discord-auth-gated and unusable; `redump.org` returns `ECONNREFUSED` from
this sandbox — so (4) in practice meant WebSearch only), (5) XBE certificate
region flags under `/mnt/d/hakux-staging/sweep/` — **not attempted**: no
verified parsing tool exists for this and no ground truth to check a hand-rolled
one against, so getting it wrong silently was a worse outcome than leaving
a "?". This is the one open item for lane.local below.

Where no source settled it, the page prints "?" and the title is listed here.

**Least-certain decision — NHL Hitz Pro (4D57001A) diverges from the brief's
own example.** The brief names NHL Hitz Pro as an illustration of a
CRASH_OR_HANG row whose cause is actually fps (implying left-off), and the
registry's `failing_all` tag is indeed `"fps"`, which the generator's
mechanical guard (`crash_hang_left_off_reason`) correctly flags as a
left-off shape. But the row's `hold_detail` carries an explicit,
human-reviewed override dated 2026-10-06: "NHL Hitz Pro hangs on the
post-team-select loading screen (guest busy, frozen frame): that is a hakuX
hang, not a pathing miss. Do not re-run it; release: issues close." I trusted
that human review over both the stale fps tag and the brief's own
illustrative text, and classified it as a true red. This is encoded in code
(`RED_OVERRIDES["4D57001A"]` in `compat_page.py`) rather than only in this
PR, specifically so a registry rebuild can't silently re-flag it without the
generator raising — any other CRASH_OR_HANG row that trips the left-off
guard without a `RED_OVERRIDES` entry causes the generator to exit non-zero.
If this override is wrong, un-color-coding it means deleting the
`RED_OVERRIDES` entry and moving the title_id to `compat_notes.tsv`'s
left-off bookkeeping (it would currently fail generation with a clear error
either way).

## For lane.local

The XBE-certificate/XDVDFS region-flag parse (source 5 in the priority
order) was deliberately not attempted — `/mnt/d/hakux-staging/sweep/` is
directly readable from this sandbox, but there is no verified tool for
pulling the game-region flags out of an XBE certificate here, and no ground
truth to check a hand-rolled parser against. Writing one blind risks a
silently-wrong region on a public page, which is worse than the current
"?" for titles sources 1-4 couldn't settle. If this is worth doing, write
and verify an XBE-certificate region-flag reader against a handful of
known-region images from the archive list first, then re-run
`compat_page.py` with the resolved regions moved into
`docs/testing/compat_notes.tsv`.
