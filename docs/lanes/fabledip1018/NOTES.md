## 1. The `[drawrec]` counters, and what they actually mean

All in `hw/xbox/nv2a/pgraph/vk/draw.c`, called from `sync_vertex_ram_buffer()`:

- **`drawrec_vtx_copied(addr, size, cpu_dirty)`**: for every vertex range actually re-uploaded this draw, `n_dirty` (and `cpu_dirty=true` -> OWED+REDO bits set) means the NV2A dirty bitmap really was set -- the guest wrote that page since the bitmap was last armed. `n_redo`/`b_redo` (`cpu_dirty=false`) means the copy happened only because the page is still in the REDO bitmap: its walk is *owed*, so the page is copied unconditionally even though nothing proves the guest touched it again since the last copy. **`redo` is the cost of not yet knowing a page is clean, not evidence the guest rewrote it.**
- **`drawrec_vtx_walk(r, at_flip)`**: re-arms every OWED page, merging runs <=16 pages apart (`DRAWREC_VTX_GAP`), up to 8 runs per batch (`DRAWREC_VTX_MAX_RUNS`) before the rest becomes one wide span. Each run is its own call to `physical_memory_dirty_bits_cleared()` -- one full TLB scan. Triggered once per flip (`walks=A+...`) or early once REDO-only copies cross 32 copies or 256KB (`DRAWREC_VTX_REDO_N`/`_B`, `walks=...+B`).
- **`drawrec_shc_consumed()`**: clears `shader_bindings_changed` once a full-path draw (key built, descriptors written) resolves against SAMEKEY or a valid LRU pipeline. `shc` counts how many draws per window took that full, expensive path and were allowed to stop re-taking it.
- **`drawrec_tick()`** emits the `[drawrec] f=... vtx dirty=... redo=... redoKB=... walks=A+B runs=... pages=... shc=...` line every 60 guest flips.

The companion instrument is `[rdc]` in `system/physmem.c` (`rdc_tick()`), which times every call into `tlb_reset_dirty_range_all()` by site: `vtx` is drawrec's own DIRECT walks, `tex` is the Vulkan texture dirty check. Per-window it reports `tcpu` (the render thread's own CPU ms that window), `rdo`/`rdous` (walk count/time), `vr` (walks that repeated within the *same* vertex-sync call -- the ones one-walk-per-batch would remove), and site hit rates (`pages` touched vs `hits` actually re-armed).

Both titles' data below answer the same question the same way: **the walk's own CPU time is a rounding error against the frame-time cost.** See sections 2-3.
